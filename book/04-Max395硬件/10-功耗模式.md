# 10　功耗模式

## 完成结果

知道这台机器的功耗档位有哪几处可以设、分别在哪里、你这台现在设的是什么。知道“把 CPU 锁在最高性能档能不能让模型跑得更快”这件事上有两派相反的说法，以及为什么本教材不替你下结论。每一项设置你都能读出当前值、改一次、验证效果、再改回去。

## 开始前需要准备什么

- 读过第 2 章最后那一节。**CPU、iGPU 和 NPU 共用同一份功耗预算这件事第 2 章已经讲过，本章不重复**，只讲档位在哪里、怎么改、改完怎么看；
- 能进 BIOS（第 7 章）；
- 一台装好 Ubuntu、能开终端的设备；
- 本章前半部分全是只读命令。真要改的时候，先把当前值抄下来——**那是你的恢复目标**。

## 新词

**功耗档位**：整机厂给这台机器设的几组功耗上限，常见的名字是性能模式、Performance Mode、Power Mode、TDP Setting。档位高，芯片允许消耗的功率大，风扇也转得响；档位低反过来。

**TDP**（Thermal Design Power，热设计功耗）：厂商给这颗芯片设定的一个功率参考值，散热系统按它来设计。同一颗芯片装进不同的整机，整机厂可以把这个值调高调低，这是同型号机器性能不一样的主要原因之一。

**调度策略**（Governor，也叫调频策略）：Linux 内核决定 CPU 频率高低的那套规则。常见的两个名字是 `performance`（尽量往高了跑）和 `powersave`（把决定权交给驱动和固件）。

**amd-pstate**：Linux 上给 AMD 处理器用的调频驱动。**在这个驱动下，`powersave` 这个名字容易误解——它不是把 CPU 锁在低频，而是让驱动和固件自己按负载调**，日常和跑模型都不会因为它就慢下来。

**EPP**（Energy Performance Preference，能效偏好）：`amd-pstate` 驱动下的一个偏好值，告诉驱动在“省电”和“性能”之间偏向哪一头。常见取值有 `performance`、`balance_performance`、`balance_power`、`power`。

**C-state**：CPU 空闲时进入的省电状态。进得越深越省电，被叫醒时的延迟也越大。有些优化脚本会屏蔽深度 C-state 来换响应速度。

**满载**：所有该出力的部件都在全力工作的状态。本教材说“满载”，指的是跑模型时 GPU 持续出力那段时间，不是桌面开几个网页。

**平台档位**（platform profile）：部分机器的固件对操作系统开放的一个档位接口，Linux 里表现为一个可以读写的文件。有的机器有，有的没有。

## 档位有两处，可能有三处

```text
一、BIOS 里的性能模式        → 整机层面的功耗上限，管的是这颗芯片总共能吃多少电
二、Linux 里的 CPU 调度策略  → 系统层面的调频规则，管的是 CPU 频率怎么变
三、固件开放的平台档位       → 有的机器有，能在系统里直接切整机档位
```

第一处和第三处是**整机厂**给的，各家不同，有的机型干脆没有。第二处是 Linux 通用的，所有机器都有。

本教材的默认立场：**这三处都保持出厂状态。** 第 6 卷跑模型的所有步骤不依赖任何一项改动。要动的话，一次只动一项，动完按本章的方法测一次。

## 第一处：BIOS 里的性能模式

**在哪里**

在 Advanced 或 Power 菜单下面，找含这些字样的选项（第 7 章）：

| 常见选项名 | 常见取值 |
| --- | --- |
| Performance Mode | Quiet / Balanced / Performance |
| Power Mode | Silent / Auto / Turbo |
| TDP Setting、Power Limit、cTDP | 具体瓦数，或 Low / Medium / High |
| Smart Fan Mode | 有的整机厂把风扇策略和功耗档位做成同一项（风扇部分见第 11 章） |

**选项名称、取值和有没有这一项，都随品牌和固件版本变化，本项目未逐机型实测，需要核验。** 以你机器上实际看到的为准，找不到就是这个固件没开放，不用继续找。

**分品牌的已知线索**

| 品牌 | 已知情况 |
| --- | --- |
| GMKtec EVO-X2 / EVO-X3 | [第 1 卷第 12 章](../01-开箱与安装/12-硬件问题处理.md)记录过：有的机型出厂就设在性能档，风扇长时间高转与这一项有关。**需要核验** |
| Beelink GTR9 Pro | 本项目未收集到这台机器的功耗档位选项记录，**需要核验** |
| Framework Desktop | 相关设置多在 Advanced → AMD CBS 下面，层级很深，**需要核验** |
| HP ZBook Ultra G1a | 笔记本形态，多数惠普机型在 BIOS 里有电源与散热相关的档位，同时系统侧也可能开放平台档位接口，**需要核验** |
| 其他品牌 | 按说明书查，或者进 BIOS 逐个菜单看一遍 |

**这一项的四件事**

- **默认状态**：随整机厂而定。**先进 BIOS 把当前值读出来、拍照、抄下来**，这是你的恢复目标。本项目未逐机型记录出厂默认值，**需要核验**；
- **什么情况才需要改**：两种。一是机器噪音大到没法在办公环境里用，往低档调；二是长期满载跑推理并且确认散热跟得上（第 11 章、第 12 章），往高档调。**没有具体问题就不要动**；
- **改完怎么验证**：改档之后，用同一个模型、同样的提示词跑一遍，记 tokens/s；同时按第 12 章的方法记温度、频率和风扇表现。**只改这一项，别的都不动**，否则测出来的差别说明不了任何事；
- **怎么恢复**：进 BIOS 改回你抄下来的原值。忘了原值就用 `Load Optimized Defaults`（[第 1 卷第 12 章](../01-开箱与安装/12-硬件问题处理.md)），**恢复默认之后要按第 9 章重新设一遍 UMA Frame Buffer Size**。

## 第二处：Linux 里的 CPU 调度策略

**先读出当前状态**（三条只读命令）

```bash
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_driver
```

输出当前用的调频驱动，Zen 5 上常见的是 `amd-pstate-epp` 或 `amd-pstate`，老一些的配置上可能是 `acpi-cpufreq`。

```bash
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
```

输出当前的调度策略。

```bash
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_available_governors
```

输出这台机器上可选的策略。`amd-pstate-epp` 驱动下通常只有 `performance` 和 `powersave` 两个。

**把读到的两个值抄下来，记进第 16 章的设备基线。这是恢复目标。**

**再读能效偏好**（只在 `amd-pstate-epp` 驱动下存在）

```bash
cat /sys/devices/system/cpu/cpu0/cpufreq/energy_performance_preference
cat /sys/devices/system/cpu/cpu0/cpufreq/energy_performance_available_preferences
```

第一条是当前偏好，第二条是可选值。**提示文件不存在，说明你这台机器用的不是这个驱动，属正常**，跳过。

**Ubuntu 装完之后不主动改这一项。** 你读到什么就是出厂加发行版默认的组合。**本项目未在基准设备上逐项记录默认值，需要核验**——所以第一步是读出来记下来，不是照抄任何教程里的“正常值”。

**怎么改**

先装工具：

```bash
sudo apt install linux-tools-common linux-tools-generic
```

看一眼当前状态：

```bash
sudo cpupower frequency-info
```

提示版本不匹配的话，按提示装对应内核版本的包：`sudo apt install linux-tools-$(uname -r)`。

改成性能优先：

```bash
sudo cpupower frequency-set -g performance
```

**这个改动重启就没了。** 它不写引导配置，也不改任何开机项，所以最省事的恢复办法是重启。想立刻改回去就把 `performance` 换成你抄下来的原值：

```bash
sudo cpupower frequency-set -g powersave
```

**改完怎么验证**

```bash
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
```

输出变成你设的那个。再看实际频率：

```bash
grep MHz /proc/cpuinfo
```

这条会列出所有核心的当前频率。空闲时和跑负载时各看一次，对比差别。

**光看频率变高不算验证成功。** 你要的是模型跑得更快，所以真正的验证是：用同一个模型、同样的提示词、同样的上下文长度跑一遍，记 tokens/s，和改之前比。第 16 章有完整的基线方法。

**这一项的四件事**

- **默认状态**：用上面三条命令读出来的值。Ubuntu 不主动改它；
- **什么情况才需要改**：只有在你怀疑调度策略拖慢了推理、并且准备按第 16 章的方法实测一次的时候。**日常使用没有理由改**；
- **改完怎么验证**：`scaling_governor` 变成新值；`grep MHz /proc/cpuinfo` 看频率变化；最终以同一负载下的 tokens/s 为准；
- **怎么恢复**：重启，或者用 `sudo cpupower frequency-set -g` 加上你抄下来的原值。

## 第三处：固件开放的平台档位

有的机器的固件会把整机档位开放给操作系统，Linux 里表现为一个文件：

```bash
cat /sys/firmware/acpi/platform_profile
cat /sys/firmware/acpi/platform_profile_choices
```

第一条是当前档位，第二条是可选档位（常见的有 `low-power`、`balanced`、`performance`）。

**提示文件不存在，说明你这台机器的固件没有开放这个接口，属正常**，这一节跳过。笔记本形态的机器（HP ZBook Ultra G1a 这类）比 Mini PC 更常见有这一项，**本项目未在任何 Max395 机型上实测过，需要核验**。

**这一项的四件事**

- **默认状态**：`cat /sys/firmware/acpi/platform_profile` 读出来的那个值，先抄下来；
- **什么情况才需要改**：和 BIOS 里的性能模式是同一类需求（噪音太大、或者确认散热有余量想放开），但这条路不用重启进 BIOS。两处**不要同时改**，否则分不清是哪一处起的作用；
- **改完怎么验证**：读回这个文件确认值变了，再按第 12 章记温度和频率，最终以同一负载下的 tokens/s 为准；
- **怎么恢复**：把原值写回去。这一项通常重启后回到固件的默认值，具体行为**随机型而定，需要核验**。

## 争议：锁 CPU 满频能不能让模型更快

材料里有两派相反的说法。本教材把两边并排放，**不下结论**。

| | 一派：锁满频有用 | 另一派：锁满频是负优化 |
| --- | --- | --- |
| **谁说的** | 社区流传的优化脚本 | nix-amd-ai 的开发者 |
| **主张** | 把调度策略锁成 `performance`、屏蔽深度 C-state，能提速 | CPU 满频会挤占 iGPU 的功耗份额，对带宽敏感的解码阶段是负优化 |
| **理由** | CPU 频率高，调度和准备数据的环节延迟低，唤醒也快 | 这颗芯片上三个计算部件共用一份功耗预算（第 2 章），CPU 多拿，iGPU 就少拿 |
| **证据强度** | **没有实机复测数据。** 本项目 2026-08-14 的来源核查记录：材料只给了转述，没有原始链接 | **同样没有实机复测数据**，来源情况相同 |
| **可能成立的条件** | 负载里 CPU 那一段占比大的场景，例如短提示、高并发的小请求、大量 token 切分工作 | 长上下文、大模型、解码阶段占绝大部分时间的场景 |

两边说的其实不是同一件事：一派看的是 CPU 那一段的延迟，另一派看的是功耗预算的分配。**它们在不同的负载形态下都可能是对的**，而判断你那台机器属于哪一种，只能实测。

**本教材的处理**：不给结论，不把任何一边写进第 6 卷的默认步骤。**整节内容需要核验。**

给客户做方案时，不要把“调了调度策略之后快了多少”写进承诺。

## 怎么在自己这台机器上判断

一次只改一个变量，测一次，记一次。方法在第 16 章有完整版，这里给最小流程：

1. **先测基线**：什么都不改，跑一个固定的任务（同一个模型、同一段提示词、同一个上下文长度），记 tokens/s、温度、频率、当时机器上还跑着什么；
2. **改一项**：比如把调度策略改成 `performance`。**只改这一项**；
3. **同样的任务再跑一遍**，记同样的几个数；
4. **改回去**，再跑一遍确认能回到基线附近。回不去说明中间还有别的变量在动；
5. **重复两三次**再下判断。单次差别可能只是后台任务的噪声。

测的时候机器上不要同时跑编译、转码、大批量数据处理。CPU 被占走会直接改变结果（第 2 章）。

## 正常结果

你手上有一张纸（或者第 16 章的基线表），上面写着这台机器的：BIOS 性能模式当前档位、`scaling_driver`、`scaling_governor`、能效偏好（如果有）、平台档位（如果有）。这几个值就是你的出厂状态和恢复目标。

跑过的读取命令都是只读的，机器上什么都没变。

## 看到不同结果怎么办

**BIOS 里找不到任何功耗或性能档位的选项**：说明这个固件没开放，跳过第一处。系统侧那两处照常可以看。

**`cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_driver` 提示没有这个文件**：说明当前内核没有为这颗 CPU 加载调频驱动。先看 `uname -r` 的内核版本，太旧的内核（6.8 一类）本来就不完全支持这颗芯片，按第 9 章第一步先升内核。

**`scaling_available_governors` 里只有 `performance` 和 `powersave` 两个**：这是 `amd-pstate-epp` 驱动的正常表现，没有 `schedutil`、`ondemand` 之类不代表缺功能。

**当前策略显示 `powersave`，你担心它在省电拖慢机器**：在 `amd-pstate` 驱动下，这个名字不代表锁低频，它把频率决定权交给驱动和固件。不放心就按“怎么在自己这台机器上判断”实测一次，别凭名字改。

**`energy_performance_preference` 或 `platform_profile` 提示文件不存在**：属正常，这两个接口不是所有机器都有。

**`sudo cpupower frequency-info` 报版本不匹配**：装对应内核版本的包，`sudo apt install linux-tools-$(uname -r)`。

**改成 `performance` 之后 tokens/s 没有变化，甚至更低了**：这正是上面那场争议的两种可能结果之一。按“改回去再测一遍”确认能回到基线，然后照实记录：**你这台机器在这个负载下，这一项改动没有收益。** 这就是有效结论，不用再折腾。

**改完之后风扇明显吵了、温度上去了**：功耗档位往上调本来就会这样。噪音和温度的取舍见第 11 章，温度和频率怎么看见第 12 章。

**机器在满载时突然变慢，而且是持续的**：先看是不是温度导致的降频（第 12 章），再看当时机器上还跑着什么（第 2 章）。这两个原因比调度策略常见得多。

**你在别处看到某台 Max395 机器“调完这一项快了多少”**：那是那台整机在那套散热、那份功耗上限、那个软件版本下的结果。整机厂不同，BIOS、散热和电源都不同（第 15 章），不能直接搬到你这台上。

## 完成检查

- 功耗档位可能在哪三处？哪一处是所有机器都有的？
- 你这台机器现在的 `scaling_driver` 和 `scaling_governor` 分别是什么？记在哪里了？
- 在 `amd-pstate` 驱动下，`powersave` 是什么意思？它等于锁低频吗？
- 改调度策略的改动会不会在重启后保留？恢复它最省事的办法是什么？
- 验证一项功耗改动，最终应该看哪个指标？只看频率变高够不够？
- 锁 CPU 满频这件事上，两派各自的主张和理由是什么？本教材为什么不下结论？
- 测一项改动时，为什么强调“一次只改一个变量”？
