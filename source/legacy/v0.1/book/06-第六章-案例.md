## 6.11 本地聊天记录检索

这个案例处理一个常见问题。聊天记录里留着项目决定和资料链接，时间久了以后很难找回。将全部记录发送给云端服务，又会增加数据授权和持续费用。

本节将讲述 Ubuntu Mini PC 如何运行本地全文检索。聊天文字保存在本机，Meilisearch 负责建立索引，systemd 定时更新。

原始方案依赖读取微信客户端的本地数据库。相关上游项目后来受到平台限制，因此本节不提供数据库解密步骤。配套项目改为读取用户自己准备的 `txt` 文件。读者可以学习 Docker 和本地数据目录，也能完成全文索引并为它增加定时更新。权限控制单独处理。

完成部署后，可以在 Mini PC 上导入聊天文本，按照关键词搜索，并设置每小时重新建立索引。这个版本还没有接入本地模型。模型问答作为后续练习，在检索稳定以后再增加。

配套部署文档：[案例 01　本地聊天记录检索](examples/01-local-chat-search/README.md)

## 6.12 飞书智能体只发送人类需要阅读的内容

一次实际使用中，Mini PC 上的运维智能体收到了一项资料整理任务。任务运行几分钟后，飞书收到了完整答案，也收到了智能体运行时生成的整个 JSON 对象。最终正文后面跟着内部推理和 Token 用量，会话标识也出现在消息里。同一条处理回执和完成结果还各出现了两次。

检查 Mini PC 时，只发现一个运维机器人进程，现有证据不支持两个机器人同时运行。日志中出现了时间接近的消息事件，而旧代码只按照 `message_id` 去重。为了覆盖平台使用不同消息标识重投相同内容的情况，修复后又增加了一层短时间文本去重。

内部字段泄露可以在代码里直接复现。Grok 返回的是一个跨多行的 JSON 对象，旧解析器却把每一行分别当成 JSON。逐行解析失败后，程序把原始 stdout 截取并发送到飞书。这样一来，原本只供程序记录的字段也进入了聊天窗口。

修复后的解析器先读取完整 JSON，只有失败时才按照 JSONL 事件处理。程序从 `text` 等允许字段中取出正文，内部字段留在运行层。发送飞书以前还有一次检查。只要发现 `thought`、`usage` 或会话标识，发送层就重新提取正文。无法提取时只返回格式错误，不发送原始对象。

重复执行使用另一道检查。程序为聊天 ID 和用户文字计算摘要，在30秒内收到相同内容时停止第二次执行。摘要进入日志，用户原文不写进这条去重日志。

修复在 Mini PC 上完成语法测试和输出过滤测试，随后重启机器人。服务重新连接飞书，原文件也保留了一份备份。这个检查只证明过滤器和运行服务正常。真实聊天中的显示结果仍需要下一条任务继续观察。

配套部署文档：[案例 02　飞书智能体输出过滤](examples/02-feishu-agent-output-filter/README.md)

## 6.13 一台 Mini PC 上的多 Agent 工作系统

这个案例处理一组已经分散的问题。聊天机器人各有入口，脚本和定时任务各自运行，任务状态与权限没有放在同一处。维护者很难判断一项任务由谁接收、谁批准、用了什么资源，失败后又该从哪里恢复。

案例使用一台常开的 Ubuntu Mini PC。公开内容只保留通用结构。真实账户、设备地址、服务名称、内部工作和运行路径不进入正文。

### 方案

系统使用一套共享 Hermes 运行时。每个岗位 Agent 有独立身份、配置、工作区、状态、日志和凭据边界。协调 Agent 接收自然语言，把任务转换为结构化工单。岗位 Agent 之间不直接发送自由文本命令，跨岗位任务经过协调 Agent 审核后才进入执行队列。

抓取、索引、RAG、备份和健康检查继续使用固定流水线。Agent 负责理解任务、选择受限工具和解释结果。Schedule 负责队列、时间、资源锁和重试，它不作为一个岗位 Agent。

### 部署

Agent Registry 记录岗位、汇报关系、运行方式和状态。每个岗位从同一模板生成独立目录。工单至少记录发起者、执行者、目标、允许路径、允许工具、禁止动作、输出要求和验收条件。

协调 Agent 可以批准普通内部任务。对外发送、公开发布、生产部署、删除、付款、账号恢复和权限扩大停在人工确认状态。一次确认只覆盖工单中写明的动作和目标。

### Schedule

原来的定时任务在发送时间才开始采集、处理和组装。处理时间增长后，整个任务可能在发送前超时。改造后，流程分成增量采集、夜间补齐、报告组装和发送。采集阶段保存游标和中间结果，组装阶段不发送，发送阶段只读取已经完成并通过检查的文件。

固定流水线按资源类型进入不同队列。大模型、小模型、浏览器、磁盘任务和外部发送各有自己的并发和锁。队列上限记录在 Schedule Registry 中，不由岗位 Agent 临时提高。

### 浏览器

浏览器任务使用独立的 `PROFILE_ID`、`CDP_PORT`、进程和锁。同一个 Profile 同时只运行一个任务。两个空白 Profile 已完成同时运行、状态隔离、锁冲突和独立停止检查。这个检查没有登录真实账号，也没有执行抓取、发送或发布。

### 模型

所有岗位 Agent 共享本地模型服务。短提取任务和复杂任务可以使用不同模型队列，本地设备暂时不能承担的任务可以进入云端模型候选流程。岗位 Agent 只提交任务，不自行修改模型端点、上下文和并发。

本地大模型和小模型做过短请求并发检查。短请求完成只说明当时的请求通过，不代表长任务和连续运行也稳定。系统级模型并发参数没有在这次检查中修改。

### 权限

身份文件只说明 Agent 的岗位和行为边界，它不授予系统控制权。目录权限、服务账号、MCP 工具、沙箱挂载和人工审批分别限制 Agent 能看到什么、能调用什么，以及哪些动作必须停下来等人确认。

Agent 可以读取服务状态的只读快照。快照只提供服务状态，不开放启动、停止和修改服务的接口。生产账号和岗位工具按岗位逐项接入，目录存在和服务运行都不等于岗位已经通过生产验收。

### 迁移故障和恢复

一次目录统一后，旧虚拟环境、MCP 命令、配置文件和沙箱挂载仍引用旧位置，部分服务因此不能按新路径启动。恢复时先保留迁移前副本，再建立有期限的兼容链接，随后逐项检查运行时路径、服务文件、环境变量和沙箱挂载。

服务按依赖顺序重启。每次恢复后重新核对工具清单，并用一张只读工单完成提交、审核、执行和结果回收。回滚副本保留到新路径完成观察，之后再由维护者决定是否删除。

### 尚未完成

每个岗位的独立聊天应用、生产账号、岗位工具和人类 Schedule 面板没有全部完成验收。连续运行观察、成本节省、Token 节省、效率和收入效果仍是 `candidate`。当前材料也不能证明这套系统可以替代一个公司或长期无人值守。

### 可以复制的做法

读者可以先复制目录模板和工单 Schema，再增加资源队列、浏览器锁和发布前检查。第一轮只使用测试数据和只读任务。对外动作继续由人确认。
