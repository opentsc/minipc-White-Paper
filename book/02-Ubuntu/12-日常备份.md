# 12　日常备份

## 这一章的任务

让机器每周自己把重要目录备份一份到移动硬盘。

做完之后，你手上有一个能随时跑的备份脚本、一份定时任务，以及一次亲手做过的还原——删掉一个文件，再从备份里把它拿回来。

## 和整盘镜像的分工

备份有两种，解决的是两件事，都要有。

**整盘镜像**在[第 1 卷第 10 章](../01-开箱与安装/10-恢复介质.md)已经做过了。它把整块 SSD 原样复制成一个文件，管的是“系统崩了、开不了机”，写回去机器就回到做镜像那一刻。代价是一次几个小时、占一整块盘的空间，所以只在装完系统、大改动之前做，不可能天天做。

**文件级备份**是这一章的事。它只复制你自己产生的那些文件，管的是“误删了、改坏了、想要昨天那一版”。几分钟跑完，可以每天跑，找回一个文件是几秒钟的事。

一句话分工：**系统崩了用镜像，文件没了用这一章。** 只有镜像，误删一个文件要还原整块盘，代价太大还会把别的新文件一起抹掉；只有文件备份，系统真起不来的时候要重装一遍系统再往回放文件。

## 开始前

- 第 1 章的 `~/ai` 目录结构在用了；
- 第 8 章的定时任务会写了，这一章直接接上；
- 一块移动硬盘，容量比 `~/ai/data` 和 `~/ai/projects` 加起来大；
- 40 分钟。

## 新词

**rsync**：Linux 上做同步的标准工具。它的特点是第二次跑只传变化的部分——第一次可能要几十分钟，之后每次几秒钟。

**镜像式同步**：让目标目录和源目录一模一样，源里删掉的文件目标里也删掉。rsync 的 `--delete` 就是干这个的，好处是备份不会越攒越乱，代价见下面的警告。

**试运行**（Dry Run）：只显示会做什么，不真的做。rsync 的 `--dry-run` 就是它，改动多、目标写不准的时候先跑一遍试运行。

## 先确认 rsync 在

```bash
rsync --version
```

输出第一行有版本号就行。提示 `command not found` 的话：

```bash
sudo apt install rsync
```

## 备份哪些，不备份哪些

**要备份的三类：**

1. **`~/ai/data`**——原始资料。扫描件、PDF、导出的表格，这些是你从外面收进来的，丢了要重新找一遍甚至找不回来；
2. **`~/ai/projects`**——项目。代码、配置、处理结果，还有第 10 章那套服务的 `compose.yaml`；
3. **`~/ai/scripts`**——脚本。第 8 章的整理脚本、这一章的备份脚本本身。

**再加上几个改过的配置文件**，`~/.bashrc`、`/etc/fstab` 这类。它们很小，但重装系统之后你多半记不起来当初改了什么。

**不备份的，第一大项是 `~/ai/models`。** 模型文件动辄几十 GB，而且它们在模型仓库上原样放着，重新下载就有。把模型放进每周备份，等于每周搬几十 GB 的东西，移动硬盘很快就满了。第 5 章把 `~/ai/models` 单独指到另一块盘上，也有这层意思。

**其余不备份的都是同一类东西：能重新生成的。** `node_modules`、`__pycache__`、`.venv` 这些目录是装依赖时自动产生的，文件成千上万，占地方还拖慢同步，删了执行一条命令就回来。

判断标准就一条：**这个文件丢了，我能不能不花钱不求人地弄回来。** 能，就不用备份。

## 第一步，写排除清单

```bash
nano ~/ai/scripts/backup-exclude.txt
```

内容：

```
models/
postgres/
node_modules/
__pycache__/
.venv/
venv/
.cache/
*.gguf
*.safetensors
*.iso
*.img
```

保存退出。

- 带斜杠的是目录名，不带斜杠、以 `*` 开头的按文件名匹配；
- `postgres/` 是第 10 章那个数据库的数据目录，为什么单独排除，本章后面说；
- `.gguf` 和 `.safetensors` 是模型文件常见的两种后缀，它们要是散落在项目目录里，这两行能拦住；
- 以后发现某个目录不值得备份，就往这个文件里加一行。

## 第二步，写备份脚本

```bash
nano ~/ai/scripts/backup.sh
```

原样抄进去：

```bash
#!/usr/bin/env bash
# 日常备份：先同步到本机 ~/ai/backup/latest，移动硬盘插着就再同步一份过去
set -euo pipefail

SOURCES=("$HOME/ai/data" "$HOME/ai/projects" "$HOME/ai/scripts")
LOCAL_DEST="$HOME/ai/backup/latest"
EXCLUDE_FILE="$HOME/ai/scripts/backup-exclude.txt"
LOG="$HOME/ai/backup/backup.log"
EXTERNAL_DEST="${1:-}"

mkdir -p "$LOCAL_DEST/config"

log() {
  echo "$(date '+%F %T') $*" | tee -a "$LOG"
}

log "开始备份"

for src in "${SOURCES[@]}"; do
  if [ ! -d "$src" ]; then
    log "跳过 $src，目录不存在"
    continue
  fi
  rsync -a --delete --exclude-from="$EXCLUDE_FILE" "$src" "$LOCAL_DEST/" >> "$LOG" 2>&1
  log "已同步 $src"
done

for f in "$HOME/.bashrc" "/etc/fstab"; do
  if [ -f "$f" ]; then
    cp -a "$f" "$LOCAL_DEST/config/"
  fi
done
log "配置文件已复制"

if [ -z "$EXTERNAL_DEST" ]; then
  log "没有给移动硬盘路径，这次只做了本机这一份"
elif [ ! -d "$EXTERNAL_DEST" ]; then
  log "找不到 $EXTERNAL_DEST，移动硬盘可能没插，这次只做了本机这一份"
else
  rsync -a --delete "$LOCAL_DEST/" "$EXTERNAL_DEST/" >> "$LOG" 2>&1
  log "已同步到 $EXTERNAL_DEST"
fi

log "备份结束"
```

给执行权限：

```bash
chmod 755 ~/ai/scripts/backup.sh
```

这个脚本做两步：

**第一步，把三个源目录同步到 `~/ai/backup/latest`。** 这是本机的一份，第 1 章约定 `ai/backup` 放的就是它。它跑得快，可以天天跑，专门对付误删和改坏。

**第二步，把整个 `latest` 同步到移动硬盘。** 移动硬盘没插就跳过，只在日志里记一行，不报错——定时任务在你不看着的时候跑，因为硬盘没插就整个失败没有意义。

`rsync` 那两行里的几个参数：

- **`-a`**：保留权限、修改时间、软链接，连子目录一起递归复制。备份一律用它；
- **`--delete`**：让目标和源保持一致，源里删掉的目标里也删掉；
- **`--exclude-from=`**：按刚才那张清单跳过；
- **`>> "$LOG" 2>&1`**：把 rsync 的详细输出和报错都收进日志文件，第 8 章讲过。

> **`--delete` 会删目标目录里的文件。** 目标写错——比如写成移动硬盘的根目录、或者写成 `~/ai/data` 本身——就会把那个位置里不属于备份的东西删掉。所以第一次跑之前，一定按下一节的做法先试运行看一遍。

## 第三步，先试运行，再真跑

第 8 章那条规矩这里同样适用：**先手动跑通，再交给定时任务。** 备份脚本还多一层，第一次要先试运行。

先看移动硬盘挂在哪（第 2 章的命令）：

```bash
ls /media/$USER/
```

输出是移动硬盘的卷标，例如 `WD-1TB`。在它上面建一个专用目录：

```bash
mkdir -p /media/$USER/WD-1TB/minipc-backup
```

**要给备份一个专用目录，不要直接用移动硬盘根目录。** 根目录上往往还有别的东西，`--delete` 会把它们清掉。

试运行一次，看它打算做什么：

```bash
rsync -a --delete --dry-run --itemize-changes \
  --exclude-from="$HOME/ai/scripts/backup-exclude.txt" \
  "$HOME/ai/data" "$HOME/ai/backup/latest/"
```

`--dry-run` 表示只看不做，`--itemize-changes` 表示每个文件都列一行、标出它要做什么。输出里以 `*deleting` 开头的行是要删的——**第一次跑不该有任何删除行**，有就是目标目录写错了，停下来核对。

看着没问题，真跑一次：

```bash
~/ai/scripts/backup.sh "/media/$USER/WD-1TB/minipc-backup"
```

卷标换成你自己的。第一次要传全部文件，慢一些。正常输出：

```
2026-08-14 16:20:01 开始备份
2026-08-14 16:20:38 已同步 /home/roland/ai/data
2026-08-14 16:21:02 已同步 /home/roland/ai/projects
2026-08-14 16:21:02 已同步 /home/roland/ai/scripts
2026-08-14 16:21:02 配置文件已复制
2026-08-14 16:23:47 已同步到 /media/roland/WD-1TB/minipc-backup
2026-08-14 16:23:47 备份结束
```

再跑第二遍，几秒钟就完了——rsync 只传变化的部分。

看结果：

```bash
ls /media/$USER/WD-1TB/minipc-backup
du -sh /media/$USER/WD-1TB/minipc-backup
```

里面应该有 `data`、`projects`、`scripts`、`config` 四个目录。

跑完要拔线的话，先弹出，做法见第 1 章，不弹直接拔可能拔在还没写完的时候。

## 只有一块盘，和有两块盘

**只有一块盘（多数人的情况）**：照上面做就行。本机那份 `~/ai/backup/latest` 和原件在同一块盘上，**它只防误删和改坏，不防硬盘坏**。真正的第二份是移动硬盘上那份，所以移动硬盘那一步不能省，也别把移动硬盘长期插着不管——插着的盘和内置盘一起遭殃的情况是有的（比如误操作、电源故障）。

**按第 5 章挂了第二块盘**：可以让本机那份直接落在第二块盘上，做法和第 5 章处理 `~/ai/models` 一样：

```bash
mkdir -p /mnt/aidata/backup
mv ~/ai/backup/* /mnt/aidata/backup/
rmdir ~/ai/backup
ln -s /mnt/aidata/backup ~/ai/backup
```

四条依次是：在第二块盘上建目录、把已有内容搬过去、删掉空的旧目录、建一个软链指过去。`~/ai/backup` 本来就是空的话，第二条会报一句找不到文件，跳过它直接做第三条。

之后脚本里的 `~/ai/backup` 一个字都不用改，文件实际落在第二块盘上。这样本机这份已经在另一块盘上了，加上移动硬盘那份，一共三份。

移动硬盘那一步两种情况都一样。

## 第四步，交给定时任务

第 8 章的做法直接套用：

```bash
crontab -e
```

加上这一行：

```
0 4 * * 0 /home/你的账户名/ai/scripts/backup.sh "/media/你的账户名/WD-1TB/minipc-backup" >> /home/你的账户名/ai/backup/cron.log 2>&1
```

`0 4 * * 0` 是每星期日凌晨 4 点，五个字段的读法见第 8 章。账户名和卷标换成你自己的，路径写全，不要用 `~`。

第 8 章说过定时任务不要都堆在同一分钟。那边整理下载文件夹是每天 3 点，这边是每周日 4 点，错开了。

验证方法也和第 8 章一样：先把时间改成一两分钟以后，等它跑，然后看日志：

```bash
tail -20 ~/ai/backup/backup.log
```

有新的一组带时间的行，就是跑过了。验证完把时间改回 `0 4`。

**每周备份意味着最坏情况下会丢掉最近 7 天的改动。** 觉得太多就改成每天，把周字段的 `0` 换成 `*`。rsync 是增量的，天天跑也不慢。

## 第五步，真的还原一个文件

**没试过还原的备份不算备份。** 现在就试一次。

造一个测试文件：

```bash
echo "这是一个测试文件 $(date)" > ~/ai/data/restore-test.txt
cat ~/ai/data/restore-test.txt
```

跑一次备份：

```bash
~/ai/scripts/backup.sh "/media/$USER/WD-1TB/minipc-backup"
```

确认备份里有它：

```bash
ls -l ~/ai/backup/latest/data/restore-test.txt
ls -l /media/$USER/WD-1TB/minipc-backup/data/restore-test.txt
```

现在故意删掉原件：

```bash
rm ~/ai/data/restore-test.txt
```

第 2 章说过命令行删除没有回收站，这里就是要演示那种情况。执行完 `ls ~/ai/data/` 看一眼，文件确实没了。

从备份拿回来：

```bash
cp ~/ai/backup/latest/data/restore-test.txt ~/ai/data/
cat ~/ai/data/restore-test.txt
```

内容原样打出来，说明这条路是通的。移动硬盘那份也试一次：

```bash
cp /media/$USER/WD-1TB/minipc-backup/data/restore-test.txt ~/ai/data/restore-test2.txt
cat ~/ai/data/restore-test2.txt
```

两个测试文件试完就删掉。

**这个演练每季度做一次。** 备份出问题的方式往往很安静——目标路径写错、移动硬盘早就没插、某个目录一直被排除在外——脚本天天跑得好好的，直到你真要用的那天才发现里面是空的。

整台机器要恢复，那是[第 1 卷第 10 章](../01-开箱与安装/10-恢复介质.md)的事：先用镜像把系统写回去，再把这一章的备份复制回 `~/ai`。

## 数据库这类目录单独处理

第 10 章那套服务的 `~/ai/projects/gitea/postgres` 目录，普通账户读不了（第 10 章说过原因），rsync 会报权限不足，所以排除清单里排掉了它。

数据库还有第二个麻烦：**运行中的数据库，文件是一直在写的**，直接复制出来的副本不保证能用。

正确的做法是先停再备：

```bash
cd ~/ai/projects/gitea
docker compose stop
sudo rsync -a ~/ai/projects/gitea/postgres "/media/$USER/WD-1TB/minipc-backup/gitea-postgres/"
docker compose start
```

停服务的那几十秒里网页打不开，所以这件事手动做，挑没人用的时候，不要塞进每周的自动备份。

更省事的办法是用数据库自己的导出命令，导出来是一个普通文件，不用停服务也能备。那属于第 3 卷服务器基础的内容。

有哪一步做不出来，到[第 15 卷：故障排查](../15-故障排查/README.md)按症状查。

## 一份不够

上面这套跑通之后，你手上有两到三份：原件、本机备份、移动硬盘。它们都在同一个房间里。

真正重要、丢了要出事的那部分资料——客户给的原始文件、你自己的项目——再放一份到别的地方：另一块常年不插在这台机器上的硬盘、放在别处的电脑、或者加密之后传云盘。往外传之前先按[第 0 卷第 8 章](../00-使用说明/08-文件保护.md)检查一遍里面有没有不能外传的内容。

## 完成检查

- `~/ai/scripts/backup.sh` 和 `~/ai/scripts/backup-exclude.txt` 都在，脚本有执行权限吗？
- 手动跑一次，`~/ai/backup/latest` 下面有 `data`、`projects`、`scripts`、`config` 吗？
- 移动硬盘上的备份目录里，内容和本机那份一样吗？
- 连着跑第二次，明显比第一次快吗？
- `crontab -l` 里有那条每周备份的任务吗？
- 删掉一个测试文件再从备份里还原回来，你亲手做过了吗？
- `--delete` 有什么风险，第一次跑之前该先做什么？
- 整盘镜像和这一章的备份，各自在什么情况下用，你能说清楚吗？
