# 项目章程 v0.1

## 项目目的

把 Mini PC 从一台收到货的设备，整理成一套初学者可以跟着执行的本地计算环境。

项目同时包含白皮书、部署文档、示例项目和必要的脚本。白皮书负责解释范围和判断，脚本负责减少重复操作，案例负责说明设备能做什么。

## 教学方法

项目采用案例教学。

每个案例从一个任务开始，例如同步文件、整理票据、运行本地模型或监控一个网站。教程不先讲完整的 Linux 知识，再让用户找用途。它先让用户看到结果，再解释这个过程中用到的目录、权限、端口、容器、日志、备份和安全边界。

每个案例使用同一结构：

```text
用户要完成什么
→ 开始前要准备什么
→ 执行步骤
→ 预期看到什么
→ 从哪里检查结果
→ 失败后怎么恢复
→ 这次学到了什么
→ 成本或收入判断还缺什么证据
```

## 用户提出的原始方向

用户收到 Mini PC 后，先部署 Ubuntu。之后假设用户没有基础，带他完成入门，并说明这台设备可以做哪些项目，包括节约云端模型成本、本地运行模型、形成收入的可能路径，以及本地算力为什么值得学习。

## 已确认事实

- 当前交付设想是给用户提供已经部署 Ubuntu 的 Mini PC。
- 目标用户包含没有 Linux 和本地算力经验的人。
- 项目希望开源。
- 内容不只写模型，还要覆盖部署、入门、项目和使用边界。

## 工作区中的已有材料

- 工作区有一台 Ubuntu Mini PC 的历史运行记录，记录过本地服务、Ollama、本地模型和网站工作台。
- 工作区还有一台 Windows Mini PC 的历史记录，它承担过网站仓库主机角色。
- 两台设备的系统、用途和网络边界不同。白皮书不能把它们写成同一台标准设备。
- 历史运行记录需要在正式发布前重新核对。它们可以作为项目材料，不能单独作为当前性能保证。

## 第一版读者

第一版只服务一个主要读者：

> 已经拿到 Mini PC，设备上有 Ubuntu，但不知道下一步该做什么的人。

其他读者包括想在本地运行模型、部署个人服务或减少云端调用的人。企业级部署、多人权限、合规审计和高可用集群暂不作为第一版主线。

## 第一版交付物

1. 一份白皮书，解释路线、项目选择和边界。
2. 一份收到设备后的部署检查表。
3. 一份 Ubuntu 初学者操作路径。
4. 一组从低难度到高难度的示例项目。
5. 一份本地模型与云端模型的选择和成本记录方法。
6. 一套公开贡献和隐私检查规则。

## 当前判断

这个项目的核心不是“卖一台小电脑”，而是把设备、系统、教程、项目和后续服务放在同一条使用路径里。

“赚钱”可以作为案例方向，不能作为白皮书的默认结果。第一版应先证明用户能完成部署、能运行一个项目、能看懂成本和风险，再讨论收入。

开源的价值可能来自三部分：

- 让用户可以自己完成基础部署。
- 让外部贡献者补充型号、脚本和案例。
- 让读者看到完整的本地部署能力，再决定是否购买设备、部署或持续支持。

这条路径是否能形成后端收入，还需要真实用户、支持工时、设备毛利和转化记录。

## 未确认事项

- 项目的正式名称和仓库名称。
- 第一批支持的 Mini PC 型号、处理器、内存和存储配置。
- Ubuntu 的具体版本和安装方式。
- 是否预装 Docker、Ollama、Tailscale、Open WebUI 等组件。
- 哪些能力放进免费开源仓库，哪些能力保留为部署和支持服务。
- 代码许可证和文档许可证。
- 本地模型成本、速度、质量和可用任务的实际记录。
- 收入案例是否来自自有项目、客户授权案例或公开资料。
- 第一批教学案例选择哪 3 个。

## 停止条件

- 没有指定设备和版本，却把性能写成普遍结论。
- 没有真实成本记录，却把本地部署写成一定更便宜。
- 没有真实客户或项目证据，却把候选项目写成赚钱方法。
- 公开仓库中出现密钥、个人记录、私有路径或真实客户材料。
- 部署步骤不能重复执行，也没有回滚或人工检查点。
