## 新词

**iGPU**（集成 GPU，integrated GPU）：和 CPU 做在同一块芯片上的图形处理器，没有自己的显存，用系统内存。与之相对的叫独立显卡（dGPU），插在主板插槽上，自带显存。这台设备上的 iGPU 是 Radeon 8060S。

**NPU**（神经网络处理单元，Neural Processing Unit）：专门做神经网络计算的加速器，特点是同样的计算耗电更少。这台设备上的 NPU 架构代号是 XDNA2。

**内核**（Kernel）：操作系统最核心的那一部分程序，负责管理硬件、内存和进程。你装的 Ubuntu 里就有一个 Linux 内核，版本号用 `uname -r` 能看到，例如 `6.17.0-...`。硬件能不能被认出来、能用到什么程度，很大程度上取决于内核版本和内核里带的驱动。

**驱动**：让操作系统能使唤某个硬件的那段程序。有的驱动在内核里，有的要另外装。Radeon 8060S 的内核驱动叫 `amdgpu`，NPU 的内核驱动叫 `amdxdna`。

**推理框架**：把模型文件加载起来、按你的输入算出回答的那套软件，例如 Ollama、llama.cpp、vLLM、Lemonade。硬件能不能被用上，取决于框架有没有支持它的那条路径。第 6 卷专讲这些。

**算子**：模型计算被拆成的一个个基本运算步骤，例如矩阵乘法、归一化、注意力计算。硬件支持某个框架，不等于这个框架用到的每个算子在这块硬件上都实现了，这是本地 AI 领域大量缺陷的来源。

**NPU-only 推理**：整个模型完全在 NPU 上跑，iGPU 不参与。

**混合推理**：同一个模型的不同部分分给不同的计算单元跑，例如一部分在 NPU、一部分在 iGPU。这两个词在第 3 节要用到。

**IOMMU**（输入输出内存管理单元）：芯片里的一个部件，管外部设备访问内存时的地址转换和权限隔离。它开着的时候，设备只能访问被允许的那部分内存。NPU 依赖它工作，本教材保持内核默认开启，理由见第 6 章。

**功耗预算**：整机在某一时刻允许消耗的总功率。CPU、iGPU、NPU 从同一份预算里分，一个多拿，另一个就少拿。

## 三个计算单元各自干什么

**CPU（16 核，Zen 5）**

跑操作系统本身、桌面、后台服务；跑那些一步接一步、逻辑复杂的程序。在本地模型这条链路上，CPU 负责的是：把你输入的文字切成 token、加载模型文件、准备数据、调度 GPU 的工作、把结果送回给你，以及跑那些没有被 GPU 接管的算子。

**iGPU（Radeon 8060S，40 个计算单元，RDNA 3.5）**

负责大批量、同样形式的乘法和加法。模型推理的绝大部分计算量是这种形式，所以这是跑本地模型的主力。规格和代号在第 3 章。

**NPU（XDNA2，50 TOPS）**

专做神经网络计算的加速器。它的长处不是绝对速度，是同样的计算耗电更少。内核文档把它描述为集成在 APU 内的多用户推理加速器，可以跑 CNN 和部分 LLM 任务（来源：kernel.org 的 AMD NPU 内核文档，访问日期 2026-08-13）。

三者的关系可以这样记：CPU 管调度和杂活，iGPU 出力，NPU 是一条另外的低功耗路线，在 Linux 上目前还没打通到日常可用（下面第 3 节详细说）。

## 跑本地大模型时实际用的是哪个

**用的是 iGPU。**

这是本教材第 6 卷所有安装步骤的前提，理由是三条公开材料：

- Ollama 的 GPU 支持列表把 gfx1151（也就是 Radeon 8060S）列入支持范围，前提是系统装了 ROCm 7 驱动，同一页还说明了 Vulkan 后端的开关（来源：Ollama 官方文档，访问日期 2026-08-13）；
- llama.cpp 的每个发布版本直接提供 Ubuntu 的 Vulkan 预编译包（来源：llama.cpp 发布页，访问日期 2026-08-13，当日最新版本为 b10405）。Vulkan 是一套图形与计算接口，走的是 GPU；
- AMD 自己的 ROCm 文档给 Ryzen AI 系列的 Linux 安装说明里，要求把用户加进 `render` 和 `video` 用户组才能调用 GPU 计算接口（来源：AMD ROCm 文档《Install Ryzen AI Software for Linux with ROCm》，访问日期 2026-08-13）。这两个组管的是 GPU 设备节点。

也就是说，主流的本地模型工具在 Linux 上的路径是“框架 → Vulkan 或 ROCm → iGPU”，NPU 不在这条路上。

**50 TOPS 这个数字容易造成误解。** 它是 NPU 的峰值指标，不是这台设备跑模型的速度，也不说明模型跑在 NPU 上。买这台设备跑本地大模型，你花钱买到的算力主要是 iGPU 那 40 个计算单元加上 128 GB 内存的容量，不是那 50 TOPS。

## NPU 在 Linux 上当前能做什么、不能做什么

这一节的结论按 2026-08-13 的材料写。这个方向变化快，用之前先按下面的来源重新核对一次。

**驱动这一层是有的**

`amdxdna` 是 NPU 的内核驱动，负责 NPU 硬件阵列、微控制器和邮箱的管理，原生支持进程隔离（来源：kernel.org 的 amdxdna 内核驱动文档，访问日期 2026-08-13）。同一批文档说明 AMD NPU 是集成在 APU 内的多用户推理加速器，通过 amdxdna 栈运行 CNN 与部分 LLM 任务。

要注意这两份文档说明的是**驱动的职责**，不证明任何一个本地大模型框架能在 Linux 上真的调用到 NPU。这是两件事。

**跑起来需要的条件**

FastFlowLM 的 Linux NPU 指南（Lemonade 站点，访问日期 2026-08-13）列出的前提是：

- XDNA 2 硬件（Max395 满足）；
- 内核 7.0 以上内置 `amdxdna`；6.x 内核要走 DKMS 自己编译安装驱动；
- NPU 固件 1.1.0.0 以上；
- IOMMU 开启；
- 装好之后用 `flm validate` 自检。

本教材的基准系统是 Ubuntu 24.04.4 加 HWE 内核 6.17（见第 9 章），按这份指南属于要走 DKMS 那一档。

**当前明确做不到的：NPU 与 iGPU 的混合推理**

同一份 FastFlowLM 指南写明：Linux 上只支持 NPU 单独推理，**NPU 与 iGPU 的混合推理仍然是 Windows 专属**。

两个词的区别：

- **NPU-only 推理**：整个模型从头到尾在 NPU 上算。能跑，但受 NPU 本身的规模和内存路径限制，能跑的模型和吞吐都有限；
- **混合推理**：把同一个模型的不同部分交给不同的计算单元，让 NPU 和 iGPU 一起出力。Windows 上有这条路，Linux 上没有。

至于混合推理具体怎么拆分模型、拆分依据是什么，材料没有说明，**需要核验**。

**已经出现过的落差**

材料里有一条记录：Lemonade 10.2.0 宣称对 Strix Halo 提供 Day Zero 支持，实际调用受阻（来源：RyzenAI-SW issue #367，访问日期 2026-08-13）。这是单一版本的报告，不代表后续版本的状态，但它说明一件事：**厂商页面上写“支持”，不等于你装上就能用。**

**本教材的处理**

本项目**没有在自己的设备上实测过 NPU 推理**，上面引用的材料自己也标注了未在本机实测。因此本卷不给 NPU 的性能数字，也不把 NPU 写进第 6 卷的主线安装步骤。**整节内容需要核验。**

给客户做方案时，不要把 NPU 算进承诺范围。要用 NPU，先按上面的条件在你自己的机器上验证一遍，再决定。

**一个和 NPU 直接相关的设置：IOMMU**

有些性能教程会让你在内核参数里加 `amd_iommu=off`，理由是内存读取更快。代价是 NPU 直接消失：`amdxdna` 依赖 IOMMU 提供的地址隔离能力，关掉之后 NPU 的设备节点就不存在了，FastFlowLM、Lemonade 的 NPU 路线全部关门。

- **默认值**：内核默认开启，本教材不改，GRUB 里不写这个参数；
- **改动条件**：本教材没有推荐改动的场景。收益在材料里是内存读取快约 6%（strixhalo.wiki 口径）到 5% 至 12%（kyuz0 跑分口径），两家口径都没有第三方复测；代价是 NPU 失效、待机失效、虚拟化与设备直通失效、DMA 防护失效；
- **验证方法**：`cat /proc/cmdline` 看这一行里有没有 `amd_iommu=off`；
- **恢复方法**：把这个参数从引导配置里删掉，重新生成引导配置，重启；
- **操作步骤见第 9 章**，完整理由见第 6 章。

## 三者共享同一份功耗预算

这一点是 Max395 这类芯片和“CPU 加独立显卡”最容易被忽略的差别。

独立显卡有自己的供电和自己的功耗上限，CPU 跑满不影响显卡能拿到多少电。Max395 上三个计算部件在同一块芯片上，共用整机厂设定的那一份功耗预算。CPU 全核跑满，iGPU 能拿到的功耗就少；反过来也一样。

对使用者的三条实际影响：

1. **跑模型的时候不要同时压满 CPU。** 一边跑推理一边跑编译、转码、大批量数据处理，推理速度会掉，掉多少取决于机器的功耗墙；
2. **同一台机器的性能数字会随后台负载变化。** 这是不能用单一跑分概括的原因之一。测基线时要说明当时机器上还跑着什么（第 16 章）；
3. **功耗档位是可以改的设置。** 默认值随整机厂而定，档位名称各家不同。改动条件、验证方法和恢复方法见第 10 章，本章不展开。

关于“把 CPU 锁在最高性能档能不能提速”，材料里有两派相反的说法：

- 一派是社区优化脚本：锁 performance、屏蔽 C-state 能提速；
- 一派是 nix-amd-ai 的开发者：APU 共享功耗预算，CPU 满频挤占 iGPU 的功耗，对带宽敏感的解码阶段是负优化。

本项目 2026-08-14 的来源核查记录写明：**两派都没有实机复测数据，材料只给了转述，没有给原始链接。** 所以本教材在这一点上不给结论，**需要核验**。要判断你那台机器，用第 16 章的方法，改一个变量测一次。

## 怎么在自己的机器上看到这三个部件

下面三条都是只读命令，不改任何设置。

**看 CPU**

```bash
grep -m1 "model name" /proc/cpuinfo
```

输出里应当出现 `AMD Ryzen AI Max+ 395` 或近似写法（[第 1 卷第 4 章](../01-开箱与安装/04-硬件规格检查.md)）。

**看 iGPU**

```bash
lspci | grep -i vga
```

输出里应当出现 AMD 或 Radeon 相关字样。

**看 NPU 的设备节点**

```bash
ls /dev/accel/
```

`amdxdna` 驱动加载之后，NPU 会以 `accel` 类设备的形式出现在这个目录下。目录不存在或者是空的，说明当前内核没有加载 NPU 驱动。

> 这条命令的路径写法来自项目的补充材料，本项目未在自己的设备上验证过，**需要核验**。看到目录不存在也不必处理，本教材主线不依赖 NPU。

## 正常结果

读完本章，你能回答：跑本地模型用的是 iGPU；NPU 在 Linux 上目前只有 NPU 单独推理这条路，还要满足内核、固件和 IOMMU 的一串前提，本项目未实测；三个部件抢同一份功耗，所以性能数字必须连测试条件一起写。

## 看到不同结果怎么办

**`ls /dev/accel/` 提示目录不存在**：说明当前内核没有加载 NPU 驱动。在 Ubuntu 24.04 的 HWE 内核 6.17 上，这属于预期内的情况，NPU 驱动要走 DKMS 单独装。本教材主线不用 NPU，可以不处理。

**你在别处看到“Max395 有 50 TOPS 的 AI 算力，所以跑模型很快”**：这句话把 NPU 的峰值指标当成了整机的推理速度。跑本地大模型用的是 iGPU，这个数字和你的 tokens/s 没有直接关系。

**你按某篇教程加了 `amd_iommu=off`，之后 NPU 不见了、机器睡不着或者虚拟机起不来**：这是这个参数的已知代价，不是故障。把参数删掉重启即可，操作步骤见第 9 章。

**你确实需要用 NPU**：按 FastFlowLM 的 Linux NPU 指南逐条核对内核版本、固件版本和 IOMMU 状态，用 `flm validate` 自检，并且把结果记进第 16 章的设备基线。在验证通过之前，不要把 NPU 写进给客户的方案。

**你的推理速度比预期慢很多**：先看当时机器上还跑着什么。功耗被 CPU 占走是常见原因之一，其他原因见第 12 章和第 15 卷。
