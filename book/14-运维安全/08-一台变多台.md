# 08　一台变多台

## 这一章的任务

手上有三台以上客户机器的时候，怎么管。

前七章讲的是一台机器的十二个月。 那一套动作在一台上是够用的，在五台上会出三个新问题：

```text
一、记不住了　　　　　哪一台是谁的、装了什么、维护到什么时候
二、巡检看不过来　　　五台每天五份输出，你不会每天看五份
三、每台都不一样　　　这一台是去年装的，那一台是接管来的，版本各不相同
```

这一章各给一个做法：设备清单、统一巡检、版本统一。

最后一个问题最难，也是这一章的正题：一个人能维护几台。

这一章不给台数结论。 给的是一个按月度工时算的判断方法，算出来的数是你自己的，不是别人的。

这是本卷最后一章。 最后一节写清这一卷做完之后你手上有什么。

## 开始前

- 前七章走完，至少有一台机器按那一套跑过三个月；
- [第 2 章](02-盯着.md)那份巡检跑在那台机器上，每天一份输出；
- [第 6 章](06-月度报告.md)那份月度报告出过至少三份；
- [第 1 章](01-维护费卖什么.md)那张月维护交付清单，每个客户一份；
- [第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)那份基线，每台一份，而且每台都存了两份；
- 一个能放台账的地方。 一张 Excel、一份表格文件、或者一个文本文件都行；这一章不要求你上一套系统；
- 你自己前三个月的实际工时记录。 第四节全靠它，没有的话那一节算不出来。

## 新词

设备台账：你手上所有客户机器的总表，一台一行。 它在[运维手册](../../playbooks/managed-support/README.md)那张服务架构图里，在“你这一头”那一栏。

统一巡检：同一份检查跑在所有机器上，结果汇总成一张表。 看的是那一张表，不是每台的原始输出。

月度工时：一台机器一个月实际占掉你多少小时。 第四节用它算上限。

## 一、设备清单

一台一行。

### 每台要记什么

十三格，分四组。

```text
【认得出是哪一台】
　编号　　　　　　　你自己编的，贴在机器上一张，台账上一行
　客户　　　　　　　公司名
　位置　　　　　　　哪个楼、哪个房间、哪个柜子，谁有钥匙

【认得出它是什么】
　机型与配置　　　　整机型号、内存、硬盘
　装的是什么　　　　系统、驱动、跑模型那层、跑着哪一套业务
　基线在哪儿　　　　机器之外那一份存在哪
　交付日 / 接管日　　哪一天开始归你管

【认得出该做什么】
　维护到期日　　　　这一年到哪一天
　服务清单　　　　　包几次巡检、几次上门、几次演练、响应等级
　下一次上门　　　　日期
　已知问题　　　　　有几条，在哪儿

【认得出找谁】
　对接人　　　　　　收报告的那个，姓名、职务、电话
　拍板人　　　　　　停机、花钱、续费找他
　管权限的人　　　　离职回收找他
```

第一格那个编号要自己编，而且要贴在机器上。

出事那天客户电话里说“我们那台机器”，你手上有五台，需要一个词把它定下来。

编号的形状随便，能排序、看得出年份就够（虚构示例里用的是 `MP-2026-007` 这种）。

贴在机器上那一张要写三样：编号、找谁、多久有人回。 这一张就是那一页说明书的缩略版，机房里那台机器上要有。

### 有三格最容易漏

一、位置那一格要写到“谁有钥匙”。

[level-90／01](../../labs/level-90/01-first-delivery-record/README.md)那条：进场信息表比线索表还敏感，它写清了那台机器在哪个房间、哪个柜子、谁有钥匙。

这一格在一台机器的时候你记得住，五台的时候记不住，而它是要上门那天唯一要紧的一格。

二、维护到期日那一格要能排序。

这一格的用处是提前两个月看见续费。

[第 11 卷第 9 章](../11-客户与报价/09-第二单在哪.md)那条：续费不是从到期前一周开始的。 台账按这一格排一次序，你就知道接下来两个月要谈几家。

三、已知问题那一格。

接管来的机器一定有。 [运维手册](../../playbooks/managed-support/README.md)那条：每份月度报告的末尾附一遍，不要只在接管那天出现一次。

台账上这一格写“有几条、在哪儿”，出报告的时候不会漏。

### 这张表放哪儿，谁能看

这张表上有客户名、机器位置、对接人电话、有钥匙的人。

[第 0 卷第 8 章](../00-使用说明/08-文件保护.md)那份不能公开的内容，这张表上占了好几条。

三条规矩：

```text
不进任何仓库、不进聊天、不进邮件正文
存两份，一份不在你那台笔记本上
笔记本换了、修了、卖了之前，先想起这张表和第 5 章那几把钥匙
```

第三条在[第 5 章](05-安全最小集.md)提过一次，本章那张模板里有专门一行。

## 二、统一巡检

做法是：同一份检查跑在所有机器上，输出汇总成一张表。

### 为什么要同一份

每台一套自己的检查，会出三件事：

```text
一、你不记得这一台查了哪几项、那一台查了哪几项
二、加了一项新检查，只加在其中几台上
三、汇总的时候对不齐——同一件事在两台上叫两个名字
```

第三件会让汇总表变得没法一眼看。

做法是把[第 2 章](02-盯着.md)那份检查当成一份，所有机器跑同一份。

机器之间的差别用参数处理，不用改脚本本身，[level-30／01](../../labs/level-30/01-remote-managed-box/README.md) 那个体检脚本已经这么做了，要查哪几个服务、SSH 在哪个端口，都是环境变量。

加检查的时候，这一条的效果最明显：[第 7 章](07-出事了.md)那次故障之后要加一项“容器重启策略逐个对”，改一处，所有机器都有了。

### 汇总成一张表

每天一张，一台一行。

列是检查项，格子里是通过、不通过、跳过。

```text
编号　　　跑没跑　　1-9 项　　磁盘　　温度　　服务　　备份　　日志　　要看的
```

这张表的用法有一条：你每天只看两列。

```text
第一列　　“跑没跑”　　今天这台机器有没有交出一份输出
最后一列　“要看的”　　今天有几件事要动手
```

第一列比后面所有列加起来都重要。

理由在[第 2 章](02-盯着.md)那条：机器停电、断网、开不了机的时候，它不会给你发“我挂了”。

汇总表上那一台今天是空的，这就是它在说话。

做法是汇总的时候把“没交输出”当成一种结果，不是当成缺数据。 空着的格子会被眼睛跳过，标成“今天没交”不会。

### 一次汇总怎么跑

两种做法，按你手上的条件选。

```text
拉过来　　　　你这一头定时连上每一台，各跑一次，收回输出
推上来　　　　每一台自己跑完，把输出发到你这一头
```

接管来的机器、或者客户不让常连的，用第二种。

做法不重抄：远程连接在[第 3 卷第 4 章](../03-服务器基础/04-SSH.md)与[第 6 章](../03-服务器基础/06-Tailscale.md)，定时任务在[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)，发消息在[第 9 卷](../09-Agent与RPA/README.md)。

有一条边界要守住：远程运维要经客户书面授权、每次留日志、客户可随时中止（[运维手册](../../playbooks/managed-support/README.md)、[第 13 卷第 7 章](../13-项目交付/07-交接与售后边界.md)）。

这一条在多台的时候更要说清楚：你这一头有一个能定时连进他们机器的东西，这件事要写在服务说明里，不要让客户自己发现。

### 月底那一次

月底要跑的是另一件事：把这一个月的输出汇总成每台的月度报告原料。

做法在 [level-100／01](../../labs/level-100/01-monthly-checkup/README.md)。 那个实验的脚本一次跑完月度巡检要看的项，输出的形状可以直接抄进[第 6 章](06-月度报告.md)那份报告的第二栏。

多台的时候，这一步是每台跑一次，不是跑一次出五份。 五个客户的报告要分开做，不要合成一张表发出去，那张表上有别人的信息。

## 三、版本要不要统一

建议统一。

### 理由两条

一、排查快。

五台机器五个版本，出事那天你要先确认这台机器是哪个版本。

统一之后，[第 15 卷](../15-故障排查/README.md)里查过一次的症状，在第二台上就是现成的答案。

二、经验能复用。

在一台上试出来的做法，能直接用在另外四台上。

这一条在升级时最有用：[第 4 章](04-升级节奏.md)那条“先在另一台同型号机器上走一遍”，在多台的时候变成了一条真正可行的路线，你有一台可以先走。

做法是排一个顺序：

```text
自己那台　　　　　先升，观察
最不关键的那一台客户机器　　　次之（要客户同意，而且要说清楚）
其余的　　　　　　　最后
```

中间那一步要说清楚，不能默默做。

照念一句（虚构示例）：

> “这一版我自己那台跑了两周没问题。您这边不是最忙的那一家，我想在您这儿先升，升完观察两周，再给别的客户升。万一有问题，当天退回去，退回去我量过，二十分钟。”

这句话里有一件事要坦白：你在他这儿先试。 说出来，客户多半会同意，而且会觉得你没有拿他当小白鼠，因为你说了。

不说而被发现，是另一回事。

### 什么情况可以不统一

四种：

```text
一、接管来的机器，一档问题以外的版本不动　　　（运维手册那条：另行报价）
二、客户的业务卡在某一个版本上　　　　　　　　那就卡着，写进已知问题
三、机型不同　　　　　　　　　　　　　　　　　不同整机的差异是真的（第 4 卷第 15 章）
四、统一的代价大过收益　　　　　　　　　　　　只有两台，各自都稳，那就别动
```

第一种是最常见的一种。

[运维手册](../../playbooks/managed-support/README.md)那条：驱动、ROCm 与系统的版本升级不含在月费里，另行报价。 接管来的机器要统一版本，那是一次单独的活，不是顺手做的。

第四种要认真对待，因为“统一”本身会让人手痒。

判断的办法是问一句：不统一，出事那天我要多花多久？ 答案是“十分钟”，那就别动；答案是“半天”，那就该统一了。

### 不统一的那几台，台账上要标出来

设备清单“装的是什么”那一格要写清版本，而且要在台账上一眼看得出哪几台和大队不一样。

做法是加一个标记：和标准版一致的写“标准”，不一致的写清哪一样不一样。

这一格的用处是出事那一刻：你看一眼台账，就知道这台机器要不要按别的路子查。

## 四、一个人能维护几台

这一节不给数字。

这个数取决于四件事，四件都和你有关：

```text
你的响应等级承诺　　　　　　2 小时和下一个工作日，差的是你的生活方式
上门还是纯远程　　　　　　　路上那半天是实打实的成本
机器是不是你装的　　　　　　不是你装的，第一年意外多
每台跑着几件事　　　　　　　一台一件和一台四件，巡检时间差好几倍
```

这四条是[运维手册](../../playbooks/managed-support/README.md)“报高报低”那两组情形的前四条，本章不重抄那两张表。

### 用月度工时算

做法四步。

第一步，记三个月的工时。

分七段记，一段一段记，不要只记总数：

```text
每天看巡检和告警　　　　　　　（含每周那三十秒自查）
处理告警和小问题
上门　　　　　　　　　　　　　含路上
出月度报告　　　　　　　　　　含收数、写、发、跟回执
季度那几件　　　　　　　　　　演练、权限审查、体检对照（摊到每个月）
故障　　　　　　　　　　　　　含电话、排查、写说明
客户来问东问西　　　　　　　　这一段最容易不记，而它是真的
```

最后一段要单独说。

它不在服务清单上，但它每个月真的在发生：一通电话问一件小事、一次微信问“这个能不能也帮我弄一下”、一次帮他看一个和这台机器没关系的问题。

不记这一段，你算出来的上限会偏高，而偏高的那一部分正是压垮你的那一部分。

[level-90／01](../../labs/level-90/01-first-delivery-record/README.md) 那条同样成立：补出来的工时永远偏小，这一点你自己要知道。

第二步，算出每台每月平均占多少小时。

三个月的总和除以三，再除以台数。

要分开算：自己装的那几台一个数，接管来的那几台另一个数。 这两个数通常差得很多。

第三步，定一个你每月愿意在运维上花多少小时。

这一步是这一节的关键，而且它不是技术问题。

要考虑三件：

```text
你还要不要接新单　　　　运维占满了，就没有时间做交付了
你的休息　　　　　　　　承诺 2 小时内回，意味着上班时间不能关静音
出事那个月的峰值　　　　平均值不是上限，出事的月份是平时的几倍
```

第三件最容易被忽略。

按平均值排满的人，出事的那个月一定爆掉。 要留出峰值的余量，留多少你自己定。

第四步，两个数一除。

```text
你每月愿意花的小时数　÷　每台每月平均小时数　＝　你现在能带几台
```

这个数算出来通常比你以为的小。

### 算出来之后有三条路

```text
一、请人　　　　把哪一段交出去，下面说
二、拒单　　　　这一单不接，或者改成按次上门
三、涨价　　　　同样的时间，收更多
```

第三条要说一句：涨价不是对老客户涨，是对新客户报得更高。

[运维手册](../../playbooks/managed-support/README.md)那条硬规矩还在：月费不打折。 它反过来也成立，你手上排满了，新单就该按“报高”那一组的价来。

### 请人的话，先交出哪一段

按这个顺序，从最容易交的开始：

```text
一、每天看汇总表　　　　这一段最容易交，规则清楚，出错代价小
二、出月度报告　　　　　收数和写，你只审最后一栏
三、季度演练里的执行部分　你定流程，他执行，记录你看
四、故障响应　　　　　　这一段最难交，最后交
```

第四段最后交的理由有两条：

一、它要判断，而判断靠的是这台机器的历史。

二、它是客户感知最强的一段。 客户对这门服务的信任，一大半建立在出事那天接电话的是谁。

### 什么时候该拒单

四种，各有理由。

一、算下来时间不够。

接了就是每一家都做不好。 这一条最简单，也最难做到。

二、响应等级你答应不了。

[运维手册](../../playbooks/managed-support/README.md)那条：接一个你做不到的响应等级，第一次没做到的那天就是这段合作结束的那天，而且他会把这件事告诉别人。

三、你没见过的机型。

[运维手册](../../playbooks/managed-support/README.md)那条：先别答应月度响应，改成按次上门。

四、客户不让你改配置。

[运维手册](../../playbooks/managed-support/README.md)那条：你没法负责一台你不能动的机器。

拒单的说法要给替代方案，不要只说不接。

照念一句（虚构示例）：

> “您这台我按月管不下来，我手上几家的响应时间都是工作日 4 小时，再加一家我兑现不了，兑现不了的承诺我不想写在合同上。有两个办法：一个是改成按次，出一次事我上一次门，不承诺响应时间；另一个是等我这边缓过来，大概什么时候我告诉您。”

这段话里有三件：说清为什么不接、给了替代方案、留了以后的口子。

说“我兑现不了的承诺不想写在合同上”这一句，比任何客套都有说服力。

## 五、设备清单模板

打印出来，或者做成一份表格。

第一份是台账，一台一行；第二份是单台明细，一台一页。

两份一起用：台账用来查看所有机器，明细用来出门前查看单台机器。

### 空白版（台账，一台一行）

```text
============================================================
　　　　　　　　　　设　备　台　账
============================================================
更新日期：　　　　　　　　共　　台
本表不进任何仓库、不进聊天、不进邮件正文。存两份，一份不在这台笔记本上。

| 编号 | 客户 | 位置 | 机型 | 装的是什么 | 版本 | 交付/接管日 | 维护到期 |
|  |  |  |  |  | □标准 □不一致： |  |  |

| 编号 | 响应等级 | 包几次上门 | 下次上门 | 已知问题 | 对接人 | 拍板人 | 权限人 |
|  |  |  |  | 　条，在哪儿： |  |  |  |

按维护到期日排序，最近两个月到期的：
　1.
　2.

这台笔记本上有哪几家的钥匙（换机 / 送修 / 卖掉之前先处理）：
============================================================
```

### 空白版（单台明细，一台一页）

```text
============================================================
　　　　　　　　　　设　备　明　细
============================================================
编号：　　　　　　　　更新日期：

---------- 一、设备身份 ----------
客户：　　　　　　　　　　　行业：
位置：楼　　　　房间　　　　柜子／桌
　　　谁有钥匙：　　　　　　进出要不要登记：□ 要　□ 不要
机器上贴的标签：□ 有（编号 / 联系人 / 响应时限）　贴在：

---------- 二、设备配置 ----------
机型与配置：
安装内容：系统　　　　　驱动　　　　　模型运行环境
　　　　　　运行业务：
版本：□ 和标准一致　□ 不一致，差异项：
基线：机器内基线文件位置　　　　　　机器外基线文件位置
```

这两份示例里有五处值得多看一眼。

第一，台账上第三台那一格“版本不一致”写清了不一致在哪、为什么不动。

只写“不一致”没有用。 写清“业务卡在这一版”，你半年后才不会手痒去统一它。

第二，台账最后那一行“这台笔记本上有哪几家的钥匙”。

这一行不属于设备，它属于你。

放在台账上的理由是：这是唯一一张你每个月都会看的表。 换笔记本、送修、卖掉的那一天，你会看见它。

三家各一把、不共用，这一条是[第 5 章](05-安全最小集.md)那三条习惯里的第一条。

第三，明细第三栏“已知问题”第 3 条那句“我无法证明对方那一头是不是还留着什么”。

这一句照实写了一件你做不到的事。

[运维手册](../../playbooks/managed-support/README.md)那条：接管一台不是你装的机器，一定会有几样你处理不掉的东西。把它们写下来、让客户签字，比默默留着强得多，出事那天，这张纸是唯一能说清楚责任的东西。

第四，明细第五栏“这一台特有的几条”。

这一栏是这两份表里最省时间的一栏。

出事那一刻你不会有空翻接管确认单，但你会看一眼这一页。 四条写在这儿，第一条就告诉你这台机器要按别的路子查。

第四条“刘工只有工作日在，周末找不到人开门”和技术无关，但它决定了周末出事那天你能不能上门。

第五，明细第三栏“下一次上门要做什么”里写了“拔电试一次（接管时那一项记为未验）”。

接管的时候没验的那一项，被挂在了下一次上门的动作上。

[level-30／01](../../labs/level-30/01-remote-managed-box/README.md)那条：软件查不到来电自启，只能拔插座试，而这一件要单独约时间。

挂在这一栏，它才不会一直拖下去。
