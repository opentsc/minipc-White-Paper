# 17　llama.cpp Vulkan

## 完成结果

你在这台设备上用 llama.cpp 的 Vulkan 后端跑通了第一个模型，**没有装 ROCm，也没有编译任何东西**——官方每个发布版本直接提供 Ubuntu 的 Vulkan 预编译包，下载解压就能用（llama.cpp 发布页，访问日期 2026-08-13）。

你还学会了两个参数，它们是本卷前面几章反复提到、一直往后推的两件事：

- **`--no-mmap`**：大模型加载卡死时用它；
- **`-ub 512`**：长上下文出问题时用它。

**这一章是本教材主线上跑起第一个模型的地方。** 第 8 章定的基准组合，主线走的就是这条路。

## 开始前需要准备什么

- **第 13 章的 Vulkan 检查通过了**——`driverName` 是 `radv`、`deviceType` 是集成 GPU。**没通过的先回去解决，本章跑不通**；
- **不需要装 ROCm。** 跳过第 11 章的读者，这一章从头到尾用得上。装了 ROCm 的读者也照样走这一章，**两条路可以并存**，互不干扰；
- 手上要有一个模型文件。**模型从哪来、怎么挑、怎么下载，在[第 6 卷](../06-本地模型/README.md)第 4 章**，本章不重讲。本章只需要**一个 8B 以内的小模型**先跑通流程；
- 硬盘上要有空间。模型文件按量化档从几 GB 到几十 GB 不等，先用 `df -h /` 看一眼（[第 4 卷第 13 章](../04-Max395硬件/13-SSD.md)）；
- **本章不装任何系统级的东西**，不用 `apt`，不需要 root，不改任何配置文件。下载的东西全在你的家目录里，**删掉那个目录就是完整卸载**；
- 本章不改内核参数、不动引导配置。[第 4 卷第 18 章](../04-Max395硬件/18-不应随意修改的设置.md)的禁区清单在本章全部保持原状。

## 新词

**llama.cpp**：一个用 C++ 写的本地推理程序。**它自带好几个后端**（第 4 章新词），Vulkan 是其中之一。本章用的就是它的 Vulkan 后端。

**预编译包**：别人已经编译好、打包上传的成品。**下载解压就能跑，不用自己编译。** 这是这条路最省事的地方（第 3 章）。

**GGUF**：llama.cpp 用的模型文件格式，文件名以 `.gguf` 结尾。**别的框架的模型文件格式不一样，不能直接混用。**

**上下文**（context）：模型这一次对话里能“记住”的内容长度，单位是 token（[第 4 卷第 4 章](../04-Max395硬件/04-统一内存.md)新词）。**上下文越长，占的内存越多**——这一条是本章后半段两个参数的共同背景。

**微批**（micro-batch）：模型处理输入时，一次送进去多少个 token。**微批越大越快，但一次要申请的显存也越大。** `-ub` 这个参数调的就是它。

**mmap**（内存映射）：一种让程序“把文件当内存用”的做法。**好处是启动快、不用先把整个文件读进内存；代价是文件的内容由系统在背后调度。** `--no-mmap` 就是关掉它，改成老老实实先读进内存。

**吞吐**（throughput）：单位时间里处理完多少东西。**跑模型时常用 tokens/s** ——每秒多少个 token。第 19 章会把这个指标讲透，**本章只跑通，不测速度**。

**层**（layer）：模型内部的一级级结构。`-ngl` 这个参数决定把其中多少层放到 GPU 上算。

## 这条路为什么是主线

第 8 章那一节的四条理由，落到这一章上是三句话：

1. **装起来最省事。** 官方发布页每个版本直接提供 Ubuntu 的 Vulkan 预编译包（llama.cpp 发布页，访问日期 2026-08-13，当日最新为 b10405）；
2. **不依赖 ROCm 对 gfx1151 的适配进度。** Vulkan 走的是 Mesa 里的 RADV（第 3 章、第 4 章），和 ROCm 是并列的两条路，不是上下级；
3. **它是材料里多份来源口径一致、可以当日常主力的组合**（第 7 章场景边界第一条）。

> **这三句话不等于“Vulkan 比 ROCm 快”。** 谁更快没有定论——材料里一条来源称针对 gfx1151，Vulkan 后端效率高于 ROCm／HIP 的实验构建；同期社区有调优后 HIP 反超的报告（llama.cpp issue #24438，访问日期 2026-08-13）。**两种结论并存，本教材不下统一结论。** 选哪条在第 19 章。

libggml-cpu.so    libllama.so         llama-cli

## 第四步：确认它认得出这块 GPU

**跑模型之前先问它看到了什么。**

```bash
cd ~/llama && ./llama-cli --list-devices
```

- **作用**：让 llama.cpp 列出它认到的计算设备。`./` 表示“当前目录下的这个程序”。**这条命令不加载模型、不占显存**，只做一次设备枚举；
- **正常输出**：一段设备列表，**里面应当有一行 Vulkan 设备**，形如

```text
ggml_vulkan: Found 1 Vulkan devices:
ggml_vulkan: 0 = AMD Radeon Graphics (RADV GFX1151) (radv) | uma: 1 | fp16: 1 | ...

Available devices:
  Vulkan0: AMD Radeon Graphics (RADV GFX1151) (xxxxx MiB, xxxxx MiB free)
```

  **要看的是三件事**：设备数量不是 0、名字里能认出是 AMD 的这块（`RADV` 或 `GFX1151` 任意一个）、括号里的显存数不是个很小的值。**具体格式、字段和数字随版本变化，本项目未固定，需要核验**——`uma: 1` 那一项说的是统一内存，和[第 4 卷第 4 章](../04-Max395硬件/04-统一内存.md)讲的是同一件事；

- **看到别的怎么办**：
  - **提示 `Permission denied`** —— 文件没有执行权限。跑 `chmod +x ~/llama/llama-cli` 加上；
  - **提示 `error while loading shared libraries`** —— 找不到旁边那些 `.so` 库。**确认你是在 `~/llama` 这个目录里跑的**（命令开头那个 `cd` 不能省）；
  - **`Found 0 Vulkan devices`** —— llama.cpp 看不到 GPU，但第一步 `vulkaninfo` 是通的。**先确认下的是 Vulkan 包不是别的包**（第三步），再回第 13 章第二步看系统上是不是注册了不止一份 Vulkan 实现；
  - **列出来的显存数只有一两个 GB** —— 显存方案那一层的问题，不是本章的问题。回[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)和第 12 章；
  - **提示 `unknown argument`** —— 这一版的参数名不一样。跑 `./llama-cli --help | head -40` 看这一版支持什么，**参数名随版本变化**；
- **怎么停止或撤销**：只读命令，不需要撤销。

**把这一行输出记进[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)的设备基线**，连同 llama.cpp 的版本号一起。**以后升级 llama.cpp 之后再跑一次对照。**

## 第五步：跑第一个模型

**先用一个 8B 以内的小模型。** 理由不是省事——**材料记录，大模型加载才会撞上下一节那个问题，8B 级的小模型没有这个现象**（素材记录，**本项目来源目录未收录对应条目，需要核验**）。**小模型先跑通，把变量减到最少。**

```bash
cd ~/llama && ./llama-cli -m ~/models/你的模型文件.gguf -p "你好，请用一句话介绍你自己。" -n 128 -ngl 99
```

- **作用**：加载模型，按给的提示词生成一段文字，然后退出。
  - `-m` 后面是模型文件的路径；
  - `-p` 后面是提示词；
  - `-n 128` 表示最多生成 128 个 token，**这一项限制了它说多久**；
  - `-ngl 99` 表示把模型的层尽量放到 GPU 上算。**99 是个偷懒的写法**——比实际层数大就等于全放上去。**不加这一项，多数版本默认在 CPU 上跑**，那就白装了；
- **正常输出**：先是一大段加载信息（几十行，包括模型的元数据、层数、量化档、Vulkan 设备信息），然后是模型生成的文字，最后是一段统计。统计那一段形如

```text
llama_perf_context_print: prompt eval time = ...  ms / ... tokens ( ... ms per token, ... tokens per second)
llama_perf_context_print:        eval time = ...  ms / ... runs   ( ... ms per token, ... tokens per second)
```

  **加载信息里要确认一件事：有没有一行写着把层放到了 Vulkan 设备上**，形如 `load_tensors: offloading 32 repeating layers to GPU`。**只在 CPU 上跑的话，这一行不会出现，或者数字是 0**；

  **统计里那两个 tokens per second 是两个不同的东西，第 19 章讲。本章先不管数字。**

- **看到别的怎么办**：
  - **提示 `failed to load model`** —— 模型文件路径不对，或者文件不完整。先 `ls -lh ~/models/` 看一眼文件在不在、大小对不对。**分卷下载的模型要下全**；
  - **提示 `unknown model architecture`** —— 这个 GGUF 用的架构这一版 llama.cpp 还不认。**换更新的 llama.cpp 版本**，或者换个模型；
  - **加载信息里看不到 offloading 那一行，跑起来很慢、`radeontop` 里 GPU 占用接近 0** —— 层没放到 GPU 上。确认 `-ngl 99` 写了没有；有的版本参数叫 `--gpu-layers`，跑 `./llama-cli --help | grep -i gpu` 查这一版怎么写；
  - **报显存不足、`vk::Device::allocateMemory` 之类的字样** —— 模型太大或者上下文开太大。先换更小的模型或更低的量化档；确实要跑大的，看下面两节；
  - **加载到一半整个卡住，GPU 占用满、什么都不输出** —— **这就是下一节要处理的那件事**，往下看；
  - **生成出来的是乱码或者完全不对题** —— 先换个模型试一次。**输出语义错误这类问题不报错，只能靠人看**（第 7 章第三条）。两个模型都乱的话，按第 20 章处理；
  - **屏幕闪一下、桌面卡住** —— GPU 那一层出问题了。处理在第 20 章；
- **怎么停止或撤销**：**按 `Ctrl+C` 停止。** 这个程序不写任何配置文件、不改系统状态，停下来就结束了，模型文件不受影响。**按了 `Ctrl+C` 之后显存没释放的情况，处理在第 20 章。**

**跑通了，本章的主线目标就达到了。** 下面两节是两个已知问题的处理办法——**现在用不上也要读一遍，撞上的时候你才知道是什么**。

## 大模型加载卡死：`--no-mmap`

**症状**（材料记录）：跑 100B 级的大模型时，模型加载之后卡住——GPU 占用 100%，一个字都不输出；按 `Ctrl+C` 之后显存不释放。走 Vulkan 后端的表现略有不同：**能加载，但生成到中途报错**。

**8B 级的小模型没有这个现象。**

**原因**（材料记录）：默认用 mmap 把模型文件映射进来，映射的数据被系统在背后挪动了。

**处理办法**：加一个参数，把模型老老实实读进内存、钉在那儿。

> **⚠️ 这个参数会让模型完整占住内存，模型比可用内存大时可能把整台机器拖住。**
>
> 表现是系统整个变卡、硬盘一直响、进程被系统强行杀掉。**这不会损坏任何东西，但当时机器基本没法用。**
>
> **动手之前先 `free -h` 看一眼可用内存，和模型文件的大小对一下**（[第 4 卷第 17 章](../04-Max395硬件/17-正常状态判断.md)讲过模型加载进来要占多大）。
>
> **恢复方法**：按 `Ctrl+C` 停掉；按不动的话等系统把进程杀掉，或者长按电源键强制关机再开机。**下次不加这个参数，改用更小的量化档。**

```bash
cd ~/llama && ./llama-cli -m ~/models/你的大模型.gguf -p "你好" -n 1024 -c 8192 --no-mmap -ngl 99
```

- **作用**：和第五步同一条命令，多了两项。
  - `--no-mmap`：**关掉内存映射**，改成先把模型完整读进内存。**代价是加载变慢**——几十 GB 的文件要真的读一遍，而且加载期间内存占用会明显上去；
  - `-c 8192`：把上下文长度设成 8192 个 token。**不写的话用默认值，不同版本默认值不一样**；
- **正常输出**：加载阶段明显变长（**几十 GB 的模型可能要等好几分钟**），加载完之后正常生成。**加载期间没有输出是正常的**，可以另开一个终端跑 `free -h` 看内存在往上走；
- **看到别的怎么办**：
  - **加了还是卡死** —— 这条素材记录的处理办法本项目未复现过。**先确认模型文件完整**（分卷的下全了没有），再按第 20 章的显存那几条查；
  - **报内存不足、系统整个变卡、进程被系统杀掉** —— `--no-mmap` 要真的把模型读进内存，**模型比可用内存大就会这样**。换更小的量化档，或者去掉 `--no-mmap` 试试别的办法；
  - **加载特别慢，慢到不像话** —— 正常，这是这个参数的代价。**硬盘的读取速度决定它有多慢**（[第 4 卷第 13 章](../04-Max395硬件/13-SSD.md)）；
- **怎么停止或撤销**：按 `Ctrl+C`。**撤销这个参数就是下次不加它**——它只影响这一次运行，不写进任何配置。

> **这条记录的来源限制要说清楚：** `--no-mmap` 这条处理办法是**素材记录，本项目来源目录未收录对应条目，事实状态 `candidate`，需要核验**（第 4 章、第 7 章已标注同一条）。**本项目没有在这台设备上复现过。** 写在这里是因为它在材料里出现过不止一次，而且撞上的时候没有别的线索。

## 长上下文出问题：`-ub 512`

**症状**（材料记录）：Vulkan 上下文超过 4096 个 token 时，触发单次缓冲区分配的 8 GB 上限，表现为内存不足；长上下文推理（材料里提到 88000 token 级）中途出现超时与设备丢失。

**原因**（材料记录）：Vulkan 那一层对**单次**内存分配有上限；微批开太大，一次要分配的量就撞上那个上限。ring 超时也是同一个方向——一次提交的活太多。

**处理办法**：把微批压小。

```bash
cd ~/llama && ./llama-cli -m ~/models/你的模型.gguf -p "你好" -n 512 -c 32768 -ub 512 -ngl 99
```

- **作用**：和上面同一条命令，多了 `-ub 512` 这一项。**它把一次送进模型的 token 数压到 512**，从而把单次要分配的显存压下来。
  - **代价是处理长提示词的速度会降**——同样多的输入要分更多次送进去；
  - `-c 32768` 是把上下文开到 32768 个 token，**长上下文场景才需要**；
- **正常输出**：正常加载、正常生成。**和不加这个参数的区别在速度和稳定性上，不在输出内容上**；
- **看到别的怎么办**：
  - **提示 `unknown argument -ub`** —— 这一版的参数名不一样。跑 `./llama-cli --help | grep -i batch` 查，常见的另一种写法是 `--ubatch-size`；
  - **压到 512 还是报内存不足** —— 再往下压试试（256），或者**把上下文 `-c` 调小**。**上下文长度是这类问题的根源**，微批只是缓解；
  - **报 `DeviceLost` 或者 `ring timeout`** —— 材料里这条和上面是同一族问题。同样先压微批、再压上下文。**反复出现的话按第 20 章处理**，那一章有专门一节；
  - **速度慢得受不了** —— 把 `-ub` 往上调（1024），在稳定和速度之间找一个你这台机器上能接受的值。**这个值没有通用答案，只能自己试**；
- **怎么停止或撤销**：按 `Ctrl+C`。这个参数同样只影响这一次运行。

> **同样的来源限制：** `-ub 512` 和 Vulkan 单次分配 8 GB 上限这两条是**素材记录，本项目来源目录未收录对应条目，事实状态 `candidate`，需要核验**（第 4 章已标注）。

## 看到不同结果怎么办

**你同时装了 ROCm，想知道这一章跑的到底是哪条路**：看第四步 `--list-devices` 的输出。**列出来的是 Vulkan 设备，跑的就是 Vulkan**。这一版的包里只有 Vulkan 后端，不会走到 ROCm 上。

**你想让它跑得快一点**：**本章不调优。** 先按第 19 章把观察方法学会——**没有观察就没有调优**，改了也不知道改对没有。

**你想让它一直跑着、别的电脑能连过来用**：那是 `llama-server` 和局域网 API 的事，在[第 6 卷](../06-本地模型/README.md)。**本章只跑一次性的命令行对话。**

**加载信息里显示只把一部分层放到了 GPU**：显存装不下全部。**这是正常的降级行为**，不是故障。要全放上去，换更小的模型或更低的量化档；也可以回[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)确认显存方案设对了。

**跑着跑着机器整个卡住、桌面假死**：这属于第 7 章第六条那一类。**先查固件版本和最近的系统更新**（第 2 章第五节），处理在第 20 章。[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)那个 `amdgpu.gpu_recovery=1` 参数就是为这种情况准备的，**那一章已经拍板，本卷不重设**。

**你搜到的教程让你装一堆依赖、自己编译**：那多半是 HIP 那条路，或者是别的硬件上的做法。**Vulkan 这条路不需要编译**（第 3 章）。HIP 那条路在第 18 章。

**新版本出来了，要不要升**：升级和回退在第 21 章、第 22 章。**这条路的升级很轻**——下新包解到新目录，跑通了再删旧的。**旧的先别删**，这是本教材一贯的做法。

**你要给客户交付**：把 llama.cpp 的版本号、模型文件名和量化档、完整的启动命令（含 `-ngl`、`-c`、`-ub` 这些参数）、以及你自己实测的日期一起写进交付文档（第 13 卷）。**只写“用 llama.cpp 跑”不算交付。**
