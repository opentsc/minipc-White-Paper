# 07　错的怎么拦

## 这一章的任务

让错的自己冒出来，不用一张张核。

**这一章是这一卷最值钱的一章。** 前六章做出来的东西是一条流水线；这一章做出来的东西才是能卖的服务。

差别在一句话上——**你不承诺它全对，你承诺错的能被拦住。**

一百多行台账摆在那儿，人一张张翻着核，前面六章省下来的时间全还回去了。这一章写一个几十行的脚本，把台账过一遍规则，**把该看的那几行挑出来**。人只看那几行。

产出是 `~/ai/scripts/validate.py` 和一份复核队列 `review.csv`。

## 开始前

- [第 5 章](05-批量处理.md)做完，`~/ai/projects/invoice-ocr/out/` 里已经有一批 JSON。**这一章不跑模型，只读那批 JSON**；
- [第 3 章](03-定义字段.md)那一节“哪些字段容易出错”读过。**那一节列的七条，这一章要给它们划一条界线**——哪几条机器拦得住，哪几条只能人看；
- [第 4 章](04-单张跑通.md)那一节“结果对不对，怎么看”真的做过，你手上有一份记录，知道自己这批单据最常错的是哪几格；
- 一个文本编辑器；
- 60 分钟。

## 新词

**校验**（validation）：**按事先定好的规则检查一条数据合不合规矩。** 它不判断内容真假，它判断这条数据自己有没有说得通的地方。

**复核队列**：**挑出来等人看的那一堆。** 这一章的产出就是它——一张 CSV，一行是一份要看的单据，后面跟着它哪儿不对。

**抽检**：**从看上去没问题的那一堆里随机抽几份，和原件对。** 这一章最后一节说它为什么不能省。

**关系校验**：**用几个字段之间的关系来查错。** 金额加税额等于价税合计，就是一条关系校验。**这一章最有用的一条规则是它，最容易被高估的一条也是它。**

## 先把边界画出来

**这一节读完再往下，它决定你后面怎么跟客户开口。**

[第 3 章](03-定义字段.md)最后那一节说过，`json_schema` 保证形状，不保证内容。**这一章的校验保证的东西同样有边界，而且这条边界要说得比准确率数字更清楚。**

分三档：

**一、机器拦得住的**——**这一格自己说不通**。空着、位数不对、日期认不出来、算不平、出现了负数、买卖双方是同一家。**这些不用看原件就知道有问题。**

**二、机器拦不住、但人一眼看得出来的**——**这一格说得通，但和票面不一样。** 购买方名称少了两个字、日期差了几天、发票号码中间错一位。**这些只有对着原件才发现得了。**

**三、两边都难发现的**——**整组数一起偏，而且它们彼此还对得上。** 下面最后一节专门讲这一类，**它是这一章最重要的一段**。

**所以这一章能承诺的是第一档，第二档靠抽检，第三档要在合同里写清楚。** 这三句话你要能对客户原样说出来。

## 六条规则

**下面这六条是本卷主线那八个字段配的一套起点，不是任何规范。** 你自己那批单据要检哪几条，照[第 4 章](04-单张跑通.md)那份对错记录来定。

### 一、必填字段不能空

[第 3 章](03-定义字段.md)分过“schema 里的必填”和“业务上的必填”两件事，**说好业务上那一件由这一章的代码管。现在兑现它。**

本卷主线业务上必填的是这五格：

```text
发票号码
开票日期
购买方名称
销售方名称
价税合计
```

**空字符串是[第 3 章](03-定义字段.md)定的信号——模型在举手说这一格我没看清。** 这五格里任何一格举了手，这一行进台账也没法用。

剩下三格（发票种类、金额、税额）空着不至于让这一行作废，**但它们空了会让第五条那个加法做不成**，所以照样会被记一笔。

### 二、发票号码位数

十几二十位的数字串，**中间错一位你看不出来**，但位数错了机器看得出来。

两件事一起检：**里面不能有不是数字的东西**，**位数要在你认的那几个里面**。

**位数是几，你要自己数一遍。** 本卷主线那批是 20 位，脚本里还留了一个 8 位，因为有些票据是 8 位。**这两个数不是规范，是本教材给的一个起点**——打开你自己那批单据数一数，把脚本里那一行改成你的。

> **这一条拦不住“位数对但中间错一位”。** 那种只能靠抽检。**位数校验的价值在于它零成本**，一行代码，能捞到明显的截断和粘连。

### 三、日期格式和范围

[第 3 章](03-定义字段.md)那段提示词要求日期照票面原样抄，**所以脚本这一头要认得出好几种写法**：`2026年07月18日`、`2026-07-18`、`2026/07/18`、`2026.07.18`。

认出来之后查两样：

- **年份不能太早。** 脚本里那个 `YEAR_MIN` 给的是 2000，**这个数按你手上那批单据的年份定**；
- **不能是将来的日期。** 一张明年的发票不存在，出现了就是读错了。

**注意 `2026年13月18日` 这种。** 格式看着对，13 月不存在。脚本里那一段 `date(year, month, day)` 会直接拒绝它，**这一步是白捡的**。

### 四、金额不能是负数，也不能不是数

两件事：

- **解析不出来的。** 最常见的是[第 3 章](03-定义字段.md)那条毛病——**模型把大写那个填进了小写那一格**，`叁仟贰佰玖拾陆元整` 填在 `金额` 里。**这一条能稳稳拦住它**；
- **负数。** 票面上不会印一个负的价税合计。出现了就是读错了，或者读到别的地方去了。

解析的时候要把票面上那些花样去掉——**逗号、全角逗号、人民币符号、“元”字、空格**。`3,296.00` 是票面的写法，`3296.00` 才是能算的数。

### 五、金额加税额等于价税合计

**这一条是六条里最有用的。**

原因很实在：**它是唯一一条不看单张、只看关系的规则。** 前面四条问的是“这一格自己说不说得通”，这一条问的是“这三格能不能对上”。

**它能捞到的东西是别的规则捞不到的**——三格里有一格被印章压住少读了一位、或者跳到隔壁那一栏去了，前面四条全过，这一条不过。

```text
金额 + 税额 = 价税合计
```

脚本里留了一分钱的余量（`0.01`），**因为小数相加会有极小的零头**，卡得太死会把好的也挑出来。

**这一条也是最容易被高估的一条。** 最后一节说它为什么不等于对。

### 六、销售方和购买方不能是同一家

**这条规则很少触发，但触发一次就是一个真问题。**

发票上这两栏挨着（[第 4 章](04-单张跑通.md)那一节“最常见的错是两个反了”）。**模型把一栏抄了两遍，两格就一模一样了。** 这种错在台账里看着毫无异样——两个都是合法的公司名。

## 完整脚本

新建文件 `~/ai/scripts/validate.py`，**和前面两个脚本放在同一个目录里**。下面这一整段照抄进去：

```python
#!/usr/bin/env python3
# validate.py —— 把第 5 章跑出来的 JSON 逐条过一遍规则，可疑的挑出来
# 用法：python3 ~/ai/scripts/validate.py ~/ai/projects/invoice-ocr
# 前提：第 5 章跑完，out/ 里有一批 JSON

import argparse
import csv
import json
import re
import sys
from datetime import date
from pathlib import Path

# —— 下面这四项是你要按自己那批单据改的 ——

REQUIRED_FIELDS = [
    "发票号码",
    "开票日期",
    "购买方名称",
    "销售方名称",
    "价税合计",
]

INVOICE_NO_LENGTHS = {8, 20}

YEAR_MIN = 2000

AMOUNT_FIELDS = ["金额", "税额", "价税合计"]

# —— 下面是规则本身 ——

DATE_PATTERNS = [
    r"^(\d{4})年(\d{1,2})月(\d{1,2})日$",
    r"^(\d{4})-(\d{1,2})-(\d{1,2})$",
    r"^(\d{4})/(\d{1,2})/(\d{1,2})$",
    r"^(\d{4})\.(\d{1,2})\.(\d{1,2})$",
]


def text_of(record, name):
    """把某一格取出来，去掉两头的空白。没有这一格就当空的。"""
    return str(record.get(name, "")).strip()


def to_number(text):
    """把票面上的金额变成一个数。变不了就返回 None。"""
    cleaned = text.replace(",", "").replace("，", "")
    cleaned = cleaned.replace("¥", "").replace("￥", "").replace("元", "")
    cleaned = cleaned.replace(" ", "")
    if cleaned == "":
        return None
    try:
        return float(cleaned)
    except ValueError:
        return None


def to_date(text):
    """把票面上的日期变成一个日期。认不出来就返回 None。"""
    for pattern in DATE_PATTERNS:
        matched = re.match(pattern, text)
        if not matched:
            continue
        year, month, day = (int(part) for part in matched.groups())
        try:
            return date(year, month, day)
        except ValueError:
            return None
    return None


def check_required(record):
    """一、业务上必填的那几格不能空。空了这一行没法用。"""
    problems = []
    for name in REQUIRED_FIELDS:
        if text_of(record, name) == "":
            problems.append("必填字段空着：" + name)
    return problems


def check_invoice_no(record):
    """二、发票号码只能是数字，位数要对得上。"""
    value = text_of(record, "发票号码")
    if value == "":
        return []
    if not value.isdigit():
        return ["发票号码里有不是数字的东西：" + value]
    if len(value) not in INVOICE_NO_LENGTHS:
        return ["发票号码位数不对，%d 位：%s" % (len(value), value)]
    return []


def check_date(record):
    """三、开票日期认得出来，而且落在合理范围里。"""
    raw = text_of(record, "开票日期")
    if raw == "":
        return []
    parsed = to_date(raw)
    if parsed is None:
        return ["开票日期认不出来：" + raw]
    if parsed.year < YEAR_MIN:
        return ["开票日期太早了：" + raw]
    if parsed > date.today():
        return ["开票日期在将来：" + raw]
    return []


def check_amounts(record):
    """四、三个金额得是数，而且不能是负数。"""
    problems = []
    for name in AMOUNT_FIELDS:
        raw = text_of(record, name)
        if raw == "":
            continue
        value = to_number(raw)
        if value is None:
            problems.append("%s这一格不是一个数：%s" % (name, raw))
        elif value < 0:
            problems.append("%s这一格是负数：%s" % (name, raw))
    return problems


def check_sum(record):
    """五、金额加税额等于价税合计。这一条最有用。"""
    net = to_number(text_of(record, "金额"))
    tax = to_number(text_of(record, "税额"))
    total = to_number(text_of(record, "价税合计"))
    if net is None or tax is None or total is None:
        return []
    if abs(net + tax - total) > 0.01:
        return ["金额 %.2f 加税额 %.2f 等于 %.2f，价税合计写的是 %.2f"
                % (net, tax, net + tax, total)]
    return []


def check_parties(record):
    """六、购买方和销售方不能是同一家。"""
    buyer = text_of(record, "购买方名称")
    seller = text_of(record, "销售方名称")
    if buyer != "" and buyer == seller:
        return ["购买方和销售方是同一家：" + buyer]
    return []


OTHER_CHECKS = [
    check_invoice_no,
    check_date,
    check_amounts,
    check_sum,
    check_parties,
]


def judge(record):
    """一条记录进来，一个结果和一串问题出去。"""
    missing = check_required(record)
    problems = list(missing)
    for check in OTHER_CHECKS:
        problems.extend(check(record))
    if missing:
        return "失败", problems
    if problems:
        return "可疑", problems
    return "通过", problems


REVIEW_HEADER = [
    "文件名", "结果", "问题",
    "发票号码", "开票日期", "购买方名称", "销售方名称",
    "金额", "税额", "价税合计",
]


def main():
    parser = argparse.ArgumentParser(description="把跑出来的 JSON 过一遍规则")
    parser.add_argument("outdir", help="第 5 章那个放结果的目录")
    args = parser.parse_args()

    outdir = Path(args.outdir).expanduser()
    json_dir = outdir / "out"
    if not json_dir.is_dir():
        sys.exit("找不到这个目录：" + str(json_dir) + "，先做完第 5 章")

    counts = {"通过": 0, "可疑": 0, "失败": 0}
    rows = []
    for path in sorted(json_dir.glob("*.json")):
        try:
            record = json.loads(path.read_text(encoding="utf-8"))
        except ValueError as error:
            counts["失败"] += 1
            rows.append([path.name, "失败", "这个 JSON 读不出来：" + str(error)]
                        + [""] * (len(REVIEW_HEADER) - 3))
            continue
        result, problems = judge(record)
        counts[result] += 1
        if result == "通过":
            continue
        row = [record.get("文件名", path.name), result, "；".join(problems)]
        row.extend(text_of(record, name) for name in REVIEW_HEADER[3:])
        rows.append(row)

    review_path = outdir / "review.csv"
    with review_path.open("w", newline="", encoding="utf-8-sig") as handle:
        writer = csv.writer(handle)
        writer.writerow(REVIEW_HEADER)
        writer.writerows(rows)

    total = sum(counts.values())
    print("一共 %d 条：通过 %d，可疑 %d，失败 %d"
          % (total, counts["通过"], counts["可疑"], counts["失败"]))
    print("要人看的 %d 条写在：%s" % (len(rows), review_path))
    if total and not rows:
        print("这一批没有挑出可疑件。抽检照做，理由看本章最后一节。")


if __name__ == "__main__":
    main()
```

**这个脚本不连服务，不读模型，也不用和前两个脚本放一起才能跑**——它只读 `out/` 里那堆 JSON。放在 `~/ai/scripts/` 是为了三个脚本挨着，好备份、好拷走。

### 三处值得单说

**一、最上面那四项是给你改的，规则本身不用动。**

```python
REQUIRED_FIELDS = [...]
INVOICE_NO_LENGTHS = {8, 20}
YEAR_MIN = 2000
AMOUNT_FIELDS = [...]
```

**换一类单据，多半只改这四行**（第 8、9、10 章都会这么干）。**会变的东西拎到最上面**，这是[第 4 章](04-单张跑通.md)那个 `API_BASE` 的老做法。

**二、每条规则是一个独立的函数，返回一串问题。**

**加一条规则的做法是照着写一个函数，把名字加进 `OTHER_CHECKS` 那张表。** 不用改别的地方。

**三、`judge` 里必填单挑出来。**

```python
missing = check_required(record)
```

必填空了直接判“失败”，别的规则不过判“可疑”。**这两档要分开，因为后面的处理完全不一样**，下面那一节说。

**第三列是这张表的价值所在**——它不只说这行有问题，它说的是哪儿有问题。**人拿着这一列去看原件，一眼就知道该盯哪一格。**

> **在 Calc 或者 Excel 里按第三列排一次序。** 同一类问题会挨在一起，**一次改一类比一份份跳着改快得多**。发现某一类特别多，那不是复核的事，那是回[第 3 章](03-定义字段.md)改提示词的事。

## 三种结果，三种处理

### 通过

**进台账，但要抽检。**

这一档是数量最多的，也是最容易让人放松的。**最后一节专门讲它为什么不等于对。**

### 可疑

**进复核队列，人看一眼，改了回写。**

**这一档是这一章真正的产物。** 它的特点是：**字段都在，形状都对，但有一处说不通。** 说不通的地方脚本已经指出来了，人只要对着原件确认那一处。

三种常见情况，处理方式不一样：

- **确实读错了** —— 改 JSON，下面那一节讲怎么改；
- **票面本身就是这样** —— 有些票据的价税合计栏本来就和明细对不上（有折扣、有零头调整）。**这种要放行，而且要记下来**——同一类多了，说明你这条规则定严了，把它改宽或者去掉；
- **票面糊得看不清** —— 那就调 `--dpi 300` 重跑这一份（[第 4 章](04-单张跑通.md)那个开关），重跑的做法下面说。

### 失败

**这一行现在不能用，先看原件。**

必填空着，说明模型在那一格举了手。**九成是原件的问题**——扫歪了、缺角、印章糊成一团、拍照的时候手抖了。

三步：

```text
1. 照文件名去 data/（或者第 6 章那个 done/）里找到原件，打开看一眼
2. 原件本身就看不清 → 拿去重扫。这一份的账现在算不了，不要硬填
3. 原件是清楚的 → 删掉它的 JSON，加 --dpi 300 重跑这一份
```

重跑单独一份的做法：

```bash
rm ~/ai/projects/invoice-ocr/out/票据-0731-041.json
python3 ~/ai/scripts/ocr_one.py ~/ai/data/invoices-2026-08/票据-0731-041.pdf --dpi 300
```

**看一眼输出，那一格出来了没有。** 出来了就把整批重跑一次（[第 5 章](05-批量处理.md)那个跳过机制会让别的份秒过），台账和复核队列都会跟着更新。

> **不要因为一份读不出来就调高整批的 DPI。** 那会让一百多份都跑慢一截，为的是救那四份。**单独救它们更划算。**

## 人工复核怎么做

**这一节给的是最小流程，五步，不用装任何东西。**

```text
1. 打开 review.csv，从上往下看
2. 照第一列的文件名，找到那份原件，并排打开
3. 照第三列指的那一格，对一眼
4. 读错了就改 out/ 里那份 JSON，改那一格
5. 全改完，重跑 validate.py 和 ocr_batch.py
```

### 第四步，改哪个文件

**复核队列第一列是原件的名字，带后缀**，比如 `票据-0731-057.pdf`。

**对应的 JSON 是把后缀换成 `.json`**（[第 5 章](05-批量处理.md)那条规矩）：

```bash
nano ~/ai/projects/invoice-ocr/out/票据-0731-057.json
```

里面就是[第 4 章](04-单张跑通.md)见过的那八格。**只改错的那一格，别的一个字不动**，冒号后面引号里的内容改掉，保存。

> **想留个痕迹的话，在里面多加一格**，比如 `"复核": "2026-08-15 张三"`。**台账不会多出这一列**（[第 5 章](05-批量处理.md)那个表头是照 schema 定死的），但你以后翻这份 JSON 的时候，知道这一行动过手。

### 第五步，为什么要重跑两个脚本

```bash
python3 ~/ai/scripts/validate.py ~/ai/projects/invoice-ocr
python3 ~/ai/scripts/ocr_batch.py ~/ai/data/invoices-2026-08 ~/ai/projects/invoice-ocr
```

- **重跑 `validate.py`** —— 复核队列重新生成，**改好的那几行应该消失了**。这是你确认自己改对了的办法；
- **重跑 `ocr_batch.py`** —— 台账重新汇一遍。[第 5 章](05-批量处理.md)那个 `write_ledger` 是**每次都从 `out/` 里重头汇**，所以你改过的值会进台账。

**这里有一个关键性质，值得单说一句：重跑 `ocr_batch.py` 不会覆盖你手改的 JSON。** [第 5 章](05-批量处理.md)那个跳过机制看到 JSON 已经在了就直接跳过，**它连模型都不会去问**。

**所以“手改 JSON 加重跑”是一条安全的回写路径。** 这不是巧合，是[第 5 章](05-批量处理.md)那个设计顺带给的。

### 接进第 6 章那个定时任务

复核不用每次手动跑。在[第 6 章](06-文件夹监测.md)那个 `ocr-watch.sh` 里，**跑完批量脚本那一行下面加一行**：

```bash
python3 "$HOME/ai/scripts/validate.py" "$OUTDIR"
```

这样每一轮跑完，复核队列自动更新一次。**盯着 `review.csv` 就行，不用再盯台账。**

## 这套校验拦得住什么，拦不住什么

**这一节是整章最重要的一段。** 上面所有东西都是工具，这一段是你要跟客户说的话。

### 拦得住的

**一句话概括：这一格自己说不通的，都拦得住。**

- 该有的没有（必填空着）；
- 形状不对（位数、日期格式、13 月）；
- 类型不对（金额栏是一串汉字）；
- 值不合理（负数、将来的日期）；
- 三格之间算不平（金额加税额对不上合计）；
- 两格不该一样却一样（买卖双方同名）。

**这一档的共同点是不用看原件。** 脚本自己就能判定，一百份和一万份的成本一样。

### 拦不住的

**一句话概括：识别成了另一个合法的值。**

**这是这一章、也是这一卷最要紧的一条边界。**

举几个具体的：

- **购买方名称**读成“远山文化传播有限责任公司”，票面上写的是“远山文化传播有限公司”。**多了两个字，是一个完全合法的公司名**，六条规则一条都不会响；
- **开票日期**读成 `2026年07月13日`，票面是 `2026年07月18日`。**格式对，范围对，8 和 3 长得像**（[第 3 章](03-定义字段.md)那条“相似的字形”）；
- **发票号码**中间错一位。**位数对，全是数字，前面那条规则过了**；
- **发票种类**从“增值税专用发票”读成“增值税普通发票”。**两个都在 `enum` 里，都合法**。

### 那条加法为什么不等于对

**这一段单独拿出来说，因为它最容易让人放心得太早。**

金额加税额等于价税合计，**证明的是这三个数彼此对得上，不是这三个数和票面对得上。**

看这一组：

```text
票面上是：  金额 3200.00　税额 96.00　价税合计 3296.00
读出来是：  金额  320.00　税额  9.60　价税合计  329.60
```

**读出来那一组，加法是成立的。** 320.00 加 9.60 正好是 329.60。六条规则全过，这一行会被判“通过”，安安静静进台账。

**而它整行都是错的。**

> **一句话记住它**：**校验不过的，一定有问题；校验过了的，不一定没问题。**

**所以抽检不能省。** 这不是保守，这是这套东西的性质决定的。

### 抽检怎么做

**从判“通过”的那一堆里随机抽，不要挑着抽。**

```bash
ls ~/ai/projects/invoice-ocr/out/*.json | shuf -n 10
```

作用：把 `out/` 里的 JSON 打乱，随便挑 10 个出来。**`shuf` 是随机抽，这一点比你自己挑重要**——你自己挑，手会不自觉地伸向看着眼熟的那几份。

抽出来的每一份，**照[第 4 章](04-单张跑通.md)那六步和原件对**：先对价税合计，再对发票号码，再对日期，再对买卖双方，最后看种类和金额税额。

**抽多少、错几格算不通过，由客户定，你不要单方面给一个数字。** [第 7 卷第 11 章](../07-RAG/11-变体-律所合同库.md)那条规矩在这里同样成立。

### 可以对客户说的三句话

**这三句照念，不要加工。**

> “这套东西不承诺每一格都对。”
>
> “它承诺的是：算不平的、缺格的、格式不对的，一份都跑不掉，全会被挑到一张表上等您看。”
>
> “剩下那一类——它读成了另一个看着也正常的值——机器拦不住，靠抽检。抽多少您定，写进验收单。”

**第三句是最重要的一句，也是最容易被省掉的一句。** 省掉它，出问题的那一天责任在你（[第 13 卷](../13-项目交付/README.md)）。
