# Mini PC 本地算力入门白皮书

版本：`v0.1` 工作稿

状态：结构稿，未完成事实核验，未公开发布

## 摘要

Mini PC 可以是一台低功耗的小型电脑，也可以成为个人服务器、开发环境、本地模型节点和自动化任务节点。

但设备买回来不等于可以使用。用户还需要完成系统部署、网络配置、权限管理、服务启动、数据备份和故障处理。

本白皮书提供一条从收到设备开始的学习路径：先让 Ubuntu 正常运行，再学习基本操作，然后完成小项目，最后根据任务选择本地模型、云端模型或两者组合。

本文不承诺某个型号一定能运行某个模型，也不承诺使用 Mini PC 一定能赚钱。所有性能、成本和收入判断都需要绑定设备、版本、任务和实际记录。

## 1．这个项目要解决什么问题

很多用户拿到 Mini PC 后，遇到的不是“不会买设备”，而是下面这些问题：

- Ubuntu 已经安装，但不知道下一步做什么。
- 会打开网页，不会使用终端。
- 能安装软件，但不知道服务是否在运行。
- 想运行本地模型，不知道内存、显存和模型大小的关系。
- 想节约云端调用费用，却没有记录调用量和实际质量。
- 想做项目，却只看到零散的软件名称。
- 想把设备用于收入项目，却没有区分工具、交付和服务。

这个项目把问题拆成五段：部署、入门、项目、成本和收入。

### 1.1 用案例学习

白皮书不要求读者先学完 Linux，再开始使用设备。每一组知识放进一个可以完成的案例中。

例如：

- 用 Uptime Kuma 监控一个网页，学习端口、容器、重启和日志。
- 用 Paperless-ngx 整理扫描文件，学习目录、持久化数据、OCR 和备份。
- 用 Ollama 和 Open WebUI 运行本地模型，学习内存、模型大小、服务接口和输出检查。
- 用 n8n 连接本地模型和定时任务，学习自动化、失败重试和人工确认点。

案例候选和一手来源见[案例库 v0.1](案例库-v0.1.md)。

## 2．收到 Mini PC 后先做什么

这一章的目标不是让用户一次学会 Linux，而是确认设备处于可使用状态。

### 2.1 硬件和系统检查

需要记录：

- 设备型号。
- CPU、内存和存储空间。
- 是否有独立 GPU 或共享显存。
- Ubuntu 版本。
- 网络连接方式。
- 设备是否能长时间稳定运行。

每一项都要保存命令输出或截图。没有记录的项目，只能写成“未核验”。

### 2.2 基础账户和更新

部署时至少处理：

- 一个日常使用账户。
- 管理员权限的使用规则。
- 系统更新。
- 时区和时间。
- 主机名。
- 磁盘空间检查。
- 基础防火墙。
- SSH 是否启用，以及允许谁连接。

不要把管理员密码、SSH 私钥和服务密钥放进公开仓库。

### 2.3 网络访问

第一版默认采用内网访问。

如果需要远程访问，应先使用 VPN 或类似的私有网络方案，再考虑公网入口。公网暴露、端口转发、域名和反向代理都需要单独的安全检查。

### 2.4 服务安装

服务安装顺序应从少到多：

1. 系统更新和基础工具。
2. 远程访问。
3. 容器运行环境或明确的服务运行方式。
4. 一个可见的测试服务。
5. 数据目录和备份。
6. 本地模型或其他项目服务。

每安装一个服务，都要记录启动方式、日志位置、端口、数据目录和卸载方法。

## 3．Ubuntu 初学者路径

### 第一步：会看文件

用户需要理解当前目录、绝对路径、相对路径、隐藏文件和文件权限。目标是能够找到项目文件和日志，而不是背命令。

### 第二步：会看进程和服务

用户需要知道一个程序是否正在运行、由谁启动、占用了什么端口、日志在哪里，以及如何停止它。

### 第三步：会看资源

至少能观察 CPU、内存、存储和网络。运行本地模型时，先记录资源占用，再决定是否更换模型。

### 第四步：会备份和恢复

备份不是复制一份文件后就结束。要知道备份内容、备份位置、备份时间和恢复步骤，并实际恢复一次测试数据。

### 第五步：会处理失败

每个教程都要有失败处理：

- 哪一步失败。
- 从哪一条日志开始看。
- 如何恢复到上一步。
- 什么情况下停止操作并寻求帮助。

## 4．可以从哪些项目开始

项目按难度排列。每个项目都要有固定输入、预期输出和检查方法。

教学顺序按“先看到结果，再增加系统复杂度”排列。第一批教程不同时部署多个大型服务。

### 4.1 个人文件和备份服务器

用途：集中保存文件，并从其他设备访问。

先学习：目录、权限、存储、备份和网络访问。

风险：误删、硬盘损坏、权限配置错误和公网暴露。

### 4.2 家庭或小团队的服务节点

用途：运行一个内部面板、知识库、下载任务或定时任务。

先学习：服务管理、日志、端口、更新和备份。

风险：服务忘记更新、弱密码、数据没有恢复方案。

### 4.3 本地知识库和文档检索

用途：把用户自己的文档整理后，在本地检索和问答。

先学习：文件格式、文本切分、索引、引用和答案核对。

风险：把模型生成内容当成原文结论，或者把私密文档上传到不需要的第三方服务。

### 4.4 本地模型助手

用途：完成摘要、分类、改写、信息提取、代码辅助等任务。

先学习：模型安装、上下文长度、量化、资源占用、输出检查和任务边界。

风险：速度慢、答案错误、模型能力不足和更新后行为变化。

### 4.5 自动化任务节点

用途：定时执行文件整理、数据抓取、报告生成或内部通知。

先学习：定时任务、失败重试、幂等、日志和人工确认点。

风险：重复执行、错误通知、访问密钥泄露和任务失控。

### 4.6 开发和预发布环境

用途：在本地运行网站、API、数据库和测试服务。

先学习：Git、环境变量、数据库备份、部署和回滚。

风险：把测试环境误当生产环境，或者把私密配置提交到仓库。

## 5．本地模型和云端模型怎么分工

本地模型不是云端模型的简单替代品。选择方式应按任务判断。

### 5.1 适合先考虑本地的任务

- 数据不希望离开本地的文档处理。
- 重复、稳定、量较大的分类或提取任务。
- 需要低额外调用费用的常驻任务。
- 需要离线或弱网运行的部分流程。
- 先做草稿，再交给人工或云端模型复核的任务。

### 5.2 适合保留云端的任务

- 需要更强推理或更大上下文的任务。
- 对速度和质量有明确要求，但本地设备无法满足的任务。
- 低频任务，购买和维护本地模型没有意义的任务。
- 需要使用云端专有工具或服务的任务。

### 5.3 混合方式

一个可行的工作流是：

```text
本地准备材料
→ 本地模型做分类、提取或初稿
→ 人工检查任务和隐私
→ 云端模型处理需要更强能力的部分
→ 本地保存结果、日志和版本
```

这只是工作流候选。是否节约成本，要记录原来的云端调用量、本地设备成本、本地耗电、维护工时、失败重跑和人工复核。

## 6．节约成本和形成收入

### 6.1 成本不能只看 API 费用

本地部署的成本至少包括：

- 设备购买成本。
- 电力和网络。
- 存储和备份。
- 软件维护。
- 模型更新和测试。
- 故障处理。
- 用户学习和支持时间。

比较时需要保留原方案和新方案的同一任务记录。

### 6.2 可以测试的节约方向

- 把重复的文档分类从云端调用移到本地。
- 把内部开发、测试和预发布服务放到本地。
- 把个人或小团队的文件、知识库和检索服务放到本地。
- 让本地设备承担定时任务，减少人工重复操作。
- 在网络不稳定时保留一部分离线工作能力。

这些是候选方向，不是自动成立的收益。

### 6.3 可以测试的收入方向

- Mini PC 的系统部署和远程协助。
- 面向特定行业的本地知识库部署。
- 小团队内部自动化任务部署。
- 本地模型运行环境和工作流配置。
- 网站、面板或内部工具的本地预发布环境。
- 设备维护、备份、更新和故障排查服务。

收入来自设备之外的交付、判断、配置、维护或持续支持。开源教程本身不能证明这些服务有市场，需要用真实咨询、购买和交付记录验证。

## 7．安全和责任边界

第一版默认遵守以下原则：

- 不默认把服务放到公网。
- 不把密钥、密码、个人资料和客户文件放入仓库。
- 不把本地运行记录写成所有设备的性能结论。
- 不把模型输出当作无需检查的事实。
- 不用白皮书替代医疗、法律、财税或投资判断。
- 不把“能安装”写成“能稳定运行”。
- 不把“能运行”写成“能产生收入”。

## 8．开源项目怎么组织

建议仓库包含四类内容：

```text
docs/       白皮书、部署文档、边界说明
scripts/    可重复的检查和部署脚本
examples/   脱敏后的项目示例
tests/      配置、文档和隐私检查
```

第一版先公开文档和低风险检查脚本。涉及真实设备密钥、客户数据、内部网络、付费服务配置和个人工作流的内容不公开。

代码许可证和文档许可证暂未确定。许可证确认前，不在仓库中放入许可证文件，也不把仓库写成已经完成开源发布。

## 9．验证方法

每个项目至少记录：

- 设备和系统版本。
- 输入材料和数据规模。
- 操作步骤。
- 运行时间。
- CPU、内存、存储和网络情况。
- 输出结果。
- 人工检查结果。
- 失败和恢复过程。
- 成本记录。

第一版不追求覆盖所有型号。先选择少量设备，把一条路径完整跑通，再扩大范围。
