# 06　文件夹监测

## 这一章的任务

新单据丢进文件夹，机器自己就处理了。

**这一章不写 Python，一行都不写。** 第 5 章那个批量脚本已经能干活，这一章只是让它按点自己跑起来。产出是一个几十行的 shell 脚本和 crontab 里的一行。

做完之后，交单据的人只做一个动作——**把文件拷进一个文件夹**。别的什么也不用管，也不用叫你。

## 开始前

- [第 5 章](05-批量处理.md)做完，`~/ai/scripts/ocr_batch.py` 已经整批跑通过一次；
- [第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)做完。**cron 的五个时间字段、`>>` 和 `2>&1`、脚本放 `~/ai/scripts`、先手动跑再交给定时——这些本章直接用，不重讲**；
- [第 2 卷第 6 章](../02-Ubuntu/06-进程与服务.md)那五个 `systemctl` 动作会用；
- 40 分钟。

## 新词

**轮询**（polling）：**每隔一段时间去看一眼有没有新东西。** 没有就走，有就处理。这一章推荐的做法。

**实时监听**：**让系统在文件出现的那一刻通知你。** 听上去更好，坑在下面那一节。

**幂等**：**同一件事做一遍和做十遍，结果一样。** [第 5 章](05-批量处理.md)那个“跑过的跳过”给了这个脚本这个性质——**这一章能成立，全靠它。**

**锁**：**一个标记，用来防止同一件事被两个人同时干。** 上一轮还在跑，这一轮到点了，看见锁就直接走开。

**收件箱**：**一个约定好的目录，别人往里丢文件，你的程序从里面取。** 下面那套目录流转的第一站。

## 两条路，先说结论

**推荐定时轮询，每 5 分钟跑一次第 5 章那个批量脚本。**

理由只有一条，但它足够硬——**第 5 章那个脚本是幂等的。** 跑过的单据在 `out/` 里已经有一个 JSON，再跑一遍它直接跳过。所以每 5 分钟跑一次，绝大多数时候它什么也不做，一秒钟就退出；有新文件的那一次，它把新的处理掉。

**重复跑没有副作用，这件事让轮询这条路简单到几乎不会出错。**

实时监听那条路下面单说一节，**结论是先别用**。

## 一、定时轮询

### 第一步，写一个壳脚本

**不要把 `python3 ocr_batch.py ...` 直接写进 crontab。** 中间隔一个 shell 脚本，为了三件事：

- **服务没起来的时候别跑。** `ocr-vlm` 停着的话，这一轮几十份全会失败，全被复制进 `failed/`，还往日志里写一堆——**跑了不如不跑**；
- **没有新文件的时候安静退出。** 每 5 分钟一次，一天 288 次，每次都往日志里写四行汇总，一个月下来日志没法看了；
- **要能临时叫停。** 下面第五步那个开关。

建文件：

```bash
nano ~/ai/scripts/ocr-watch.sh
```

下面这一整段照抄进去：

```bash
#!/usr/bin/env bash
# ocr-watch.sh —— 每隔几分钟看一眼收件箱，有新的就跑一遍第 5 章那个批量脚本
# 跑过的会被跳过，所以重复跑不会重复干活

set -uo pipefail

INDIR="$HOME/ai/data/invoices-2026-08"
OUTDIR="$HOME/ai/projects/invoice-ocr"
BATCH="$HOME/ai/scripts/ocr_batch.py"

stamp() { date '+%F %T'; }

# 一、暂停开关在的话，什么也不做
if [ -f "$OUTDIR/.pause" ]; then
  exit 0
fi

# 二、服务没在跑就别跑，跑了全是失败
if ! systemctl is-active --quiet ocr-vlm; then
  echo "$(stamp) ocr-vlm 没在跑，这一轮跳过"
  exit 0
fi

# 三、收件箱不在就别跑
if [ ! -d "$INDIR" ]; then
  echo "$(stamp) 找不到 $INDIR，这一轮跳过"
  exit 0
fi

# 四、数一下有几份是新的。一份都没有就安静退出，不留日志
new=0
while IFS= read -r -d '' file; do
  name="$(basename "$file")"
  stem="${name%.*}"
  if [ ! -f "$OUTDIR/out/$stem.json" ]; then
    new=$((new + 1))
  fi
done < <(find "$INDIR" -type f \
  \( -iname '*.pdf' -o -iname '*.png' -o -iname '*.jpg' \
     -o -iname '*.jpeg' -o -iname '*.tif' -o -iname '*.tiff' \) \
  -mmin +1 -print0)

if [ "$new" -eq 0 ]; then
  exit 0
fi

# 五、有新的才跑
echo "$(stamp) 有 $new 份新的，开始跑"
python3 "$BATCH" "$INDIR" "$OUTDIR"
echo "$(stamp) 这一轮结束"
```

保存退出，然后给执行权限（[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)那一步）：

```bash
chmod 755 ~/ai/scripts/ocr-watch.sh
```

### 这个脚本里有三处值得单说

**一、`set -uo pipefail`，没有 `-e`。**

[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)那个整理脚本用的是 `set -euo pipefail`，多一个 `-e`——**任何一条命令出错就立刻停**。那里是对的，因为那个脚本在搬文件，错了要马上停手。

**这个脚本不搬文件，它只是叫另一个脚本干活**，而那个脚本自己会把失败记进 `failures.log`（[第 5 章](05-批量处理.md)那个 `note_failure`）。加了 `-e` 的话，批量脚本一返回非零值，最后那行“这一轮结束”就打不出来了，你反而少看到一行日志。

**二、`-mmin +1`，只挑一分钟以上没动过的。**

这一条是本章最容易被忽略、又最容易出事的地方。

**一份文件出现在目录里，不等于它已经拷完了。** 从网络盘拖一个 80 MB 的扫描件过来要几秒到几十秒，这段时间里文件已经在那儿了，但里面只有一半内容。这时候去读它，`pdftoppm` 会报错，这一份就白白进了 `failed/`。

`-mmin +1` 的意思是**只看一分钟内没有被改动过的文件**。拷贝还在进行中的文件，修改时间一直在刷新，这一轮就轮不到它，等下一轮。

> **一分钟够不够，看你的文件从哪儿来。** 本地拷贝一分钟绰绰有余；从一条很慢的网络拷几百 MB，把它改成 `-mmin +5`。**这个数不是规范，是你自己那条路上量出来的。**

**三、`stem="${name%.*}"`，把后缀去掉。**

第 5 章那个脚本给 `票据-0731-018.pdf` 生成的 JSON 叫 `票据-0731-018.json`——**去掉后缀，换成 `.json`**。这里数新文件用的是同一条规矩，所以数出来的和批量脚本真正要处理的是同一批。

### 第二步，先手动跑一遍

**这一条是[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)的规矩，本章照办：任何脚本都要先手动跑通，再交给定时任务。**

```bash
~/ai/scripts/ocr-watch.sh
```

**手上那批单据已经全跑完的话，这一次应该什么也不打印，直接退出**——因为没有新的。这就对了。

往收件箱里丢一份新的，再跑一次：

```bash
cp 某份新单据.pdf ~/ai/data/invoices-2026-08/
sleep 70
~/ai/scripts/ocr-watch.sh
```

`sleep 70` 是等过那一分钟。这一次屏幕上应该是：

```text
2026-08-15 16:03:12 有 1 份新的，开始跑
[1/129] 票据-0731-018.pdf 跳过，已经跑过了
...
[129/129] 票据-0801-001.pdf 好了，13.8 秒
---
这一轮：成功 1，跳过 128，失败 0，一共 0.3 分钟
台账 129 行：/home/你的账户名/ai/projects/invoice-ocr/ledger.csv
2026-08-15 16:03:29 这一轮结束
```

（**上面的份数和秒数是格式示意，不是实测值。**）

**看两个地方**：中间那一大串“跳过”说明幂等在起作用；台账行数比刚才多了一行。

### 第三步，写进 crontab

```bash
crontab -e
```

**不要加 `sudo`**，理由[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)说过。在文件末尾加这一行：

```text
*/5 * * * * /usr/bin/flock -n /home/你的账户名/ai/projects/invoice-ocr/.lock /home/你的账户名/ai/scripts/ocr-watch.sh >> /home/你的账户名/ai/projects/invoice-ocr/watch.log 2>&1
```

**`你的账户名` 换成你自己的**，用 `whoami` 查。这一行从左到右四段，一段一段说。

**第一段 `*/5 * * * *`** —— 每 5 分钟一次。[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)那张表里 `*/10` 那个例子的写法，把 10 换成 5。

**第二段 `/usr/bin/flock -n .../.lock`** —— **这是本章新加的东西，前面没讲过。**

问题是这样的：批量跑一次可能要半小时，而 cron 每 5 分钟就来敲一次门。不管的话，第二轮会在第一轮还没跑完的时候起来，**两个脚本同时读同一个目录、同时往同一个 `out/` 里写、同时重汇同一张台账**。

`flock` 拿的就是新词里那把锁。**第一轮跑起来的时候把 `.lock` 这个文件锁住，跑完才松开。** 第二轮来的时候锁还在，`-n` 的意思是“拿不到就立刻走人，不排队等”，于是它一声不响地退出，5 分钟后再来。

先确认这个命令在哪儿：

```bash
which flock
```

**打印出 `/usr/bin/flock` 就照上面那行写。** 打印出别的路径，把 crontab 里那一段换成打印出来的那个。[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)那条“路径必须写全”在这里同样成立。

**第三段是脚本本身的全路径。** 不要写 `~/ai/scripts/...`。

**第四段 `>> ... 2>&1`** —— 输出追加进日志，报错也一起收。这两样[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)讲透了，**这里一个字不改地照用**。

存盘退出，看一眼表里有什么：

```bash
crontab -l
```

### 第四步，确认它真的在跑

**写进去不等于跑得起来。** 三个地方各看一眼，一个都别跳。

**一看日志文件。** 这是唯一能证明脚本干了什么的东西：

```bash
tail -20 ~/ai/projects/invoice-ocr/watch.log
```

**没有新文件的那些轮次不会留下任何一行**，所以这个文件里应该只有真正干过活的记录。

**二看 cron 有没有把命令发出去**（[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)那条命令）：

```bash
journalctl -u cron --since "20 minutes ago"
```

正常会看到每 5 分钟一行 `CMD (/usr/bin/flock -n ...)`。**这一行只证明 cron 按点把命令发出去了，不证明脚本干成了事**——那要看上一条。

**三做一次端到端的实测。** 这一步才是真正的验收：

```text
1. 记下现在台账有多少行（打开 ledger.csv 看一眼，或者 wc -l）
2. 往 ~/ai/data/invoices-2026-08/ 里拷一份新单据进去
3. 什么也不做，等 6 分钟
4. 再看台账，多了一行没有
```

**多了一行，这一章就成了。** 没多，按顺序查这四样：`crontab -l` 里那行在不在、脚本有没有执行权限（`ls -l ~/ai/scripts/`，看有没有 `x`）、路径是不是写全了、`watch.log` 里有没有报错。还查不出来，到[第 15 卷：故障排查](../15-故障排查/README.md)按症状查。

### 第五步，怎么临时停掉

**要停的场合是有的**——机器要重启、要换模型、要改提示词整批重跑、客户那边送来一批不该现在处理的东西。

**最省事的一条，放一个暂停开关**：

```bash
touch ~/ai/projects/invoice-ocr/.pause
```

脚本第一句就在看这个文件在不在，在就直接退出。定时任务照常触发，但什么也不干。

恢复：

```bash
rm ~/ai/projects/invoice-ocr/.pause
```

**这条比去改 crontab 好用**，因为它不需要进编辑器，也不会误删别的定时任务。**而且它可以写进脚本里给别人用**——交付给客户的时候，告诉对接人“要暂停就建这个文件，要恢复就删掉”，比教他用 `crontab -e` 安全得多。

**另外两条路，知道就行**：

- **注释掉 crontab 那一行。** `crontab -e`，在那行最前面加一个 `#`，保存退出。**适合长期停用**；
- **`sudo systemctl stop cron`。** 这条把机器上所有定时任务一起停了，**不只是你这一个**。[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)如果还有别的任务在表里，它们也跟着停。**除非你确定表里只有这一条，否则别用这个。**

## 二、实时监听为什么先别用

Linux 上有一套叫 inotify 的机制，装一个 `inotify-tools` 包之后，一句 `inotifywait -m -e close_write 那个目录` 就能守在那儿，有文件写完就吐一行出来，接着触发处理。

**听上去比每 5 分钟去看一眼高级，实际用起来有三个坑。**

**一、触发的时机不好把握。** 一份文件从出现到写完是一个过程，不是一个瞬间。监听“文件被创建”这个事件的话，**文件刚出现你就冲上去读，读到的是半份**。监听“写完关闭”这个事件好一些，但不同的复制方式表现不一样——有的工具先写一个临时名字再改名，有的分几次写，跨网络的复制还可能中断重来。**这些情况本项目没有逐个验证过。**

**二、监听程序自己得一直活着。** 它是一个要常驻的进程，得做成服务（[第 2 卷第 6 章](../02-Ubuntu/06-进程与服务.md)），得管它崩了怎么办。

**三、这一条最要命——它停着的那段时间，事件是补不回来的。** 监听进程崩了、机器重启了、你手动停了忘了起，**这期间丢进去的文件不会有任何事件**，等你把它起回来，那些文件就静静躺在那儿，谁也不会去处理它们。

**轮询没有这个问题。** 它每一轮都是重新数一遍目录，**不管你停了五分钟还是停了三天，起回来的第一轮就把攒下的全处理了。**

> **一句话**：实时监听快几分钟，代价是漏了不知道。**这一卷做的是单据处理，晚 5 分钟没人在意，漏一张有人在意。**

## 三、目录流转：收件箱、处理中、已完成、失败

上面那套已经能跑了。**单据一多，它会露出一个毛病**——收件箱里的东西只进不出，跑到几千份的时候，每一轮都要把这几千份重新数一遍，而且你一眼看不出哪些是这个月新来的。

这一节给一套目录流转，**四站**：

```text
~/ai/data/
└── invoices-inbox/                收件箱：交单据的人只往这里丢

~/ai/projects/invoice-ocr/
├── working/                       处理中：这一轮正在处理的
├── done/                          已完成：处理完的原件，按月分
│   └── 2026-08/
├── out/                           每份一个 JSON（第 5 章那个）
├── failed/                        失败的副本和 failures.log（第 5 章那个）
└── ledger.csv                     台账
```

**每一站的意思**：

- **收件箱**——**它只有一个身份，就是投递口**。里面的东西是待办，空着就是没有待办。给对接人的说明只有一句话，“把文件拷进这个文件夹”；
- **处理中**——**这一轮认领下来的**。从收件箱搬进来这个动作，等于打了个招呼“这些归我了”，下一轮不会再碰它们；
- **已完成**——**跑出来 JSON 的，原件搬到这里**。按月分目录，将来找原件按月翻；
- **失败**——第 5 章那个 `note_failure` 已经在往这里写了，**本节不改它**。

### 先把一件事说清楚

[第 4 章](04-单张跑通.md)那三条规矩的第一条是**“`data/` 里只有原件，脚本一个字都不往里写”**。这一节的脚本要从 `data/invoices-inbox/` 里把文件搬走，**看上去是破了这条规矩。**

**没破，但要说清楚差别在哪儿**：

- **改写文件内容**是那条规矩禁止的事。搬家不改内容，**文件一个字节都没变**，`mv` 只是换了个位置；
- **收件箱不是原件库，是中转站。** 原件的最终归宿是 `done/`，那才是以后要长期留着、要能翻回去核对的地方；
- **收件箱这个目录本身是这一套自己建的**，不是客户原来放东西的地方。**客户原来那份留在他自己那儿，进收件箱的已经是一份拷贝。**

> **交付给客户的时候这句话要说出口**：“您把文件拷进来，不要用剪切。处理完我把原件放在另一个文件夹里，按月份分好，随时能翻。”

### 流转脚本

建文件 `~/ai/scripts/ocr-flow.sh`：

```bash
#!/usr/bin/env bash
# ocr-flow.sh —— 收件箱进，已完成出
# 用它替代 ocr-watch.sh，crontab 里换个名字就行

set -uo pipefail

INBOX="$HOME/ai/data/invoices-inbox"
PROJ="$HOME/ai/projects/invoice-ocr"
WORKING="$PROJ/working"
DONE="$PROJ/done/$(date +%Y-%m)"
OUT="$PROJ/out"
BATCH="$HOME/ai/scripts/ocr_batch.py"

stamp() { date '+%F %T'; }

if [ -f "$PROJ/.pause" ]; then
  exit 0
fi

if ! systemctl is-active --quiet ocr-vlm; then
  echo "$(stamp) ocr-vlm 没在跑，这一轮跳过"
  exit 0
fi

mkdir -p "$INBOX" "$WORKING" "$DONE" "$OUT"

# 一、收件箱里一分钟以上没动过的，搬进处理中
picked=0
while IFS= read -r -d '' file; do
  name="$(basename "$file")"
  target="$WORKING/$name"
  if [ -e "$target" ]; then
    target="$WORKING/$(date +%H%M%S)-$name"
  fi
  mv "$file" "$target"
  picked=$((picked + 1))
done < <(find "$INBOX" -maxdepth 1 -type f -mmin +1 -print0)

# 二、处理中是空的就收工，不留日志
if [ -z "$(ls -A "$WORKING")" ]; then
  exit 0
fi

echo "$(stamp) 收进 $picked 份，处理中一共 $(ls -1 "$WORKING" | wc -l) 份"
python3 "$BATCH" "$WORKING" "$PROJ"

# 三、出了 JSON 的，原件搬进已完成
finished=0
for file in "$WORKING"/*; do
  [ -e "$file" ] || continue
  name="$(basename "$file")"
  stem="${name%.*}"
  if [ -f "$OUT/$stem.json" ]; then
    target="$DONE/$name"
    if [ -e "$target" ]; then
      target="$DONE/$(date +%H%M%S)-$name"
    fi
    mv "$file" "$target"
    finished=$((finished + 1))
  fi
done

echo "$(stamp) 这一轮交付 $finished 份，还留在处理中的 $(ls -1 "$WORKING" | wc -l) 份"
```

```bash
chmod 755 ~/ai/scripts/ocr-flow.sh
```

crontab 那一行**只把脚本名换掉**，其余一个字不动：

```text
*/5 * * * * /usr/bin/flock -n /home/你的账户名/ai/projects/invoice-ocr/.lock /home/你的账户名/ai/scripts/ocr-flow.sh >> /home/你的账户名/ai/projects/invoice-ocr/watch.log 2>&1
```

### 三处设计说明

**一、重名的时候加时分秒。** `mv` 覆盖同名文件不问一句（[第 2 卷第 2 章](../02-Ubuntu/02-终端.md)那一条，[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)那个脚本也是这么处理的）。**两个人同一天各交一份 `扫描件.pdf` 过来，不加这一手，先来那份就没了。**

**二、失败的会留在“处理中”，这是故意的。** 跑完之后 `out/` 里没有它的 JSON，它就搬不走，**下一轮会被再试一次**。服务当时正好在重启、文件正好拷了一半，下一轮就补上了。

**三、留在“处理中”太久的，是真有问题。** 一份文件在 `working/` 里躺过好几轮还没出去，那不是运气问题：

```bash
ls -lt ~/ai/projects/invoice-ocr/working/
cat ~/ai/projects/invoice-ocr/failed/failures.log
```

按[第 5 章](05-批量处理.md)那三类原因处理——文件坏了、格式不认、服务断了。**处理不了的自己挪走**，别让它每 5 分钟拖累一次。

> **这三个目录的数字合起来是一张进度表**：收件箱里几份是没开始的，处理中几份是卡住的，已完成里几份是交出去的。**客户问“做到哪儿了”，看一眼这三个数就答得上来。**

## 四、什么时候值得换成 systemd timer

[第 2 卷第 8 章](../02-Ubuntu/08-定时任务.md)最后提过一句，systemd 自己也能做定时。**这一卷用 cron 就够，不用换。** 下面这一节只在你碰上那一种情况时才有用。

**那一种情况是——机器夜里关机。**

cron 只在到点那一刻看机器开没开。**关着的时候错过的那几轮，开机之后不会补跑。** 这对本章的场景其实无所谓，因为下一轮照样会把攒下的处理掉。但如果你把间隔调得很长（比如每天凌晨跑一次），而机器那天凌晨正好关着，**这一天就整个漏了**。

systemd timer 有一项 cron 没有的东西，叫 `Persistent=true`——**开机时发现错过了一次，立刻补跑。**

两个文件，都放在 `/etc/systemd/system/` 下面：

```ini
# /etc/systemd/system/ocr-watch.service
[Unit]
Description=OCR 收件箱处理

[Service]
Type=oneshot
User=你的账户名
ExecStart=/home/你的账户名/ai/scripts/ocr-flow.sh
```

```ini
# /etc/systemd/system/ocr-watch.timer
[Unit]
Description=每 5 分钟跑一次 OCR 收件箱处理

[Timer]
OnBootSec=2min
OnUnitActiveSec=5min
Persistent=true

[Install]
WantedBy=timers.target
```

装上并起来：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ocr-watch.timer
```

`enable --now` 是[第 2 卷第 6 章](../02-Ubuntu/06-进程与服务.md)那张表最后一行——**现在起来，下次开机也自己起来。**

看它下一次什么时候跑：

```bash
systemctl list-timers ocr-watch.timer
```

看它跑了什么：

```bash
journalctl -u ocr-watch.service --since today
```

**换过来之后，crontab 里那一行要删掉**，否则两套一起跑。

**它比 cron 多给你三样**：日志走 `journalctl`，和别的服务一个口子；`systemctl` 管起停，和[第 2 卷第 6 章](../02-Ubuntu/06-进程与服务.md)那五个动作一样；错过了能补跑。**代价是多两个文件、多一个 `sudo`。** 本章的场景里这三样都用不太上，所以正文推荐 cron。
