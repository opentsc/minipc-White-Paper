# 12　温度与频率

## 完成结果

能用命令看到这台机器的 CPU 温度、GPU 温度和当前频率，知道跑模型时这两个数字正常会怎么变，知道什么叫降频以及降频不等于故障。最要紧的是：**你手上有一份自己这台设备的基线，以后任何“是不是变慢了、是不是太热了”的问题，都拿它来对照，而不是去网上找一个正常区间。**

## 开始前需要准备什么

- 一台装好 Ubuntu、能开终端的设备；
- 读过第 11 章，机器已经摆在合适的位置；
- 本章要装两个查看工具，**其余全是只读命令，不改任何设置**；
- 建立基线那一节要占大约一小时，机器在这段时间里不能干别的。

## 新词

**传感器**（Sensor）：芯片和主板上用来测温度、电压、转速的小部件。Linux 通过驱动把它们的读数暴露成文件，工具再把这些文件读出来显示。

**Tctl**：AMD 处理器给出的一个**控制用**温度值。它是芯片自己用来决定要不要降频的依据，不一定等于某个物理位置的实际温度。**不用纠结它到底是哪里的温度**，要用的是它在同一台机器上前后的变化。

**edge / junction / mem**：GPU 那一段常见的三个温度读数，分别对应芯片边缘、核心结温、显存。这台设备上 GPU 和 CPU 在同一块芯片上，所以这几个数字和 CPU 那边会一起动。

**降频**（Throttling）：芯片主动把运行频率降下来。原因有两类：温度到了上限，或者功耗到了上限。**这是设计行为，是芯片在保护自己，不是故障。**

**稳态**：负载持续一段时间之后，温度和频率不再明显变化，停在一个位置。**判断一台机器的表现要看稳态，不是看开跑那几秒的瞬时值。**

**基线**：你这台机器在几个固定状态下的一组记录（温度、频率、速度、室温）。以后所有判断都和它比。

**采样**：隔一段时间读一次数。看温度变化过程要连续采样，不能只看一次。

## 先装工具

两个工具，都在 Ubuntu 的软件源里。

```bash
sudo apt install lm-sensors
sudo sensors-detect
```

`sensors-detect` 会问一串问题，**一路按回车用默认值即可**。它做的事是探测这台机器上有哪些传感器芯片，并把结果记下来。这一步跑过一次就不用再跑。

```bash
sudo apt install radeontop
```

`radeontop` 用来看 GPU 的占用情况。

装工具会往系统里加软件包，不装也能开机、也能跑模型，只是看不到这些数字。

## 怎么看 CPU 温度

```bash
sensors
```

输出分成几段，每段开头是一个芯片名。CPU 温度通常在 `k10temp` 开头的那一段里，里面有一行 `Tctl`。

看连续变化：

```bash
watch -n 2 sensors
```

`watch` 是每隔一段时间重复执行一条命令，`-n 2` 表示每 2 秒一次，屏幕原地刷新。按 `Ctrl+C` 退出。

跑模型的时候，开一个终端跑这条，另一个终端跑推理，就能看着温度往上爬、爬到哪里停下来。

## 怎么看 GPU 温度

**这台设备上 GPU 和 CPU 在同一块芯片上**，所以 GPU 温度和 CPU 温度是同一块硅片上不同位置的读数，会一起动。

同一条命令：

```bash
sensors
```

在 `amdgpu` 开头的那一段里看 `edge`、`junction`、`mem` 这几行。

`sensors` 里没有 `amdgpu` 段的话，还有一条路：

```bash
cat /sys/class/drm/card*/device/hwmon/hwmon*/temp1_input
```

输出是一个大数字，**单位是千分之一度**——`45000` 就是 45°C。

> 这条路径的写法各内核版本略有差异，**提示文件不存在属正常，本项目未在 Max395 机型上实测过这条路径，需要核验**。以 `sensors` 的输出为主。

## 怎么看当前频率

**CPU 频率**

```bash
grep MHz /proc/cpuinfo
```

列出所有核心的当前频率，单位 MHz。这条和[第 1 卷第 12 章](../01-开箱与安装/12-硬件问题处理.md)用的是同一条。

只看前几个核心、连续看：

```bash
watch -n 1 "grep MHz /proc/cpuinfo | head -4"
```

`head -4` 是只取前 4 行，16 个核心全列出来一屏放不下。

另一个读法（单位是 kHz，要自己除以 1000）：

```bash
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq
```

**GPU 的忙闲程度**

```bash
radeontop
```

看 `gpu` 那一栏的百分比：空闲时接近 0，跑模型时长时间保持在高位。同一个界面里的 `gtt` 那一栏是第 9 章验证显存时看的那个。按 `q` 退出。

**GPU 频率**

```bash
cat /sys/class/drm/card*/device/pp_dpm_sclk
```

输出是几档频率，当前生效的那一档前面有个 `*` 标记。

> **文件不存在属正常**，这个接口在不同内核版本和不同硬件上不一定开放。**本项目未在 Max395 机型上实测过，需要核验。** 材料里另一个常被提到的工具是 `amdgpu_top`，安装方式随发行版而定，本项目同样未实测。

GPU 频率读不到也不影响判断——**温度、GPU 占用率和 tokens/s 这三个已经够用了**。

## 什么叫降频

芯片把频率降下来，原因有两类，**在这台机器上要分清**：

**一、温度到上限（温度墙）**

温度爬到芯片设定的上限，为了不继续升温，频率降下来。表现是：温度稳定在某个值不再上升，同时频率明显低于刚开跑时。

**二、功耗到上限（功耗墙）**

功耗到了整机厂设定的上限。这台机器上还多一层——**CPU、iGPU、NPU 共用同一份功耗预算**（第 2 章），CPU 多拿一点，iGPU 就少拿一点。表现是：温度还不算高，频率就已经降下来了。

**两类都不是故障。** 芯片一开始冲到很高的频率、几秒到几十秒之后回落到一个稳定值，是这类芯片的正常行为。要判断的是**回落之后停在哪里**，以及**这个位置和你的基线比是高是低**。

第三种情况要单独拿出来说：**频率低但温度也不高、功耗也没到上限**，那多半和散热无关，去看功耗档位和调度策略（第 10 章）或者后台还跑着什么（第 2 章）。

## 跑模型时温度和频率的正常变化过程

一次完整的推理大致分四段。**下面说的是变化的形状，不是具体数值。**

**一、加载模型**

模型文件从 SSD 读进内存。这一段主要是磁盘和 CPU 在忙，GPU 还没怎么动，温度小幅上升。文件几十 GB 的话这一段要好几十秒。

**二、读你的提示词**

GPU 短时间高强度出力，功耗和温度快速上冲。提示词越长这一段越久。频率在这个阶段通常最高。

**三、一个字一个字往外生成**

GPU 持续中高负载，**这是最长的一段**。温度继续爬，爬到某个位置进入稳态；频率从最高点回落，也停在一个位置。

**这一段的稳态值就是你要记的东西。**

**四、跑完之后**

负载停止，温度在几十秒到几分钟内回落，风扇转速跟着降下来。

**正常的形状是**：温度上去、稳住、跑完落回来；频率冲高、回落、稳住。

**不正常的形状是**：温度一直爬不进稳态，一路往上；或者温度和频率剧烈来回震荡；或者跑到一半负载自己断了。

## 建立你自己这台设备的基线

**本章不给“正常温度是多少度”这样的数字。** 不同型号、不同散热设计、不同室温差别很大（[第 1 卷第 12 章](../01-开箱与安装/12-硬件问题处理.md)已经写过同一件事，**需要核验**），任何一个通用区间搬到你这台上都可能得出错误结论。

能用的判断方式只有一个：**先量出你这台机器健康时的样子，以后拿它比。**

**三个状态，各测一次**

| 状态 | 怎么制造 | 记什么 |
| --- | --- | --- |
| 空闲 | 开机后什么都不做，等 5 分钟 | CPU 温度、GPU 温度、CPU 频率、风扇主观噪音档、室温 |
| CPU 满载 | 下面给的压力命令，跑 5 分钟 | 同上，另记持续时间 |
| 跑模型满载 | 固定模型、固定提示词、固定上下文长度，连续跑 30 分钟以上 | 同上，另记 tokens/s、`radeontop` 里 `gpu` 和 `gtt` 两栏的表现 |

**CPU 满载那一档的压力命令**（可选）：

```bash
sudo apt install stress-ng
stress-ng --cpu 16 --timeout 300s
```

`--cpu 16` 是压满 16 个核心，`--timeout 300s` 是 5 分钟后自动停。**机器有散热疑点的时候先别跑这一档**，直接从跑模型那一档开始，边跑边盯着温度。

**记录表**

```text
日期：
室温：
摆放位置（有没有变过）：
BIOS 功耗档位：
调度策略（scaling_governor）：
风扇档位：
—— 空闲 5 分钟 ——
CPU 温度（Tctl）：
GPU 温度（edge / junction）：
CPU 频率（前 4 个核心）：
风扇噪音（听不见 / 听得见 / 影响）：
—— 跑模型满载 30 分钟 ——
模型与量化档：
上下文长度：
温度稳态：
频率稳态：
tokens/s：
radeontop 的 gpu 占用：
风扇噪音：
当时机器上还跑着什么：
```

这份表的完整版和长期存放位置在第 16 章。**没有它，后面所有的判断都只能靠感觉。**

**什么时候要重测基线**

- 刷过主板固件（第 8 章）；
- 改过 BIOS 功耗档位或风扇策略（第 10 章、第 11 章）；
- 换过摆放位置或换了房间；
- 换过内核、驱动或推理框架的版本（第 5 卷、第 6 卷）；
- 清过灰；
- 季节变了、室温有明显变化。

**换了条件的旧基线不能拿来比。** 记得把每次的条件一起记下来，原因就在这里。

## 怎么判断是散热问题还是正常行为

拿现在的读数和基线对照，按这张表走。**对照的前提是室温和摆放没变，负载是同一个。**

| 你看到的 | 更可能是 | 下一步 |
| --- | --- | --- |
| 温度稳态、频率稳态、tokens/s 都和基线接近 | 正常 | 不用处理 |
| 温度稳态明显高于基线，频率明显低于基线 | 散热变差了 | 查摆放和进风口积灰（第 11 章）。都排除了再看室温 |
| 温度和基线差不多，但频率明显更低、速度明显更慢 | 不是散热 | 查功耗档位和调度策略（第 10 章）、查后台还跑着什么（第 2 章）、查软件版本有没有换过（第 5 卷、第 6 卷） |
| 温度一直往上爬，进不了稳态 | 散热跟不上，或进风被挡 | 停下负载，按第 11 章检查摆放和进风口。恢复之后再跑一次看能不能进稳态 |
| 温度和频率剧烈来回震荡 | 需要单独排查 | 记录波动的周期和幅度，按[第 15 卷](../15-故障排查/README.md)处理 |
| 满载跑一会儿就黑屏、死机、画面冻住 | 不是单纯的温度问题 | 按[第 1 卷第 12 章](../01-开箱与安装/12-硬件问题处理.md)的“满屏白字报错或画面冻住”处理，先拍照 |
| 室温比测基线那天高很多 | 环境变量 | 把室温记进去再比。夏天和冬天的数据不能直接对照 |
| 机身烫到手不能碰、闻到焦味、有异响 | 立刻断电 | 不要继续测试，联系卖方（[第 1 卷第 12 章](../01-开箱与安装/12-硬件问题处理.md)） |

**一条通用的判断办法**：**温度高、频率低，一起出现**，指向散热；**温度不高、频率也低**，指向功耗档位、调度策略或者后台负载。

## 这一章涉及的可改设置

**本章的所有查看命令都是只读的，不改任何设置。**

和温度、频率相关的可改项都在前两章，四件事在那里写全了：

- BIOS 功耗档位、CPU 调度策略、平台档位 → 第 10 章；
- BIOS 风扇策略、摆放位置 → 第 11 章。

本章唯一会改动系统的是装工具，也按四件事写一遍：

**装 `lm-sensors`、`radeontop`、`stress-ng`**

- **默认状态**：Ubuntu 装完之后这三个都没装；
- **什么情况才需要改**：要看温度、看 GPU 占用、造一个可重复的 CPU 负载时装。不装不影响开机和跑模型；
- **改完怎么验证**：`sensors` 有输出、`radeontop` 能打开界面；
- **怎么恢复**：`sudo apt remove lm-sensors radeontop stress-ng`。这几个包只是读数据和造负载，卸掉不影响系统。

## 正常结果

`sensors` 能输出 CPU 温度（`k10temp` 段的 `Tctl`）和 GPU 温度（`amdgpu` 段的 `edge` 或 `junction`）；`grep MHz /proc/cpuinfo` 能列出 16 个核心的当前频率；`radeontop` 能看到 `gpu` 占用在空闲时接近 0、跑模型时保持高位。

你手上有一份填好的基线表，至少包含空闲和跑模型满载两个状态，并且记了当时的室温和摆放位置。

跑模型时温度上去、稳住、跑完落回来，频率冲高之后回落到一个稳定值——这是正常的形状。

## 看到不同结果怎么办

**`sensors` 提示找不到命令**：`lm-sensors` 没装上，重新执行 `sudo apt install lm-sensors`。

**`sensors` 有输出但没有 `k10temp` 那一段**：先确认 `sudo sensors-detect` 跑过并且一路按了回车。跑过之后重启一次再试。

**`sensors` 里没有 `amdgpu` 那一段**：用本章给的 sysfs 路径试；仍然没有的话，先确认 GPU 驱动是不是正常加载了（第 5 卷）。

**`sensors` 输出里有一堆看不懂的电压和温度**：正常。只看 `k10temp` 的 `Tctl` 和 `amdgpu` 的 `edge`、`junction` 就够了，其余可以不管。

**`cat /sys/class/drm/card*/device/pp_dpm_sclk` 提示文件不存在**：属正常，这个接口不一定开放。不影响判断，用温度、GPU 占用和 tokens/s 这三个。

**跑模型时频率从很高掉到一个低不少的值**：**这通常是正常的。** 判断依据是掉下来之后停在哪里，以及这个位置和基线比是高是低，不是看掉了多少。

**温度看起来很高，但你不知道算不算高**：这正是要建立基线的原因。**不要去网上找一个数字来比。** 按上面的表格测出你这台机器健康时的稳态，以后拿它比。真正要警惕的是“比自己的基线明显高了”，不是“比别人的数字高”。

**跑模型时 `radeontop` 的 `gpu` 一栏一直接近 0**：说明模型没有跑在 GPU 上，这不是温度问题。按第 5 卷和第 6 卷检查后端和驱动。

**空闲时温度就不低**：先看是不是有程序在占 CPU（`top`，按 `q` 退出）；刚装完系统或刚做完更新的那十几分钟属正常；再看摆放和进风口（第 11 章）。

**同一个模型，今天的 tokens/s 比基线低不少，温度却和基线差不多**：不是散热。查后台还跑着什么（第 2 章），查有没有换过驱动或框架版本（第 5 卷、第 6 卷），查功耗档位和调度策略有没有被动过（第 10 章）。

**你在别处看到某台 Max395 的温度数字**：那是那台整机在那套散热、那个室温、那个负载下的结果。整机厂的散热设计各不相同（第 15 章），别人的数字不是你的判据。
