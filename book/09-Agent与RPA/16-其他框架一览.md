# 16　其他框架一览

## 这一章的任务

**这一卷从[第 2 章](02-n8n装起来.md)起，主线一直是 n8n。**

**这一章回答两个问题：还有哪些别的选择，以及为什么这一卷选了它。**

**这一章不教任何一个框架怎么用。** 每一个给一段定位——**适合谁、不适合谁**，读完你能做的事是：客户或者同行提到某个名字的时候，**你说得出它大概是干什么的，以及它跟你手上这套东西是不是一回事。**

**这一章有一件事要先说明白：下面这些名字里，本项目只核对过其中一部分的官方资料。**

**核对过的写出处；没核对过的写“需要核验”，并且只写到定位为止，不写功能清单、不写版本号、不写部署步骤。** 这一条在 OpenClaw 那一节尤其要紧——**那一节整节是方向篇。**

## 开始前

- 前面十五章读过，**尤其是[第 1 章](01-Agent是什么.md)那个“能自己决定下一步调什么工具的程序”**。这一章反复用它；
- [第 3 章](03-第一个工作流.md)那条“加节点、连线、执行”的体验。**这一章讲的差别，一半是这种体验上的差别**；
- **不需要动手，40 分钟。**

## 新词

**框架**：**一套写好的骨架，你往里面填自己的东西。** 这一章里多数名字是框架。

**编排**：**决定几件事按什么顺序、什么条件发生。** n8n 那张画布干的就是这件事，**只不过它用的是拖节点，别的框架用的是写代码。**

**协议**：**两边约好的说话方式。** 它不是软件，装不了也跑不了，**它规定的是“你发什么过来我认”。** 这一章里 MCP 属于这一类。

**代码这条路**：**用编程语言把流程写出来。** 和 n8n 那张画布是同一件事的两种做法，**差别在谁能改它、和出了事怎么查。**

## 先分清两类东西

**下面这些名字混在一起讲会乱，先分成两堆。**

```text
第一堆：你在上面搭流程的东西
    n8n（本卷主线）
    LangGraph
    CrewAI
    AutoGen

第二堆：不是搭流程的东西
    MCP          —— 一套协议，管模型怎么调工具
    AgentCPM     —— 模型那一头，不是框架
    OpenClaw     —— 一整套要装到企业里的系统（方向篇）
```

**第一堆里，n8n 和另外三个的分界线只有一条：n8n 那条路上流程画在画布上，另外三条路上流程写在代码里。**

**这一条分界线决定了后面所有的取舍**，最后那一节会回到它。

## LangGraph

**定位：用代码把一个 agent 的流程写成一张图——有节点、有边、有状态，可以绕回去再来一遍。**

**它适合的场合：**

- **流程里有循环。** “试一次，不行就换个办法再试”“边做边看，条件够了才往下”——**这类控制流在画布上画得出来，但画得很难看**；
- **写这套东西的人会写代码，而且以后维护它的还是程序员**；
- **要把一个 agent 的每一步都攥在自己手里。**

**它不适合的场合：**

- **交付给非程序员维护。** 客户那边没有人会读代码的话，**这条路上的每一次小改动都要找你**；
- **要给客户看流程。** 这一条下面单独说；
- **只是把三四件事串起来。** 那种事在画布上五分钟，**用代码写要先搭一套工程。**

**本项目未核对 LangGraph 的官方文档、当前版本与许可，需要核验。** 上面这段只是定位，**不是它的功能说明。**

## CrewAI

**定位：把几个“角色”凑成一个小组，各自有分工，按你定的顺序或者层级协作。**

**它的表达方式跟另外几个不一样。** 你描述的不是“先做 A 再做 B”，**是“有一个负责查资料的、一个负责写初稿的、一个负责审的”**，然后让它们按角色走一遍。

**它适合的场合：**

- **任务本身就是几个人分工干的**，照着搬进来读着顺；
- **做原型、做演示、做内部试验**——**这种表达方式讲给人听最容易懂。**

**它不适合的场合：**

- **要精确控制每一步。** 角色这种表达方式天然模糊，**“这一步到底发生了什么”不如画布上那么一目了然**；
- **交付给客户当生产流程**——**理由和上面一条是同一条**，出了事你要能指着某一步说它错在这儿。

**本项目未核对 CrewAI 的官方文档、当前版本与许可，需要核验。**

## AutoGen

**定位：让几个 agent 用互相对话的方式协作，也可以把人放在这个对话里。**

**它跟 CrewAI 的差别在于组织方式**——CrewAI 是分工，AutoGen 是对话。**几个 agent 你一句我一句，讨论出一个结果。**

**它适合的场合：**

- **研究和试验。** 想看看几个 agent 互相讨论能不能把一件事做对，**这条路最直接**；
- **中间要人插一句的场合。** 人也可以是对话里的一方。

**它不适合的场合：**

- **要求结果稳定的生产流程。** 对话这种方式每一次跑出来的路径可能都不一样，**而客户那条流程要的是每天一样**；
- **要算成本的场合。** 几个 agent 来回讨论，**调模型的次数不好预估**——本地跑不心疼钱，但心疼时间。

**本项目未核对 AutoGen 的官方文档、当前版本与许可，需要核验。**

## AgentCPM

**定位：它跟上面三个不是一类东西——上面三个是框架，它是模型那一头。**

**这个名字指向的是把 agent 能力做进小模型、让它能跑在端侧设备上的这一支路线。**

**为什么这一段这么短，两条：**

**一、它跟这一卷的主线不冲突，也不替代。** 这一卷的做法是“流程用 n8n 编排，判断交给本地模型”（[第 5 章](05-案例一-模型摘要.md)那条 HTTP Request）。**换一个模型只是换那一行 `model` 的名字**（[第 6 卷第 7 章](../06-本地模型/07-多模型切换.md)那张常备表）。

**二、本项目未核对 AgentCPM 的官方仓库、当前状态、许可与可用的模型文件，需要核验。** 所以这一段不写它能做什么、不写怎么装、不写它在这台机器上跑不跑得动。

**要评估它的话，走[第 6 卷](../06-本地模型/README.md)那套办法**——**能不能 `ollama pull`、拉下来跑一句话看看**，比读任何介绍都快。

## MCP

**定位：一套协议，规定模型怎么调外部工具和数据。**

**这是这一章里唯一一个有可引用出处的名字。**

A2A 那个项目在自己的说明里划过两者的边界——**MCP 管模型调用工具与数据，A2A 管 agent 之间的协作与任务转移**（[来源目录](../../reference/source-catalog.md)“RAG／OCR／Agent 应用”一节，访问日期 2026-08-13）。

**它跟这一章别的名字不是一个层面的东西。**

**框架是你搭流程的地方；协议是两边约好的说话方式。** 你不会“用 MCP 搭一条流程”，**你会让某个东西“支持 MCP”，然后另一个支持 MCP 的东西就能调它。**

**它对这一卷的实际意义是什么：**

**这一卷里，模型调工具这件事是你自己接的**——[第 5 章](05-案例一-模型摘要.md)那个 HTTP Request 是你填的地址，[第 7 章](07-案例二-进件分类.md)那个分类结果是你写代码接到下一个节点上的。**每接一样东西，你写一次。**

**MCP 想解决的就是这个“每接一样写一次”。** 工具那一头按协议提供，模型这一头按协议调用，**中间不用你每次写胶水。**

**要不要在客户方案里用它，本章不给判断。** 用不用取决于两件事——**你要接的那个东西支不支持它、你手上这套东西支不支持它**。**这两件都要核验，本项目未核对任何一方的当前支持情况。**

> **客户提到这个名字的时候，多半不是在问技术。** 他是在问“你这套东西以后能不能接别的”。**答法是指着[第 5 章](05-案例一-模型摘要.md)那个节点说：现在接一样东西是填一个地址加一段提示词，一天的事。** 这句话比解释协议管用。

## 方向篇：OpenClaw 那种企业部署

**这一节整节是方向篇，性质和[第 13 章](13-方向篇-采购审核.md)一样。**

**这个名字在读者的提问里会反复出现，指的是一类需求：把一整套 agent 系统装到企业自己的机器上，而不是用别人的云。**

**这一节不写它的功能清单、不写部署步骤、不写价格、不写版本号。**

**理由只有一条**：**本项目未取得可引用的官方文档、版本信息、许可条款与部署要求，需要核验。** 硬写一份出来，读者拿去跟客户谈，**谈的是一份编的东西。**

**能写的是这个：要评估任何一套“装到企业里的 agent 系统”，先查这五件事。**

```text
1. 许可是什么。能不能商用、能不能给客户装、要不要付费。
   —— 这一条排第一，它能一票否决。

2. 部署要几个组件。一个容器，还是十几个。
   —— 这一条决定交付重量，理由下一节说。

3. 更新有多快，怎么更新。
   —— 更新太快，你装给客户的那一版三个月后没人管了；
      更新要停机的话，客户的流程也要跟着停。

4. 数据往哪儿走。有没有任何一步要连外面。
   —— 这一条是本地部署这门生意的根。有一步连外面，
      「数据不出场所」这句话就不能说（第 13 卷）。

5. 谁在维护它。一个公司、一个基金会，还是几个人。
   —— 客户会问「这东西三年后还在不在」。
```

**这五条不是本教材独有的，它对第一堆里任何一个框架同样成立。** 上面那几段之所以只写定位不写别的，**就是因为这五条本项目一条都没核对。**

> **客户直接点名要某一套系统的时候，做法是：先把这五条查一遍，查完再报价。** **查这五条本身就是工作量，可以单独收费**（[第 17 章](17-这个能力怎么卖.md)）。**查完的结论是“这套不适合你们”也算交付**——**能说不的那种交付，客户下一单还会找你。**

## 为什么这一卷主线选 n8n

**四条理由。前三条是技术上的，第四条是交付时才看得出来的。**

### 一、单个容器

**一条 `docker run`，一个数据目录，没了。**

官方文档给的镜像是 `docker.n8n.io/n8nio/n8n`，容器内监听 5678，数据卷挂在容器内的 `/home/node/.n8n`（[第 2 章](02-n8n装起来.md)已引官方文档，访问日期 2026-08-15）。**这一卷从头到尾就这一个容器。**

**这一条比听上去重要。** 这一卷做出来的东西是要装到别人机器上的，**装的东西越少，交付越轻，出事的地方越少**（[第 2 章](02-n8n装起来.md)那句话，原样成立）。

**对照一下另一头**：本项目在素材核对阶段记录过，另一类同方向的产品用 Compose 部署一次要拉起十几个组件——**交付一台演示机等于交付一套微服务运维**。**这一条本卷未再核对，需要核验**，但那个量级的差别不会因为版本变化而消失。

### 二、界面上看得见每一步

**[第 3 章](03-第一个工作流.md)那个体验：点开一个节点，看得到它收到了什么、吐出了什么。**

**这一条在整本教材里被反复用来排查**——[第 4 章](04-案例一-抓网页.md)抄字段名、[第 5 章](05-案例一-模型摘要.md)看表达式预览、[第 11 章](11-日志与重试.md)从失败那一次跳回编辑器。

**代码那条路上这些事都要靠打印和日志。** 差别不在能不能做，**在于要不要先搭一套东西才能做。**

### 三、非程序员能维护

**这一条是给客户看的。**

**客户那边要改一个时间点、加一个收件人、在黑名单里加一个词**——**画布上是点两下的事。**

**换成代码那条路，同样的改动要有人能打开一个项目、改对地方、不弄坏别的、然后重新部署一次。** 客户那边多半没有这个人，**结果是每一次小改动都要找你**——你以为这是好事（有维护费），**实际是坏事**：三次小改动之后客户会觉得这东西离了你就动不了，**而这是客户最不喜欢的感觉。**

### 四、客户能自己看懂那张流程图

**这一条是交付的时候才看得出来的，也是四条里最值钱的一条。**

**你把画布转过去给客户看，他能指着某个节点问“这一步是干什么的”。**

**这件事的价值有三处：**

- **谈需求的时候**——客户看着图说“这儿要加一道确认”，**比听你描述有效得多**；
- **验收的时候**——[第 10 章](10-案例三-人工确认.md)那张六条清单要对着每一个节点过一遍，**画布上一个一个指过去，客户全程跟得上**；
- **出事的时候**——**指着那个红掉的节点说“断在这儿，原因是这个”**，比拿一段日志给他看强一百倍。

**第三处最要紧。** 一套东西出过一次事而客户没有失去信任，**多半是因为他看得见它是怎么坏的。**

> **这四条合起来是本教材的判断，不是任何评测结论。** 它们成立的前提是这一卷的场景——**单台机器、小客户、交付出去之后要有人维护。** 换一个场景（比如一个团队自己内部用、维护的人就是写它的人），**这四条里有三条不成立，那时候代码那条路更好。**

## 怎么挑：不看排名，看你要做什么

**这一节不给排名，一个都不给。**

**理由是排名要有一个统一的标准，而这几个东西根本不在同一条赛道上**——拿协议跟框架比、拿模型跟编排工具比，**比出来的名次没有任何意义。**

**换一种问法：你要做的是什么样的东西。**

| 你要做的是 | 往哪个方向看 |
| --- | --- |
| **把几件事串起来，定时跑，出错要能查，还要交给别人维护** | **n8n**（这一卷） |
| **一个流程里要绕回去重试、要按状态走不同的路，而且维护的人是程序员** | **LangGraph 那条路** |
| **几个角色分工干一件事，先做个原型看看行不行** | **CrewAI 那条路** |
| **让几个 agent 讨论着把一件事做出来，做研究或者试验** | **AutoGen 那条路** |
| **让模型能调更多外面的工具，而且不想每接一样写一次** | **MCP 那条路** |
| **换一个判断得更准的脑子** | **不是框架的事，[第 6 卷](../06-本地模型/README.md)换模型** |
| **客户点名要某一整套系统装进他们公司** | **先查那五条，再谈**（上面那一节） |

**两条判断放在最后：**

**一、先把这一卷这条走通，再看别的。**

**不是因为它最好，是因为你手上要先有一条能交出去的东西。** 三个案例、一套日志与重试、一张人工确认清单——**这些东西换到任何一条路上都成立**，**而框架换一个，前面十五章要重学的其实只有“怎么把节点连起来”那一部分。**

**二、别为了框架换框架。**

**客户不会为你用了哪个框架付钱。** 他付钱是因为那件事被自动做完了、出错的时候有人知道、该停的地方停住了。**这三件事跟框架的关系比想象的小。**
