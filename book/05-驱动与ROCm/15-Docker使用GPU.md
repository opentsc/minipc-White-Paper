# 15　Docker 使用 GPU

## 完成结果

你能说清容器是什么、为什么本地 AI 这一摊经常用容器、以及在这台设备上让容器用到这块 GPU 需要哪两样东西。手上有一条最小可验证的命令：起一个容器，在容器里看到 `gfx1151`。你也知道容器里装的东西和宿主机上装的东西是什么关系——**哪些可以各装各的，哪些是共用的、绕不过去的**——以及容器删掉之后什么会丢、什么不会丢。

**本章还要澄清一件容易被 NVIDIA 的教程带偏的事：AMD 这条路不需要装额外的容器运行时。**

## 开始前需要准备什么

- 读过第 5 章和第 6 章，知道 `/dev/kfd` 和 `/dev/dri` 这两个名字是什么、`render` 和 `video` 两个用户组是干什么的；
- 读过第 12 章。**第 12 章在宿主机上确认过设备节点在不在、能不能读**，本章要把同样的确认在容器里再做一遍。宿主机上就不通的，容器里不会变通；
- 走 Vulkan 那条路的读者（跳过了第 11 章、没装 ROCm）：**本章前半段照样适用**。设备节点映射和用户组这两件事和 ROCm 无关。只有用 ROCm 镜像做验证的那一段用不上；
- **本章会装一个软件（Docker），并且会改一处用户组。** 两处都按本教材的规矩写全了默认值、改动条件、验证方法和恢复方法；
- 本章不改任何内核参数、不动引导配置。[第 4 卷第 18 章](../04-Max395硬件/18-不应随意修改的设置.md)的禁区清单在本章全部保持原状。

## 新词

**容器**：把一个程序和它依赖的所有东西（库、命令行工具、配置）打包在一起、和宿主系统隔开运行的方式。第 5 章新词里给过一句话的解释，本章展开。**它不是虚拟机**——虚拟机里跑的是另一个完整的操作系统，容器里没有自己的内核，用的是宿主机那一个。这一条差别是本章后半段的关键。

**镜像**（image）：容器的模板，一个打包好的只读文件集合。**镜像是死的，容器是活的**——从同一个镜像可以起很多个容器，互不影响。

**标签**（tag）：镜像名后面用冒号跟着的那一串，用来区分同一个镜像的不同版本，比如 `ubuntu:24.04` 里的 `24.04`。**不写标签就等于写了 `latest`，而 `latest` 指向的东西随时会变。** 要可重复，就把标签写全。

**宿主机**（host）：跑着容器的那台机器本身，也就是你手上这台。和“容器里”对着说。

**挂载**（mount）：把宿主机上的一个目录接进容器里，让容器能读写它。**这是容器和宿主机之间共享文件的正常做法**，模型文件就是靠它进去的。

**设备节点**：Linux 把硬件表示成 `/dev` 目录下的文件，程序通过读写这些文件来使唤硬件。这块 GPU 对应的是 `/dev/kfd` 和 `/dev/dri`（第 5 章、第 12 章）。**容器默认看不到宿主机的设备节点，要显式映射进去。**

**容器运行时**（container runtime）：真正把容器跑起来的那一层。**这个词在本章出现，是因为 NVIDIA 那条路要额外装一个，AMD 这条路不用。**

**卷**（volume）：Docker 自己管理的一块持久存储。和挂载解决的是同一类问题，区别在于卷放在 Docker 的地盘里，挂载指向你自己选的目录。**本教材只用挂载**，因为路径看得见、备份好做。

## 为什么本地 AI 这一摊经常用容器

一句话：**省掉手工编译。**

具体是三件事。

**一、依赖太多，版本互相咬。** 一套能跑起来的推理环境，底下是 ROCm 那一摞库（第 5 章），上面是 Python、PyTorch 和一堆包。这些东西的版本之间互相有要求（第 8 章表二就是在讲这个）。**镜像是别人已经把这一摞配通了之后打的包**，你直接用。

**二、有些软件在这台设备上根本没有预编译包。** vLLM 就是这样：官方文档写明 Linux x86 上对 gfx1151 只有源码编译路径，没有预编译包（vLLM v0.12.0 安装文档，访问日期 2026-08-13）。**不用容器，你就得自己编译一遍**——而第 7 章那张表里编译时共享内存超限那一条，正是编译阶段会撞上的问题。

**三、装坏了好清。** 直接装在系统里的东西，卸载不干净是常事（第 11 章末尾那一整节卸载路径就是为这个写的）。容器删掉就是删掉，宿主机上除了镜像文件不留别的。

**反过来说，容器不解决什么，本章后半段会写清楚。** 先说一句最要紧的：**容器不能给你一个不同的内核。**

## AMD 和 NVIDIA 的做法不一样

这一节是本章最容易被网上教程带偏的地方。

**NVIDIA 那条路**：要在宿主机上额外装一个容器运行时（常见名字是 NVIDIA Container Toolkit），起容器时加一个类似 `--gpus all` 的参数。**很多写“Docker 用 GPU”的教程讲的都是这一套。**

**AMD 这条路**：不装额外的容器运行时。做法是**把两个设备节点直接映射进容器**——AMD 的官方文档在讲容器里跑 vLLM 时写明要加 `--device=/dev/kfd` 与 `--device=/dev/dri`（AMD 官方文档，访问日期 2026-08-13）。

| | NVIDIA | AMD（这台设备） |
| --- | --- | --- |
| 宿主机要不要装额外的容器运行时 | 要 | **不要** |
| 起容器时怎么给 GPU | 一个 `--gpus` 之类的参数 | **两个 `--device` 映射** |
| 宿主机上要不要装计算栈 | 要装驱动 | 驱动随内核（第 2 章）；**ROCm 装不装看你走哪条路** |
| 权限怎么给 | 由运行时处理 | **靠用户组 `render` 和 `video`**（第 11 章第七步） |

**所以你搜到 `--gpus all` 在这台设备上不管用，不是你写错了，是那条命令属于另一家的做法。**

> **本表只说做法不同，不比较两家谁好。** 本教材只覆盖手上这台设备。

## 第一步：确认 Docker 装了没有

```bash
docker --version
```

- **作用**：打印 Docker 的版本号，用来确认它装没装。这条命令只读；
- **正常输出**：一行，形如

```text
Docker version 26.1.3, build 26.1.3-0ubuntu1~24.04.1
```

**版本号随你装的是哪一版变化，本项目未固定，需要核验。要看的是有没有这一行，不是数字是多少**；

- **看到别的怎么办**：
  - **提示 `command not found`** —— 没装。往下看这一节剩下的部分；
  - **有版本号，但下一步跑 `docker` 命令报连不上** —— 装了但服务没起来。看第二步；
- **怎么停止或撤销**：只读命令，不需要撤销。

**没装的话，Docker 的完整安装、镜像管理和 Docker Compose 在[第 2 卷](../02-Ubuntu/README.md)第 16 章、第 17 章。本章不重讲那一套**，只给一条最省事的装法，够跑通本章的验证。

> **⚠️ 装 Docker 会往系统里加一个常驻服务，并且会改动网络配置（它会建自己的虚拟网桥）。**
>
> 这不是替换系统核心组件，**但它是一个开机自启、一直在后台跑的东西**。零基础读者先想清楚要不要它：**只走 Vulkan 那条路跑 llama.cpp 和 Ollama 的话，本教材主线不需要 Docker**（第 17 章的预编译包解压就能用）。
>
> **恢复方法**：`sudo apt purge docker.io` 卸掉，然后 `sudo reboot`。卸载不会删掉已经下载的镜像文件，那些在 `/var/lib/docker/` 下面，要一起清掉就再跑 `sudo rm -rf /var/lib/docker`。**跑那条删除命令之前先确认你没有把重要数据放进容器卷里**。

```bash
sudo apt install docker.io
```

- **作用**：从 Ubuntu 自带的软件源装 Docker。`docker.io` 是 Ubuntu 打的包名；
- **正常输出**：一串下载和安装的进度，最后回到提示符。中间会问一次要不要继续，输入 `y` 回车；
- **看到别的怎么办**：
  - **提示 `Unable to locate package`** —— 软件源清单太旧或者没开 universe 仓库。先跑一次 `sudo apt update` 再重试（[第 1 卷第 9 章](../01-开箱与安装/09-系统更新.md)讲过这条命令的作用和它的三种写法）；
  - **提示有包冲突，或者提示已经装过 `docker-ce`** —— 这台机器上装过 Docker 官方仓库那一版。**两套不要并存**，按[第 2 卷](../02-Ubuntu/README.md)第 16 章处理，本章不展开；
  - **装完之后 `docker --version` 还是找不到** —— 重新登录一次，或者直接 `sudo reboot`；
- **怎么停止或撤销**：`sudo apt purge docker.io`，卸完重启。

> `docker.io` 这个包名、以及 Ubuntu 仓库版和 Docker 官方仓库版的差别，属于 Ubuntu 的通用行为，**本项目未针对这台设备单独实测，需要核验**。要装官方仓库那一版，按[第 2 卷](../02-Ubuntu/README.md)第 16 章走。

```bash
sudo systemctl status docker
```

- **作用**：看 Docker 那个后台服务在不在跑。`systemctl` 是管服务的命令（[第 2 卷](../02-Ubuntu/README.md)第 11 章、第 15 章）。这条命令只读；
- **正常输出**：一段状态信息，第三行左右有 `Active:` 字样，后面跟着 `active (running)`，形如

```text
● docker.service - Docker Application Container Engine
     Loaded: loaded (/usr/lib/systemd/system/docker.service; enabled; preset: enabled)
     Active: active (running) since Thu 2026-08-14 09:12:03 CST; 2min ago
```

- **看到别的怎么办**：
  - **`Active: inactive (dead)`** —— 服务没起来。跑 `sudo systemctl start docker` 起它；
  - **`Active: failed`** —— 起失败了。用 `sudo journalctl -u docker -n 30` 看最后 30 行日志，抄下来；
  - **屏幕停在那儿退不出去** —— 这条命令用的是分页显示。**按 `q` 退出**；
- **怎么停止或撤销**：只读命令，不需要撤销。要停服务是 `sudo systemctl stop docker`，**停掉之后所有容器都不跑了**。

## 第二步：让当前账户能用 Docker

装完之后直接跑 `docker` 命令，多半会报权限错误。原因是 Docker 的控制入口默认只有 root 和 `docker` 组能用。

> **⚠️ 把账户加进 `docker` 组，等于把这个账户提到了和 root 差不多的权限。**
>
> 理由是容器可以把宿主机的任意目录挂载进去并以 root 身份读写。**这一步不是本教材的必需项**——你也可以每条命令前面都加 `sudo`，效果一样，只是麻烦。
>
> **多人共用的机器、或者要交付给客户的机器，本教材建议不加，用 `sudo` 走。** 自己一个人用的开发机可以加。
>
> **恢复方法**：`sudo gpasswd -d $USER docker`，然后**重新登录**。用户组的改动不重新登录不生效，加和退都一样。

**先看现在是什么状态：**

```bash
groups
```

- **作用**：打印当前账户属于哪些用户组。第 11 章第七步跑过同一条。这条命令只读；
- **正常输出**：一行用空格分开的组名，形如

```text
roland adm cdrom sudo dip video plugdev render lpadmin
```

**这一步要看的是里面有没有 `docker`。** 顺带确认 `render` 和 `video` 也在——**这两个是 GPU 那一侧要用的，和 `docker` 组是两回事，不能互相替代**；

- **看到别的怎么办**：
  - **没有 `render` 或者没有 `video`** —— 回第 11 章第七步补上。**容器里能不能用 GPU 靠的是这两个，不是 `docker` 组**；
  - **有 `docker`** —— 这一步不用做了；
- **怎么停止或撤销**：只读命令，不需要撤销。

**决定要加的话：**

```bash
sudo usermod -a -G docker $LOGNAME
```

- **作用**：把当前账户加进 `docker` 组。`-a` 表示追加，**这个 `-a` 不能省**——省了会把你原来所在的其他组全部顶掉，包括 `sudo` 组（第 11 章第七步写过同一条注意事项）；
- **正常输出**：**除了要密码那一行，屏幕上什么都不显示。** 成功的时候这条命令不说话；
- **看到别的怎么办**：
  - **提示 `group 'docker' does not exist`** —— Docker 没装成功，回第一步；
  - **跑完 `groups` 还是没有 `docker`** —— **正常，要重新登录才生效**。注销再登录，或者 `sudo reboot`；
- **怎么停止或撤销**：`sudo gpasswd -d $USER docker`，然后重新登录。

**不加组的读者**：下面所有 `docker ...` 的命令，前面加 `sudo` 就行，其余完全一样。**本章后面的命令都按不加 `sudo` 写**，你自己补上。

## 第三步：让容器用上这块 GPU 需要哪两样东西

**只有两样。记住这两样，本章的核心就拿到了。**

**一、把两个设备节点映射进容器**

```text
--device=/dev/kfd
--device=/dev/dri
```

- `/dev/kfd` 是计算那一侧的入口（第 5 章、第 12 章）；
- `/dev/dri` 是显示与渲染那一侧的目录，里面有 `renderD128` 这类节点（第 12 章）。

**这两个映射是 AMD 官方文档写明的**（讲容器里跑 vLLM 那一篇，访问日期 2026-08-13）。**Vulkan 那条路只用得到 `/dev/dri`，ROCm 那条路两个都要。** 图省事就两个都加，多加一个不会出问题。

**二、容器里的那个用户要在 `render` 和 `video` 组里**

宿主机上的用户组（第 11 章第七步）**不会自动带进容器**。容器里跑的是容器自己的用户。处理办法有两种：

| 办法 | 怎么写 | 什么时候用 |
| --- | --- | --- |
| 用镜像里预设好的用户 | 什么都不加 | **官方的 ROCm 或 vLLM 镜像通常已经处理好了**，先按这个试 |
| 把宿主机的组编号带进去 | `--group-add video --group-add render` | 上一种不行时补这两项 |

**先按第一种试，报权限错误再加第二种那两项。** 官方镜像里预设用户的具体做法随镜像版本变化，**本项目未固定，需要核验**。

**除了这两样，不需要别的。** 不装容器运行时，不加 `--privileged`（那个参数把容器的权限全开，**本教材不用**，多数情况下用不着，而且它把容器和宿主机之间的隔离基本拆掉了）。

## 第四步：一条最小可验证的命令

分两步走。**第一步用一个通用镜像，只验证设备节点进去了；第二步用 ROCm 镜像，验证容器里认得出 `gfx1151`。**

分开走的理由：第一步不需要下载几个 GB 的大镜像，**出问题时能立刻分清是映射的问题还是镜像的问题**。

### 验证一：设备节点进到容器里了吗

```bash
docker run --rm --device=/dev/kfd --device=/dev/dri ubuntu:24.04 ls -l /dev/kfd /dev/dri
```

- **作用**：起一个 Ubuntu 24.04 的容器，把两个设备节点映射进去，在容器里列一下这两个东西在不在、权限是什么，然后容器自己退出。
  - `run` 是起一个容器并在里面执行一条命令；
  - `--rm` 表示这条命令跑完就把容器删掉，**不留垃圾**；
  - `ubuntu:24.04` 是镜像名加标签；
  - 后面的 `ls -l ...` 是要在容器里执行的那条命令。

  **第一次跑会先下载镜像**，大小约几十 MB，取决于网络，可能要等一会儿；

- **正常输出**：先是几行下载进度，然后是列出来的结果，形如

```text
Unable to find image 'ubuntu:24.04' locally
24.04: Pulling from library/ubuntu
...
Status: Downloaded newer image for ubuntu:24.04
crw-rw---- 1 root  render 234,   0 Aug 14 01:12 /dev/kfd

/dev/dri:
total 0
crw-rw---- 1 root  video  226,   0 Aug 14 01:12 card0
crw-rw---- 1 root  render 226, 128 Aug 14 01:12 renderD128
```

  **要看的是三样东西在不在：`/dev/kfd`、`card0`、`renderD128`。** 前面的权限串和后面的编号、日期随机器变化，**本项目未固定这些数字，需要核验**；

- **看到别的怎么办**：
  - **提示 `permission denied while trying to connect to the Docker daemon socket`** —— 当前账户没有 Docker 的使用权限。回第二步：要么加进 `docker` 组并重新登录，要么这条命令前面加 `sudo`；
  - **提示 `error gathering device information ... no such file or directory`，并且提到 `/dev/kfd`** —— **宿主机上就没有这个节点**。这不是容器的问题，回第 12 章。没装 ROCm 的读者也可能是这种情况，那就把 `--device=/dev/kfd` 去掉，只留 `/dev/dri` 跑一次；
  - **同样的报错但提到 `/dev/dri`** —— 宿主机上 GPU 那一层就不通。**必须回第 12 章解决**，容器里想不出办法；
  - **容器起来了，但 `ls` 报 `No such file or directory`** —— 映射参数没写对，检查有没有把 `--device=` 写成 `--devices=` 或者漏了等号；
  - **下载卡住不动** —— 网络问题。按 `Ctrl+C` 中断，换个时间或者按[第 1 卷第 9 章](../01-开箱与安装/09-系统更新.md)换软件源镜像的思路给 Docker 配镜像加速（具体做法在[第 2 卷](../02-Ubuntu/README.md)第 16 章）；
- **怎么停止或撤销**：命令跑完容器就自己删了（`--rm` 的作用），不需要撤销。中途要停按 `Ctrl+C`。下载下来的镜像还在，删它的命令在本章“停止和清理”那一节。

### 验证二：容器里看得到 gfx1151 吗

**这一步要一个装了 ROCm 的镜像。**

> **本教材不固定镜像名。** 官方镜像的名字和标签随版本滚动——AMD 的容器文档里那个基础镜像已经被主线合并淘汰过一次（AMD 官方文档，访问日期 2026-08-13），vLLM 那一侧也废弃过一批镜像（vLLM 官方文档，访问日期 2026-08-13）。
>
> **正确做法是动手当天去官方页面抄当前的镜像名**，抄的时候把页面地址和日期一起记进[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)的设备基线。**本项目未固定镜像名，需要核验。**

```bash
docker run --rm --device=/dev/kfd --device=/dev/dri \
  --group-add video --group-add render \
  你抄下来的镜像名:标签 rocminfo
```

- **作用**：起一个装了 ROCm 的容器，在里面跑 `rocminfo`。`rocminfo` 是第 14 章第一样东西，作用和输出怎么读**那一章已经写全，本章不重抄**。行末的 `\` 是把一条长命令折成多行，照抄时连着 `\` 一起抄，或者写成一行；
- **正常输出**：和第 14 章在宿主机上跑出来的应当是同一回事——一大段 agent 列表，**里面能找到 `gfx1151`**。只想看关键那一行的话，把命令末尾的 `rocminfo` 换成

```text
bash -c "rocminfo | grep gfx"
```

  输出形如

```text
  Name:                    gfx1151
      Name:                    amdgcn-amd-amdhsa--gfx1151
```

  **这两行的具体格式随 ROCm 版本变化，需要核验**（第 14 章已标注同一条）；

- **看到别的怎么办**：
  - **只看到 CPU，找不到 `gfx1151`** —— 先去宿主机上跑一遍第 14 章。**宿主机上也看不到，问题不在容器**；宿主机上看得到、容器里看不到，看下面两条；
  - **报权限相关的错，或者 `rocminfo` 只列出 CPU** —— 容器里那个用户不在 `render`、`video` 组里。命令里已经加了 `--group-add`，还不行的话，**先在宿主机上跑一遍 `groups` 确认你自己在这两个组里**（第 11 章第七步）；
  - **报 `no such file or directory` 找不到 `rocminfo`** —— 这个镜像里没装 ROCm 的工具，或者路径没配进去。换镜像，或者把命令写成 `bash -c "/opt/rocm/bin/rocminfo"` 试一次；
  - **报镜像拉不下来（`manifest unknown` 之类）** —— 镜像名或标签抄错了，也可能那个标签已经下架。**回官方页面重新抄**；
  - **镜像下载了几个 GB 之后失败** —— 磁盘空间不够或网络中断。`df -h /` 看一眼剩余空间（[第 4 卷第 13 章](../04-Max395硬件/13-SSD.md)）；
- **怎么停止或撤销**：`--rm` 保证容器跑完就删。中途按 `Ctrl+C`。**镜像本身留在磁盘上**，ROCm 类镜像通常有几个 GB，清理办法在下面一节。

**这两步都过了，容器这条路就通了。** 记住结论的形式：**通不通看的是 `gfx1151` 出现在容器里的输出中，不是容器能不能起来。**

## 容器里和宿主机上装同一套东西，区别在哪

这是本章后半段的主题。**先给一张表，再逐条解释。**

| | 容器里 | 宿主机上 |
| --- | --- | --- |
| ROCm 版本 | 各装各的，**可以和宿主机不同** | 一台机器一套（第 11 章） |
| PyTorch、vLLM 这类框架 | 各装各的，互不干扰 | 装了就是全局的 |
| 内核 | **没有自己的，用宿主机那一个** | 就是它自己 |
| AMDGPU 驱动 | **没有自己的，用宿主机那一个** | 随内核（第 2 章） |
| Mesa／RADV | 镜像里可以自带一份 | 系统自带（第 3 章） |
| 用户组权限 | 容器里的用户，要单独处理 | `render`、`video`（第 11 章第七步） |
| 删掉之后 | 容器内改的东西全没了 | 要按卸载步骤拆（第 11 章末尾） |

### 版本可以不同，但内核是共用的

**这一条是整章最要紧的一句。**

容器里可以装 ROCm 7.2，宿主机上装的是 7.0.2，或者宿主机压根没装 ROCm——**这三种情况都成立，互不影响**。因为 ROCm 的那一摞库是用户态的东西（第 5 章），打包进镜像就行。

**但内核不是。** 容器没有自己的内核，用的是宿主机开机时起来的那一个（本章新词里那句“它不是虚拟机”说的就是这件事）。所以：

> **第 8 章表二里那些跟内核有关的门槛，容器一条都绕不过。**
>
> - 内核低于 6.16.9 时 ROCm 只看得到约 15.5 GB 显存（ROCm issue #5444，已关闭并标记已解决，修复在内核侧，访问日期 2026-08-13）。**在容器里装一个更新的 ROCm，这个数字不会变。**
> - ROCm 7.2 的官方文档要求内核不低于 6.18.4（AMD 官方文档，访问日期 2026-08-13）。**拉一个 7.2 的镜像，不等于满足了那个要求。**

**AMDGPU 驱动同理**——它是内核里的模块（第 2 章），容器里没有第二份。

**所以判断顺序是这样的：**

1. **内核那一层的问题，只能在宿主机上解决**（升内核，第 21 章）；
2. **ROCm 及以上那一层的问题，可以靠换镜像绕开**；
3. **分不清是哪一层，先在宿主机上跑第 12 章和第 14 章。宿主机上就不通的，不要在容器里找答案。**

### 什么情况该用容器，什么情况直接装

| 你要做什么 | 建议 | 理由 |
| --- | --- | --- |
| 跑 llama.cpp 的 Vulkan 版本 | **直接装** | 官方有 Ubuntu 的预编译包，解压就能用（第 17 章），容器只是多一层 |
| 跑 Ollama | **直接装** | 官方安装脚本会建服务、把用户加进 `render` 和 `video` 组（Ollama 官方文档，访问日期 2026-08-13），第 6 卷第 5 章 |
| 跑 PyTorch | **两条路都行** | 直接装适合长期用一套；容器适合要同时试几个版本。第 16 章两条都给 |
| 跑 vLLM | **容器** | 官方在这台设备上不提供预编译包，只有源码编译路径（vLLM 官方文档，访问日期 2026-08-13）。**容器是绕开自己编译的那条路** |
| 要同时试两个 ROCm 版本 | **容器** | 宿主机上只能装一套，叠加安装第 11 章明确不建议 |
| 交付给客户、要能一键重来 | **容器** | 镜像名加标签写死，别人照着起就是同一套 |
| 内核相关的问题 | **都不行** | 见上一节。这类问题只能在宿主机上解决 |

**本教材主线的选择是：Vulkan 那条路直接装，vLLM 走容器，PyTorch 看你自己。** 理由在第 8 章那一节：能用 Vulkan 解决的不装 ROCm，能不多一层的不多一层。

### 数据和模型文件怎么在两边共享

**靠挂载。** 模型文件动辄几十 GB，不能打进镜像，也不该在容器里重下一遍。

```bash
docker run --rm --device=/dev/kfd --device=/dev/dri \
  -v ~/models:/models \
  ubuntu:24.04 ls -l /models
```

- **作用**：把宿主机上的 `~/models` 目录接进容器，在容器里它叫 `/models`，然后列一下里面有什么。`-v` 后面的写法是 `宿主机路径:容器里的路径`，中间一个半角冒号；
- **正常输出**：宿主机 `~/models` 目录里的文件列表。目录是空的就只有一行 `total 0`；
- **看到别的怎么办**：
  - **提示宿主机那个目录不存在** —— Docker 有的版本会替你建一个空目录，有的会报错。**先在宿主机上 `mkdir -p ~/models` 建好**，别让 Docker 替你猜；
  - **容器里能看到文件，但写不进去** —— 容器里那个用户对宿主机目录没有写权限。**只读用途本来就不该给写权限**，模型文件建议加 `:ro` 写成 `-v ~/models:/models:ro`；
  - **`~` 没有被替换成你的家目录** —— 有些写法下不会展开。改成写全的路径，比如 `/home/你的用户名/models`；
- **怎么停止或撤销**：`--rm` 保证容器跑完就删，挂载关系跟着消失。**宿主机上那个目录和里面的文件不受影响**。

**两条规矩：**

1. **模型文件放宿主机，用挂载进容器。** 不要下载进容器里——容器一删就没了，下次还得重下；
2. **挂载路径写全、写死。** 交付给客户的启动命令里，路径要能一眼看出模型在哪（第 13 卷）。

### 容器删掉之后，什么会丢什么不会丢

| 东西 | 容器删掉之后 |
| --- | --- |
| 容器里 `apt install` 装的软件 | **丢** |
| 容器里改的配置文件 | **丢** |
| 容器里下载的模型 | **丢** |
| 挂载进去的目录里的文件 | **不丢**，那是宿主机上的 |
| 镜像本身 | **不丢**，还占着磁盘 |
| 宿主机上的 ROCm、驱动、内核 | **不丢**，容器动不了它们 |

**读这张表要带走的一句话：想留下来的东西，就得在挂载进去的目录里。**

这一条有个直接后果：**在容器里一顿调试、装了一堆东西、跑通了——然后容器一删，全白干。** 正确做法是把改动记下来（写成一份启动命令加一份安装步骤），下次照着重来一遍。

**用 `--rm` 的读者不会犯这个错**，因为你从一开始就知道它跑完就没了。不加 `--rm` 起的容器会一直留着，用 `docker ps -a` 能看到，那种更容易让人误以为东西存住了。

## vLLM 在这台设备上的两条路

第 7 章那一节的结论要在这里落到具体做法上：**vLLM 截至 2026-08-13 在这台设备上不能当生产推理端点**，两条关键缺陷都还没关闭（编译时共享内存超限 vLLM issue #45871，V1 引擎图捕获挂起 vLLM issue #32180）。

**能跑通的姿势是：官方容器加 `--enforce-eager` 加纯文本模型。** 代价是性能明显下降、视觉模型不能碰。

**两条路：**

**一、用官方容器**（本教材如果要跑 vLLM，走这一条）

镜像名去 vLLM 的官方安装文档上抄当天的那个，**本项目未固定镜像名，需要核验**；素材里记录的当前官方镜像是 `vllm/vllm-openai-rocm`，**这一条本项目来源目录未收录对应条目，需要核验**。起容器的两个设备映射和上面第四步一样。

启动 vLLM 时要加的参数：

```text
--enforce-eager
```

- **作用**：关掉图捕获。**不加这个，V1 引擎在启动阶段会永久挂起**（vLLM issue #32180，2026-08-13 核对仍未关闭，AMD 项目内标记进行中）。**代价是性能明显下降**——官方 issue 里写明的绕过办法就是这样，这一条要写进给客户的说明里；
- **正常输出**：服务正常启动，日志走完初始化那几步，最后打印出监听的地址和端口。**具体措辞随 vLLM 版本变化，本项目未固定，需要核验**；
- **看到别的怎么办**：
  - **启动阶段停在某一行不动，几分钟没进展** —— 就是那条挂起缺陷。**确认这个参数确实加上了**；加了还挂的，抄下停住的那一行，去 vLLM 的缺陷页面对；
  - **报不支持 gfx1151** —— 镜像不对。回本节开头那一段，**别用旧的开发版镜像**；
  - **加载视觉模型时段错误、子进程死掉** —— 已知问题，**只跑纯文本模型**（vLLM issue #37151，访问日期 2026-08-13）；
- **怎么停止或撤销**：按 `Ctrl+C` 停掉服务，或者在另一个终端 `docker stop 容器ID`。**撤销这个参数就是下次不加它**，去掉之后大概率又挂起。

> **⚠️ 有一个网上常见的做法在这台设备上是有害的：`HSA_OVERRIDE_GFX_VERSION=11.0.0`。**
>
> 素材记录：在 vLLM 上把 gfx1151 伪装成 gfx1100 之后，HIP 计算内核与多设备通信的初始化崩溃、引擎进程直接死掉。**这条素材本项目来源目录未收录对应条目，需要核验**，但方向和第 6 章、第 7 章讲的原理一致。
>
> **本教材不用这个变量的任何写法**（第 7 章）。恢复方法：把这个环境变量从启动命令、shell 配置文件或服务配置里删掉，重启对应的服务。

**二、源码编译**（第 6 章提到过，这里给出关键那一项）

自己编译时要指定目标架构，写法是

```text
PYTORCH_ROCM_ARCH=gfx1151
```

- **作用**：告诉编译过程给 gfx1151 这个目标生成代码对象（第 6 章、第 7 章讲过为什么必须指定）。**不指定，编出来的东西认不出这块 GPU**；
- **正常输出**：编译过程一路走完，最后回到提示符。**本项目没有在这台设备上把这条路走通过，需要核验**；
- **看到别的怎么办**：
  - **报 `local memory (66032) exceeds limit (65536)`** —— 已知缺陷，**官方没有修复，用户端没有绕过的办法**，只能改源码（vLLM issue #45871，2026-08-13 核对仍未关闭）。**回上面那条路，用官方容器**；
  - **报别的编译错误** —— 抄下完整报错，连同 ROCm 版本、内核版本和 vLLM 的源码版本；
- **怎么停止或撤销**：按 `Ctrl+C` 中断编译。**完整撤销是把源码目录删掉**，编译产物都在那里面，系统里不留东西。

**本教材不推荐这条路。** 写在这里是为了让你看到别人的教程时知道那一项是干什么的。

**这一条素材记录里旧的 `rocm/vllm-dev` 那套 nightly 镜像加载模型即报不支持 gfx1151，禁用相关功能的一整套环境变量也无效**（素材记录，**本项目来源目录未收录对应条目，需要核验**）。**别走那条路。**

## 停止和清理

**看现在有哪些容器在跑：**

```bash
docker ps
```

- **作用**：列出正在跑的容器。加 `-a` 是连停掉的一起列。这条命令只读；
- **正常输出**：一行表头，下面是容器列表。**按本章的做法（都加了 `--rm`），这里应该是空的**，只有表头；
- **看到别的怎么办**：
  - **有你不认得的容器在跑** —— 先别删。用 `docker inspect 容器ID` 看它是什么，或者问装这台机器的人；
- **怎么停止或撤销**：只读命令，不需要撤销。

**停掉一个在跑的容器：**

```bash
docker stop 容器ID或名字
```

- **作用**：让容器里的程序正常退出。容器 ID 从 `docker ps` 的第一列抄，抄前几位就够；
- **正常输出**：回显那个 ID 或名字，一行；
- **看到别的怎么办**：
  - **等了十几秒还没停** —— Docker 会先客气地要求退出，超时才强杀。**长时间不停的用 `docker kill 容器ID`**，那是直接杀掉；
  - **提示 `No such container`** —— ID 抄错了，重新 `docker ps` 看一眼；
- **怎么停止或撤销**：停掉的容器可以用 `docker start 容器ID` 再起来，前提是没删。

**看镜像占了多少磁盘：**

```bash
docker images
```

- **作用**：列出本地有哪些镜像、各多大。这条命令只读；
- **正常输出**：一张表，`SIZE` 那一列是大小。**ROCm 和 vLLM 类的镜像常在几 GB 到十几 GB**；
- **看到别的怎么办**：
  - **一个都没有** —— 还没下载过，或者被清过；
- **怎么停止或撤销**：只读命令，不需要撤销。

**删掉不要的镜像：**

```bash
docker rmi 镜像名:标签
```

- **作用**：删掉一个镜像，释放磁盘；
- **正常输出**：几行 `Untagged:` 和 `Deleted:`；
- **看到别的怎么办**：
  - **提示镜像正被容器使用** —— 有容器还在用它。先 `docker ps -a` 找到那个容器，`docker rm 容器ID` 删掉再来；
- **怎么停止或撤销**：**删掉的镜像没有撤销，只能重新下载。** 网络慢的话这一步的代价不小，删之前想清楚。

## 这一章涉及的可改设置

| 设置 | 默认状态 | 改动条件 | 验证方法 | 恢复方法 |
| --- | --- | --- | --- | --- |
| 装不装 Docker | **未安装** | 要跑 vLLM，或者要同时试几个 ROCm 版本 | `docker --version` 有输出、`systemctl status docker` 是 `active (running)` | `sudo apt purge docker.io` 之后重启；镜像文件在 `/var/lib/docker/`，要清就一起删 |
| 当前账户加不加 `docker` 组 | **不加** | 自己一个人用的机器，嫌每条命令加 `sudo` 麻烦 | `groups` 输出里有 `docker`，并且 `docker ps` 不报权限错 | `sudo gpasswd -d $USER docker` 之后**重新登录** |

**本章不新增任何内核参数，不动引导配置，不改设备节点权限。** [第 4 卷第 18 章](../04-Max395硬件/18-不应随意修改的设置.md)那张禁区清单在本章全部保持原状。

## 正常结果

做完本章，你手上应当有这几样：

- `docker --version` 有输出，`systemctl status docker` 显示 `active (running)`；
- 验证一跑通：容器里能列出 `/dev/kfd`、`card0`、`renderD128`；
- 装了 ROCm 的读者，验证二跑通：容器里的 `rocminfo` 输出中出现 `gfx1151`；
- 你能说出让容器用上这块 GPU 只需要两样东西：**两个设备节点映射，加容器里那个用户在 `render` 和 `video` 组里**；
- 你知道 AMD 这条路**不需要装额外的容器运行时**，`--gpus all` 是另一家的写法；
- 你能说出容器和宿主机之间**哪些可以各装各的（ROCm、框架），哪些是共用的（内核、AMDGPU 驱动）**；
- 你知道模型文件要放宿主机、用挂载进容器，容器删掉之后只有挂载目录里的东西留得住。

## 看到不同结果怎么办

**你按网上的教程加了 `--gpus all`，报错说找不到 GPU 驱动**：那是 NVIDIA 那条路的写法。换成本章第三步的两个 `--device` 映射。

**宿主机上第 14 章能看到 `gfx1151`，容器里看不到**：按顺序查三件事——设备映射两个参数写全了没有、命令里加没加 `--group-add video --group-add render`、镜像里到底有没有 ROCm。**三件都对还不行，换一个镜像标签再试一次**，官方镜像的行为随版本变化。

**宿主机上第 14 章就看不到 `gfx1151`**：**不要在容器里找答案。** 回第 12 章和第 14 章，那两章的异常分支比本章全。

**你在容器里装了一个更新的 ROCm，显存还是只看到那么多**：显存那道门槛在内核侧（ROCm issue #5444，访问日期 2026-08-13），**容器绕不过**。要解决得升宿主机的内核，在第 21 章，**动手之前先做备份，步骤见第 9 章**。

**容器里跑得动，宿主机上跑不动（或者反过来）**：这说明差异在 ROCm 及以上那一层，不在内核。**把两边的版本抄下来对照**——容器里跑 `rocminfo`、宿主机上跑 `rocminfo`，两份输出并排放。抄进[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)的设备基线，注明哪一份是容器里的。

**磁盘被镜像占满了**：`docker images` 看大小，`docker rmi` 删不要的。**删之前确认那个镜像你还拿不拿得到**——有些标签会下架。剩余空间怎么看在[第 4 卷第 13 章](../04-Max395硬件/13-SSD.md)。

**你想给客户交付一套容器方案**：把镜像名、标签、完整的启动命令、挂载路径和核验日期一起写进交付文档。**只写“用 Docker 跑”不算交付**——标签一变，跑出来的就是另一套东西（第 13 卷）。

**你不想装 Docker**：本教材主线不强制。走 Vulkan 那条路跑 llama.cpp 和 Ollama 不需要它（第 17 章、第 6 卷）。**vLLM 那一侧确实绕不开容器或源码编译**，而 vLLM 本来就不在本教材的基准组合里（第 8 章）。
