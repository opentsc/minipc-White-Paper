## 这批材料能说明什么

这批来源能说明相关项目提供 Linux、Docker 或自托管方式，也能说明安装时要处理哪些数据和服务。

它们不能单独说明：

- 某个 Mini PC 型号一定能稳定运行。
- 本地运行一定比云端便宜。
- 用户完成教程后可以直接对外收费。
- 一个项目的官方安装命令适合直接复制进我们的交付脚本。

正式进入白皮书前，每个案例还要在指定设备、Ubuntu 版本和网络环境中跑一遍。

## 案例 0：先让一个容器跑起来

用户任务：在 Ubuntu 上安装 Docker Engine，并运行官方测试容器。

预期结果：终端显示测试容器已经运行完成。

教学内容：

- Ubuntu 软件源和系统版本。
- Docker 服务是否启动。
- 镜像和容器的区别。
- 为什么安装成功要用一个固定测试验证。
- Docker 暴露端口时与防火墙的关系。

成本或收入位置：没有。这个案例只建立后续项目的运行基础。

主要风险：Docker 官方文档说明，容器端口可能绕过 `ufw` 或 `firewalld` 规则。教程不能把“防火墙已开启”写成“容器端口一定没有暴露”。

一手来源：[Docker Engine on Ubuntu](https://docs.docker.com/engine/install/ubuntu/)

## 案例 1：给其他服务做一个监控面板

用户任务：用 Uptime Kuma 监控一个网页或局域网服务。

预期结果：浏览器打开监控面板，显示目标服务的在线状态。

教学内容：

- 容器端口映射。
- 数据卷和持久化。
- 容器自动重启。
- 服务地址和局域网地址。
- “服务进程在运行”和“用户可以访问”是两种检查。

成本或收入位置：可以作为后续维护服务的基础模块，但这一案例不证明客户会付费。

主要风险：官方安装说明指出 NFS 不适合作为 Uptime Kuma 的数据存储位置。通知渠道中的令牌不能进入公开仓库。

一手来源：[Uptime Kuma 安装说明](https://github.com/louislam/uptime-kuma/wiki/%F0%9F%94%A7-How-to-Install)

## 案例 2：让两台设备同步一个文件夹

用户任务：让电脑和 Mini PC 同步一个测试文件夹。

预期结果：一台设备中新建的测试文件出现在另一台设备上。

教学内容：

- 设备 ID。
- 本地目录和远程目录。
- 文件权限。
- 后台服务。
- 同步与备份的区别。

成本或收入位置：可以测试是否减少第三方同步空间的使用，但需要把硬盘、备份和维护成本一起计算。

主要风险：同步会把删除和错误修改传播到其他设备。教程必须另外安排版本保留或备份验证。

一手来源：[Syncthing Getting Started](https://docs.syncthing.net/intro/getting-started.html)

## 案例 3：把票据和扫描文件放进本地档案库

用户任务：把一批测试 PDF 或图片交给 Paperless-ngx，完成归档、OCR 和检索。

预期结果：用户可以在浏览器中找到文件，并查看识别后的文本和标签。

教学内容：

- Docker Compose。
- 文档入口目录、媒体目录和数据库。
- OCR 语言。
- 管理员账户。
- 更新、备份和恢复。

成本或收入位置：可以测试减少人工命名、分类和查找时间。是否节约成本，要记录原来的处理时间和人工复核时间。

主要风险：原始文件和数据库都需要备份。官方文档还说明，某些网络文件系统不支持默认的文件通知方式。

一手来源：[Paperless-ngx Setup](https://docs.paperless-ngx.com/setup/)

## 案例 4：把手机照片备份到本地图库

用户任务：在 Mini PC 上运行 Immich，把一组测试照片导入本地图库。

预期结果：用户可以在网页或客户端查看导入的照片。

教学内容：

- Docker Compose v2。
- 图片目录、上传目录和数据库目录。
- Linux 文件系统权限。
- 容量规划。
- 升级前备份。

成本或收入位置：可以比较云端照片存储订阅和本地设备成本。不能只比较月费，还要计算硬盘、异地备份和维护。

主要风险：官方要求数据库放在支持 Linux 所有权和权限的文件系统上。照片只有一份时不能称为备份。

一手来源：[Immich Requirements](https://immich.app/docs/install/requirements/) 、[Immich Quick Start](https://docs.immich.app/overview/quick-start/)

## 案例 5：在局域网播放自己的媒体文件

用户任务：用 Jellyfin 建立一个测试媒体库。

预期结果：浏览器或客户端可以播放测试视频。

教学内容：

- 媒体目录的只读挂载。
- 配置、缓存和媒体文件分开保存。
- CPU 转码与硬件加速。
- 用户权限和局域网访问。
- 日志和升级。

成本或收入位置：可以测试是否替代部分媒体管理软件或云端转码，但版权来源和共享范围必须单独处理。

主要风险：容器内的硬件加速需要设备映射。不同 CPU、GPU 和编码格式的表现不能互相替代。

一手来源：[Jellyfin Container](https://jellyfin.org/docs/general/installation/container/)

## 案例 6：运行一个家庭自动化面板

用户任务：在 Ubuntu 的 Docker 环境中运行 Home Assistant Container，并接入一个测试设备或模拟实体。

预期结果：浏览器打开 Home Assistant，看到实体状态。

教学内容：

- 主机网络模式。
- 时区。
- 配置目录。
- USB、Bluetooth 或其他设备映射。
- 长期运行和更新。

成本或收入位置：可以发展为家庭或小空间的部署服务候选，但设备兼容、现场安装和售后工时需要另外核算。

主要风险：Home Assistant Container 不包含 Home Assistant OS 的 Apps 功能。教程必须说明安装方式的差异。

一手来源：[Home Assistant on Linux](https://www.home-assistant.io/installation/linux)

## 案例 7：在浏览器里使用本地模型

用户任务：在 Ubuntu 上安装 Ollama，运行一个适合当前设备的模型，再用 Open WebUI 提供浏览器界面。

预期结果：用户可以在局域网浏览器中提交一个固定问题并获得回复。

教学内容：

- 模型下载和磁盘占用。
- CPU、GPU、内存和共享显存。
- Ollama 服务和接口。
- Open WebUI 容器、端口和持久化数据。
- 固定提示词、响应时间和输出质量记录。

成本或收入位置：可以测试把重复分类、摘要或提取任务移到本地。是否节约 API 费用，要使用同一批任务比较质量、速度、耗电、维护和人工复核。

主要风险：模型能加载不等于任务质量达标。服务只在本地网络开放，不默认暴露到公网。

一手来源：[Ollama Linux](https://docs.ollama.com/linux) 、[Open WebUI Quick Start](https://docs.openwebui.com/getting-started/quick-start/)

## 案例 8：让本地模型完成一个定时流程

用户任务：用 n8n、Ollama 和一个测试数据源完成“读取文本→本地模型分类→保存结果”的流程。

预期结果：固定输入产生一条可以检查的分类记录，失败时留下日志。

教学内容：

- 多容器编排。
- 工作流凭据。
- 定时触发。
- 本地模型接口。
- 失败重试、重复执行和人工确认。

成本或收入位置：这是“小团队自动化部署”的候选案例。收入仍来自流程设计、接入、验收和维护，不来自安装 n8n 本身。

主要风险：n8n 使用 fair-code 许可，不能直接把它描述成传统开源软件。示例中必须使用测试凭据和测试数据。

一手来源：[n8n Self-hosted AI Starter Kit](https://github.com/n8n-io/self-hosted-ai-starter-kit) 、[n8n Hosting Examples](https://github.com/n8n-io/n8n-hosting)

## 案例 9：建立一个个人文件云

用户任务：用 Nextcloud AIO 建立测试账户，并上传、下载和恢复一个测试文件。

预期结果：用户可以在浏览器中管理文件，并完成一次备份和恢复测试。

教学内容：

- 多容器服务。
- 数据目录和数据库。
- 域名、证书和本地访问。
- 更新和 BorgBackup。
- 用户账户和权限。

成本或收入位置：可以比较文件协作订阅和本地部署成本，也可以作为小团队部署服务候选。

主要风险：Nextcloud AIO 会管理多个容器，并涉及 Docker socket、端口和备份。它不适合作为第一个 Docker 教程。

一手来源：[Nextcloud All-in-One](https://github.com/nextcloud/all-in-one)

## 案例 10：让 Mini PC 执行一次代码任务

用户任务：把 Mini PC 注册为 GitHub Actions self-hosted runner，在测试仓库中执行一个固定任务。

预期结果：GitHub Actions 页面显示任务由这台 Runner 完成，并能查看对应日志。

教学内容：

- Runner 注册和标签。
- 后台服务。
- 工作目录和权限。
- 日志。
- 任务隔离和清理。

成本或收入位置：可以测试减少云端 CI 使用量，或者为内部项目提供固定构建环境。要比较使用频率、维护工时、电力和安全成本。

主要风险：工作流代码会在本地设备上执行。这个案例只用于受控测试仓库，不用于接收不可信的公开仓库任务。

一手来源：[GitHub Self-hosted Runners](https://docs.github.com/en/actions/reference/runners/self-hosted-runners) 、[Adding Self-hosted Runners](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners)

## 第一批建议

第一批只做 3 个案例：

1. Uptime Kuma：用户能看到一个面板，也能学到端口、数据卷、重启和日志。
2. Paperless-ngx：用户有自己的文件作为输入，可以学到数据目录、OCR、备份和恢复。
3. Ollama＋Open WebUI：对应 Mini PC 本地算力主线，可以开始记录模型、速度、质量和成本。

Docker 测试容器作为所有案例的共同前置步骤，不单独算成一个白皮书项目。
