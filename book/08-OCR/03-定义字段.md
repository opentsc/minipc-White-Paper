# 03　定义字段

## 这一章的任务

想清楚要从单据里抽哪几格，把它写成一份规矩交给模型。

**这一章不写代码，不跑脚本。** 产出是一个文件——`~/ai/scripts/invoice_schema.json`，第 4 章和第 5 章的脚本都读它。

**这一章是这一卷里最不像技术活、但最决定成败的一章。** 字段定歪了，后面两章跑得再顺，出来的台账也没人用；字段定对了，换一类单据也只是再写一份这样的文件（第 8 章）。

## 开始前

- [第 2 章](02-环境准备.md)做完，`ocr-vlm` 服务在跑；
- **手上有 10 张真实单据，同一类的**。发票就全是发票，别混着快递单。**这一条是本章的主要材料，没有它这一章做不了**；
- 一个文本编辑器。用[第 2 卷第 1 章](../02-Ubuntu/01-桌面与文件.md)那个文件管理器双击打开文本文件就行，或者终端里 `nano`；
- 40 分钟，其中一半时间在翻那 10 张单据。

## 新词

**schema**（结构说明）：**一份写明“数据长什么样”的说明书。** 有哪几个字段、每个字段叫什么名字、是文字还是数字、哪几个必须有。**它不是数据，是数据的模子。**

**JSON Schema**：用 JSON 写的 schema。上面那句说明书，本身也写成 JSON。**这一章产出的就是这个东西。**

**json_schema 约束**：**把 schema 交给模型，让它只能按这个模子输出。** 不是求它、不是提醒它，是从技术上让它写不出别的形状。第 4 章那个脚本里 `response_format` 那三行干的就是这件事。

**必填**（required）：schema 里标着必填的字段，**输出里这一格必须出现**。注意这句话的意思——**是必须出现，不是必须有内容**。这一条下面单说一节，**它是这一章最容易理解错的地方**。

**枚举**（enum）：**把一个字段的取值限死在几个选项里**，模型只能从里面挑一个，挑不出第五个。

**空字符串**：什么都没有的那一格，写成 `""`。**这一卷用它表示“这一格模型没读到”**，是一个信号，不是一个错误。

## 先拿 10 张真实的摊开

**不要一上来就设计 30 个字段。**

新手最常见的做法是打开一张空白发票模板，把上面每一个格子都抄进 schema——发票代码、机器编号、校验码、开票人、复核人、收款人、备注、密码区……**做完你会得到一份三十几个字段的 schema，然后发现两件事**：

- **一大半字段没人用**。下游那张台账里，财务真正会看的就那么五六列；
- **字段越多，模型出错的机会越多**，而且每多一个字段，第 7 章要校验的东西就多一条。

**正确的顺序是反的：先看你有什么，再看谁要什么。**

### 动作一：把 10 张摊开，把格子列出来

真的去做，不要凭印象。拿那 10 张单据，一张一张看过去，把**每一张上面都有的东西**记下来，把**只有几张有的东西**单独记一栏。

你会很快发现三件事：

- **有些格子并不是每张都有。** 备注栏经常是空的，购买方的地址电话时有时无；
- **有些格子每张都有，但长得不一样。** 日期有的写 `2026年07月18日`，有的写 `2026-07-18`；
- **有些格子人从来不看。** 机器编号、校验码，你自己想想上次什么时候用过它。

### 动作二：拿三个问题筛一遍

每一个候选字段，问这三句，**有一句答不上来就先划掉**：

- **这一格下游谁用？** 说得出具体的人和具体的用法——财务要用它对账、仓库要用它核数量。**说不出来的划掉**；
- **没有它会怎样？** 整行数据作废，还是只是少一列。**只是少一列的，先划掉，以后要再加**；
- **票面上一定有吗？** 十张里有九张没有的东西，抽它没有意义。

**筛完剩下的通常就是五到十个。** 这一卷主线的发票筛下来是 8 个，下面那份 schema 就是它。

> **以后要加字段随时能加。** 改一下这个 JSON 文件，重跑一次就有了。**一开始少定几个，比一开始多定二十个好得多**——多定的那些你还得一个个去核对它对不对。

## 必填和选填，是两件事

**这一节读慢一点，它是这一章最容易理解错的地方。**

“必填”这个词在这里有两个完全不同的意思，混起来会让你后面两章都别扭。

**一、schema 里的必填**（`required`）：**这一格必须出现在输出里。**

模型可以给你 `"发票号码": ""`，那也算出现了。**它管的是形状，不管内容。**

**二、业务上的必填**：**这一格必须有内容，空了这一行就没用。**

发票号码空着的那一行，进了台账也没法对账，**它得被挑出来给人看**。

**这两件事不在同一层，也不在同一章处理**：

| | schema 里的必填 | 业务上的必填 |
| --- | --- | --- |
| 管什么 | 这一格出不出现 | 这一格有没有内容 |
| 谁来管 | 模型，被 schema 约束着 | **校验代码，第 7 章** |
| 空着算不算过 | **算过** | **不算，要挑出来** |
| 写在哪儿 | 本章这份 JSON 的 `required` 里 | 第 7 章那份校验规则里 |

**所以本章这份 schema 里，八个字段全部写进 `required`。**

理由很实在：**每一格都出现，第 5 章那张表的列才对得齐。** 少一格就少一列，几百行里有的行八列有的行六列，汇总的时候要多写一堆判断。**让模型每次都把八格交齐，读不到的那格交一个空字符串**——这既省事，又给了你一个信号：**空字符串就是模型在举手说这一格我没看清。**

业务上的必填照样要定，定在纸上，等第 7 章写成代码。**本卷主线这 8 个字段里，业务上必填的是这 5 个**：

```text
发票号码
开票日期
购买方名称
销售方名称
价税合计
```

剩下三个（发票种类、金额、税额）**空着不至于让这一行作废**，但空得多了说明这批扫描件质量有问题，值得回头看。

## 哪些字段容易出错

**这一节列的东西，直接决定第 7 章要校验哪几格。** 现在心里有数，到那一章不会漏。

**一、手写体。** 手写的金额、手写的日期、签名。**这是最容易错的一类，没有之一。** 印刷体和手写体混在一张纸上的时候，模型往印刷体那边偏。

**二、印章压住的地方。** 红色的发票专用章盖在数字上，被压住的那一位可能被读成别的数，**也可能被跳过**。跳过一位的金额从 3296 变成 326，**位数变了但看上去仍然是一个正常的金额**。

**三、金额的大小写。** 票面上同一个数出现两次，一次是 `¥3296.00`，一次是 `叁仟贰佰玖拾陆元整`。**模型有时会拿大写那个去填小写那一格**，出来的东西是 `叁仟贰佰玖拾陆元整`，格式全错但内容不假。

**四、日期格式。** 同一批单据里日期写法不统一是常态。**这一卷的做法是照票面原样抄，不让模型统一格式**——统一格式这件事交给后面的程序做，模型改格式的时候顺手改错内容的事发生过。

**五、位数长的号码。** 发票号码这类十几二十位的数字串，**中间错一位你看不出来**。第 7 章会用位数和校验规则拦它。

**六、相似的字形。** 数字里的 `0` 和字母 `O`、`1` 和 `l`，中文里字形接近的字。**小字号和低分辨率下更容易混。**

**七、多栏和表格串行。** 明细行一多，模型可能把上一行的金额配到下一行的品名上。[第 6 卷第 11 章](../06-本地模型/11-视觉模型.md)写过这条毛病，**这一卷主线的 8 个字段里没有明细表，就是为了绕开它**。真要抽明细，那是第 9 章的事。

**上面七条里，第二、三、五条是能被机器拦住的**——金额加税额对不上合计、格式不对、位数不对，都能写成规则。**第一、四、六条拦不住，只能靠人抽检。** 第 7 章会把这条界线画清楚。

## json_schema 是什么，为什么非要它

### 不给约束的时候，它会怎么样

第 2 章那次 curl 你已经见过一次了——**问它图上写了什么，它给你一段话。**

这段话每次都不一样。同一张票问两遍，第一遍它可能这么开头：

```text
这是一张增值税普通发票，以下是票面信息：
发票号码是 24417000000012345678，开票日期为 2026 年 7 月 18 日……
```

第二遍它可能直接给你一段 JSON，但字段名叫 `invoice_no`；第三遍字段名变成 `发票号`；第四遍它在 JSON 前面加了一句“好的，我来帮您整理”。

**每一遍它都很配合，但每一遍的形状都不一样。** 你写的程序按第一遍的形状去取值，第二遍就取不到了。

**这不是模型不听话，是你没给它模子。** 一段自然语言的要求，它按自己的理解执行，理解每次都有一点点不同。

### 给了约束之后

`json_schema` 约束是从技术上限制它能写出什么。**服务在模型每吐一个字的时候都检查一遍这个字符合不合 schema，不合的直接不让它出现。**

结果是：

- **它写不出 JSON 以外的东西**，包括前面那句客套话；
- **字段名只能是你定的那八个**，写不出 `invoice_no`；
- **多写一个字段也不行**（下面那个 `additionalProperties` 管这件事）；
- **要求出现的那几格一定会出现**。

**所以第 4 章那个脚本拿到返回之后，可以直接 `json.loads` 解析，不用写一堆容错。** 这是这一卷能做成流水线的技术前提。

### 但它只管形状，不管对错

**这一句要记牢，它是这一卷最重要的一条边界。**

`json_schema` 保证你拿到的是一个合法的、八个字段齐全的 JSON。**它一点也不保证里面的金额是对的。**

模型读错了金额，schema 一样让它过——**因为读错的金额也是一个合法的字符串**。

**形状归 schema 管，内容归第 7 章的校验管。** 把这两件事分清楚，你就不会指望 schema 帮你解决准确率问题。

## 发票的 schema

**下面这份就是本卷主线要用的。** 在 `~/ai/scripts/` 下面新建一个文件，名字叫 `invoice_schema.json`，内容照抄：

```json
{
  "type": "object",
  "properties": {
    "发票种类": {
      "type": "string",
      "enum": ["增值税专用发票", "增值税普通发票", "电子发票", "其他"]
    },
    "发票号码": {
      "type": "string"
    },
    "开票日期": {
      "type": "string"
    },
    "购买方名称": {
      "type": "string"
    },
    "销售方名称": {
      "type": "string"
    },
    "金额": {
      "type": "string"
    },
    "税额": {
      "type": "string"
    },
    "价税合计": {
      "type": "string"
    }
  },
  "required": [
    "发票种类",
    "发票号码",
    "开票日期",
    "购买方名称",
    "销售方名称",
    "金额",
    "税额",
    "价税合计"
  ],
  "additionalProperties": false
}
```

存到这个位置：

```text
/home/你的账户名/ai/scripts/invoice_schema.json
```

**`~/ai/scripts` 是[第 2 卷第 1 章](../02-Ubuntu/01-桌面与文件.md)定的放脚本的地方**，第 4、5 章那两个脚本也放这儿，三个文件挨着。

### 逐字段说

**`"type": "object"`** —— 最外面这一层是一个对象，也就是一对大括号包着的一组字段。**发票是一张一张的，一张出一个对象。**

**`properties`** —— 下面这一层列的就是八个字段。**顺序有意义**：第 5 章那张台账的列顺序照抄这里，所以按你看单据的顺序排，别乱排。

- **`发票种类`** —— 唯一一个带 `enum` 的字段。**模型只能从那四个里挑一个**，挑不出第五个。最后那个 `其他` 是兜底——真碰上不在列表里的票种，它有地方放，不至于硬塞进前三个里。**没有兜底项的 enum 是危险的**；
- **`发票号码`** —— 票面右上角那一串。**这是台账里最要紧的一格**，去重、对账、回溯原件全靠它；
- **`开票日期`** —— 照票面原样抄，不统一格式。上面那一节说过理由；
- **`购买方名称`**、**`销售方名称`** —— 只要名称，不要纳税人识别号和地址电话。**为什么不要**：按上面那三个问题筛过一遍，识别号在这张台账里没人用。真要用，加一格就是；
- **`金额`** —— 不含税的那个数；
- **`税额`** —— 税那一格；
- **`价税合计`** —— 小写的那个数。**这三格是第 7 章校验的主角**，它们之间有一条能算的关系。

**`required`** —— 八个字段全在里面，理由上面那一节写了：**让每张票都交齐八格，台账的列才对得齐。**

**`"additionalProperties": false`** —— **不许它自己加字段。** 不写这一行的话，模型有时候会热心地多给你一个 `备注` 或者 `说明`，多出来的列会让第 5 章那张表参差不齐。

### 三条定 schema 的规矩

**一、全部用字符串，一个数字类型都不用。**

`"type": "string"`，不是 `"type": "number"`。理由有三条：

- **票面上的金额带逗号**，`3,296.00` 不是一个合法的数字，用数字类型的话模型得先替你改写，改写的时候就有可能改错；
- **要的是票面原样**，不是模型算出来的值。用数字类型等于默许它做一次转换；
- **读不到的时候要能填空**。数字类型填不了空字符串，模型只能填 `0`——**而 `0` 看起来像一个正常的金额**，比空字符串危险得多。

**校验和换算是第 7 章的事，模型这一层只负责抄。**

**二、schema 定得越死，输出越稳。**

能限死的就限死：**取值固定的用 `enum`，不许加字段用 `additionalProperties`，该出现的写进 `required`。** 每多一条约束，模型能跑偏的空间就少一块。

**三、字段名用中文。**

这一卷的字段名直接就是台账的列名，**给人看的**。写成 `invoice_no` 之后你还得再维护一张中英对照表。**目录名用英文是因为要在命令里打，字段名不用打，用中文是对的**——[第 7 卷第 2 章](../07-RAG/02-收集与整理文档.md)给文件名定过同样的规矩。

## 光有 schema 还不够，还要一句话

**schema 管形状，提示词管态度。**

同一份 schema 配不同的话，出来的东西不一样。**这一卷主线用的是下面这一段**，第 4 章的脚本里原样写着它：

```text
这是一张发票的图片。把票面上的信息读出来，严格按给定的 JSON 结构输出，
不要输出 JSON 以外的任何文字。看不清或者票面上没有的字段，填空字符串，
不要猜，也不要编。金额和日期照票面原样抄，不要换算，不要改写格式。
```

四句话，每一句都对着上面某一个坑：

- **第一句**告诉它这是什么、要干什么；
- **第二句**和 schema 说的是同一件事，**两边都说一遍，双保险**；
- **第三句是这段话里最值钱的一句**。不说这句，模型看不清的时候会按常理编一个像样的值；说了这句，它把那一格交空出来。**空字符串是信号，编出来的值是灾难**；
- **第四句**堵住金额大小写和日期格式那两个坑。

> **这段话你会改很多遍。** 跑完第 4 章那一张，看哪一格错，回来改这段话，是这一卷最常见的调整动作。**改提示词比改 schema 快，也比换模型有用。**

## 事实来源和版本日期

- **`response_format` 里 `json_schema` 约束的具体写法**（本卷用的是 `{"type": "json_schema", "schema": {...}}`）：素材记录取自 llama-server 的文档，**本项目未在这台设备上核对，需要核验**，事实状态 `candidate`。写法随 llama.cpp 版本变化，对不上时以 llama.cpp 官方文档与 `./llama-server --help` 的输出为准；**另一种常见写法是 OpenAI 那一套 `{"type": "json_schema", "json_schema": {"name": "...", "schema": {...}}}`**，第 4 章的脚本里把这两种都写在注释里了；
- **JSON Schema 里 `type`、`properties`、`required`、`enum`、`additionalProperties` 这几个关键字的含义**：属 JSON Schema 规范的通用行为，**本项目未逐项在这台设备上验证服务端实现支持到哪一层，需要核验**。**特别是 `additionalProperties` 与 `enum` 在约束解码里是否被完整执行，随实现变化**；
- **约束解码保证输出形状但不保证内容正确**：这是本教材的判断，依据是[第 6 卷第 11 章](../06-本地模型/11-视觉模型.md)已写明的“它不报错，它编”。**本章不给任何准确率数字**；
- **正文里那份 schema 的字段选择、`enum` 的四个票种、五个业务必填字段，是本教材为主线案例挑的一组起点，不是任何行业规范或票据标准**。**你自己那批单据要抽哪几格，按本章那三个问题自己筛**；
- **正文里的发票号码、金额、公司名等示例值全部为虚构**，不对应任何真实单位与真实票据；
- **各类字段的出错倾向（手写体、印章遮挡、大小写混填、日期格式、位数长的号码、相似字形、表格串行）**：[第 6 卷第 11 章](../06-本地模型/11-视觉模型.md)已写明其中几条属视觉模型的通用毛病，**本项目未在这台设备上成规模测试过各类字段的出错分布，需要核验**，事实状态 `candidate`；
- `~/ai/scripts` 放脚本、目录名用小写英文、文件名给人看用中文：[第 2 卷第 1 章](../02-Ubuntu/01-桌面与文件.md)与[第 7 卷第 2 章](../07-RAG/02-收集与整理文档.md)已定，**本章沿用不重讲**；
- 事实状态标记的含义见[证据与发布规则](../../reference/证据与发布规则.md)；
- 本章核验日期：2026-08-15。
