## 新词

**守护进程（daemon）**：在后台一直跑着、不占终端窗口、开机时自动起来的程序。Docker 就是靠一个守护进程在后台干活，你敲的 `docker` 命令只是去跟它说话。**它没起来的话，`docker` 命令什么都做不了**——本章第四节第一条讲的就是这件事。

**虚拟环境**：Python 的一种隔离方式，把某个项目要用的包全装进一个独立目录里，不和系统自带的 Python 混在一起（第 16 章第二步建过一个）。**进了虚拟环境，这个终端里的 `python` 和 `pip` 就是那个目录里的那一份。**

**系统 Python**：Ubuntu 自己装的那一份 Python。**系统里有一批工具靠它跑**，所以它不能随便装东西进去——本章第三节第一条讲的就是这件事。

**公钥（也叫 GPG 密钥）**：软件源用来给自己的软件包签名的一份文件。`apt` 拿它核对下载回来的包有没有被人改过（第 11 章新词）。**加一个新软件源时公钥要和地址一起加进来**，否则 `apt` 拒绝用这个源。

**依赖冲突**：包 A 要求包 C 是 1.0 版，包 B 要求包 C 是 2.0 版，两个要求同时满足不了。`apt` 遇到这种情况会停下来报错，**不会替你决定听谁的**。

**锁（lock）**：同一时间只允许一个程序动软件包，用一个文件当令牌。**拿着令牌的那个没跑完，别人只能等**——本章第一节第五条讲的就是这件事。

**头文件（`.h` 文件）**：编译时要用的一种文件，里面写着某个库提供哪些函数、怎么调。**装一个库通常分两个包**：跑起来要用的那个，和编译时要用的那个（名字末尾带 `-dev`）。编译报缺头文件，缺的就是后面那个。

**二进制**：编译好、敲路径就能直接运行的程序文件（第 21 章新词）。

## 一、apt 和软件源

**这一节的报错全都出现在 `sudo apt update`、`sudo apt install` 或者 `sudo apt upgrade` 之后。**

### 第一条：公钥错误

**症状**，形如

```text
W: GPG error: https://某个地址 noble InRelease: The following signatures couldn't be verified because the public key is not available: NO_PUBKEY 1234ABCD5678EFGH
E: The repository 'https://某个地址 noble InRelease' is not signed.
```

**原因**：这个软件源要求验签，但系统里没有它的公钥。三种来路——加源时只加了地址没加公钥；公钥过期了；源那边换了签名密钥。

**解决**：**分两种情况，先看是哪个源出的错。**

```bash
grep -rl "报错里那个域名" /etc/apt/
```

- **作用**：在 `/etc/apt/` 下面所有文件里找哪一份写了这个地址。`-r` 表示往子目录里找，`-l` 表示只打印文件名不打印内容。这条命令只读；
- **正常输出**：一行或几行文件路径，形如

```text
/etc/apt/sources.list.d/amdgpu.list
```

- **看到别的怎么办**：
  - **什么都没输出** —— 那个源不在这几处，可能写在 `/etc/apt/sources.list` 的注释外或者别的位置。把域名换短一点再找一次；
  - **列出的是 `ubuntu.sources`** —— **官方源出了公钥问题很少见**，多半是系统时间不对（本节第六条）或者装过什么改了钥匙串的东西。**不要动这个文件**，先看第六条；
- **怎么停止或撤销**：只读命令，不需要撤销。

**情况一，出错的是第 11 章加的 AMD 官方源。** 那个源的公钥是由官方安装器包带进来的（第 11 章第三步），**处理办法是回第 11 章第二步和第三步重新装一次那个安装器包**，本章不重抄。

**情况二，出错的是别人的源。** **本教材主线只加第 11 章那一个源**，别的都是你自己或者别人加的。做法二选一：

- **不需要它了**：按第 22 章路径三把这个源移掉，这是本教材推荐的做法；
- **确实需要它**：**回那个源的官方页面，照抄它给的加公钥命令。** 本教材不替你写这条命令——加公钥等于告诉系统“信任这个来源签的所有包”，**照抄网上随手搜到的命令是有风险的，必须从那个项目自己的官方页面抄。**

**验证**：

```bash
sudo apt update
```

- **作用**：刷新软件包清单（[第 1 卷第 9 章](../01-开箱与安装/09-系统更新.md)讲过这条命令）。**它不安装、不升级、不删除任何东西**；
- **正常输出**：一串 `命中:`、`获取:` 开头的行，**末尾没有 `W:` 也没有 `E:`**；
- **看到别的怎么办**：还是同一条公钥错，说明公钥没加成功或者加的不是这个源的。回上一步重看是哪个文件；
- **怎么停止或撤销**：这条命令只更新清单，**执行完系统里的软件版本没有任何变化**，不需要撤销。

### 第二条：404 Not Found

**症状**，形如

```text
E: Failed to fetch https://某个地址/pool/main/x/xxx_1.2.3_amd64.deb  404  Not Found [IP: 1.2.3.4 443]
E: Unable to fetch some archives, maybe run apt-get update or try with --fix-missing?
```

**原因**：三种。你手里的清单是旧的，源那边的包已经换了新版本；源的路径变了；软件源地址里的发行版代号写错了（Ubuntu 24.04 的代号是 `noble`）。

**解决**：

```bash
sudo apt update
```

- **作用**、**正常输出**、**怎么停止或撤销**：同上一条那条 `apt update`；
- **看到别的怎么办**：
  - **`update` 之后重新装就好了** —— 那就是清单旧了，最常见的一种；
  - **`update` 自己也报 404** —— 源的路径变了或者代号写错了。往下看；

```bash
grep -r "" /etc/apt/sources.list.d/ /etc/apt/sources.list
```

- **作用**：把所有软件源配置的内容连同文件名一起打印出来，方便一眼看清写了什么。这条命令只读；
- **正常输出**：每行前面是文件名，后面是那一行的内容。**要核两样**：地址对不对，发行版代号是不是 `noble`（Ubuntu 24.04 的代号）；
- **看到别的怎么办**：
  - **代号写成了别的**（`jammy`、`focal` 之类） —— 那是别的 Ubuntu 版本的代号，**这个源在你这台机器上本来就不该用**。按第 22 章路径三移掉；
  - **地址明显是拼错的** —— 同上，移掉重加；
- **怎么停止或撤销**：只读命令，不需要撤销。

**验证**：`sudo apt update` 末尾没有 `E:`，再重跑原来那条 `install`。

### 第三条：依赖冲突

**症状**，形如

```text
The following packages have unmet dependencies:
 某个包 : Depends: 另一个包 (>= 2.0) but 1.5 is to be installed
E: Unable to correct problems, you have held broken packages.
```

**原因**：要装的东西和系统上已有的东西版本对不上。**在这一卷里，最常见的来路是加了第三方软件源**（第 10 章那一整节的禁区），其次是装 ROCm 时中断过。

**解决**：**从最轻的往下走，能在上一步解决就不要进行下一步。**

**第一步，先让 apt 自己修一次。**

```bash
sudo apt --fix-broken install
```

- **作用**：让 `apt` 自己找出缺的、装错的依赖，把它们补齐或者拆掉。**这条是本章出现频率最高的一条命令**，第 11 章、第 10 章、第 22 章都用过它；
- **正常输出**：列出它打算装什么、拆什么，问 `Y/n`。**按回车之前把列出来的包名读一遍**，确认里面没有你还在用的东西。之后是滚动的安装输出；
- **看到别的怎么办**：
  - **提示 `0 upgraded, 0 newly installed, 0 to remove`** —— 它认为没有可修的。往下走第二步；
  - **它打算拆掉一大批东西，里面有 `gdm3`、`xorg` 这类** —— **按 `n` 取消。** 这说明依赖被牵连得很深，直接走第三步；
  - **中途报错停下** —— 记下报错的那个包名，走第二步；
- **怎么停止或撤销**：问 `Y/n` 时按 `n` 取消，什么都不会变。**已经跑了一半按 `Ctrl+C`**，会留下半装状态，重跑同一条命令补齐。

**第二步，看清楚是哪个源引起的。**

**这一卷里的依赖冲突，十有八九来自多加的软件源。** 用上面第二条那条 `grep -r` 看有哪些源，**不是第 11 章那个 AMD 官方源的，按第 22 章路径三移掉，再重跑 `sudo apt update` 和 `--fix-broken install`。**

**第三步，把包状态整体对回去。**

**上面两步都推不动的时候，走第 22 章路径四末尾那一条**——用第 9 章的 `02-软件包清单-可回读.txt` 把系统的包状态整体对回备份那一天的样子。**那一节前面有警告块，动手前读完。**

**验证**：

```bash
sudo apt install -f --dry-run
```

- **作用**：模拟一次“修复依赖”，`--dry-run` 表示只打印会做什么、**不真的做**。`-f` 是 `--fix-broken` 的短写法；
- **正常输出**：末尾一行形如

```text
0 upgraded, 0 newly installed, 0 to remove and 0 not upgraded.
```

  **四个数字全是 0，说明依赖已经是干净的**；

- **看到别的怎么办**：还有数字不是 0，说明没修完，回第一步再跑一次；
- **怎么停止或撤销**：这条命令什么都不动。

### 第四条：dpkg 中断

**症状**，形如

```text
E: dpkg was interrupted, you must manually run 'sudo dpkg --configure -a' to correct the problem.
```

**原因**：上一次装包或者升级跑到一半停了——断电、按了 `Ctrl+C`、终端被关掉。**系统里留下了装了一半的包**，`apt` 在这个状态下拒绝干别的活。

**这一条在这一卷里很常见**，因为装 ROCm 那一步要拆装几十上百个包，中途停下的机会不少。

**解决**：

```bash
sudo dpkg --configure -a
```

- **作用**：把所有装了一半的包配置完成。`-a` 表示“全部”。**这条命令做的是把上次没做完的事做完，不是撤销**；
- **正常输出**：几行 `Setting up 包名 ...`，然后回到提示符。**装了一半的包不多的话，几秒钟就完；ROCm 那种情况可能要一两分钟**；
- **看到别的怎么办**：
  - **报某个包配置失败** —— 记下那个包名，跑 `sudo apt install --reinstall 那个包名` 重装它，再跑一次本条命令；
  - **跑完还是报同一句 `dpkg was interrupted`** —— 跑 `sudo apt --fix-broken install`（本节第三条），再回来跑一次；
  - **报磁盘空间不足** —— 先去第二节腾地方，再回来；
- **怎么停止或撤销**：**跑到一半按 `Ctrl+C` 会让状态更乱**，尽量让它跑完。真中断了就重跑同一条。**这条命令没有“撤销”**——它是把没做完的事做完，撤销的方向是第 22 章。

**验证**：

```bash
sudo apt update
```

四件事同第一条那条 `apt update`。**跑得完、不再提 `dpkg was interrupted`，就算好了。**

### 第五条：锁被占用

**症状**，形如

```text
E: Could not get lock /var/lib/dpkg/lock-frontend. It is held by process 3421 (unattended-upgr)
E: Unable to acquire the dpkg frontend lock (/var/lib/dpkg/lock-frontend), is another process using it?
```

**原因**：另一个程序正在动软件包。**最常见的是 Ubuntu 自己的后台自动更新**（报错里那个 `unattended-upgr` 就是它），其次是你自己开了两个终端同时在跑 `apt`。

**解决**：**第一选择是等。**

```bash
ps aux | grep -i apt
```

- **作用**：列出当前正在跑的、名字里带 `apt` 的进程。`ps aux` 是列出所有进程，`grep` 负责筛。这条命令只读；
- **正常输出**：一行或几行。**要认的是有没有 `unattended-upgrade`、`apt-get`、`aptd` 这类**（末尾那一行 `grep -i apt` 是这条命令自己，不算）；
- **看到别的怎么办**：
  - **确实有一个在跑** —— **等它跑完。** 后台自动更新通常几分钟结束，隔一分钟再跑一次这条命令看还在不在；
  - **一个都没有，但锁还在** —— 上一个进程非正常退出，锁文件留下了。往下看那个警告块；
- **怎么停止或撤销**：只读命令，不需要撤销。

> **⚠️ 网上有一类做法是直接 `sudo rm /var/lib/dpkg/lock*` 把锁文件删掉。** **这台设备上不要一上来就这么做。**
>
> **真有一个进程还在动包，删了锁等于让两个程序同时改同一批文件**，结果是包数据库损坏——那比原来的问题严重得多，修起来要走第 22 章路径四甚至第六节的兜底。
>
> **正确顺序是**：先用上面那条 `ps aux` 确认没有进程在跑；确认了还是不行，**重启一次**（重启会清掉遗留的锁）；重启之后依然报同一句，再考虑删锁文件，**并且删完立刻跑 `sudo dpkg --configure -a`**（本节第四条）。

**验证**：重新跑一次原来那条 `apt` 命令，不再报锁的错就是好了。

### 第六条：系统时间不对

**症状**，形如

```text
E: Release file for https://某个地址/dists/noble/InRelease is not valid yet (invalid for another 5h 12min 3s). Updates for this repository will not be applied.
```

**原因**：这台机器的时间比实际时间早或者晚太多。**软件源的清单文件带着签发时间**，机器上的时间对不上，`apt` 会认为这份清单还没生效或者已经过期。**主板电池没电、长时间断电、BIOS 里时间设错，都会这样。**

**解决**：

```bash
timedatectl
```

- **作用**：显示系统当前的时间、时区、以及有没有在和网络时间服务器同步。这条命令只读；
- **正常输出**：几行，形如

```text
               Local time: 四 2026-08-14 10:23:41 CST
           Time zone: Asia/Shanghai (CST, +0800)
System clock synchronized: yes
              NTP service: active
```

  **要看两行**：`Local time` 和现在的实际时间差多少，`System clock synchronized` 是不是 `yes`；

- **看到别的怎么办**：
  - **时间差了好几个小时或者好几天** —— 往下走；
  - **`System clock synchronized: no`、`NTP service: inactive`** —— 网络时间同步没开，往下走；
  - **时间对、也同步着** —— **那问题不在时间上**，回索引表重找；
- **怎么停止或撤销**：只读命令，不需要撤销。

```bash
sudo timedatectl set-ntp true
```

- **作用**：打开网络时间同步，让系统自己去和时间服务器对时。**这是本章唯一一条改系统设置的命令**，改的是时间同步的开关；
- **正常输出**：**什么都不显示**（除了要密码那一行）。等十几秒再跑一次 `timedatectl`，`System clock synchronized` 应该变成 `yes`，时间也对上了；
- **看到别的怎么办**：
  - **等了几分钟还是 `no`** —— 这台机器连不上时间服务器。先确认能不能上网（第六节），或者是网络里挡掉了对时的端口，这种情况要问管网络的人；
  - **提示 `Failed to set ntp`** —— 时间同步服务没装或者被停了。跑 `sudo systemctl status systemd-timesyncd` 看状态；
- **怎么停止或撤销**：`sudo timedatectl set-ntp false` 关掉。**关掉之后时间就不自动对了**，本教材不建议关。

**时间一直不对、每次开机都要重设**：那多半是主板电池没电了，属于硬件问题，回[第 1 卷第 12 章](../01-开箱与安装/12-硬件问题处理.md)。

**验证**：`sudo apt update`，不再报 `not valid yet`。

## 二、磁盘空间不足

**症状**，形如

```text
E: You don't have enough free space in /var/cache/apt/archives/.
```

或者

```text
OSError: [Errno 28] No space left on device
```

或者编译、下载模型跑到一半突然停下，报 `No space left on device`。

**原因**：系统盘满了。**这一卷特别容易撞上，因为三样东西都很占地方**：ROCm 那一摞装完通常几个 GB；容器镜像常在几 GB 到十几 GB（第 15 章）；模型文件一个就可能几十 GB。

**解决**：**先看清楚是哪一块满了，再决定删什么。**

```bash
df -h
```

- **作用**：列出每个挂载点用了多少、还剩多少。`-h` 表示用人能读的单位。这条命令只读；
- **正常输出**：一张表，看 `已用%` 和 `可用` 两列。**要认两行**：挂载点是 `/` 的那一行（系统盘），和挂载点是 `/boot` 或者 `/boot/efi` 的那一行（如果有）；
- **看到别的怎么办**：
  - **`/` 那一行 `已用%` 到了 100%** —— 系统盘满了，往下走；
  - **`/boot` 那一行满了，`/` 还很空** —— **这是装了太多内核的典型症状**，往下看专门那一段；
  - **满的是别的挂载点**（比如你另外挂的数据盘） —— 那上面放的多半是模型文件，自己看要删哪个；
- **怎么停止或撤销**：只读命令，不需要撤销。

**第一步，清 apt 的缓存。这一步最安全。**

```bash
sudo apt clean
```

- **作用**：删掉 `apt` 下载回来的那些 `.deb` 安装包缓存。**这些包已经装完了，留着只是为了万一要重装时不用再下**，删掉不影响任何已经装好的软件；
- **正常输出**：**什么都不显示**（除了要密码那一行）。跑完再看 `df -h`，通常能腾出几百 MB 到几个 GB；
- **看到别的怎么办**：**腾出来的空间很少** —— 说明缓存本来就不多，往下走第二步；
- **怎么停止或撤销**：**没有撤销，也不需要撤销。** 删掉的都是能重新下载的安装包缓存。

**第二步，清不再需要的包和旧内核。**

```bash
sudo apt autoremove
```

- **作用**：拆掉“只因为被别的包依赖才装进来、现在没人用了”的那些包，**旧内核也归它清**（[第 1 卷第 9 章](../01-开箱与安装/09-系统更新.md)）；
- **正常输出**：列出要拆什么、问 `Y/n`。**按回车之前把列表读一遍**；
- **看到别的怎么办**：
  - **它打算拆掉你还在用的东西** —— **按 `n` 取消**，一个一个手工拆你确认不要的；
  - **它打算拆掉 `linux-image` 开头的包** —— **看清楚拆的不是 `uname -r` 报的那一个**（第 22 章路径一那个警告块）。是的话按 `n` 取消；
- **怎么停止或撤销**：问 `Y/n` 时按 `n` 取消。**已经拆掉的包要装回来，得知道包名**——所以按回车之前要把列表读一遍。

> **⚠️ `/boot` 分区满了是这一卷的常见坑。** 每装一个内核，`/boot` 里就多一份文件，装过几次之后就满了，**表现是升级时报错、甚至下次开机进不去**。
>
> **处理办法就是上面那条 `sudo apt autoremove`**，它会清掉系统判断为不再需要的旧内核。**不要手工去删 `/boot` 里的文件**——删到正在用的那一份，下次开机进不去系统（[第 1 卷第 9 章](../01-开箱与安装/09-系统更新.md)那个警告块）。
>
> **万一已经删坏了**：用恢复 U 盘进 Live 模式（[第 1 卷第 10 章](../01-开箱与安装/10-恢复介质.md)），或者走第 22 章第六节的兜底。

**第三步，找出到底是什么占了地方。**

```bash
du -sh ~/* | sort -h
```

- **作用**：算出你家目录下每一项各占多大，然后按大小从小到大排。`du` 是算目录大小，`-s` 表示只报总数不逐个列，`-h` 是人能读的单位，`sort -h` 按这种单位排序。这条命令只读；
- **正常输出**：一行一项，最后几行就是最占地方的，形如

```text
1.2M	/home/用户名/minipc-backup
4.6G	/home/用户名/llama
48G	/home/用户名/models
```

  **这一卷里最占地方的通常是模型文件和容器镜像**；

- **看到别的怎么办**：
  - **跑得很慢** —— 目录里文件多，正常。等它跑完，或者按 `Ctrl+C` 中断；
  - **报一堆 `Permission denied`** —— 有些目录你读不了，不影响结果；
  - **家目录加起来也没占多少，磁盘还是满的** —— 占地方的在系统目录里。跑 `sudo du -sh /var/* | sort -h` 看，**最常见的是 `/var/lib/docker`（容器镜像）和 `/var/log`（日志）**；
- **怎么停止或撤销**：只读命令，不需要撤销。

**容器镜像占地方的话**，第 15 章“停止和清理”那一节写过怎么看、怎么删（`docker images` 和 `docker rmi`），**本章不重抄**。那一节有一句要记住：**删掉的镜像没有撤销，只能重新下载。**

**验证**：`df -h` 里 `/` 那一行的 `可用` 回到一个合理的数。**装 ROCm 之前建议至少留 20 GB，跑模型的机器建议留得更多。**

## 三、Python 环境相关

**这一节的报错全都出现在敲 `pip` 或者跑 Python 代码的时候。** 涉及的步骤在第 16 章。

### 第一条：pip 装到系统 Python 上

**症状**，形如

```text
error: externally-managed-environment

× This environment is externally managed
╰─> To install Python packages system-wide, try apt install
    python3-xyz, where xyz is the package you are trying to
    install.
```

**原因**：**Ubuntu 24.04 起，系统自带的那份 Python 被标记成“由系统管理”**，`pip` 直接往里装东西会被拒绝。这不是故障，是保护——**系统里有一批工具靠这份 Python 跑，装乱了会连累它们。**

**解决**：**用虚拟环境，这是唯一推荐的做法。**

第 16 章第二步已经写全了三条命令（装 `python3-venv`、`python3 -m venv ~/torch-env`、`source ~/torch-env/bin/activate`），**每条都带着四件事，本章不重抄，回[第 16 章](16-PyTorch-ROCm.md)照做。**

> **⚠️ 网上有一类做法是加 `--break-system-packages` 强行装进系统 Python。** **本教材不建议在这台设备上这么做。**
>
> 这个参数的名字本身就说明了后果：**它绕过的是保护，不是障碍。** 装乱之后的典型表现是系统自带的工具报奇怪的错，而且很难查到是哪个包引起的。
>
> **万一已经这么装过了**：把装进去的包记下来，用 `pip uninstall 包名` 一个个卸掉；卸不干净、系统工具已经出毛病的，走第 22 章路径四末尾那条把包状态对回去。**建虚拟环境重来一遍，比修坏掉的系统 Python 省事得多。**

**验证**：进了虚拟环境之后（提示符前面有 `(torch-env)` 这样的括号），跑

```bash
which python3
```

- **作用**：报出这个终端里敲 `python3` 实际跑的是哪个文件。这条命令只读；
- **正常输出**：**路径里带着你的虚拟环境目录名**，形如

```text
/home/用户名/torch-env/bin/python3
```

- **看到别的怎么办**：
  - **输出是 `/usr/bin/python3`** —— **虚拟环境没进去**，提示符前面那个括号也不会有。回第 16 章第二步再跑一次 `source` 那一条；
- **怎么停止或撤销**：只读命令，不需要撤销。

### 第二条：虚拟环境没激活

**症状**：明明装过某个包，跑代码时报

```text
ModuleNotFoundError: No module named 'torch'
```

或者 `pip list` 里看不到你装过的东西。

**原因**：**虚拟环境只对当前那个终端生效**（第 16 章第二步原话）。换了一个终端窗口、关了又开、或者机器重启过，那个括号就没了，你敲的 `python3` 又变回系统那一份。

**解决**：

```bash
source ~/torch-env/bin/activate
```

- **作用**：进入这个虚拟环境。**从这一刻起，这个终端里跑的 `python` 和 `pip` 都是虚拟环境里的那一份**（第 16 章第二步讲过）。**目录名换成你自己的**；
- **正常输出**：提示符最前面多出一个括号，形如

```text
(torch-env) 用户名@minipc:~$
```

- **看到别的怎么办**：
  - **提示符没变** —— 路径写错了，或者这个终端有别的配置在干扰。换一个终端窗口重试；
  - **提示 `No such file or directory`** —— 这个虚拟环境不在。跑 `ls -d ~/torch-env*` 看实际有哪些（第 22 章路径四那条命令）；
- **怎么停止或撤销**：输入 `deactivate` 退出，括号消失。

**每开一个新终端都要跑一次这条命令。** 这是虚拟环境的设计，不是麻烦——**它保证了你不会在不知情的时候往系统 Python 里装东西。**

**验证**：跑上面第一条那条 `which python3`，路径里带着虚拟环境目录名。

### 第三条：版本冲突

**症状**，形如

```text
ERROR: pip's dependency resolver does not currently take into account all the packages that are installed.
某个包 1.2.3 requires 另一个包<2.0, but you have 另一个包 2.1.0 which is incompatible.
```

或者装完一个新包之后，原来能跑的代码报起了奇怪的错。

**原因**：同一个环境里两个包对第三个包的版本要求打架。**`pip` 会把新的那个装上，然后告诉你“这样是不兼容的”，但它不会替你回滚。**

**解决**：**本教材的做法是建一个干净的新环境，不在乱掉的环境里修。**

理由是第 16 章那句话：**虚拟环境里的东西全在一个目录里，删掉就干净了。** 修一个乱掉的环境要一个个对版本，建一个新的只要几分钟。

```bash
python3 -m venv ~/torch-env-干净的
```

- **作用**：建一个新的空虚拟环境。**旧的那个不动**——留着是为了万一新的装不出来还能回去用（第 22 章路径四）；
- **正常输出**：**什么都不显示**，几秒钟后回到提示符；
- **看到别的怎么办**：
  - **提示 `ensurepip is not available`** —— `python3-venv` 没装，回第 16 章第二步；
  - **提示目录已存在** —— 换个名字；
- **怎么停止或撤销**：`rm -rf ~/torch-env-干净的`。**这一个目录里只有包，删了不影响别的。**

**然后按第 16 章第三步在新环境里装东西。** **一次装一个、装完验一次**，这样出问题时你知道是哪一个引起的。

> **本项目给不出 PyTorch 在这台设备上可推荐的版本号，需要核验**（第 8 章表一那一行）。已知的三条相关记录用的都是每日构建，**不能当作版本推荐**。所以“装哪一版”这件事没有标准答案，**做法是你自己选一版、装进新环境、跑第 16 章那两段验证代码，通过了就把版本号和日期记进[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)的基线。**

**验证**：在新环境里跑第 16 章那两段验证代码，两段都过。

## 四、Docker 相关

**这一节的报错全都出现在敲 `docker` 命令的时候。** 涉及的步骤在第 15 章。

### 第一条：守护进程没起来

**症状**，形如

```text
Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?
```

**原因**：Docker 靠一个后台守护进程干活（本章新词），**你敲的 `docker` 命令只是去跟它说话**。它没起来，命令就没人接。三种来路——没装、装了但没启动、启动失败了。

**解决**：**先看它是什么状态。**

```bash
sudo systemctl status docker
```

- **作用**：查 Docker 这个后台服务现在是什么状态。`systemctl` 是管系统服务的命令。这条命令只读；
- **正常输出**：几行，第三行左右形如

```text
     Active: active (running) since Thu 2026-08-14 09:12:03 CST; 1h 11min ago
```

  **`active (running)` 就是正常。** 输出可能占满屏幕并停住等你按键，**按 `q` 退出**；

- **看到别的怎么办**：
  - **`inactive (dead)`** —— 没启动，往下走；
  - **`failed`** —— 启动失败了。看后面几行的报错，最常见的是磁盘满（第二节）；
  - **提示 `Unit docker.service could not be found`** —— **Docker 根本没装**。回第 15 章第一步；
- **怎么停止或撤销**：只读命令，不需要撤销。**输出停住不动时按 `q`。**

```bash
sudo systemctl start docker
```

- **作用**：把 Docker 的守护进程启动起来。**这一次有效，机器重启之后按系统的设置来**；
- **正常输出**：**什么都不显示**（除了要密码那一行）。跑完再跑一次上面那条 `status`，应该变成 `active (running)`；
- **看到别的怎么办**：
  - **提示 `Job for docker.service failed`** —— 启动失败。跑 `sudo journalctl -u docker -n 30` 看最后 30 行日志，**最常见的原因是磁盘满**（第二节）；
  - **启动了但过几秒又挂了** —— 同上，看日志；
- **怎么停止或撤销**：`sudo systemctl stop docker` 停掉它。**停掉之后所有容器都会停**，跑着东西的时候不要停。

**验证**：

```bash
docker ps
```

- **作用**：列出正在跑的容器（第 15 章“停止和清理”那一节讲过）。这条命令只读；
- **正常输出**：一行表头，下面可能是空的。**能跑出表头就说明守护进程通了**；
- **看到别的怎么办**：还是报连不上，回上一条看状态；报权限错，去下一条；
- **怎么停止或撤销**：只读命令，不需要撤销。

### 第二条：权限

**症状**，形如

```text
permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock
```

**原因**：你这个账户没有和 Docker 守护进程说话的权限。**这和第 12 章第四项那个 GPU 权限问题是同一类**——都是用户组的事，都要重新登录才生效。

**解决**：**第 15 章第二步已经写全了做法**（把当前账户加进 `docker` 组，然后注销重新登录），**本章不重抄，回[第 15 章](15-Docker使用GPU.md)那一步。**

**本章补两句：**

- **加完组必须注销重新登录**，或者干脆重启。**已经登录的这个会话不会自动更新**——这句话第 11 章新词里写过，在这里同样成立。**改完之后原地重跑命令还是报同样的错，十有八九是这个原因；**
- **临时救急可以在命令前面加 `sudo`**（`sudo docker ps`）。**这只是绕过去，不是解决**，而且用 `sudo` 跑出来的容器和不用 `sudo` 跑出来的互相看不见，容易搞混。**本教材建议按第 15 章加组，不要长期用 `sudo` 跑 docker。**

**验证**：注销重新登录之后，**不带 `sudo`** 跑 `docker ps`，能跑出表头。

### 第三条：拉镜像失败

**症状**，三种，形如

```text
Error response from daemon: Get "https://某个地址/v2/": net/http: request canceled while waiting for connection
```

```text
Error response from daemon: manifest for 某个镜像:某个标签 not found: manifest unknown
```

```text
failed to register layer: write /usr/lib/...: no space left on device
```

**原因**：分别是网络连不上、镜像名或标签写错、磁盘满。

**解决**：**先看是哪一种。**

- **第一种（超时、连接被取消）** —— 网络问题，去第六节；
- **第二种（`manifest unknown`）** —— 镜像名或者标签写错了。**这一卷里最容易撞上的一次是 vLLM 的官方镜像换过**：官方废弃了旧镜像、统一到当前的官方镜像（vLLM 官方安装文档，访问日期 2026-08-13）。**照着旧教程抄镜像名，就会撞上这个错。** 做法是回那个项目的官方页面核对当前的镜像名和标签，**并把你核对的日期记下来**；
- **第三种（`no space left on device`）** —— 磁盘满，去第二节。**容器镜像常在几 GB 到十几 GB**（第 15 章），是这一卷里最占地方的东西之一。

**关于标签，第 15 章新词里那句话在这里要重复一遍**：**不写标签就等于写了 `latest`，而 `latest` 指向的东西随时会变。** 要可重复，就把标签写全，并且记下来。

**验证**：

```bash
docker images
```

- **作用**：列出本地有哪些镜像、各多大（第 15 章讲过）。这条命令只读；
- **正常输出**：一张表，刚拉下来的那个镜像在里面，`SIZE` 那一列是它的大小；
- **看到别的怎么办**：表里没有它，说明没拉成功，回上面看是哪一种；
- **怎么停止或撤销**：只读命令，不需要撤销。**要删镜像用 `docker rmi`**，第 15 章那一节有，**删掉的镜像没有撤销，只能重新下载。**

## 五、编译相关

**这一节的报错出现在第 18 章那条路上**（自己编译 llama.cpp 的 HIP 版）。

### 第一条：缺头文件

**症状**，形如

```text
fatal error: curl/curl.h: No such file or directory
    5 | #include <curl/curl.h>
      |          ^~~~~~~~~~~~~
compilation terminated.
```

**原因**：编译要用的那个库，系统上只装了“跑起来要用的那一半”，没装“编译时要用的那一半”（本章新词里的头文件）。**Ubuntu 把这两半拆成了两个包，编译时要用的那个名字末尾带 `-dev`。**

**解决**：**先看报错里缺的是哪个头文件，再找对应的包。**

第 18 章第二步已经写了这条路要装的编译工具（`build-essential`、`cmake`、`git`、`libcurl4-openssl-dev`），**大多数缺头文件的报错是那一步漏了某一项**，回[第 18 章](18-llama.cpp-HIP.md)第二步照做一遍就解决了。

**报错里的头文件不在那一步的清单里**，用下面这个办法找包名。

```bash
sudo apt install apt-file && sudo apt-file update
```

- **作用**：两条。第一条装 `apt-file` 这个工具，它能查“某个文件属于哪个软件包”；第二条让它把文件清单下载下来。**第二条要下载几十 MB，慢的话是正常的**；
- **正常输出**：第一条是常规安装输出；第二条是下载进度，最后回到提示符；
- **看到别的怎么办**：
  - **提示 `Unable to locate package`** —— 先 `sudo apt update` 再重试；
  - **第二条下载卡住** —— 网络问题，去第六节；
- **怎么停止或撤销**：`sudo apt purge apt-file` 卸掉。**这是个只用来查东西的小工具，留着不占什么地方。**

```bash
apt-file search curl/curl.h
```

- **作用**：查哪个软件包里有这个头文件。**把 `curl/curl.h` 换成你报错里那个**。这条命令只读；
- **正常输出**：一行或几行，冒号前面是包名，形如

```text
libcurl4-openssl-dev: /usr/include/x86_64-linux-gnu/curl/curl.h
```

  **冒号前面那个就是要装的包**；

- **看到别的怎么办**：
  - **什么都没输出** —— 清单没下载完，重跑一次 `sudo apt-file update`；或者这个头文件不来自 Ubuntu 官方源，**那多半是 ROCm 那一摞里的，回第 11 章确认 ROCm 装全了**；
  - **列出好几个包** —— 挑名字最像、末尾带 `-dev` 的那个；
- **怎么停止或撤销**：只读命令，不需要撤销。

```bash
sudo apt install 上一步查到的包名
```

- **作用**：装上那个开发包。**包名照上一步的输出原样抄**；
- **正常输出**：常规的安装输出，问 `Y/n`，按回车装完；
- **看到别的怎么办**：
  - **提示 `Unable to locate package`** —— 包名抄错了，或者要先 `sudo apt update`；
  - **提示要拆掉一大批东西** —— **按 `n` 取消**，这是依赖冲突，去第一节第三条；
- **怎么停止或撤销**：`sudo apt purge 那个包名` 再 `sudo apt autoremove`。

**验证**：回第 18 章第五步重跑编译，**同一个头文件不再报错**。**通常会接着报下一个缺的头文件**，那是正常的——按同样办法一个一个补。

### 第二条：编译时内存不够被杀

**症状**，形如

```text
c++: fatal error: Killed signal terminated program cc1plus
compilation terminated.
```

或者

```text
g++: internal compiler error: Killed (program cc1plus)
```

**原因**：**编译进程被系统杀掉了**，因为内存不够。编译时同时开的进程越多，吃的内存越多；这台机器上还有一层特殊情况——**显存是从系统内存里划的**（[第 4 卷第 6 章](../04-Max395硬件/06-UMA与GTT.md)），要是同时有模型在跑，可用内存会更紧。

**这一条不是 GPU 的问题，所以收在本章不收在第 20 章**——换任何一台内存紧张的机器编译大项目都会遇到。

**解决**：**先确认真的是被杀了。**

```bash
sudo dmesg | grep -i "killed process"
```

- **作用**：在内核日志里找有没有“某个进程被杀掉了”的记录。`dmesg` 是看内核日志（第 12 章、[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)用过）。这条命令只读；
- **正常输出**：**编译确实是被杀的话**，能看到一行形如

```text
[12345.678] Out of memory: Killed process 8899 (cc1plus) total-vm:8123456kB ...
```

  **看到 `cc1plus` 或者 `c++` 这类名字，就确认了**；

- **看到别的怎么办**：
  - **一行都没有** —— **不是内存的问题**。把编译的完整报错抄下来，回第 18 章“看到不同结果怎么办”那一节；
  - **被杀的是别的进程名**（比如 `ollama`、`llama-cli`） —— 那是跑模型时的内存问题，不是编译问题。第 20 章第三节；
- **怎么停止或撤销**：只读命令，不需要撤销。

**做法是把并行数调小。** 第 18 章第五步用的是 `-j 8`，**改成 `-j 4` 或者 `-j 2` 再编一次**。第 18 章那张“这一章涉及的可改设置”表里写着这一行：**机器卡就调小，改数字重跑。**

**编译之前先把跑着的模型停掉**，也能腾出一大块内存。怎么看现在有什么在跑，第 19 章第一节讲过。

**验证**：重新编译能跑完，第 18 章第六步能看到 `gfx1151`。

## 六、网络相关

**症状**：下载慢到几十 KB/s、`apt update` 卡很久、下到一半断掉、报

```text
Could not connect to 某个地址:443 (1.2.3.4). - connect (110: Connection timed out)
```

**原因**：这一卷要下载的东西大多在国外的服务器上——Ubuntu 官方源、AMD 的软件源、GitHub 的发布页、容器镜像仓库、模型文件。**国内网络访问这些地方，慢和断都很常见。**

**解决**：**分三种情况。**

### Ubuntu 官方源慢

**换成国内镜像站。** [第 1 卷第 9 章](../01-开箱与安装/09-系统更新.md)“换软件源镜像（国内网络）”那一整节已经写全了——**先备份、用图形界面换源、换完之后验证、出错怎么还原**，四步都有。**本章不重抄，回那一章。**

**换完之后回来重跑本章第一节那条 `sudo apt update`**，末尾没有 `E:` 就是好了。

### AMD 的软件源慢或者连不上

**这一条本教材给不出镜像方案。** 第 11 章加的是 AMD 官方源，**本项目来源目录没有收录“AMD ROCm 软件源的国内镜像”的条目，事实状态是待核验。**

**能给的做法是两条：**

- **重试。** 断流常常是一次性的，`sudo apt update` 再跑一次往往就过了；
- **在网络好的时段做。** 装 ROCm 那一步要下载几个 GB（第 11 章第五步会先告诉你要下多少），**中途断了就要走第 22 章路径二重来**，不如挑网络稳的时候一次做完。

### GitHub 的发布页下不动

第 17 章下载 llama.cpp 的预编译包、第 18 章拉源码，都要访问 GitHub。

**本教材的做法是：用浏览器下载，不用命令行下载。** 第 17 章第二步就是这么写的——**浏览器能显示进度、能断点续传、失败了能重来**，比在终端里干等强。下载到 `~/Downloads` 之后再按第 17 章第三步解压。

**下载模型文件时**，本项目来源目录收录过一个镜像站的条目（用于 GGUF 模型仓库的文件页），**它是社区转档仓库的镜像，不是模型原厂，页面随仓库更新变化，访问日期 2026-08-13**。模型下载属于[第 6 卷](../06-本地模型/README.md)的范围，**本卷不展开。**

### 通用的两条

**一、下载之前先看要下多少。** `apt` 在问 `Y/n` 之前会告诉你“需要下载 xxx MB”（[第 1 卷第 9 章](../01-开箱与安装/09-系统更新.md)）；`docker pull` 会显示每一层的进度。**心里有数，才知道卡住是不是不正常。**

**二、断了之后重跑同一条命令。** `apt` 和 `docker pull` 都支持接着上次下——**已经下完的那部分不会重下**。这一点和从头再来差别很大。

**验证**：把原来那条命令重跑一遍，能跑完。

## 看到不同结果怎么办

**你的报错和索引表里的关键词对不上**：先按本章开头那个分工判断——**报错里有没有 GPU 相关的字样**。有就去第 20 章；都没有就去[第 15 卷](../15-故障排查/README.md)。

**一条命令报了好几个错，不知道看哪一个**：**看第一个。** 后面那些常常是被第一个拖出来的，第一个解决了后面往往跟着消失。

**按本章做完之后，出现了另一个错**：**这是正常的**，尤其是缺头文件那一条——补一个接着报下一个。按索引表继续找就是。

**同一个错反复出现**：说明根因没解决。**最常见的两种情况**：软件源那一层没干净（回第一节第三条第二步，看有没有多余的源），或者磁盘一直在满（回第二节，看是不是有东西在持续写）。

**本章的办法试了不管用**：**先确认你试的那一条对应的症状确实是你看到的那个。** 报错原文抄全（包括第一行和最后一行）、连同你的环境（Ubuntu 版本、内核版本、你在做哪一章的哪一步）一起记下来，再往[第 15 卷](../15-故障排查/README.md)走。

**你想一次改好几项来碰运气**：**不要。** 一次只改一项，改完验证一次。这句话[第 4 卷第 10 章](../04-Max395硬件/10-功耗模式.md)定过、第 20 章和第 21 章都重申过。

**你在给客户排障，要给一个时间承诺**：**能承诺的是排查步骤和一个明确的降级方案，不是修复时间。** 这句话第 20 章那一节写过，在本章同样成立。

**排查过程中你改了系统里的东西**：**每改一处记一处**，包括改了什么、改之前是什么、怎么改回去。这是[第 4 卷第 18 章](../04-Max395硬件/18-不应随意修改的设置.md)那一整章的做法，**排障时最容易忘。**
