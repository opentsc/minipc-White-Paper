# 07　多模型切换

## 这一章的任务

在这台机器上装几个模型，用的时候按需要换。

前面六章从头到尾只用了一个模型。真用起来很快会不够——问代码的时候想要一个会写代码的，丢张图进去的时候想要一个能看图的。**这一章解决“装几个”和“怎么换”这两件事**，最后给一套常备组合。

## 开始前

- 第 3 章做完，`ollama list` 和 `ollama ps` 能跑；
- 第 4 章做完，浏览器里能对话；
- 第 1 章那两张对照表在手边，**这一章挑模型全按它，不重抄**；
- 硬盘还有几十 GB 空间。先看一眼 `df -h ~`（[第 2 卷第 5 章](../02-Ubuntu/05-磁盘与空间.md)）；
- 40 分钟，下载时间另算。

## 新词

**加载**（load）：把模型文件从硬盘读进内存。**读完才能对话**，几十 GB 的模型这一步要等十几秒到几分钟。

**卸载**（unload）：把模型从内存里放出来，那块内存还给系统。**硬盘上的文件还在**，下次用再加载一遍。

**常驻**：让模型一直留在内存里不卸载。省掉每次的加载等待，代价是那块内存一直被占着。

## 装几个模型，占的是硬盘，不是内存

**这是这一章第一件要想通的事。**

模型装在硬盘上，一个模型一份文件。装十个就占十份硬盘。**内存只在加载的时候才被吃掉**——没在用的模型躺在硬盘上，一个字节内存都不占。

所以“这台机器能装几个模型”和“这台机器能同时跑几个模型”是两个问题：

- **能装几个，看硬盘。** 一块 1 TB 的固态硬盘装十几个 20 GB 的模型没问题；
- **能同时跑几个，看内存。** 第 1 章那条 90 GB 的权重预算管的是这一头——**所有同时加载着的模型加起来**不超过它。

想通这一条，后面就好办了：**多装几个是很便宜的事，多加载几个才要算账。**

## 盘上有什么

```bash
ollama list
```

作用：列出这台机器上已经有哪些模型。这条命令只读，第 3 章速查表里有。

正常输出是一张表：

```text
NAME                  ID              SIZE      MODIFIED
qwen3.6-35b:latest    a1b2c3d4e5f6    22 GB     2 days ago
qwen3:4b              f6e5d4c3b2a1    3.3 GB    3 days ago
```

四列的意思是：名字、内部编号、**占多大硬盘**、上次改动是什么时候。

**`SIZE` 这一列是硬盘占用，不是内存占用。** 内存那一头看下面的 `ollama ps`。

删掉一个：

```bash
ollama rm qwen3:4b
```

作用：把这个模型从硬盘上删掉。正常输出一行 `deleted 'qwen3:4b'`。

**删掉的是 Ollama 自己那个模型目录里的那一份。** 第 3 章走路二导进来的模型，`~/ai/models` 下面那个原始的 `.gguf` 文件不受影响——那是两份东西（第 3 章讲过可能占两份空间）。真要腾空间，两边都要看一眼。

删之前想清楚一件事：**删掉再想用就要重新下一遍**，几十 GB。硬盘还宽裕就先留着。

## 在 Open WebUI 里换模型

第 4 章讲过左上角那个模型选择框。这里补三点日常会用到的。

**一、每次新建对话都能选。** 换个话题就新建一个对话，顺手把模型也换了。

**二、对话中途也能换。** 在同一个对话里换模型，前面的聊天记录会跟着送给新模型——**这是好事也是坏事**：好在能接着聊，坏在前面那个模型说的话成了新模型的输入，它有时候会顺着往下编。**换模型之后要是发现答得怪，先新建一个对话再问一遍。**

**三、列表里没有你刚装的那个。** 刷新一下页面。还是没有，说明 Open WebUI 那一头没重新读 Ollama 的模型列表，回第 4 章那四步查连接。

## 内存里有什么

```bash
ollama ps
```

作用：列出**当前加载在内存里**的模型。第 3 章用它确认过 GPU，这一章用它看内存。

正常输出：

```text
NAME                  ID              SIZE      PROCESSOR    UNTIL
qwen3.6-35b:latest    a1b2c3d4e5f6    24 GB     100% GPU     4 minutes from now
```

**和 `ollama list` 比，多了两列**：

- **`PROCESSOR`** —— 跑在哪儿。要的是 `100% GPU`，怎么读、看到别的怎么办，[第 3 章](03-Ollama.md)那一节已经写全，**本章不重讲**；
- **`UNTIL`** —— 还有多久被卸载。这一列是下面两节的主角。

**这里的 `SIZE` 比 `ollama list` 里的大一点**，因为它算的是运行占用，比权重文件多出 KV cache 和计算缓冲那两块（第 1 章那条公式）。

**一行都没有，就是内存里现在什么都没加载。** 去问一句话它就回来了。

想马上把它请出去：

```bash
ollama stop qwen3.6-35b
```

作用：把这个模型从内存里卸下来，硬盘上的文件不动。**要腾内存给另一个大模型的时候用它**，比干等着自动卸载快。

## 同时加载两个会怎样

先说结论：**放得下就并存，放不下就不并存。**

Ollama 允许同时加载多个模型，上限由一个环境变量控制：

```text
OLLAMA_MAX_LOADED_MODELS
```

官方文档的说法是，它管“最多有几个模型可以同时加载，**前提是可用内存放得下**”，默认值是 GPU 数量乘以 3，纯 CPU 推理时是 3（Ollama FAQ，访问日期 2026-08-14）。这台机器一块 GPU，所以默认是 3。

**默认值对多数人够用，不用去改。** 真要改，用第 3 章那套动作：

```bash
sudo systemctl edit ollama
```

在两行注释之间的 `[Service]` 段里加一行 `Environment="OLLAMA_MAX_LOADED_MODELS=2"`，然后 `sudo systemctl daemon-reload` 加 `sudo systemctl restart ollama`。**这台机器上已经有的那几行环境变量写在同一段里，一行一个**（第 4 章讲过）。

### 内存不够的时候

按官方文档那句“前提是放得下”，**内存放不下第二个模型时，Ollama 不会硬塞**。

试一次就知道了：先让一个 22 GB 的模型加载着，再去问另一个模型一句话，然后跑 `ollama ps` 看两个还在不在。

> **放不下的时候它到底是先卸旧的、还是拒绝加载、还是把一部分层甩到 CPU 上，本项目没有在这台设备上实测过，需要核验。** 你自己试出来的结果记进第 16 章那张测试表。

**能确定的是表现不会是“报一个明白的错”**——最容易撞上的是第 3 章说过的那种：`ollama ps` 里 `PROCESSOR` 从 `100% GPU` 变成混合值，模型还能答，只是慢了好几倍。**换模型之后觉得变慢，先跑一次 `ollama ps`。**

### 一个更省事的做法

**别追求同时加载。** 这台机器加载一个 20 GB 的模型只要十几秒，日常来回切两个模型，等待完全可以接受。

**真正需要并存的场景只有一种**：几个人同时在用，各用各的模型。那属于并发，在第 15 章。

## 什么时候卸载，怎么让它常驻

**默认是 5 分钟。** 官方文档写明模型在内存里留 5 分钟没人用就被卸掉（Ollama FAQ，访问日期 2026-08-14）。`ollama ps` 的 `UNTIL` 那一列显示的就是这个倒计时。

这个默认值挺合理：偶尔用一次不占着内存，连着用的时候也不会每句话都重新加载。

不合适的场景有两种。

**一、你希望它随叫随到。** 家里人晚上零零散散地问，每次都要等十几秒加载。让它常驻：

```bash
sudo systemctl edit ollama
```

在 `[Service]` 段里加一行：

```ini
Environment="OLLAMA_KEEP_ALIVE=-1"
```

然后 `sudo systemctl daemon-reload`、`sudo systemctl restart ollama`。

`-1` 的意思是不自动卸载。官方文档说这个变量收一个时长写法（例如 `10m`）、一个秒数、负数表示一直留着、`0` 表示用完立刻卸（Ollama FAQ，访问日期 2026-08-14）。

**常驻的代价要说清楚**：那个模型的内存从此一直占着，直到你 `ollama stop` 或者重启服务。一个 22 GB 的模型常驻，第 1 章那 90 GB 的预算就先去掉 22 GB。**只让日常那一个常驻，别三个都常驻。**

**二、你要马上腾内存。** 不等 5 分钟，直接 `ollama stop 模型名`。

## 建议的常备组合

装三个，各管一摊。**三个都按第 1 章那两张表挑**，加起来的硬盘占用和内存占用都留足余量。

| 用途 | 模型 | 仓库 | 推荐档 | 大概占多少 |
| --- | --- | --- | --- | --- |
| 日常对话 | Qwen3.6-35B-A3B | `unsloth/Qwen3.6-35B-A3B-GGUF` | UD-Q4_K_M | 22.1 GB |
| 代码 | Qwen3-Coder-30B-A3B-Instruct | `unsloth/Qwen3-Coder-30B-A3B-Instruct-GGUF` | Q4_K_M | 18.6 GB |
| 视觉 | Muse-Glimmer-30B | `unsloth/Muse-Glimmer-30B-GGUF` | UD-Q4_K_XL 加 mmproj | 15.9 GB 加 2.05 GB |

**文件大小取自 2026-08-14 的仓库文件列表，下载当天以页面上标的为准。**

三个加起来约 59 GB 硬盘。**三个同时加载也在第 1 章那 90 GB 的权重预算里**，所以真要三个并存也放得下——不过按上一节的建议，日常用不着。

### 为什么这样配

**日常对话那个就是主线用的那个，第 2 章已经下好了。** 它是 MoE，35B 总参数每个 token 只激活 3B，出字不慢；中文能用；原生上下文长；**而且它自带视觉能力**——第 2 章顺手下的那个 `mmproj-F16.gguf` 就是干这个的（第 11 章讲怎么用）。

**代码那一格挑了轻的那个，不是最强的那个。** 第 1 章那张表里代码模型还有一档 49.6 GB 的（第 10 章讲），比这个强，但也重得多。日常在编辑器里连着用，**加载快、出字快比“再聪明一点”值钱**。真要啃一个大工程再换重的那个。

**视觉那一格严格说可以空着**，因为日常那个模型本身就能看图。单独列一格的理由是：Muse-Glimmer-30B 只有 15.9 GB，**加载比 35B 那个快，看一眼截图这种小事用它更顺手**；它也是给第 9 卷那些 agent 场景留的一个备选。**只想装两个的话，就把这一格去掉，看图交给日常那个。**

### 装法

**下载流程第 2 章已经讲全了，这里只给仓库名和一行命令。**

代码那个：

```bash
hf download unsloth/Qwen3-Coder-30B-A3B-Instruct-GGUF --include "*Q4_K_M*" --local-dir ~/ai/models/qwen3-coder-30b
```

视觉那个（**两个文件都要下**，`mmproj` 那个是看图用的投影文件）：

```bash
hf download unsloth/Muse-Glimmer-30B-GGUF Muse-Glimmer-30B-UD-Q4_K_XL.gguf mmproj-Muse-Glimmer-30B-Q8_0.gguf --local-dir ~/ai/models/muse-glimmer-30b
```

下完照第 3 章那套写 Modelfile、`ollama create` 导进去。**懒得写 Modelfile 的话，Ollama 的模型库里这两个都有**，直接拉：

```bash
ollama pull qwen3-coder:30b
ollama pull muse-glimmer:30b
```

**这两个名字是 2026-08-14 在 Ollama 模型库里查到的，库里的条目随时增删**，动手当天去 `ollama.com/library` 上看当前有什么。两条路的取舍第 3 章那张表已经写清，**本章不重讲**。

ollama list

三个都在，`SIZE` 加起来和上面那张表对得上，这一节就完成了。
