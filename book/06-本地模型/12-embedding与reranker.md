## 新词

**向量**（vector）：一串排好队的数字，例如 `[0.13, -0.42, 0.77, ...]`。**它就是一串数，没有别的含义**，意思由生成它的模型赋予。

**embedding**（嵌入）：把一段文字变成一个向量的过程，也指变出来的那个向量。**这一章装的第一个模型干的就是这件事。**

**维度**（dimension）：那串数字有多长。一个 embedding 模型的维度是固定的，同一个模型吐出来的每个向量都一样长。

**相似度**（similarity）：两个向量有多接近，算出来是一个数。**数大就是这两段文字意思接近。**

**检索**（retrieval）：从一堆文字里找出跟问题相关的那几段。**知识库的第一步永远是检索**，找不对，后面模型说得再流利也没用。

**reranker**（重排模型）：把检索出来的一批结果重新排一遍顺序的模型。**这一章装的第二类模型干的是这件事**，它本章不装，往下有一节说清为什么。

**知识库**：一堆文档被切成小段、算成向量、存起来，以后能按意思去搜的那一套东西。[第 7 卷](../07-RAG/README.md)整卷讲它。

## 关键词搜不出来的那些东西

先说清楚为什么需要这两个模型。

假设你把公司的一堆制度文件丢进机器，然后问一句“东西买回来不满意怎么办”。

**按关键词搜，搜的是字面。** 文件里那一段写的是“退换货流程”，里面一个“不满意”都没有，一个“东西”也没有。**字面对不上，搜不到。**

反过来，搜“流程”这两个字，能搜出全公司所有带“流程”的段落，几百条，**里面有一条是你要的，其余全是噪音**。

这是关键词检索的两个老毛病：**同一件事换个说法就搜不到；一个常用词能命中一大片。**

**embedding 解决的就是这件事。** 它不比字面，比意思。

## embedding：把文字变成一串数字

一段文字送进 embedding 模型，出来一串数字。就这么简单。

关键在下面这一条：

**意思相近的两段文字，出来的两串数字也相近。**

“东西买回来不满意怎么办”和“退换货流程”，字面上一个字都不重叠，但它们的向量会挨得很近。“今天中午吃什么”的向量离它俩都远。

**于是搜索变成了算数题**：把问题算成一个向量，跟库里每一段的向量挨个比一下，把最近的那几段拿出来。**比的是意思，不是字面。**

这里有一件事现在就要记住，后面第 7 卷会反复用到：

> **同一个知识库，从头到尾必须用同一个 embedding 模型。** 换了模型，向量的“坐标系”就换了，新算出来的问题向量和库里旧的向量没法比。**换模型就得把整个库重新算一遍。**
>
> 第 6 章提过一句同样的事——换 embedding 模型时，知识库可以整个重建索引，但对话里直接传过的那些文件不会跟着更新。**这就是为什么要在建库之前先把模型定下来。**

## 最小验证：让它把一句话变成一串数字

第 8 章那个接口上有一个专门的端点，`/v1/embeddings`。**用它跑一次，看见返回，这一章的验证就算过了。**

### 先用 curl 看一眼

```bash
curl -s http://localhost:11434/v1/embeddings \
  -H "Content-Type: application/json" \
  -d '{
    "model": "bge-m3",
    "input": "东西买回来不满意怎么办"
  }' | python3 -m json.tool | head -20
```

作用：把一句话发给 embedding 端点，把返回的 JSON 排版打印出来，只看前 20 行。

- **`-H` 和 `-d`** —— 第 8 章拆过，一个说“我发的是 JSON”，一个是发过去的内容；
- **`"input"`** —— 要算成向量的那段文字。**对话端点那边叫 `messages`，这里叫 `input`**，别写混了；
- **`| head -20`** —— 只显示前 20 行。**这一段不能省**：返回里那串数字有上千个，不截一下会刷满整个屏幕。

**正常输出**形如（**下面是格式示意，具体数值和长度随模型变化**）：

```json
{
    "object": "list",
    "data": [
        {
            "object": "embedding",
            "index": 0,
            "embedding": [
                0.013422,
                -0.041185,
                0.077390,
                ...
            ]
        }
    ],
    "model": "bge-m3",
    "usage": {
        "prompt_tokens": 11,
        "total_tokens": 11
    }
}
```

**要看的就是 `embedding` 那个数组。** 它就是这句话的向量。**这串数字本身没什么好看的**——它对人不可读，看一眼确认它出来了就行。

### 再用 Python 看见“意思相近”

上面那一步只证明接口通了。**下面这一段才是这一章真正要给你的东西**：亲眼看见意思相近的两句话，算出来的数确实更接近。

在第 8 章那个环境里新建一个文件叫 `embed_test.py`，内容照抄：

```python
import math

import requests

# 换成你那台 Mini PC 的地址，本机跑就用 localhost
BASE = "http://localhost:11434/v1"
MODEL = "bge-m3"

# 前两句意思接近，第三句无关
SENTENCES = [
    "东西买回来不满意怎么办",
    "退换货流程",
    "今天中午吃什么",
]


def embed(text):
    """把一段文字送去算成向量，返回一个数字列表。"""
    resp = requests.post(
        BASE + "/embeddings",
        json={"model": MODEL, "input": text},
        timeout=120,
    )
    resp.raise_for_status()
    return resp.json()["data"][0]["embedding"]


def cosine(a, b):
    """算两个向量的相似度，结果越接近 1 越像。"""
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    if na == 0 or nb == 0:
        return 0.0
    return dot / (na * nb)


vectors = [embed(s) for s in SENTENCES]

print("向量长度（维度）：", len(vectors[0]))
print()

for i in range(len(SENTENCES)):
    for j in range(i + 1, len(SENTENCES)):
        score = cosine(vectors[i], vectors[j])
        print("%.4f  “%s” 对 “%s”" % (score, SENTENCES[i], SENTENCES[j]))
```

跑它：

```bash
~/ai-client/bin/python embed_test.py
```

**正常输出**是一行维度，然后三行两两比较，形如：

```text
向量长度（维度）： 1024

0.xxxx  “东西买回来不满意怎么办” 对 “退换货流程”
0.xxxx  “东西买回来不满意怎么办” 对 “今天中午吃什么”
0.xxxx  “退换货流程” 对 “今天中午吃什么”
```

**要看的是三个数的大小关系，不是三个数本身。**

**第一行那个数应该明显大于后两行。** 前两句意思挨着，第三句跟谁都不挨着。**这就是整套按意思搜索的全部原理**，后面第 7 卷做的所有事都建在这一条上。

> **数值本身不用记，也不用跟别人的比。** 不同的 embedding 模型算出来的分数不在一个尺度上，**同一个模型内部的大小关系才有意义**。上面输出里的维度写的是运行时打印的实际值，**本教材不写死这个数字**——`len()` 跑一次就知道。

逐段说清这个程序：

- **`embed()`** —— 发一个请求，从返回里取出那串数字。路径是 `data[0].embedding`，**念法和第 8 章那条 `choices[0].message.content` 一样**；
- **`timeout=120`** —— 第 8 章说过这一项不能省。embedding 比生成快得多，120 秒足够；
- **`cosine()`** —— 算相似度的那个公式，叫余弦相似度。**它做的事是：不管两个向量各自多长，只看它们指的方向像不像。** 数学不用管，记住结果越接近 1 越像就够了；
- **`zip(a, b)`** —— 把两串数字一位一位对起来。**两个向量长度必须一样**，同一个模型出来的天然一样长；
- **`na == 0 or nb == 0`** —— 防一个除零。正常不会碰到，写上是习惯。

**这段代码本身没有直接用处**，它的用处是让你亲眼确认这个模型在你这台机器上是好使的。**第 7 卷会把这一步藏进工具里，你不用再自己写。**

### 报不出来的时候

- **返回里说模型不存在** —— 名字写错了，或者没拉下来。跑 `ollama list` 照抄；
- **返回里说这个模型不支持 embeddings** —— 你填的是一个对话模型。**对话模型和 embedding 模型是两类东西**，把 `MODEL` 换成上面拉的那个；
- **`Connection refused`** —— 接口没通，回第 8 章那一节。

其余的到[第 15 卷：故障排查](../15-故障排查/README.md)按症状查。

## reranker：结果不准的时候才加

**先说结论：这一章不装它，多数人也用不上。**

它是干什么的：

**embedding 那一步是粗筛。** 它把库里成千上万段文字全部算成向量，提问的时候拿问题的向量去比一遍，几十毫秒就能从一万段里挑出二十段。**快，但是粗**——因为库里那些向量是各段文字自己算的，算的时候并不知道你会问什么。

**reranker 是精挑。** 把问题和候选那二十段**一起**送进模型，让它逐条打分，重新排序，把最相关的三段挑到前面。**它看得准，因为它同时看到了问题和答案。**

**代价是慢。** 二十个候选就要跑二十次，而且每次都要把问题和那一段完整读一遍。**所以没人拿它去筛一万段**——那是 embedding 的活。

**两个搭起来的分工是：embedding 从一万里挑二十，reranker 从二十里挑三。**

**什么时候才需要它：**

- 检索出来的段落**明明库里有对的，就是排不到前面**；
- 问题问得绕一点就找不着；
- 一个知识库里有很多写法相近、内容不同的文档（各版本合同、各年度制度），**粗筛分不开它们**。

**什么时候不需要：**

- 刚建库，还没测过效果。**先用 embedding 单跑，看效果再说**；
- 库不大，几百段以内。粗筛出来的前几条基本就够；
- 你已经能接受当前的结果。

> **这是一个补救手段，不是必备件。** 先把 embedding 那条路跑通、用起来、发现不够准，再回头加 reranker。**一上来就全套装齐，出了问题你分不清是哪一层的事。**

**具体装哪个 reranker、怎么接进检索流程**，在[第 7 卷](../07-RAG/README.md)。**Ollama 的模型库里 reranker 类模型的条目名、以及 Ollama 当前版本对重排的支持方式，本项目未核实，需要核验**——第 7 卷动手那一章会重新核对当天的情况。
