# 18　llama.cpp HIP

## 完成结果

你自己编译出一份走 HIP 后端的 llama.cpp，**编译时指定了 `gfx1151` 这个目标架构**，并且避开了一个已知会让编译直接失败的选项。编译出来的东西和第 17 章那份 Vulkan 版**放在不同目录里并存**，随时可以两边对着跑。

**你还要带走一句本章反复强调的话：这条路不适合“装完就用”。** 第 7 章场景边界第二条的原话是——**适合你已经跑通了 Vulkan、想再比一次的时候走。**

## 开始前需要准备什么

- **装过 ROCm，并且第 14 章的检查通过了。** 这一章从头到尾要用 ROCm 里的编译器。**跳过第 11 章、没装 ROCm 的读者，整章用不上，直接去第 19 章**；
- **第 17 章跑通了。** 先有一份能跑的 Vulkan 版做参照，本章编出来的东西才有对比的意义。**顺序反过来走，出问题时你分不清是编译的锅还是这台设备的锅**；
- 手上有第 17 章用过的那个模型文件，**同一个文件两条路都能用**（GGUF 格式和后端无关）；
- 硬盘上要有空间。**源码加编译产物通常要几 GB**，先 `df -h /` 看一眼（[第 4 卷第 13 章](../04-Max395硬件/13-SSD.md)）；
- **时间准备**：编译要跑一段时间，**期间 CPU 会长时间满载**，机器会热、风扇会响。这是正常的（[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)）。**别在要用机器干别的事的时候编**；
- 本章不改内核参数、不动引导配置、不设 `HSA_OVERRIDE_GFX_VERSION`。[第 4 卷第 18 章](../04-Max395硬件/18-不应随意修改的设置.md)的禁区清单在本章全部保持原状。

## 新词

**编译**：把人写的源码翻译成机器能执行的指令。**第 17 章那条路省掉的就是这一步**——那边下载的是别人已经编译好的成品。

**源码**：程序的原始文本，人能读能改的那一份。

**构建工具**：指挥编译过程的程序。llama.cpp 用的是 `cmake`。

**构建目录**：编译过程中生成的一堆中间文件和最终产物放的地方。**它和源码目录分开，删掉不影响源码。**

**编译选项**：告诉构建工具“要不要开某个功能”的开关，写法是 `-D` 加名字加 `=ON` 或 `=OFF`。**本章的核心就是两个选项：一个必须开，一个绝对不开。**

**目标架构**：见第 7 章新词。这台设备是 `gfx1151`。**编译时不指定它，编出来的东西认不出这块 GPU。**

**并行编译**：同时开多个进程一起编，快很多。`-j` 后面跟数字，表示开几个。

**rocWMMA**：ROCm 里一个做矩阵运算加速的库。**本章要避开的那个选项就是用它的**——它对这台设备所在的架构支持不完备。

**FlashAttention**：一种把注意力计算做得更省内存的实现。本章要避开的那个选项名字里的 `FATTN` 指的就是它。

## 先说清楚这条路的四条已知限制

**动手之前先看完这四条。看完你可能会决定不走这条路，那也是本章的一个合理结果。**

**一、有一个选项开了就编不过。**

开 `GGML_HIP_ROCWMMA_FATTN` 编译 llama.cpp 会失败，原因是 rocWMMA 对 RDNA 3.5 的后端支持不完备（rocm-libraries issue #4618，2026-02-15，访问日期 2026-08-13）。**这条记录的环境是 Fedora，未覆盖 Ubuntu，需要核验**；同一个 issue 曾被提前关闭但故障仍复现。

**本章的做法是不开它。** 网上有教程让你开——**那些教程多半不是在这块 GPU 上写的**。

**二、大模型加载有已知的处理办法。**

第 17 章那一节的 `--no-mmap`，在 HIP 这条路上同样适用。**材料记录 HIP 后端的表现是加载后 GPU 占用 100%、一个字不输出、按 `Ctrl+C` 之后显存不释放**（素材记录，**本项目来源目录未收录对应条目，需要核验**）。

**三、和 Vulkan 谁更快，没有定论。**

材料里一条来源称针对 gfx1151，Vulkan 后端效率高于 ROCm／HIP 的实验构建；同期社区有调优后 HIP 反超的报告（llama.cpp issue #24438，访问日期 2026-08-13）。**两种结论并存，和版本、量化档、上下文长度、具体分支都强相关。**

**本章不下结论，第 19 章也不下统一结论**，那一章教的是怎么在你自己这台机器上测一次。

**四、这条路的维护成本比第 17 章高。**

第 17 章升级是下个新包解压；这条路每次升级都要重新拉源码、重新编译一遍。**而且它依赖 ROCm，ROCm 一升级可能就要重编。**

> **有一个数字要放在这里，并且要带着它的限制读：** AMD 在 ROCm issue #5339 里记录过一个 31.9 倍的提速（2025-10-14，访问日期 2026-08-13）。**那来自单一场景的单次测试**（第 7 章已标注），素材里对应的是 Whisper 那一类场景，**不是文本生成的 tokens/s，也不是你这台机器的预期值**。**不要拿这个数字做任何承诺。**

## 第四步：配置编译

**这是本章最关键的一条命令。**

```bash
cd ~/llama-hip-src && HIPCXX="$(hipconfig -l)/clang" HIP_PATH="$(hipconfig -R)" cmake -S . -B build -DGGML_HIP=ON -DGPU_TARGETS=gfx1151 -DCMAKE_BUILD_TYPE=Release
```

- **作用**：告诉构建工具用什么编译器、开哪些功能、为哪个 GPU 生成代码。逐项拆开：

| 这一项 | 干什么 |
| --- | --- |
| `HIPCXX="$(hipconfig -l)/clang"` | 指定用 ROCm 自带的那个编译器，**不是系统默认的那个** |
| `HIP_PATH="$(hipconfig -R)"` | 告诉它 ROCm 装在哪儿 |
| `-S .` | 源码在当前目录 |
| `-B build` | 产物放到 `build` 子目录 |
| `-DGGML_HIP=ON` | **开 HIP 后端。这一项必须开** |
| `-DGPU_TARGETS=gfx1151` | **指定目标架构。这一项不写，编出来的东西认不出这块 GPU**（第 6 章、第 7 章） |
| `-DCMAKE_BUILD_TYPE=Release` | 编成优化过的正式版，不是调试版 |

  **`$(...)` 这个写法是让终端先跑括号里那条命令，把它的输出填到这个位置。** 所以这条命令里其实嵌了第一步跑过的那两条。

- **正常输出**：几十行检查信息，最后两行形如

```text
-- Configuring done
-- Generating done
-- Build files have been written to: /home/你的用户名/llama-hip-src/build
```

  **中间会有一行提到 HIP 或者 gfx1151，那是它在确认目标架构。具体措辞随版本变化，需要核验**；

- **看到别的怎么办**：
  - **提示找不到 HIP 或者 `Could NOT find hip`** —— `HIP_PATH` 没指对。先单独跑一次 `hipconfig -R` 看输出是什么，把那个路径直接写进命令里，不用 `$(...)`；
  - **提示找不到 `clang`** —— 同理，先单独跑 `hipconfig -l`，确认那个目录下真的有一个叫 `clang` 的文件（`ls $(hipconfig -l)`）；
  - **提示找不到 CURL** —— 第二步那个 `libcurl4-openssl-dev` 没装上。装上重来，或者在命令末尾加 `-DLLAMA_CURL=OFF`（**这一项的写法随版本变化，需要核验**）；
  - **提示 `Unknown CMake command` 或者 CMake 版本太低** —— Ubuntu 仓库里的 `cmake` 版本不够新。**这属于版本组合问题**，抄下完整报错，看 llama.cpp 源码里的构建说明要求哪一版；
  - **报别的错，看不懂** —— **把最后 20 行抄下来**。配置阶段的报错基本都是“某个东西没找到”，顺着那个名字查；
- **怎么停止或撤销**：按 `Ctrl+C` 中断。要重来就 `rm -rf ~/llama-hip-src/build` 把构建目录删掉，**源码不受影响**，再重跑这条命令。

> **⚠️ 不要加 `-DGGML_HIP_ROCWMMA_FATTN=ON`。**
>
> 开这一项在这台设备所在的架构上**会让编译直接失败**——rocWMMA 对 RDNA 3.5 的后端支持不完备（rocm-libraries issue #4618，2026-02-15，访问日期 2026-08-13，**环境为 Fedora，未覆盖 Ubuntu，需要核验**）。
>
> **网上有教程让你开它。看到就跳过那一行。**
>
> **万一加了怎么办**：编译会在中途报错停下。`rm -rf ~/llama-hip-src/build` 删掉构建目录，去掉那一项重新配置。**没有别的后果**——配置和编译都在那个目录里，没碰系统。

## 第五步：编译

```bash
cd ~/llama-hip-src && cmake --build build --config Release -- -j 8
```

- **作用**：真正开始编译。`-j 8` 是同时开 8 个进程。
  - **这个数字怎么定**：一般取 CPU 核心数或者略少一点。这台设备的核心数用 `nproc` 查。**开满会让机器在编译期间基本没法干别的**，留一两个核心会舒服些；
- **正常输出**：一长串带百分比的进度，形如

```text
[  1%] Building CXX object ggml/src/CMakeFiles/ggml-base.dir/ggml.cpp.o
...
[ 78%] Building HIP object ggml/src/ggml-hip/CMakeFiles/ggml-hip.dir/...
...
[100%] Built target llama-cli
```

  **中间出现一些 `warning:` 是正常的**，编译过程里的警告不等于失败。**看最后有没有报 `Error` 并且中途停下**；

  **这一步要跑一段时间**，具体多久取决于 `-j` 开了多少和这台机器当时的功耗档位（[第 4 卷第 10 章](../04-Max395硬件/10-功耗模式.md)）。**本项目未实测这台设备上的编译耗时，需要核验**；

- **看到别的怎么办**：
  - **报 `local memory ... exceeds limit`** —— 这是第 7 章那张表里 vLLM 那条同族的问题（Wave32 上共享内存超限）。**llama.cpp 上本项目未记录到这条**，出现的话抄下完整报错；
  - **报和 `wmma` 或 `rocwmma` 有关的错** —— 上一步加了那个不该加的选项。回第四步的警告块；
  - **编到一半机器卡住、风扇狂转** —— 正常，`-j` 开太大了。按 `Ctrl+C` 停下，把 `-j` 调小重来。**编译是可以断点续编的**，重跑同一条命令会接着上次的进度；
  - **报内存不足、进程被系统杀掉** —— 同样是 `-j` 开太大，每个编译进程都要吃内存。调小重来；
  - **温度报警或者机器自己关机** —— 回[第 4 卷第 11 章](../04-Max395硬件/11-风扇与散热.md)和[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)，**这属于散热问题，不是编译的问题**；
- **怎么停止或撤销**：按 `Ctrl+C` 中断，进度保留。**完整撤销是 `rm -rf ~/llama-hip-src`**，源码和产物一起删掉，系统里什么都不留。

## 第六步：确认它认得出这块 GPU

```bash
cd ~/llama-hip-src/build/bin && ./llama-cli --list-devices
```

- **作用**：和第 17 章第四步同一条命令，这次跑的是刚编出来的这一份。**编译产物通常在 `build/bin` 下面，具体位置随版本变化，需要核验**；
- **正常输出**：一段设备列表，**里面应当有一行 ROCm 或 HIP 设备**，形如

```text
ggml_cuda_init: found 1 ROCm devices:
  Device 0: AMD Radeon Graphics, gfx1151 (0x1151), VMM: no, Wave Size: 32

Available devices:
  ROCm0: AMD Radeon Graphics (xxxxx MiB, xxxxx MiB free)
```

  **三件事要确认**：设备数不是 0、**能看到 `gfx1151` 这个字样**、`Wave Size` 是 32（第 6 章、第 7 章讲过这台设备是 Wave32）。

  **输出里出现 `cuda` 字样是正常的**——和第 16 章 `torch.cuda` 那一条同一个道理，是历史遗留的命名，**不代表要装 CUDA**。**具体格式随版本变化，本项目未固定，需要核验**；

- **看到别的怎么办**：
  - **提示 `No such file or directory`** —— 产物不在 `build/bin`。用 `find ~/llama-hip-src/build -name "llama-cli"` 找一下；
  - **找到 0 个设备** —— 按顺序查三件：第 14 章的 `rocminfo` 能不能看到 `gfx1151`；`groups` 里有没有 `render` 和 `video`（第 11 章第七步）；第四步的 `-DGPU_TARGETS=gfx1151` 写了没有。**第三件最常漏**；
  - **报找不到对应的代码对象、`no kernel image is available`** —— 目标架构没指定对（第 6 章、第 7 章）。**删掉构建目录重新配置一遍，确认 `-DGPU_TARGETS=gfx1151` 那一项在**；
  - **列出来的是 Vulkan 设备不是 ROCm 设备** —— 你跑的是第 17 章那一份。确认命令里的路径是 `~/llama-hip-src/build/bin`；
  - **报权限相关的错** —— 回第 11 章第七步；
- **怎么停止或撤销**：只读命令，不需要撤销。

**把这一行输出、加上第三步抄的提交编号，一起记进[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)的设备基线**，注明这是 HIP 那一份。

## 第七步：跑一次，和 Vulkan 那份用同一个模型

```bash
cd ~/llama-hip-src/build/bin && ./llama-cli -m ~/models/你的模型文件.gguf -p "你好，请用一句话介绍你自己。" -n 128 -ngl 99
```

- **作用**：和第 17 章第五步**完全一样的命令**，只是换了程序的路径。**参数的含义第 17 章已经写全，本章不重抄**；
- **正常输出**：加载信息里能看到 ROCm 或 HIP 设备、offloading 那一行有数字，然后是生成的文字和统计；
- **看到别的怎么办**：
  - **大模型加载后卡住、GPU 占用满、不输出** —— **加 `--no-mmap`**，第 17 章那一节写全了症状、原因、代价和来源限制，**本章不重抄**；
  - **报 `hipMalloc` 相关的错、显存不足** —— **先排除“假的内存不足”**（第 6 章、第 7 章）。回第 14 章看 `rocm-smi` 报的显存数对不对，处理在第 20 章；
  - **报 `Memory access fault by GPU node-1`** —— 材料里记录过这条（ROCm issue #5824，访问日期 2026-08-13，**环境是 Fedora 与 Nobara，不是 Ubuntu，需要核验**）。先按第 2 章第五节查固件版本和最近的系统更新，处理在第 20 章、第 21 章；
  - **生成出来的东西和 Vulkan 那份差别很大、或者是乱的** —— **先确认是不是真的错了**，这类问题不报错，只能靠人看（第 7 章第三条）。两边用同一个模型、同一段提示词对着看；
  - **按 `Ctrl+C` 之后显存不释放** —— 材料记录过这个现象（素材记录，**需要核验**）。处理在第 20 章；
- **怎么停止或撤销**：按 `Ctrl+C`。这个程序不写配置、不改系统状态。

## 两份东西怎么并存

**它们本来就是两份独立的程序，放在两个目录里，互不知道对方存在。**

| | Vulkan 那一份 | HIP 这一份 |
| --- | --- | --- |
| 在哪 | `~/llama` | `~/llama-hip-src/build/bin` |
| 怎么来的 | 下载官方预编译包（第 17 章） | 自己编译（本章） |
| 要不要 ROCm | **不要** | **要** |
| 怎么升级 | 下新包解到新目录 | 拉新源码重新编一遍 |
| 怎么删 | `rm -rf ~/llama` | `rm -rf ~/llama-hip-src` |

**跑哪一份，看你敲的是哪个路径。** 这是本教材不建议把它们加进系统路径的理由——**加进去之后你就分不清跑的是哪一份了**。

**要对着测，两边用同一个模型文件、同一段提示词、同一个上下文长度。** 方法在第 19 章，**那一章会讲怎么把变量控住**。

## 看到不同结果怎么办

**编译报的错本章没列**：配置阶段的报错基本是“某个东西没找到”，顺着名字查；编译阶段的报错先看是不是 `-j` 开太大导致的内存不足。**都不是的话，把最后 20 行完整抄下来**，连同 ROCm 版本、内核版本、源码的提交编号一起。**这三样不写清，报错没法判断。**

**编出来了，但比 Vulkan 那份慢**：材料里两种结论都有（llama.cpp issue #24438，访问日期 2026-08-13）。**慢不代表你编错了。** 用第 19 章的方法测一次，把结果记进基线，**按你自己那台机器的数字选**。

**编出来了，但比 Vulkan 那份快**：同上。**同样只对你这台机器、这个版本、这个模型成立**，不要写成普遍结论，更不要写进给客户的承诺。

**你想开一堆网上说能提速的编译选项**：**一次只开一个，每开一个测一次**。这是[第 4 卷第 10 章](../04-Max395硬件/10-功耗模式.md)那套判断方法的通用规矩。**本教材只保证本章这一组选项能编过**，别的组合本项目没有测过，**需要核验**。

**ROCm 升级之后这一份跑不起来了**：正常。**这条路和 ROCm 绑在一起**，ROCm 一动就可能要重编。删掉构建目录重新走第四步和第五步。升级和回退在第 21 章、第 22 章。

**你不想留着编译工具链**：把 `~/llama-hip-src/build/bin` 里的东西拷到别处，然后按上面那张表卸掉工具链。**注意它依赖 ROCm 的库，ROCm 不能卸。**

**你决定不走这条路了**：`rm -rf ~/llama-hip-src` 删掉，工具链按表卸掉。**第 17 章那份 Vulkan 版不受任何影响。** 这是本教材主线的默认状态。

**你在给客户做交付，在想给哪一份**：**默认给 Vulkan 那一份**（第 19 章会把理由写全）。这一份的维护成本更高、依赖更多，**除非你自己实测出它在客户那个具体场景上明显更好，并且愿意长期维护它**。
