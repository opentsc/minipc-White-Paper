# 15　并发与多人同用

## 这一章的任务

测出你这台机器能同时供几个人用。

**注意是“测出”，不是“查出”。** 这一章不给“这台机器能供 5 个人用”这种数字——**那个数取决于你用哪个模型、开多长上下文、大家问的问题有多长**，别人测出来的搬不到你这儿。这一章给的是一套测法和一张记录表。

**这件事直接关系到往后怎么跟客户说话。** 一台机器卖出去，对方一定会问“我们十几个人够不够用”。**手上有自己测的记录，你答得出来；没有，你只能猜。**

## 开始前

- 第 8 章做完，`http://192.168.1.50:11434/v1` 这个接口从别的机器连得上；
- 第 8 章那个 Python 环境还在（`~/ai-client`，里面装了 `requests`）；
- 第 1 章那两条估内存的规则记得（权重 90 GB 以内，留 20 GB 给 KV cache 和缓冲）；
- 第 7 章那两个环境变量你设过一次，知道 `systemctl edit ollama` 怎么用；
- 手上有一个已经能用的模型，本章一律拿主线那个举例；
- 60 分钟，其中测试本身要跑好几轮。

## 新词

**并发**（concurrency）：**几个人同时提问。** 严格说是同一时刻有多个请求在这台机器上等着被处理。

**排队**：请求一个一个来，前一个答完了才轮到后一个。**后面的人干等。**

**并行**：几个请求同时在算。**每个人都在被服务，但每个人都变慢一点。**

**响应时间**：从发出请求到收到完整回答，一共花了多少秒。**这是用的人真正在意的那个数。**

**首字延迟**：从发出请求到看见第一个字冒出来，花了多少秒。开了流式（第 8 章）的界面上，人感受到的“卡不卡”主要是这一项。

**槽位**（slot）：推理服务同时处理多个请求时，每一路占的那份资源。**一个槽位一份上下文。**

## 一台机器同时被几个人问，会发生什么

**先说物理事实：这台机器只有一份内存、一块 GPU。** 几个人同时提问，这些活最终都要在同一块芯片上算完。

**默认的行为是排队。** Ollama 有一个环境变量管这件事：

```text
OLLAMA_NUM_PARALLEL
```

官方文档说它的**默认值是 1**（Ollama FAQ，访问日期 2026-08-14）。**默认是 1 的意思就是：同一个模型一次只处理一个请求，第二个人得等第一个人答完。**

三个人同时问，各自要 20 秒的话，第三个人拿到答案是 60 秒之后。**他会觉得这机器坏了。**

**把它调大，就变成并行**——同时开几个槽位，几个请求一起算。**但并行不是白来的**，两笔账要付：

**第一笔，速度。** 算力就那么多，四路一起跑，每一路都比单跑慢。**总的吞吐可能上去了，单个人的等待时间不一定变短。**

**第二笔，内存。** 这一笔更硬，下一节单说。

> **第 7 章那个 `OLLAMA_MAX_LOADED_MODELS` 和这一章的不是一回事。** 那个管的是**同时加载几个不同的模型**（一个人用中文模型、一个人用代码模型）；这一章的 `OLLAMA_NUM_PARALLEL` 管的是**同一个模型同时处理几个请求**。两件事各占各的内存，**都要算进第 1 章那个预算里**。

## 内存是硬约束

第 1 章那条公式在并发场合要改一个地方：

```text
单人时：运行占用 ≈ 权重 + KV cache + 1 到 3 GB 计算缓冲
并发时：运行占用 ≈ 权重 + KV cache × 并行路数 + 计算缓冲
```

**权重只有一份，KV cache 每一路各一份。**

拿主线那个模型代一遍。`Qwen3.6-35B-A3B` 走 UD-Q4_K_M，权重 22.1 GB；第 1 章算过它 32K 上下文的 KV cache 约 2.7 GB：

```text
1 路：22.1 + 2.7  ×1 = 24.8 GB，加缓冲约 27 GB
4 路：22.1 + 2.7  ×4 = 32.9 GB，加缓冲约 35 GB
8 路：22.1 + 2.7  ×8 = 43.7 GB，加缓冲约 46 GB
```

**这台机器的 120 GiB 预算下，这个模型开到 8 路都不紧张。**

**换个模型完全不是这个结论。** 第 1 章算过 `Llama-3.3-70B` 每 token 的 KV 是前者的 4 倍，32K 上下文一路就要 10.7 GB：

```text
4 路：43（权重）+ 10.7 ×4 = 85.8 GB，加缓冲逼近 90 GB
```

**同样开 4 路，一个宽松，一个顶格。** 所以这一章的第一条动作永远是：**先按你实际要用的模型和上下文长度算一遍，再决定开几路。**

> **上下文长度是这里最容易被忽略的乘数。** 把上下文从 32K 拉到 128K，KV cache 涨 4 倍，**并行路数就得砍到四分之一**。想多人同用，上下文别默认拉满——第 13 章讲过怎么按实际需要开。

**顶着上限开并行的表现和第 1 章说的一样**：不是干脆报错，而是有人的对话稍微长一点就崩，或者模型被判显存不够、掉一部分层到 CPU 上（第 3 章那个 `ollama ps` 里的混合值）。**这种问题比报错难查得多。**

## 把并行打开

和第 4 章、第 7 章、第 8 章设环境变量是同一个动作：

```bash
sudo systemctl edit ollama
```

**在两行注释之间**，把这一行加进已有的那个 `[Service]` 段里：

```ini
[Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"
Environment="OLLAMA_KEEP_ALIVE=-1"
Environment="OLLAMA_NUM_PARALLEL=4"
```

**这台机器上前面几章设过的那几行都写在同一段里，一行一个**（第 8 章讲过，分成几段 `[Service]` 是最常见的写错法）。

生效：

```bash
sudo systemctl daemon-reload
sudo systemctl restart ollama
```

确认写进去了：

```bash
systemctl cat ollama --no-pager
```

**输出的后半段能看到你刚加的那一行。**

> **`4` 这个数是拿来起步的，不是推荐值。** 下面那套测法就是用来找你自己该填几的。**先算内存够不够，再往上试。**

## 自己测：最小并发测试脚本

**这一节是这一章真正的交付物。**

在第 8 章那个环境里新建一个文件叫 `concurrency_test.py`，内容照抄：

```python
import statistics
import sys
import time
from concurrent.futures import ThreadPoolExecutor

import requests

# 换成你那台 Mini PC 的地址和模型名
BASE = "http://192.168.1.50:11434/v1"
MODEL = "qwen3.6-35b"

# 每个人问的那一句。三百字的回答，长到能看出差别，短到不用等太久
PROMPT = "用三百字介绍一下你自己，不要分点。"

# 这一轮同时发几个请求。命令行上给，不给就按 1 算
N = int(sys.argv[1]) if len(sys.argv) > 1 else 1


def one_request(index):
    """发一个请求，返回（编号，耗时秒数，生成了多少 token，出错信息）。"""
    started = time.time()
    try:
        resp = requests.post(
            BASE + "/chat/completions",
            json={
                "model": MODEL,
                "messages": [{"role": "user", "content": PROMPT}],
            },
            timeout=900,
        )
        resp.raise_for_status()
        data = resp.json()
        usage = data.get("usage") or {}
        return index, time.time() - started, usage.get("completion_tokens", 0), ""
    except Exception as err:
        return index, time.time() - started, 0, str(err)


print("并发数 %d，模型 %s" % (N, MODEL))
print("先发一个请求把模型加载进内存，这一次的耗时不算数……")
warm = one_request(-1)
print("热身用了 %.1f 秒。" % warm[1])
if warm[3]:
    print("热身就出错了：%s" % warm[3])
    sys.exit(1)

print("开始。")
wall_started = time.time()
with ThreadPoolExecutor(max_workers=N) as pool:
    results = list(pool.map(one_request, range(N)))
wall = time.time() - wall_started

print()
print("编号    耗时（秒）    生成 token    出错")
for index, spent, tokens, err in sorted(results):
    print("%4d %12.1f %13d    %s" % (index, spent, tokens, err or "无"))

times = [spent for _, spent, _, err in results if not err]
failed = len(results) - len(times)

print()
if times:
    print(
        "最快 %.1f 秒，最慢 %.1f 秒，中位 %.1f 秒"
        % (min(times), max(times), statistics.median(times))
    )
print("全部完成用了 %.1f 秒，失败 %d 个" % (wall, failed))
```

跑它。**从 1 路开始，一级一级往上加：**

```bash
~/ai-client/bin/python concurrency_test.py 1
~/ai-client/bin/python concurrency_test.py 2
~/ai-client/bin/python concurrency_test.py 4
~/ai-client/bin/python concurrency_test.py 8
```

**正常输出**每一轮长这样（**数字是你自己那台机器的，这里只给形状**）：

```text
并发数 4，模型 qwen3.6-35b
先发一个请求把模型加载进内存，这一次的耗时不算数……
热身用了 xx.x 秒。
开始。

编号    耗时（秒）    生成 token    出错
   0         xx.x           xxx    无
   1         xx.x           xxx    无
   2         xx.x           xxx    无
   3         xx.x           xxx    无

最快 xx.x 秒，最慢 xx.x 秒，中位 xx.x 秒
全部完成用了 xx.x 秒，失败 0 个
```

逐段说清这个程序：

- **`ThreadPoolExecutor(max_workers=N)`** —— 开 N 个线程，**同时**把请求发出去。这是这个脚本的全部机关，其余都是记时间和排版；
- **热身那一次** —— 模型第一次加载要十几秒到几分钟（第 7 章那一节）。**不热身的话，第一轮的数字里混着加载时间，没法比。** 热身的耗时单独打印出来，看一眼就好；
- **`timeout=900`** —— 并发的时候单个请求会比平时慢，超时给宽一点。**这一项不能省**，理由第 8 章讲过；
- **`sorted(results)`** —— 按编号排一下，输出好看；
- **`usage.get("completion_tokens", 0)`** —— 这一次生成了多少 token（第 8 章讲过 `usage` 怎么用）。**并发时各个请求生成的长度不完全一样**，看着这一列才知道耗时的差别有多少是长度造成的；
- **`try` 包住整段** —— 并发起来之后，有的请求会失败（超时、内存不够、连接被断）。**失败也要记下来，不能让整个脚本崩掉。** 失败个数是这一章一个重要信号。

> **这个脚本模拟的是最狠的一种情况：所有人在同一秒按下回车。** 真实的情况通常没这么集中，所以测出来的数字偏保守。**保守一点正好**——拿去跟客户说话的时候，宁可低估。

## 测的时候另开两个窗口盯着

**光看脚本的输出不够**，同时要看机器那一头。

**一、模型有没有掉到 CPU 上**

```bash
ollama ps
```

**`PROCESSOR` 那一列还是 `100% GPU` 才算数**（第 3 章那一节）。并发开大之后内存吃紧，Ollama 可能把一部分层挪到 CPU 上——**这时候测出来的耗时不是这台机器的真实能力，是降级之后的能力。**

**二、内存到哪儿了**

```bash
watch -n 2 free -h
```

`available` 那个数在往下掉，**掉到只剩几个 GB 就是顶到墙了**。同时看一眼 `radeontop` 里 `gtt` 那一行（第 3 章讲过怎么读），**它涨的量应该和上面那条公式算出来的对得上。**

**三、温度和频率**

并发测试是一段持续的满载，**这正好是[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)说的“跑模型满载”那个状态**。那一章讲了怎么读传感器、什么叫稳态、多久算测到位，**本章不重抄**。

**长时间并发之后温度稳态明显比单人时高，是正常的。** 高到开始降频，说明这台机器在这个负载下的瓶颈在散热不在算力——**那属于[第 4 卷第 11 章](../04-Max395硬件/11-风扇与散热.md)的事。**

## 舒适人数怎么判断

看三条，缺一不可。

**一、最慢那一个还能不能接受。**

**看最慢的，不看平均。** 用的人等的是自己那一条，不是平均值。**四个人里有一个等了两分钟，那台机器对他来说就是不能用。**

**二、内存有没有顶到墙。**

`free -h` 里 `available` 还剩多少，`ollama ps` 有没有掉到混合值。**顶格跑的系统，平时看着好好的，某一次对话长一点就出事。**

**三、有没有请求失败。**

**失败个数不是 0，这一档就不算过。** 哪怕只有一个，也说明这个并发数在这台机器上不稳。

**满足这三条的最大并发数，就是你这台机器在这套条件下的舒适人数。**

> **条件一变，这个数就得重测。** 换模型、换量化档、改上下文长度、改 `OLLAMA_NUM_PARALLEL`、装了别的服务上去，**任何一项变了，旧的记录不能用。** 这条规矩和[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)那份基线是一样的。

## 这一章不给数字

**本教材不写“这台机器能供几个人用”。**

理由和[第 5 卷第 19 章](../05-驱动与ROCm/19-后端选择.md)不给 tokens/s 是同一条：**这个数取决于模型、量化档、上下文长度、提问的长度、回答的长度、机器当时的温度和功耗档位，还有整机厂的散热设计。** 换掉其中任何一项，答案就不一样。

**网上和商品页上流传的那些“可支持 10 人同时使用”，一律当成没说。** 它们不给条件，不给测法，也没有第三方复测。

**你自己那张表上的数字才是能用的。**

## 卖给客户的时候怎么说

**这一节是这一章存在的商业理由。**

客户问“我们二十个人够不够”，**有三种答法，只有一种能用**：

- **不能说“够”或者“不够”。** 你不知道他们二十个人怎么用——是一天问三句，还是整天挂着？
- **不能引用别人的数字。** 上一节那条。
- **要说条件和测法。** 形状是这样：

```text
在 XX 模型、UD-Q4_K_M 量化档、32K 上下文、OLLAMA_NUM_PARALLEL 设为 4 的条件下，
本机于 2026-XX-XX 实测：4 个请求同时发出，全部成功，最慢一个 XX 秒。
8 个请求同时发出时有 X 个失败。
上述数值只在该条件下成立，换模型或改上下文长度需要重测。
```

**这段话每一句都有出处，都能当场再跑一遍验证。** 这就是可以交付的东西。

**再往上一层的做法**——限制每个人的并发、给不同的人分不同的模型、排队排不过来时给一个明确的提示——**属于产品化，在[第 10 卷](../10-产品化/README.md)。** 本卷只管测出这台机器的边界在哪儿。
