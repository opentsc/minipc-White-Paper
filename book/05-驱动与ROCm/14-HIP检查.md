# 14　HIP 检查

## 完成结果

ROCm 和 HIP 这条路通了。`rocminfo` 里能看到一个 `gfx1151` 的 GPU，`rocm-smi` 里的显存总量和[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)设的对得上，`hipconfig` 报出的版本不低于 7.0.2。这三样输出怎么读你已经知道。

常见的四种异常你也知道怎么办：看不到 GPU、只看到很小的显存、权限不足、程序报显存申请失败。

你同时清楚一件事：**通了不等于全部算子可用**，这句限制是 AMD 自己在缺陷追踪里写的（第 5 章、第 7 章）。

**本章全是只读命令，不装任何东西，也不改任何设置。**

## 开始前需要准备什么

- **第 11 章装过 ROCm，并且重启或重新登录过。** 跳过第 11 章的读者**整章跳过本章**，直接去第 15 章；
- **第 12 章五项全过**，尤其是第三项（`/dev/kfd` 在）和第四项（`test -r /dev/kfd` 输出“可以读”）。**这两条不过，本章一定过不去**；
- 读过第 5 章（ROCm 的组成）、第 6 章（HIP）、第 7 章（gfx1151 的已知问题）、第 8 章（版本门槛）。**本章不重讲这四章的内容，只做检查**；
- 大约 15 到 30 分钟；
- 手边有第 9 章建的那个备份目录，本章末尾要往里写一个文件。

## 新词

**agent**：`rocminfo` 里对每一个计算设备的称呼。**CPU 也会被列成一个 agent**，这一点第一次看输出的人最容易搞混——看到两个 agent 是正常的，一个是 CPU，一个才是 GPU。

**HSA**：ROCm 最底下那层运行时的名字（第 5 章）。`rocminfo` 打印的就是这一层看到的东西，输出开头几行的标题里带这三个字母。

**内存池**（pool）：`rocminfo` 里对每个 agent 可用内存的分段描述。这块 GPU 上会看到不止一个池，对应[第 4 卷第 6 章](../04-Max395硬件/06-UMA与GTT.md)讲的静态预留和动态借用两部分。

**`gfx1151`**：这台设备的目标标识（第 7 章、[第 4 卷第 3 章](../04-Max395硬件/03-Radeon-8060S.md)）。**本章要在输出里找的就是这个字串。**

**`hipMalloc`**：HIP 里申请显存的那个函数（第 5 章那张表提过）。程序报错里出现这个名字，说明是申请显存那一步失败了，本章最后一节专讲怎么看。

**PATH**：一串目录，敲一条命令时系统按这串目录挨个找（第 11 章新词）。ROCm 的命令装在 `/opt/rocm/bin` 下面。

## 这一章要跑的三样东西

| 工具 | 看什么 | 通过的标准 |
| --- | --- | --- |
| `rocminfo` | ROCm 认到了哪些计算设备 | 有一个 `Device Type: GPU` 的 agent，`Name` 是 `gfx1151` |
| `rocm-smi` | 显存、温度、占用 | 能跑出表；GTT 总量和第 4 卷设的对得上 |
| `hipconfig` | HIP 的版本和路径 | 版本不低于 7.0.2 |

**三样都过，HIP 这条路就算通了。**

## 第一样：`rocminfo`

```bash
rocminfo
```

- **作用**：打印 ROCm 最底下那层运行时认到的所有计算设备，以及每个设备的详细属性。**这是判断“ROCm 认没认出这块 GPU”的主要手段**（第 5 章那张组成表列过它）。这条命令只读，不装也不改任何东西；
- **正常输出**：几百行，结构是先一段系统属性，再一个一个列 agent。节选形如

```text
=====================
HSA System Attributes
=====================
Runtime Version:         1.1
Runtime Ext Version:     1.6
System Timestamp Freq.:  1000.000000MHz
...

==========
HSA Agents
==========
*******
Agent 1
*******
  Name:                    AMD Ryzen AI Max+ 395 w/ Radeon 8060S Graphics
  Uuid:                    CPU-XX
  Marketing Name:          AMD Ryzen AI Max+ 395 w/ Radeon 8060S Graphics
  Device Type:             CPU
...
*******
Agent 2
*******
  Name:                    gfx1151
  Uuid:                    GPU-XX
  Marketing Name:          AMD Radeon Graphics
  Device Type:             GPU
  ...
  Pool Info:
    Pool 1
      Segment:                 GLOBAL; FLAGS: COARSE GRAINED
      Size:                    ...
```

> **上面的数值和字串都是格式示意。** agent 的编号、内存池的大小、运行时版本随你的机器和 ROCm 版本变化。**本项目未固定这些数字，需要核验。要看的是形状，不是数字。**

**要看三件事：**

1. **有没有一个 `Device Type: GPU` 的 agent**；
2. **那个 agent 的 `Name` 是不是 `gfx1151`**；
3. **`Agent 1` 是 CPU，这是正常的**，不要把它当成 GPU 没认出来。

- **看到别的怎么办**：
  - **提示 `command not found`** —— 两种可能。先跑 `ls /opt/rocm/bin/rocminfo`，文件在就说明是 PATH 的问题，用全路径跑一次：`/opt/rocm/bin/rocminfo`。**能跑起来就是 PATH 没配上**，处理办法在本章“命令找不到怎么办”那一节。文件不在，说明 ROCm 没装或者装得不完整，回第 11 章；
  - **只有 CPU 那一个 agent，没有 GPU** —— **这是本章第一号异常**，专门一节在下面；
  - **报 `Permission denied` 或者权限相关的字样** —— **这是本章第二号异常**，专门一节在下面；
  - **直接段错误，或者报错里出现 `libhsa-runtime64.so`** —— 那是 HSA 运行时那一层（第 5 章）。这类问题材料里记录过，处理在第 20 章、第 23 章。**先把 `dmesg` 的最后几十行抄下来**：`sudo dmesg | tail -40`；
  - **GPU 那个 agent 在，但 `Name` 不是 `gfx1151`** —— 抄下来记进[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)的设备基线，然后按第 7 章那张“哪些软件已经原生支持”的表对。**不要设 `HSA_OVERRIDE_GFX_VERSION` 把它改成别的**（第 7 章）；
- **怎么停止或撤销**：只读命令，不需要撤销。输出很长，按 `Ctrl+C` 中断。

**只看关键行：**

```bash
rocminfo | grep -E "^  Name:|Device Type:"
```

- **作用**：从 `rocminfo` 的输出里只挑出设备名和设备类型那两类行。开头那个 `^  ` 是为了只匹配缩进两格的 `Name:`，避开输出里别的地方出现的同名字段。这条命令只读；
- **正常输出**：四行（两个 agent 各两行），形如

```text
  Name:                    AMD Ryzen AI Max+ 395 w/ Radeon 8060S Graphics
  Device Type:             CPU
  Name:                    gfx1151
  Device Type:             GPU
```

**要找的就是 `gfx1151` 配 `GPU` 这一对**；

- **看到别的怎么办**：
  - **一行都没有，但 `rocminfo` 本身有输出** —— 输出里的字段缩进和这里写的对不上（不同 ROCm 版本的格式略有差异）。改用 `rocminfo | grep -i gfx` 再试一次；
  - **只有 CPU 那两行** —— 同上面第一号异常；
  - **其余分支同上一条**；
- **怎么停止或撤销**：只读命令，不需要撤销。

## 第二样：`rocm-smi`

```bash
rocm-smi
```

- **作用**：打印每块 GPU 当前的温度、功耗、频率和占用，一行一块。名字里的 smi 是 system management interface。**这是看 GPU 在不在干活的主要手段**（第 5 章那张组成表列过它）。这条命令只读；
- **正常输出**：一张表，形如

```text
========================= ROCm System Management Interface =========================
=================================== Concise Info ===================================
GPU  Temp   AvgPwr  SCLK    MCLK    Fan  Perf  PwrCap  VRAM%  GPU%
0    41.0c  6.0W    800Mhz  1000Mhz N/A  auto  N/A     1%     0%
====================================================================================
```

**空载时 `GPU%` 接近 0 是正常的**。有几列显示 `N/A` 也正常——这块 GPU 是集成的，风扇和功耗上限这类信息不一定暴露给它（[第 4 卷第 11 章](../04-Max395硬件/11-风扇与散热.md)讲过类似情况）；

- **看到别的怎么办**：
  - **提示 `command not found`** —— 同 `rocminfo`，先试全路径 `/opt/rocm/bin/rocm-smi`；
  - **报权限错误** —— 看下面第二号异常那一节；
  - **表里一块 GPU 都没有** —— 回第一样，`rocminfo` 那边多半也看不到；
  - **大部分列都是 `N/A`** —— 可以接受。本章的判断依据是 `rocminfo` 和显存那一条，不是这张表的列全不全；
- **怎么停止或撤销**：只读命令，不需要撤销。

**看显存（本章最要紧的一条）：**

```bash
rocm-smi --showmeminfo vram gtt
```

- **作用**：打印这块 GPU 的两个内存池各有多大、用了多少。`vram` 是 BIOS 静态预留的那一块，`gtt` 是从系统内存动态借的那一块（[第 4 卷第 6 章](../04-Max395硬件/06-UMA与GTT.md)）。[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)第六步提到过这条命令，说“装好 ROCm 之后可以再查一层”，**这里就是那一层**。这条命令只读；
- **正常输出**：几行，形如

```text
============================ ROCm System Management Interface ============================
================================== Memory Usage (Bytes) ==================================
GPU[0]		: VRAM Total Memory (B): 536870912
GPU[0]		: VRAM Total Used Memory (B): 12582912
GPU[0]		: GTT Total Memory (B): 131941395456
GPU[0]		: GTT Total Used Memory (B): 8388608
==========================================================================================
```

**要看的是 `GTT Total Memory` 那一行，应当在 120 GiB 量级。**

数字是字节，换算起来费劲，用下面这一句直接看 GB：

```bash
rocm-smi --showmeminfo vram gtt | grep Total\ Memory
```

同样只读，作用是只留下两行总量；看到别的按下面的异常分支走；不需要撤销。

> **判断显存配置是否生效，以内核日志和 `/sys` 下的参数文件为准，不以这条命令为准。**
>
> [第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)原话：gfx1151 上 ROCm 对静态和动态两个池的汇报口径反复过几次。第 12 章第五项那三条（`/proc/cmdline`、`/sys/module/ttm/parameters/pages_limit`、`dmesg` 里的两行）才是主要依据。**本章这一条是拿来和它们对照的，对不上时先信第 12 章那三条。**

- **看到别的怎么办（四种情况，按数值分）**：

  **一、`GTT Total Memory` 约 15.5 GB**

  这是内核 6.15 及更早版本上的已知缺陷，**任何内核参数都绕不过**（ROCm issue #5444，2026-08-13 核对已关闭并标记已解决，修复在内核侧）。

  先确认内核版本：`uname -r`。低于 6.16.9 的话，**唯一出路是升内核**。

  > **⚠️ 升内核属于替换系统核心组件。**
  >
  > **动手之前先做备份，步骤见第 9 章**，并确认恢复 U 盘能启动（[第 1 卷第 10 章](../01-开箱与安装/10-恢复介质.md)）。升级步骤在[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)第一步。
  >
  > **升完开不了机**：按[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)“改坏了开不了机怎么办”那一节，从办法一开始——开机按住 `Shift` 调出 GRUB 菜单，在 `Advanced options for Ubuntu` 里选旧版本的内核启动。**装新内核不会删掉旧内核**，GRUB 菜单里旧的那一项一直在，这是这条路的退路。

  **二、`GTT Total Memory` 约 62.2 GB**

  两种成因，查 `cat /proc/cmdline` 就能分开：

  - **里面有 `amdgpu.gttsize`** —— 设了已废弃的参数，而 TTM 仍为默认值，内核日志会报两者不一致，HIP 按小的那一边汇报（ROCm issue #5595）。**本教材不设这个参数**。删掉的完整命令在[第 4 卷第 18 章](../04-Max395硬件/18-不应随意修改的设置.md)第四条：用 `/etc/default/grub.bak` 覆盖回去、`sudo update-grub`、重启；
  - **里面没有 `ttm.pages_limit`** —— 根本没设过，走的是默认上限（约为系统内存的 50%，AMD 官方文档）。回[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)补设。

  **本章不改任何内核参数**，两种情况都是回对应的章处理。

  **三、只显示 512 MB 或者 2 GB**

  那是 BIOS 静态预留的那一块，说明这条命令只读到了 VRAM 那个池、没读到 GTT。**先看第 12 章第五项的 `dmesg` 里 GTT 那一行是不是 `122880M`**——那一行对，就是这个工具的汇报口径问题，不是配置失败（[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)记录过监控工具不适配动态显存的情况）。那一行也不对，按上面第二种处理。

  **四、数值和第 12 章第五项对得上，就是正常。**

- **怎么停止或撤销**：只读命令，不需要撤销。**这一条只是读数，不改任何配置。**

## 第三样：`hipconfig`

```bash
hipconfig --version
```

- **作用**：打印 HIP 的版本号。**这是核对第 8 章那道版本硬门槛的地方**。这条命令只读；
- **正常输出**：一行版本号，形如

```text
7.0.2-abc1234
```

**前三段（`7.0.2`）是要看的，必须不低于 7.0.2。** 这是第 8 章表二写明的硬门槛：低于这一版，gfx1151 不在 ROCm 的官方支持范围里（ROCm issue #5339，AMD 在 issue 中说明，2026-08-13 核验）；

- **看到别的怎么办**：
  - **提示 `command not found`** —— 先试全路径 `/opt/rocm/bin/hipconfig`。看下面“命令找不到怎么办”；
  - **版本低于 7.0.2** —— 这个组合在这台设备上不成立。**按第 11 章末尾的卸载回退路径拆干净，再照第 11 章重装**，第一步抄版本号的时候确认不低于 7.0.2；
  - **报找不到编译器，或者报某个路径不存在** —— ROCm 装得不完整。回第 11 章第五步跑一次 `--dry-run` 对照，看漏了哪些包；
  - **版本号和第 11 章第一步抄下来的对不上** —— 装进去的不是你以为的那一版。以这条命令报的为准，抄进设备基线；
- **怎么停止或撤销**：只读命令，不需要撤销。

**看完整配置：**

```bash
hipconfig
```

- **作用**：打印 HIP 的完整配置——装在哪、用的编译器在哪、平台是什么、目标架构是什么。这条命令只读；
- **正常输出**：十几行到几十行，里面能看到 ROCm 的安装路径、`HIP_PLATFORM` 是 `amd`、编译器的位置。**具体字段随版本变化，本项目未固定，需要核验**；
- **看到别的怎么办**：
  - **`HIP_PLATFORM` 不是 `amd`** —— 有人设过环境变量把它改了。跑 `env | grep -i hip` 看一眼，找到那一行删掉；
  - **报路径不存在** —— 同上一条，ROCm 装得不完整；
- **怎么停止或撤销**：只读命令，不需要撤销。

**另外两个选项第 18 章会用到：**

```bash
hipconfig -R
hipconfig -l
```

- **作用**：两条。`-R` 打印 ROCm 的根目录，`-l` 打印编译器所在的目录。**第 18 章自己编译 llama.cpp 的 HIP 版本时要用到这两个值**，本章先确认它们报得出来。两条都只读；
- **正常输出**：各一行路径，形如

```text
/opt/rocm
/opt/rocm/lib/llvm/bin
```

**具体路径随版本变化，本项目未固定，需要核验**；

- **看到别的怎么办**：
  - **什么都不输出** —— 这一版的 `hipconfig` 选项写法不同。跑不带选项的 `hipconfig`，在完整输出里找对应的字段；
  - **报的路径用 `ls` 一看不存在** —— ROCm 装得不完整，回第 11 章；
- **怎么停止或撤销**：只读命令，不需要撤销。

## 命令找不到怎么办

`rocminfo`、`rocm-smi`、`hipconfig` 三条里有任何一条提示 `command not found`，看这一节。

**先分清是两种情况里的哪一种：**

```bash
ls /opt/rocm/bin/rocminfo /opt/rocm/bin/rocm-smi /opt/rocm/bin/hipconfig
```

- **作用**：看这三个程序文件在不在 ROCm 的安装目录里。这条命令只读；
- **正常输出**：三行路径，说明文件都在

```text
/opt/rocm/bin/hipconfig  /opt/rocm/bin/rocminfo  /opt/rocm/bin/rocm-smi
```

- **看到别的怎么办**：
  - **三个都在，但敲名字跑不起来** —— **PATH 的问题**。`/opt/rocm/bin` 不在 PATH 里，系统找不到它们。**临时办法是用全路径跑**：`/opt/rocm/bin/rocminfo`。本章的检查用全路径照样做得完，先把检查做完；
  - **提示某一个或几个不存在** —— ROCm 装得不完整。回第 11 章第五步用 `--dry-run` 对照，或者走卸载回退路径拆干净重装；
  - **整个目录都不存在** —— ROCm 没装。回第 11 章；
- **怎么停止或撤销**：只读命令，不需要撤销。

**关于把 `/opt/rocm/bin` 加进 PATH**：这属于改你自己账户的 shell 配置，第 9 章第五步备份过 `~/.bashrc` 和 `~/.profile`。**本教材不在本章做这件事**，理由是本章能用全路径做完，而改 shell 配置改错了会影响你所有的终端会话。真要改，改法和恢复方法在[第 2 卷](../02-Ubuntu/README.md)，改之前把第 9 章那份备份找出来放手边。

## 第一号异常：只看到 CPU，看不到 GPU

`rocminfo` 里只有一个 `Device Type: CPU` 的 agent，没有 GPU 那个。

**这是本章最常见的一种情况。按顺序查三件事，不要跳。**

**一、权限（最常见）**

```bash
groups
```

四件事同第 12 章第四项：作用是打印当前账户所在的组，只读；正常输出里同时有 `render` 和 `video`；缺了就按[第 1 卷第 8 章](../01-开箱与安装/08-第一个账户.md)补加、**然后注销重新登录**；只读命令不需要撤销。

```bash
test -r /dev/kfd && echo 可以读 || echo 不能读
```

四件事同第 12 章第四项：作用是真的试一次能不能读那个设备节点，只读；正常输出是“可以读”；输出“不能读”就是权限没生效，**注销重新登录**再试；只读命令不需要撤销。

**故障总表里对“普通用户跑 `rocminfo` 报权限错误”给的原因就是这一条**：用户不在 `render`、`video` 组里（AMD 官方文档，访问日期 2026-08-13）。

**最容易忽略的一点：组加了但没重新登录。** 第 12 章第四项讲过怎么发现这种情况——`groups` 和 `id -nG` 输出不一致，或者 `groups` 有但 `test -r` 说不能读。

**二、设备节点**

```bash
ls -l /dev/kfd
```

四件事同第 12 章第三项：作用是看这个设备节点在不在、属于哪个组，只读；正常输出一行，属组是 `render`；提示不存在就说明第 11 章那一步没生效，**先确认重启过**（第 11 章第八步），重启过还没有就回第 12 章第二项看 AMDGPU 模块加载了没有；只读命令不需要撤销。

**三、版本**

```bash
hipconfig --version
```

四件事同上面第三样：作用是打印 HIP 的版本号，只读；正常输出是一行版本号；报找不到命令按“命令找不到怎么办”那一节；只读命令不需要撤销。

**低于 7.0.2 的话，gfx1151 不在这一版的官方支持范围里。按第 11 章末尾的卸载路径拆干净重装。**

> **⚠️ 三件事都查完还是看不到 GPU 的时候，不要设 `HSA_OVERRIDE_GFX_VERSION`。**
>
> 那是旧版本的做法，当前版本不需要（Ollama issue #14855，2026-03，同一条来源写明这一点）；其中 `11.0.0` 那种写法在这台设备上是有害的——材料记录在 vLLM 上会让 HIP 计算内核与多设备通信的初始化崩溃、引擎进程直接死掉（**素材记录，本项目来源目录未收录对应条目，需要核验**）。
>
> **正确动作是对照第 8 章那张表核对版本**：内核够不够 6.16.9、ROCm 够不够 7.0.2、你用的那个软件版本够不够新。**三件里任何一件不达标，加变量都不解决问题**（第 7 章原话）。
>
> **已经设了想撤销**：跑 `env | grep HSA` 看当前这个终端里有没有；有的话找到它写在哪儿——可能在 `~/.bashrc`、`~/.profile`，也可能在 `/etc/environment` 或某个服务的配置里——把那一行删掉，重开终端或重启对应的服务。这几处第 9 章第五步都备份过。**服务那一侧怎么看在第 20 章。**

**三件事都正常、版本也够，还是看不到 GPU**：把 `rocminfo` 的完整输出和 `sudo dmesg | tail -40` 一起存下来，去第 20 章、第 23 章。**在 24.04 上跑 ROCm 属于官方支持矩阵之外的社区用法**，第 8 章定下的做法是：遇到 ROCm 那一层说不清的问题，**第一动作是换更新的内核，不是加参数**。

## 第二号异常：权限不足

`rocminfo` 或 `rocm-smi` 报 `Permission denied`，或者报资源不足一类的错。

**几乎总是同一个原因**：当前账户不在 `render` 和 `video` 组里，或者加了组但没重新登录。

按上面第一号异常的第一步查。**加组的操作在[第 1 卷第 8 章](../01-开箱与安装/08-第一个账户.md)，第 11 章第七步也写过，本章不重复教。**

**两件不要做的事：**

- **不要用 `sudo` 跑这几条命令绕过去。** 用 `sudo rocminfo` 确实能跑出来，但那证明的是 root 有权限，**不是你的账户有权限**。你跑推理程序的时候用的是自己的账户，不是 root。用 `sudo` 试一次可以，用来判断权限对不对可以，**但不能当成解决了**；
- **不要去 `chmod` 那些设备节点。** 第 12 章讲过：那些文件每次开机重新生成，改了下次开机就没了。

## 第三号异常：程序报 `hipMalloc` 相关的错

**这一类错出现在你跑程序的时候，不是跑上面那三条命令的时候。**

典型表现：程序报显存申请失败或者内存不足，而 `free -h` 显示宿主机内存还剩很多。故障总表里对应的说法是“加载超过该值的模型报假 OOM”。

**按顺序查三件事：**

**一、ROCm 报出来的显存总量是多少**

```bash
rocm-smi --showmeminfo vram gtt
```

四件事同上面第二样：作用是打印两个内存池各有多大，只读；正常输出里 `GTT Total Memory` 在 120 GiB 量级；数值不对按那一节的四种情况处理；只读命令不需要撤销。

只有 15.5 GB 或者 62.2 GB 的话，按上面第二样那四种情况处理。**这是最常见的成因**——不是模型太大，是 ROCm 只看到了一小块。

**二、有没有设已废弃的那个参数**

```bash
cat /proc/cmdline
```

四件事同第 12 章第五项：作用是打印本次开机传给内核的参数，只读；正常输出里只有[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)那三个；**出现 `amdgpu.gttsize` 就是它**，删掉的完整命令在[第 4 卷第 18 章](../04-Max395硬件/18-不应随意修改的设置.md)第四条；只读命令不需要撤销。

ROCm issue #5595 记录的情形正是这个：设了 `amdgpu.gttsize` 而 TTM 仍为默认值时，**128 GB 的机器照样报内存不足**。

**三、上面两条都对，那就是模型本身超了**

量化档和上下文长度都影响占用（第 6 卷）。**大模型加载有已知的处理办法**（第 4 章、第 7 章都提过，**那条本项目来源目录未收录对应条目，需要核验**），处理在第 17 章和第 23 章。

**本章不处理第三种情况**——那是应用那一层的事，本章只负责确认底下这一层没问题。

## 看到什么算通过

**四条，全部成立才算：**

1. `rocminfo` 里有一个 `Device Type: GPU` 的 agent，**`Name` 是 `gfx1151`**；
2. `rocm-smi` 能跑出表，不报权限错；
3. `rocm-smi --showmeminfo vram gtt` 里 **`GTT Total Memory` 在 120 GiB 量级**，和第 12 章第五项、[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)的内核日志对得上；
4. **`hipconfig --version` 报出的版本不低于 7.0.2**。

**四条都成立，HIP 这条路就算通了。**

## 通了之后不能得出的结论

**这一节和上一节一样重要，尤其是要给客户承诺的时候。**

**一、通了不等于全部算子可用。**

这句话不是本教材的推断，是 AMD 自己在缺陷追踪里写明的限制（ROCm issue #5339，2025-10-14，2026-08-13 核验）。**支持矩阵里有这个标识，和每个算子都有对应实现，是两回事**（第 5 章、第 7 章）。

**二、通了不说明 ROCm 比 Vulkan 快。**

两种结论材料里都有：一条来源称针对 gfx1151，Vulkan 后端效率高于 ROCm／HIP 的实验构建（llama.cpp issue #24438）；同期社区有调优后 HIP 反超的报告。**两者与版本、量化档、上下文长度、具体分支强相关，不能当普适结论。** 本教材不下统一结论，选哪条在第 19 章，测法在[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)。

**三、llama.cpp 走 HIP 有编译条件。**

开 `GGML_HIP_ROCWMMA_FATTN` 这个选项编译会失败，rocWMMA 对 RDNA 3.5 的支持不完备（rocm-libraries issue #4618，2026-02-15，**环境为 Fedora，未覆盖 Ubuntu**）。**本章通过了不代表那条编译路径能走通**，第 18 章处理。

**四、Ollama 走 ROCm，材料内部对立。**

一条记录说 30B 模型约 40 tokens/s 正常可用（Ollama issue #14855）；另一条报告输出通顺但语义完全错误（Ollama issue #17604，2026-08-13 核对已关闭且未显示解决说明，**且原帖标题称两个后端都出过错误**）。

**两条来源直接打架，本教材不替它们下结论**（第 7 章）。实际做法：Ollama 那一侧本教材不默认走 ROCm；真走了之后出现输出乱套，按第 19 章换后端。**这类问题不报错，只能靠人看**——本章四条全过也发现不了它。

**五、vLLM 另说。**

本教材不把 vLLM 列入基准（第 7 章、第 8 章）。两条关键缺陷截至 2026-08-13 核对都还没关闭。**本章通过了，不等于 vLLM 能跑起来。**

**六、还有一批 gfx1151 专有问题。**

第 7 章那张表列了本项目收集到并核对过的那些，**没写进来的不等于不存在**，状态也会变。第 20 章按场景处理。

## 把这一轮输出记下来

```bash
{
  echo "=== 采集时间 ==="; date
  echo "=== rocminfo 关键行 ==="; rocminfo | grep -E "^  Name:|Device Type:"
  echo "=== rocm-smi ==="; rocm-smi
  echo "=== 显存 ==="; rocm-smi --showmeminfo vram gtt
  echo "=== HIP 版本 ==="; hipconfig --version
  echo "=== ROCm 根目录 ==="; hipconfig -R
  echo "=== HSA 相关环境变量 ==="; env | grep HSA
} > ~/minipc-backup/2026-08-14/08-HIP检查.txt 2>&1
```

- **作用**：把上面三样的输出连同标题行一起写进备份目录里的一个文件。写法和第 9 章第三步、第 12 章末尾那一段一样，末尾的 `2>&1` 表示报错信息也一起写进去——**最后那一条 `env | grep HSA` 本来就该没有输出**，那个“空”本身也是要记录的状态（第 7 章）。**日期换成你第 9 章建目录时用的那个**；
- **正常输出**：**屏幕上什么都不显示**，输出全进文件了；
- **看到别的怎么办**：
  - **屏幕上出现 `>` 提示符，光标停住不动** —— 大括号没配对，命令没复制全。按 `Ctrl+C` 取消，**连最后那一行 `} > ... 2>&1` 一起重新复制一次**；
  - **提示 `No such file or directory`** —— 备份目录的日期写错了。跑 `ls ~/minipc-backup/` 看看实际是哪个；
  - **文件里几条命令全是 `command not found`** —— PATH 的问题，把命令改成全路径（`/opt/rocm/bin/rocminfo` 这样）再跑一次；
- **怎么停止或撤销**：跑到一半按 `Ctrl+C` 中断。撤销就是删掉这个文件重跑。**这一段只读系统状态、只写一个新文件，不改动系统上任何东西。**

**把这几项抄进[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)的设备基线：**

```text
ROCm 版本（hipconfig --version 报的）：
GPU agent 名称：gfx1151
GTT Total Memory（rocm-smi 报的）：
GTT 实际生效值（第 12 章第五项的 dmesg）：
本次核对日期：
```

**两个 GTT 数值都记，是因为它们的口径可能不一样**（[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)记录过这件事）。以后出问题时，知道当初这两个数各是多少，能省很多事。

## 正常结果

- `rocminfo` 里有两个 agent，一个 CPU 一个 GPU，GPU 那个的 `Name` 是 `gfx1151`；
- `rocm-smi` 能跑出表，空载时 `GPU%` 接近 0；
- `rocm-smi --showmeminfo vram gtt` 里 `GTT Total Memory` 在 120 GiB 量级，和第 12 章第五项对得上；
- `hipconfig --version` 报出的版本不低于 7.0.2；
- `hipconfig -R` 和 `hipconfig -l` 各报出一个存在的路径（第 18 章要用）；
- `env | grep HSA` 什么都不输出；
- 备份目录里多了 `08-HIP检查.txt`，设备基线也填了。

**这些都成立，ROCm 和 HIP 这条路就算通了。**

## 看到不同结果怎么办

**三条命令全都提示找不到**：先跑 `ls /opt/rocm/bin/` 看文件在不在。在就是 PATH 的问题，用全路径做完本章；不在就回第 11 章。

**只看到 CPU，看不到 GPU**：本章第一号异常那一节，按权限、设备节点、版本的顺序查。**最常见的是加了组没重新登录。**

**报权限错误**：本章第二号异常那一节。**不要用 `sudo` 绕过去当成解决了。**

**显存只有 15.5 GB**：内核版本的问题，升内核，**升之前先做备份**。本章第二样那一节有完整的警告和退路。

**显存只有 62.2 GB**：查 `/proc/cmdline`，有 `amdgpu.gttsize` 就按[第 4 卷第 18 章](../04-Max395硬件/18-不应随意修改的设置.md)第四条删掉；没有 `ttm.pages_limit` 就回[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)补设。**本章不改内核参数。**

**`hipconfig --version` 报的版本低于 7.0.2**：这个组合在这台设备上不成立。按第 11 章末尾的卸载回退路径拆干净重装。

**四条全过，但跑 PyTorch 还是报错**：那是应用那一层的事，第 16 章处理。**先对照第 7 章那张问题表**——PyTorch 那几条记录里，最基础的张量操作触发内存访问错误那一条**环境是 Fedora 与 Nobara，不是 Ubuntu，需要核验**；`torch.randn` 触发缺页那一条是单一构建与内核版本的报告，**未给修复结论**。

**四条全过，但输出的内容明显是错的**：这是最麻烦的一种——**它不报错，你得自己看出来结果是错的**（第 5 章原话）。Ollama 走 ROCm 上有这类报告，材料内部对立（第 7 章）。**先确认输出是不是真的错了**，确认之后按第 19 章换后端。

**你想知道现在该走 Vulkan 还是 HIP**：第 19 章专讲这件事。**本章和第 13 章都通了，说明两条路都可用，选哪条按你要跑什么、按你自己实测的数字定**，不按别人的结论定。

**你搜到的教程让你设 `HSA_OVERRIDE_GFX_VERSION`**：先看那篇教程的日期和版本。**本教材不设这个变量的任何写法**，理由和撤销办法在本章第一号异常那个警告块里，完整说明在第 7 章。

**你在给客户交付，要写“ROCm 可用”这句话**：可以写，但要连着写三样——ROCm 版本号、内核版本、你核对的日期。**同时要写清楚“这台机器上的 ROCm 在 AMD 官方支持矩阵之外”这一条**（第 8 章）。拿本章的通过去背书 vLLM 的部署或者训练场景，是这台设备上最容易出事的一种做法（第 7 章、第 13 卷）。

**表里某条已知问题的状态你想确认现在还在不在**：直接去看对应的页面。本章引用的所有状态核对日期都是 2026-08-13，**这些东西变得很快**（第 8 章）。

- 默认 GTT 上限约为系统内存的 50%：[AMD Strix Halo system optimization](https://rocm.docs.amd.com/en/docs-7.2.0/how-to/system-optimization/strixhalo.html)，AMD 官方文档，访问日期 2026-08-13，面向 ROCm 7.2、不代表 Ubuntu 24.04 上的行为，事实状态 `official_source`。**同一份文档要求内核不低于 6.18.4，本教材基准 6.17 在其之下，含义见第 8 章**；
- 显存方案（BIOS 设最低档加 `ttm.pages_limit=31457280`、`ttm.page_pool_size=31457280`）、120 GiB 的换算、**ROCm 对两个内存池的汇报口径反复过几次、以内核日志与 `/sys` 下的参数文件为准**：[第 4 卷第 6 章](../04-Max395硬件/06-UMA与GTT.md)与[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)已拍板并记录，核验日期 2026-08-13。**本章只核对，不重设**；
