# 09　停止与恢复

## 完成结果

任何时候遇到卡住、出错或意外中断，都知道怎样安全停止并回到可用状态。

## 开始前需要准备什么

只需要读，不需要操作。遇到具体问题时，对照本章找到对应情况处理。

## 新词

**服务**（Service）：在后台持续运行的程序，如本地模型服务、数据库、SSH 服务。系统启动时可以自动开始，也可以手动启动和停止。

**进程**（Process）：正在运行的程序实例。每个进程有一个数字编号，叫做 PID（进程 ID）。

**挂起**（Hang）：程序没有响应，也没有报错，停在那里不动。可能是在等待输入、等待资源，或者遇到了死锁。

**崩溃**（Crash）：程序异常退出，通常会在终端或日志里留下错误信息。

**回退**（Rollback）：把配置或数据恢复到之前某个可用状态。

**快照**（Snapshot）：某个时间点的完整系统或数据副本，用于恢复。

**systemctl**：Ubuntu 里管理服务的命令行工具，可以用来启动、停止、重启和查看服务状态。

**journalctl**：Ubuntu 里查看系统日志的命令行工具，可以显示服务的运行记录和错误信息。

## 遇到命令卡住

在终端运行命令时，命令一直在运行没有结束，或者长时间没有输出：

1. 等待一段时间（下载大文件或处理大量数据时，正常等待时间可能达到几分钟）；
2. 确定需要停止时，按 `Ctrl+C`，这会发送终止信号，大多数程序会停止；
3. 如果 `Ctrl+C` 没有响应，按 `Ctrl+Z` 把程序暂停并挂到后台。这时 shell 会显示一个方括号里的数字，比如 `[1]`，那是**作业号**，指这个终端里第几个后台作业。用作业号终止它：

```bash
kill %1
```

- 作用：给 1 号后台作业发终止信号；
- 范围：只影响当前这个终端窗口里的这个作业，不影响其他终端和系统服务；
- 注意：`%1` 里的 1 要换成你看到的实际作业号。被 `Ctrl+Z` 暂停的程序不一定立刻响应终止信号，等几秒再用 `jobs` 命令确认它是否已经结束；
- 停止方法：这条命令本身瞬间执行完，不需要中断。

4. 如果终端本身没有响应，打开一个新的终端窗口，先查进程 ID：

```bash
ps aux | grep 程序名
```

- 作用：列出当前所有进程，再从里面筛出名字里含有你输入的那段文字的行。中间的 `|` 叫**管道符**，意思是把左边命令的输出交给右边命令继续处理；
- 范围：只读取和显示，不修改任何东西，执行它不会造成损失；
- 结果怎么读：每行第二列的数字就是进程 ID（PID）。你还会看到一行是 `grep` 命令自己，忽略它；
- 停止方法：输出太长刷屏时按 `Ctrl+C`。

确认 PID 之后再终止它：

```bash
kill PID
```

- 作用：给指定编号的进程发终止信号，请它自己退出；
- 范围：只影响这一个进程。**PID 写错会终止别的程序**，所以执行前把上一步查到的数字和进程名再核对一遍；
- 注意：不要对不认识的系统进程执行这条命令。只终止你自己刚才启动的那个程序；
- 如果进程没有退出：说明它不响应普通终止信号。这种情况先到本章“遇到系统卡死”一节按顺序处理，不要直接加 `-9` 强制杀，强制终止可能让它正在写的文件停在写了一半的状态。

## 遇到服务无法启动

服务启动失败时：

```bash
systemctl status 服务名
```

这个命令显示服务的当前状态和最近几行日志，通常可以看到失败原因。

如果需要更多日志：

```bash
journalctl -u 服务名 -n 50
```

`-n 50` 表示显示最近 50 行。把 `服务名` 替换成具体的服务名称，比如 `ollama`（本地模型服务）、`ssh`（远程登录服务）或 `nginx`（一个常用的网页服务程序）。

上面这两条命令都只读取信息，不改变系统状态，可以放心执行。输出太长时按 `Ctrl+C` 或 `q` 退出。

根据日志中的错误信息，进入对应章节的“看到不同结果怎么办”部分处理。不要直接删除服务文件来“解决”问题，先定位原因。

修改配置后，用下面的命令重启服务：

```bash
sudo systemctl restart 服务名
```

- 作用：先停止该服务，再重新启动，让新的配置生效；
- 范围：只影响这一个服务，不重启整台设备。但这个服务在重启的几秒内不可用，如果有人正在使用它，请求会失败；
- 前置条件：命令带 `sudo`，以管理员权限执行，会要求输入你的密码；
- 停止方法：这条命令通常几秒内返回。如果一直不返回，按 `Ctrl+C` 中断，再用 `systemctl status 服务名` 看它当前停在什么状态；
- 恢复方法：重启后服务仍然起不来，说明改动的配置有问题。按本章“遇到配置出错需要回退”一节，用 `.bak` 备份把配置换回去，再重启一次。

## 遇到系统卡死

键盘和鼠标没有响应，屏幕不动，等待 1 分钟后仍然没有恢复：

- 先尝试用 SSH 从另一台设备登录，查看系统状态（前提是 SSH 服务仍然在运行，SSH 登录方法见[第 3 卷](../03-服务器基础/README.md)）；
- 如果无法 SSH，长按电源键 5 到 10 秒强制断电，设备会重启；
- 强制断电后，启动时系统可能提示需要检查文件系统，按提示操作，不要跳过检查。

强制断电不是安全的停止方式，可能导致文件系统出现错误，应避免在数据库写入中途或大文件操作中途使用。重要数据建议定期备份（见[第 3 卷](../03-服务器基础/README.md)备份章节）。

## 遇到本地模型错误

本地模型报错或无法加载时：

1. 记录完整的错误信息（包括所有行，不只是最后一行）；
2. 确认模型文件是否完整，例如用 `ollama list` 列出已安装模型（Ollama 的使用方法见[第 6 卷](../06-本地模型/README.md)）；
3. 确认内存是否足够，运行以下命令查看当前可用内存：

```bash
free -h
```

`-h` 表示以可读格式（GB、MB）显示。`available` 列的数字是当前可以使用的内存量；

4. 关闭其他占用大量内存的服务，再重新尝试加载模型；
5. 问题仍然存在，进入[第 15 卷：故障排查](../15-故障排查/README.md)，按症状查找。

## 遇到配置出错需要回退

修改了配置文件后，服务停止工作：

1. 确认你修改的是哪个配置文件；
2. 如果你修改前有备份（如保存为 `配置名.bak`），用备份替换当前文件，再重启服务；
3. 如果没有备份，配置文件在 Git 仓库内时，用以下命令查看修改内容：

```bash
git diff 配置文件路径
```

查看修改历史：

```bash
git log --oneline 配置文件路径
```

4. 确认修改位置后，手动把改错的内容改回去，再重启服务。

建议：修改任何配置文件之前，先复制一份到同名加 `.bak` 后缀的文件作为临时备份：

```bash
cp 配置文件名 配置文件名.bak
```

## 遇到系统更新中断

系统更新中途断电或中断，或更新后某些服务不能正常工作：

1. 运行以下命令修复中断的包安装：

```bash
sudo apt-get install -f
```

- 作用：`-f` 是修复（fix）的意思。系统检查有哪些软件包的依赖关系断了，然后补装或调整它们，把软件包状态恢复成完整的；
- 范围：**作用于整台设备的软件包，不限于你刚才在装的那一个**。它可能安装新的包，也可能移除冲突的包；
- 执行前先看清楚：命令会先列出打算安装和移除的包，等你输入 `y` 确认才动手。列表里如果出现你不认识的、和当前问题无关的包被移除，先输入 `n` 取消，把这份列表记下来再查，不要直接确认；
- 停止方法：确认之前按 `Ctrl+C` 或输入 `n` 可以安全取消。已经开始安装之后不要中断，中途断开会让软件包状态更乱；
- 恢复方法：执行后系统仍然不正常，记录完整输出，进入[第 15 卷：故障排查](../15-故障排查/README.md)，不要反复重跑这条命令。

2. 运行以下命令检查某个包是否已安装：

```bash
dpkg --list | grep 包名
```

3. 问题仍然存在，记录错误信息，进入[第 15 卷：故障排查](../15-故障排查/README.md)按症状查找。

## 异常处理总结

| 情况 | 第一步 |
| --- | --- |
| 命令卡住 | 按 `Ctrl+C` |
| 服务不启动 | `systemctl status 服务名` 看日志 |
| 系统卡死 | 先尝试 SSH，不行再长按电源键 |
| 模型加载失败 | `free -h` 检查内存 |
| 配置出错 | 恢复备份或 `git diff` 查改动 |
| 更新中断 | `sudo apt-get install -f` |
