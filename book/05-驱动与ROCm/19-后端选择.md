## 新词

**tokens/s**：每秒处理多少个 token，是跑模型时最常看的一个数。**它不是一个数，是两个**——本章第二节讲这件事。

**提示词处理阶段**（prompt eval，也叫预填充）：模型把你给它的那段输入读进去、算出内部状态的过程。**这一段是一次性的，输入多长就要处理多长。**

**生成阶段**（eval，也叫解码）：模型一个 token 一个 token 往外吐的过程。**你看到的“它在打字”就是这一段。**

**计算密集**与**带宽密集**：一个任务是被算力卡住，还是被内存读取速度卡住。**这台设备上这两个阶段分属两边**，是本章解释“为什么不同模型差那么多”的关键。

**降频**：见[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)。

**参数量**：模型有多少个参数，常写成 7B、30B、120B，B 是十亿。

**MoE**（混合专家）：一种模型结构，每次只激活其中一部分参数。**所以 MoE 模型的“实际干活的参数量”比它的总参数量小得多**，速度表现和同样大小的普通模型不一样。

## 一、跑模型时怎么观察这台设备

**先说方法，再说指标。**

### 摆好三个终端

**观察要和跑模型同时进行，所以至少开三个终端窗口：**

| 窗口 | 跑什么 | 看什么 |
| --- | --- | --- |
| 一号 | 推理命令（第 17 章或第 18 章） | tokens/s、有没有报错 |
| 二号 | `radeontop` | GPU 占用、显存占用 |
| 三号 | `watch -n 2 sensors` | 温度 |

**顺序是：先把二号和三号开起来看空闲状态，再在一号里开跑。** 反过来的话你不知道空闲时是什么样，也就看不出变化。

### 装工具

```bash
sudo apt install lm-sensors radeontop
```

- **作用**：一次装两个查看工具。`lm-sensors` 看温度，`radeontop` 看 GPU 占用和显存。**[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)已经装过的会提示已经是最新版**；
- **正常输出**：一串安装进度，或者 `is already the newest version`；
- **看到别的怎么办**：提示找不到包就先 `sudo apt update`。装完 `lm-sensors` 还要跑一次 `sudo sensors-detect`（**一路回车用默认值**），那一步[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)已经写全；
- **怎么停止或撤销**：`sudo apt purge lm-sensors radeontop`。**不建议撤销**，这两个工具只读硬件状态，不改任何东西。

### 看 GPU 有没有在干活

```bash
radeontop
```

- **作用**：实时显示 GPU 各部分的忙闲程度和显存占用。**这条命令只读，不改任何东西**；
- **正常输出**：一个会自己刷新的界面，形如

```text
Graphics pipe  87.50% │ ██████████████████░░ │
      Event Engine   0.00% │                      │
   Vertex Grouper  0.00% │                      │
      Texture Addresser 12.50% │ ██░░░░░░░░░░░░░░░░░░ │
             ...
             vram  1.20% 245.32mb │ ░░░░░░░░░░░░░░░░░░░░ │
              gtt 42.31% 54321.00mb │ ████████░░░░░░░░░░░░ │
```

  **要看的是两行：**

  1. **最上面那一行 `Graphics pipe`（有的版本写 `gpu`）** —— GPU 的总体忙闲。**空闲时接近 0，跑模型时应当长时间保持在高位**；
  2. **`gtt` 那一行** —— 这块 GPU 实际用掉的内存。**这台设备上模型主要占的是这一行，不是 `vram` 那一行**（[第 4 卷第 6 章](../04-Max395硬件/06-UMA与GTT.md)讲过为什么）。

  **字段名、排版和数值随 `radeontop` 版本和内核变化，本项目未固定，需要核验**；

- **看到别的怎么办**：
  - **提示 `command not found`** —— 上一步没装成功；
  - **报权限相关的错** —— 有的机器上要 `sudo radeontop`。**能不加就不加**；
  - **跑着模型，`Graphics pipe` 却接近 0** —— **这是最要紧的一种异常**：模型在 CPU 上跑，GPU 根本没参与。回第 17 章第五步看 `-ngl` 那一项写了没有、加载信息里有没有 offloading 那一行；
  - **`gtt` 那一行的总量明显小于你的内存** —— 显存方案那一层的问题。回[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)和第 12 章，**本章不重设**；
  - **界面乱码或者排版错位** —— 终端窗口太窄。拉宽再试；
- **怎么停止或撤销**：**按 `q` 退出。** 这个程序只读，退出就完了。

### 看显存的另一个读法

**装了 ROCm 的读者还有一条：**

```bash
watch -n 2 rocm-smi --showmeminfo vram
```

- **作用**：每 2 秒刷新一次，显示 ROCm 那一侧报的显存使用情况。**`rocm-smi` 的完整说明和异常分支在第 14 章第二样，本章不重抄**。`watch` 的用法在[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)。这条命令只读；
- **正常输出**：一张表，跟着模型加载往上走，形如

```text
Every 2.0s: rocm-smi --showmeminfo vram

======================= ROCm System Management Interface =======================
GPU[0] : VRAM Total Memory (B): xxxxxxxxxxx
GPU[0] : VRAM Total Used Memory (B): xxxxxxxxxxx
================================================================================
```

  **数值随机器和 ROCm 版本变化，本项目未固定，需要核验**（第 14 章已标注同一条）；

- **看到别的怎么办**：
  - **报的总量和 `radeontop` 的 `gtt` 对不上** —— **这两个工具看的不是同一个东西**，对不上是常态。判断依据以第 14 章那一章为准；
  - **报的总量只有十几 GB** —— 第 7 章那张表里的两条已知问题（内核版本、已废弃的内核参数）。回第 14 章和第 20 章；
  - **模型明明跑着，用量却是 0** —— 跑的是 Vulkan 那条路。**`rocm-smi` 看不到 Vulkan 那一侧的占用**，改用 `radeontop`；
- **怎么停止或撤销**：按 `Ctrl+C` 退出 `watch`。只读命令，不需要撤销。

### 温度、频率和功耗

**这三样[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)已经写全了，本章不重讲。** 那一章有：

- `sensors` 怎么看 CPU 的 `Tctl` 和 GPU 的 `edge`、`junction`；
- `grep MHz /proc/cpuinfo` 怎么看 CPU 频率；
- `cat /sys/class/drm/card*/device/pp_dpm_sclk` 怎么看 GPU 频率（**那一章标注了这条路径未实测，需要核验**）；
- **什么叫降频、两类降频怎么区分**；
- **跑模型时温度和频率的正常变化过程**。

**功耗那一项那一章的原话是：没有功率计就写“未测”。** 系统里读不到整机功耗，[第 4 卷第 10 章](../04-Max395硬件/10-功耗模式.md)讲的是 BIOS 里的功耗档位，不是实时读数。**本章不新增功耗的读法。**

**本章要接上去的只有一句：跑模型时的温度和频率，要在同一次测量里和 tokens/s 一起记。** 温度爬到降频之后 tokens/s 会掉——**分开记就看不出这个因果**。

## 二、tokens/s 到底怎么读

### 它是两个数，不是一个

第 17 章跑完模型时那段统计，形如

```text
llama_perf_context_print: prompt eval time = ...  ms / ... tokens ( ... ms per token, ... tokens per second)
llama_perf_context_print:        eval time = ...  ms / ... runs   ( ... ms per token, ... tokens per second)
```

**两行，两个 tokens per second，说的是两件事：**

| | 提示词处理阶段 | 生成阶段 |
| --- | --- | --- |
| 在干什么 | 把你的输入读进去 | 一个 token 一个 token 往外吐 |
| 统计里哪一行 | `prompt eval` | `eval` |
| 一次跑几个 token | **一批一批地处理** | **一次只能出一个** |
| 卡在哪 | 算力（计算密集） | 内存读取速度（带宽密集） |
| 数字通常 | **大得多** | **小得多** |
| 用户感受 | 提交之后等多久开始出字 | 出字的速度快不快 |

**这两个数不能混着说。** 有人说“这台机器能跑 500 tokens/s”，多半说的是提示词处理那一段；说“能跑 40 tokens/s”，说的是生成那一段。**问清楚是哪一个，这是本章最实用的一句。**

**两个阶段一次只能出一个 token 的原因**：生成下一个 token 要用到上一个 token 的结果，**没法并行**。所以生成阶段的瓶颈在“把模型参数从内存里读一遍要多久”，而不是“算得快不快”。

### 为什么同一台机器不同模型差那么多

**五个变量，每一个都能让数字变好几倍：**

**一、参数量。** 参数越多，生成每个 token 要读的数据越多，生成阶段就越慢。**这是最直接的一条。**

**二、量化档。** 同一个模型压得越狠，文件越小、要读的数据越少、生成越快，**代价是质量下降**（量化档的解释见第 4 章新词，选型在[第 6 卷](../06-本地模型/README.md)）。

**三、模型结构。** MoE 模型每次只激活一部分参数，**所以一个总参数量很大的 MoE，生成速度可能比一个小得多的普通模型还快**。拿总参数量比速度会得出错的结论。

**四、上下文长度。** 上下文越长，每生成一个 token 要照顾的东西越多，**生成速度会随着对话变长而往下掉**。测的时候不固定上下文长度，两次结果没有可比性。

**五、这台机器当时的状态。** 温度爬到降频之后速度会掉（[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)）；BIOS 里的功耗档位不同结果不同（[第 4 卷第 10 章](../04-Max395硬件/10-功耗模式.md)）；机器上同时跑着别的东西也会影响。

**所以：** 一个 tokens/s 的数字，**不写清模型、量化档、上下文长度、后端、软件版本和测的时候机器什么状态，就等于没写。**

### 本教材不给速度数字

**这一条是硬的。**

材料里有两个第三方的速度记录，第 17 章那张表已经列过，这里再说一次它们的限制：

| 数字 | 设备与出处 | 版本与条件 | 日期 |
| --- | --- | --- | --- |
| 30B 级 Qwen3-Coder 达 101.0 tokens/s | 某社区指南，Beelink 机型，个人实测 | **单一作者的机器与软件版本**，没有第三方复测 | 访问日期 2026-08-13 |
| 本机跑 MoE 模型约 40 tokens/s | 某整机商品页的买家评价 | **没给量化档与上下文长度** | **没有绝对日期**，访问日期 2026-08-13 |
| Ollama 跑 30B 模型约 40 tokens/s | Ollama 的一个社区问题追踪帖 | 同帖内对 ROCm 是否可用的记录与另一帖冲突 | 访问日期 2026-08-13 |
| 某场景 31.9 倍提速 | AMD 在 ROCm 的问题追踪里记录 | **单一场景的单次测试**，不是文本生成的 tokens/s | 访问日期 2026-08-13 |

**这四个数字都不是你这台机器的预期值。** 它们的用处是说明某条路“能跑”，不是说明“能跑多快”。

> **给客户承诺速度，只能拿你自己那台机器、在指定版本下、跑指定模型实测出来的数字，并且带上实测日期。** 拿别人的数字做承诺，是这台设备上最容易出事的做法之一（第 7 章、第 8 章、第 13 卷）。

## 三、三条路并列

**先把三条路摆清楚，再谈怎么选。**

| | Vulkan | ROCm／HIP | CPU |
| --- | --- | --- | --- |
| 底下是谁 | Mesa 里的 RADV（第 3 章、第 4 章） | ROCm 那一摞，含 HIP（第 5 章、第 6 章） | 处理器本身 |
| 要不要装 ROCm | **不要** | **要**（第 11 章） | 不要 |
| 装起来多麻烦 | 下载解压（第 17 章） | 装 ROCm，可能还要自己编译（第 11 章、第 18 章） | 什么都不用装 |
| 哪些软件能走 | llama.cpp、Ollama | llama.cpp、Ollama、PyTorch、vLLM | 几乎全都能，但慢 |
| 速度 | **和 HIP 谁快没有定论** | **和 Vulkan 谁快没有定论** | **明显慢**，本教材不当主力 |
| 出问题时的排查面 | 小（少一整层） | 大（多 ROCm 那一层） | 最小 |

**CPU 这条路本章列出来，是为了三件事：**

1. **它是所有后端的兜底。** GPU 那一层出问题时，程序常常自己退回 CPU 跑——**跑得动，但速度没有意义**（第 13 章那一节讲软件模拟时是同一个道理）；
2. **它是排查工具。** 怀疑 GPU 那一层算错了的时候，用 CPU 跑同一个模型同一段提示词对一次，**能分清是模型的问题还是后端的问题**；
3. **不要把“退回 CPU 跑”当成正常。** 第一节那条“跑着模型 `Graphics pipe` 却接近 0”的异常，说的就是这件事。

## 四、决策表

**按你要跑什么查这张表。**

| 你要跑什么 | 推荐走哪条 | 理由 | 当前已知限制 |
| --- | --- | --- | --- |
| **llama.cpp** | **Vulkan**（第 17 章） | 官方每个发布版本直接提供 Ubuntu 预编译包，下载解压就能用；不依赖 ROCm 对 gfx1151 的适配进度 | 长上下文要 `-ub 512`，大模型加载要 `--no-mmap`，**这两条都是素材记录，本项目未复现，需要核验** |
| **llama.cpp，想再比一次** | ROCm／HIP（第 18 章） | 跑通 Vulkan 之后想对比时走 | 开 `GGML_HIP_ROCWMMA_FATTN` 编译失败（rocm-libraries issue #4618，**环境为 Fedora，未覆盖 Ubuntu**）；维护成本高，ROCm 一升级可能要重编 |
| **Ollama** | **Vulkan** | 第 7 章第三条：Ollama 走 ROCm 材料内部对立，**本教材不默认走 ROCm** | 走 ROCm 有输出语义错误的报告（Ollama issue #17604，2026-08-13 核对已关闭且未显示解决说明，**原帖标题称两个后端都出过错误**）；具体配置在[第 6 卷](../06-本地模型/README.md)第 3 章 |
| **PyTorch（推理）** | **ROCm／HIP**（第 16 章） | **没有别的路**。PyTorch 在这台设备上只走 ROCm（第 4 章那张表） | 本项目给不出可推荐的版本号，**需要核验**；材料里的基础操作崩溃与挂起两条记录**环境是 Fedora 与 Nobara，不是 Ubuntu** |
| **PyTorch（训练）** | ROCm／HIP，**并且逐项避雷** | 同上，没有别的路 | bf16 有 5 项精度边界缺陷，特定超参组合梯度必然 NaN（ROCm issue #6034，**训练场景、单一每日构建**）。**本教材主线不是训练** |
| **vLLM** | ROCm／HIP，**走官方容器**（第 15 章） | 官方在这台设备上不提供预编译包，只有源码编译路径 | 两条关键缺陷 2026-08-13 核对仍未关闭（#45871、#32180）；能跑通的姿势是官方容器加 `--enforce-eager` 加纯文本模型，**性能明显下降、视觉模型不能碰**。**不做生产推理端点** |
| **只是想先跑起来看看** | **Vulkan** | 步骤最少，出问题时排查面最小 | 同第一行 |
| **交付给客户** | **Vulkan** | 依赖少、升级轻、出问题时少一整层要查 | 承诺要绑版本号、模型、量化档和实测日期（第 13 卷） |

**这张表的每一行都对应第 7 章那六条场景边界里的一条，本章没有新增任何结论。**

## 五、本教材的默认推荐：Vulkan 优先

**这是本卷的拍板，四条理由。**

**一、它是分场景唯一被多份来源一致认为可以当主力的那条。**

第 7 章场景边界第一条：llama.cpp 和 Ollama 走 Vulkan，是材料里多份来源口径一致认为可以当日常主力的组合。**其余几条路的结论都带条件、带冲突、或者明确不稳。**

**二、装起来最省事，出问题时排查面最小。**

Vulkan 这条路只有两层：内核里的 AMDGPU，加 Mesa 里的 RADV（第 2 章、第 3 章）。**这两层装完 Ubuntu 就有。** ROCm 那条路要在这之上再叠一整摞（第 5 章），出问题时多一层要查。

**三、它不依赖 AMD 的计算栈对 gfx1151 的适配进度。**

第 4 章的原话。**第 7 章那张问题表里的大多数条目，走 Vulkan 这条路根本不会碰到**——它们是 ROCm 那一层的问题。

**四、ROCm 在 Ubuntu 24.04 上属于官方支持矩阵之外。**

ROCm 7.2 的官方文档要求内核不低于 6.18.4，点名的发行版不含 Ubuntu 24.04（AMD 官方文档，访问日期 2026-08-13）。**第 8 章由此定下的三条做法，本章原样引用：**

- **能用 Vulkan 解决的，不装 ROCm；**
- **要跑 PyTorch，装 ROCm，但心里清楚自己在矩阵之外；**
- **遇到 ROCm 那一层说不清的问题，第一动作是换更新的内核，不是加参数。**

> **“Vulkan 优先”不等于“Vulkan 更快”。** 快慢没有定论（下一节）。这条推荐的依据是**稳定性口径的一致性、安装成本和排查成本**，不是速度。

**这也回答了第 5 章末尾那个问题——要不要装 ROCm：**

- **只跑 llama.cpp 和 Ollama：可以不装。**
- **要跑 PyTorch 或 vLLM：装，没有别的路。**
- **拿不准：先不装，按第 17 章跑通 Vulkan 再说。** ROCm 随时可以后补，第 11 章那一章是独立的。

## 六、两处材料冲突，本章并列写，不下统一结论

**这两处第 7 章已经标出来了，本章按同样的处理。**

### 冲突一：Vulkan 和 ROCm／HIP 谁更快

**一边**：针对 gfx1151，Vulkan 后端效率高于 ROCm／HIP 的实验构建（llama.cpp issue #24438，访问日期 2026-08-13）。

**另一边**：同期社区有调优后 HIP 反超的报告。

**两种结论并存，和版本、量化档、上下文长度、具体分支都强相关。** 本教材不替它们下结论。

**实际处理**：**你要知道你这台机器上哪条快，只能自己测一次**，方法在下一节。测出来的结果**只对你这台机器、这个版本、这个模型成立**。

### 冲突二：Ollama 走 ROCm 到底行不行

**一边**：某个社区问题追踪帖记录 30B 模型约 40 tokens/s 正常可用（Ollama issue #14855，2026-03，访问日期 2026-08-13）。

**另一边**：另一个帖子报告输出通顺但语义完全错误（Ollama issue #17604，访问日期 2026-08-13，2026-08-13 核对已关闭且未显示解决说明，**且原帖标题称 Vulkan 与 ROCm 两个后端都出过错误**，与素材“切 Vulkan 即正常”的记录有出入）。

**两条来源直接打架，本教材不替它们下结论。**

**实际处理**（第 7 章第三条的原话落到操作上）：

- **本教材不默认让 Ollama 走 ROCm**；
- **真走了之后出现输出乱套，换后端**；
- **换之前先确认输出是不是真的错了**——这类问题不报错，只能靠人看。**拿同一段提示词让另一条路跑一次，两边输出对着看。**

**Ollama 那一侧怎么切后端**：Ollama 的官方 GPU 支持文档里有 Vulkan 后端的开关（Ollama 官方文档，访问日期 2026-08-13）。**素材里记录的具体环境变量写法（`OLLAMA_VULKAN=1`、`OLLAMA_IGPU_ENABLE=1`，必要时加 `AMD_VULKAN_ICD=RADV`）本项目来源目录未收录对应条目，需要核验**——**动手当天以 Ollama 官方文档上的写法为准**。完整的 Ollama 配置在[第 6 卷](../06-本地模型/README.md)第 3 章。

> **第 3 章那句话在这里落地：看到一个 `名字=值` 的写法，先分清它是给哪一层的。** 上面这几个是给推理框架的环境变量，**不是内核参数**，不写进引导配置。**本教材不设 `HSA_OVERRIDE_GFX_VERSION` 的任何写法**（第 7 章）。

> **⚠️ 要让这类环境变量对以服务方式运行的软件生效，得改它的服务配置文件，改错会让服务起不来。**
>
> **改之前先备份那个文件**：`cp 那个文件 那个文件.bak`。
>
> **恢复方法**：`cp 那个文件.bak 那个文件`，然后 `sudo systemctl restart 服务名`。**服务起不来时用 `sudo journalctl -u 服务名 -n 30` 看最后 30 行日志。**
>
> **怎么确认某个服务当前被设了哪些环境变量、变量写在哪儿、怎么删干净**，在第 20 章第九节。

## 七、怎么在自己这台机器上比一次

**五步，一步都不能省。** 这套方法[第 4 卷第 10 章](../04-Max395硬件/10-功耗模式.md)讲过，本章把它套到后端上。

**第一步：把变量固定下来。**

同一个模型文件、同一个量化档、同一段提示词、同一个上下文长度（`-c`）、同一个生成长度（`-n`）。**这五样有一样不一样，两次结果就没有可比性。**

**第二步：先测空闲状态。**

按[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)的方法，空闲 5 分钟测一次温度和频率。**这是这一轮测量的起点**，不同起点测出来的数不能直接比。

**第三步：一次只跑一条路，跑够时间。**

先跑 Vulkan 那份（第 17 章），记两个 tokens/s、`radeontop` 的占用和 `gtt` 峰值、温度稳态。**跑够 30 分钟以上**——短跑测不出降频，[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)那一节讲过温度爬到稳态要时间。

**第四步：等机器凉回去，再跑另一条。**

**这一步最容易被跳过。** 上一轮结束时机器是热的，接着跑下一轮，第二条路天然吃亏。**等温度回到空闲状态附近再开始。**

**第五步：重复两三次再下判断。**

单次结果的波动可能比两条路的差距还大。**两三次的结果方向一致，才算一个结论。**

> **测完把两轮结果都填进[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)的基线表，一轮一份，注明后端。** 只留赢的那一份，以后就不知道差距有多大了。

**测出来之后怎么用：**

- **差距很小（一两成以内）** —— **选 Vulkan**。省下来的是维护成本和排查成本，那比这点差距值钱；
- **HIP 明显快，并且你愿意长期维护它** —— 可以用，**但要清楚 ROCm 一升级可能要重编**（第 18 章）；
- **差距很大但方向不稳，几次测下来一会儿这边快一会儿那边快** —— **说明还有没控住的变量**。回第一步；
- **不管怎么测都比材料里那些数字低很多** —— 正常，那些数字不是你这台机器的预期值。**和你自己的基线比，不和它们比。**

## 八、什么时候该换后端

**四种情况：**

**一、当前这条路跑不起来。** 报错在第 20 章的症状表里对，**先按那一章处理，不要一上来就换后端**——换了之后问题还在的话，你白折腾一遍。

**二、输出内容不对。** 输出通顺但语义错、无视提示词（第 7 章第三条）。**先确认是不是真的错了**，再换另一条路跑同一段对照。

**三、要跑的东西这条路走不了。** 要跑 PyTorch 或 vLLM，Vulkan 这条路没有——**这不是换后端，是本来就得走另一条**（第 4 章那张表）。

**四、实测下来另一条明显更好，并且你复测过。** 按上一节那五步走完。

**不该换后端的情况也说一下：**

- **看到网上有人说另一条更快** —— 那是别人的机器（本章第二节）；
- **机器整个卡住、桌面假死** —— **那多半不是后端的问题**。第 7 章第六条：这类问题和你用哪个推理框架无关，**先查固件版本和最近的系统更新**（第 2 章第五节），处理在第 20 章；
- **显存看起来不对** —— 那是显存方案那一层（[第 4 卷第 6 章](../04-Max395硬件/06-UMA与GTT.md)、[第 4 卷第 9 章](../04-Max395硬件/09-UMA设置.md)）或者第 7 章那两条已知问题，换后端解决不了。

## 正常结果

读完并做完本章，你应当有这几样：

- 三个终端并排，跑模型的同时能看到 GPU 占用、显存、温度；
- 你能说出 tokens/s 是两个数、分别对应哪两个阶段、各自卡在什么上；
- 你能说出让同一台机器上不同模型速度差很多的五个变量；
- 基线表第八组填好了，**tokens/s 那一行写了两个数并注明了后端和日期**；
- 你手上有一张决策表：要跑什么，走哪条路，理由和限制是什么；
- 你知道**本教材的默认推荐是 Vulkan 优先，以及那四条理由**；
- 你知道**这条推荐的依据不是速度**——快慢没有定论；
- 你知道那两处材料冲突本教材并列写，**不下统一结论**；
- 你知道要比一次得走哪五步，以及为什么第四步不能省。

## 看到不同结果怎么办

**你测出来 HIP 比 Vulkan 快**：材料里两种结论都有。**这只对你这台机器、这个版本、这个模型成立**，记进基线，不要写成普遍结论。

**你测出来两条路差不多**：**选 Vulkan**，理由是本章第五节那四条，和速度无关。

**你测出来的数字比材料里那几个低很多**：正常。那些数字来自不同机型、不同版本、不同量化档和上下文长度，**都不是你这台机器的预期值**（第 7 章已标注同一条）。

**跑模型时 `radeontop` 里 GPU 占用一直很低**：**先确认层放到 GPU 上了没有**（第 17 章第五步 `-ngl` 那一项）。放上去了还低的话，看是不是在提示词处理和生成之间来回切——**生成阶段本来就是带宽密集，GPU 的算力单元不一定跑满**。判断依据是 tokens/s 有没有明显低于你自己上一次的基线。

**跑着跑着 tokens/s 掉下来了**：先看温度。**温度到稳态之后降频，速度会掉**（[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)那一节讲过两类降频怎么区分）。也可能是上下文变长了——**对话越长生成越慢，这是正常的**。

**客户问你这台机器能跑多少 tokens/s**：**反问三件事**——跑什么模型、什么量化档、多长的上下文。**这三件不定，这个问题没有答案。** 定了之后自己测一次，报你测出来的数字，带日期和版本（第 13 卷）。

**有人拿一个 tokens/s 的数字来跟你比**：**问清楚是哪个阶段的数**（本章第二节第一张表）。提示词处理那一段的数字比生成那一段大得多，混着说会得出完全错的结论。

**你想装个图形界面的工具来看这些**：本教材用命令行工具，理由是不依赖桌面、能远程看、能存成文本进基线（[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)）。材料里提到过 `amdgpu_top` 这一类，[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)标注了**本项目未实测，需要核验**。

**你只装了 Vulkan、没装 ROCm，本章有一半命令跑不了**：**正常，那是设计如此**。`rocm-smi` 那一条跳过，`radeontop` 和 `sensors` 两条不需要 ROCm。
