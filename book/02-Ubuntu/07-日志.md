# 07　日志

## 这一章的任务

让一个服务当场起失败，然后从日志里把失败的原因找出来。

做完之后，机器上任何一个服务出问题，你都知道去哪儿看、怎么把有用的那几行捞出来、怎么存成文件发给能帮上忙的人。第 6 章的 5 个动作管的是启停，这一章管的是起不来的时候怎么办。

## 开始前

- 第 6 章的 `systemctl status` 会用了；
- 用有 `sudo` 权限的账户操作；
- 20 分钟。

## 新词

**日志**（Log）：程序把自己干了什么、出了什么错，一行一行记下来的文字。每行开头通常是时间。

**journald**：systemd 的日志服务。全系统的日志由它收在一起，用 `journalctl` 这个命令读。它存的是二进制格式，用 `cat` 打不开，必须用 `journalctl`。

**分页器**（Pager）：输出超过一屏时系统自动调用的翻页程序，Ubuntu 上是 `less`。方向键翻行，空格翻页，`q` 退出。第 6 章说 `status` 的输出按 `q` 退出，退的就是它。

**日志级别**（Priority）：每条日志带一个严重程度。常用的三档从重到轻是 `err`（错误）、`warning`（警告）、`info`（一般信息）。按级别过滤能一下子把噪音去掉。

## 日志在两个地方

**第一个地方是 journal**，systemd 管的那套。系统自己、所有服务、内核，日志都进这里。看它用 `journalctl`。这是本章的主角。

**第二个地方是 `/var/log` 目录**，一批程序自己写的文本文件。看看有哪些：

```bash
ls /var/log
```

作用：列出这个目录下的日志文件。里面的东西各机器不一样，装了什么软件就多什么文件。

任何一台 Ubuntu 上都有的两个，值得记住：

```bash
tail -20 /var/log/apt/history.log
```

作用：看最近几次装了、卸了、升级了哪些软件包，`tail -20` 是只看最后 20 行。哪天系统突然不对劲，先看这个文件里最近动过什么，常常一眼就找到原因。

```bash
tail -20 /var/log/dpkg.log
```

作用：比上一个更细，每个包的安装动作一行一行记着。

`syslog`、`auth.log` 这类文件有的机器有、有的没有，取决于装没装 `rsyslog` 那个老牌日志程序。你的 `/var/log` 里没有它们不是故障，说明这台机器的系统日志只进 journal，去 `journalctl` 里查就是了。

普通账户能不能读全部系统日志，看它在不在 `adm` 组里。Ubuntu 安装时建的第一个账户默认在，所以下面的命令不用 `sudo` 也能跑。哪条命令输出空空的或者说没权限，前面加 `sudo` 再来一次。

## 制造一个错误

要练怎么找错，手上得先有一个错。下面这条命令临时造一个服务，让它去列一个根本不存在的目录，它必然失败：

```bash
sudo systemd-run --unit=log-demo /usr/bin/ls /no-such-directory
```

- `systemd-run` 的作用是临时造一个服务，跑一条命令。这个服务不写配置文件，跑完就不占地方；
- `--unit=log-demo` 给它起个名字，等会儿要拿这个名字查日志；
- 后面那两段是让它执行的命令，`/usr/bin/ls` 必须写完整路径，`/no-such-directory` 是一个不存在的目录。

正常输出一行：

```
Running as unit: log-demo.service
```

这行的意思是“已经作为 log-demo.service 跑起来了”，不代表它成功了。它一秒之内就会失败。

## 从日志里找出原因

### 第一步，看状态

```bash
systemctl status log-demo
```

输出类似：

```
× log-demo.service - /usr/bin/ls /no-such-directory
     Loaded: loaded (/run/systemd/transient/log-demo.service; transient)
  Transient: yes
     Active: failed (Result: exit-code) since Thu 2026-08-14 15:20:11 CST; 12s ago
    Process: 12345 ExecStart=/usr/bin/ls /no-such-directory (code=exited, status=2)
```

`Active` 那行是 `failed`，和第 6 章 `active (running)` 的位置是同一行。这一步只告诉你“它挂了”，没告诉你为什么挂。

### 第二步，看它的日志

```bash
journalctl -u log-demo
```

- `-u` 后面跟服务名，意思是只看这一个服务的日志。不加 `-u` 就是全系统的日志混在一起，几万行，没法看；
- 这是本章最重要的一条命令。以后任何服务出问题，第一反应就是它。

输出类似：

```
8月 14 15:20:11 minipc-01 systemd[1]: Started log-demo.service.
8月 14 15:20:11 minipc-01 ls[12345]: /usr/bin/ls: 无法访问 '/no-such-directory': 没有那个文件或目录
8月 14 15:20:11 minipc-01 systemd[1]: log-demo.service: Main process exited, code=exited, status=2
8月 14 15:20:11 minipc-01 systemd[1]: log-demo.service: Failed with result 'exit-code'.
```

**第二行就是原因**：那个目录不存在。系统语言是英文的话这行显示成 `cannot access '/no-such-directory': No such file or directory`，说的是同一件事。

每行的格式是固定的：时间、主机名、哪个程序写的（方括号里是它的 PID），然后才是内容。

怎么在一堆日志里认出关键那行？往下看三条经验：

1. **看最后 20 行就够**。服务失败时，原因通常紧挨着失败那几行；
2. **`systemd[1]` 开头的行是系统在报告状态**，`Started`、`Failed with result` 这类，它只说结果；
3. **程序名开头的行才是程序自己说的话**，上面那行 `ls[12345]` 就是。真正的原因几乎总在这种行里。

### 第三步，清理

```bash
sudo systemctl reset-failed log-demo
```

作用：把这个失败记录清掉，`systemctl status log-demo` 之后会提示找不到这个服务。日志还在，`journalctl -u log-demo` 照样查得到。

## 四个常用法

下面拿 `cron` 这个服务举例。它负责按时间自动执行命令，每台 Ubuntu 上都有、一直在跑、也一直在写日志，拿来练手正合适，下一章会正式用到它。

### 一、`-u` 只看一个服务

```bash
journalctl -u cron
```

服务名换成你要查的那个。名字记不准就用第 6 章的 `systemctl list-units --type=service` 先列一遍。

### 二、`-n` 只看最后几行

```bash
journalctl -u cron -n 50
```

作用：只显示最近 50 行。不加 `-n` 的话，日志从几天前开始滚，翻半天翻不到你要的地方。**日常查问题就用这个，先看 50 行，不够再加。**

### 三、`-f` 盯着新出来的日志

```bash
journalctl -u cron -f
```

作用：先显示最后几行，然后停在那里不退出，有新日志就实时打出来。

用法是开两个终端窗口：一个跑着 `-f` 盯日志，另一个去执行 `sudo systemctl restart 服务名`，重启过程中冒出来的每一行都会当场出现在第一个窗口里。服务起不来时这是最快的排查方式。

按 `Ctrl+C` 退出，注意不是 `q`。

### 四、`--since` 按时间截取

```bash
journalctl -u cron --since today
```

作用：只看今天的。`--since` 认好几种写法：

```bash
journalctl --since "2026-08-14 09:00" --until "2026-08-14 10:30"
```

```bash
journalctl --since "1 hour ago"
```

```bash
journalctl --since "2 days ago" -u cron
```

日期和时间要用引号包起来，中间有空格，不加引号 shell 会当成两个东西。`--until` 是截止时间，不写就到现在。

**“昨天下午三点多的时候出过一次问题”这种情况，用的就是它。** 把时间范围掐到出问题那前后十分钟，几万行日志立刻剩下几十行。

## 按关键词找

管道符 `|` 和 `grep` 在第 2 章用过，日志上照样用：

```bash
journalctl -u cron --since today | grep -i error
```

`grep` 只留下含指定关键词的行，`-i` 表示不分大小写，`Error`、`ERROR`、`error` 都能匹配上。常用的关键词就那么几个：`error`、`fail`、`denied`、`refused`、`timeout`。

只看出错的，不看别的：

```bash
journalctl -p err -b
```

- `-p err` 表示只要 `err` 及以上级别的日志；
- `-b` 表示只看本次开机以来的。`-b -1` 是上一次开机那一段，机器自己重启过之后想知道重启前发生了什么，用它。

这条命令输出很短，正常的机器上可能只有几行，是开机之后做一次体检的好办法。

配套的还有一条，第 6 章提过：

```bash
systemctl --failed
```

作用：列出所有起失败的服务。输出是 `0 loaded units listed` 就是没有服务出问题。

## 把日志存成文件发出去

自己看不懂，要发给卖方或者会的人，别截图，截图看不全也搜不了。存成文本文件：

```bash
journalctl -u cron -n 200 --no-pager > ~/ai/data/cron-2026-08-14.log
```

- `>` 表示把输出写进文件，不显示在屏幕上。**文件已经存在的话会被覆盖**，所以文件名带上日期；
- `--no-pager` 表示不要翻页，一次全吐出来；
- 存进 `~/ai/data` 是因为第 1 章约定原始资料放这儿。

看一眼存出来的文件有多少行：

```bash
wc -l ~/ai/data/cron-2026-08-14.log
```

**发出去之前先读一遍。** 日志里可能带着你的账户名、内网地址、文件路径，有的程序还会把令牌写进日志。哪些内容不能往外发、发之前怎么检查，见[第 0 卷第 8 章](../00-使用说明/08-文件保护.md)，这里不重复。

## 日志占了多少地方

```bash
journalctl --disk-usage
```

正常输出一行，例如 `Archived and active journals take up 320.0M in the file system.`。

日志会一直长，系统默认按磁盘剩余空间自动限制，一般不用管。真觉得占多了，删掉旧的：

```bash
sudo journalctl --vacuum-time=7d
```

作用：只保留最近 7 天的日志，更早的删掉。执行完会列出删了哪些文件。

想设一个固定上限，要改 journald 的配置文件，那是第 11 章的内容。

有哪一步做不出来，到[第 15 卷：故障排查](../15-故障排查/README.md)按症状查。

## 完成检查

- `sudo systemd-run --unit=log-demo /usr/bin/ls /no-such-directory` 执行之后，`systemctl status log-demo` 的 `Active` 那行是 `failed` 吗？
- `journalctl -u log-demo` 的输出里，你能指出哪一行是真正的失败原因吗？
- `systemd[1]` 开头的行和程序名开头的行，哪种更可能写着原因？
- `-n 50`、`-f`、`--since today` 三个分别在什么时候用？
- 退出 `-f` 按什么键，退出分页器按什么键？
