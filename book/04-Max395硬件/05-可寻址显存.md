# 05　可寻址显存

## 完成结果

能说清 GPU 实际能用到多少内存由哪几件事决定，能区分 BIOS 静态预留和内核动态分配这两条路径，知道 Windows 上看到的上限为什么和 Linux 不一样，并且能识别几个常见的错误认知。

## 开始前需要准备什么

- 读过第 4 章，知道 128 GB 是整机内存；
- 本章末尾有三条只读命令，想跟着看的话需要一台装好 Ubuntu 的设备；
- **本章不改任何设置。** 改 BIOS 的操作在第 7 章和第 9 章，改内核参数的操作在第 9 章。

## 新词

**可寻址显存**（graphics-addressable memory）：GPU 在某一时刻能够访问到的那部分内存的总量。这台设备上它不是一个固定的硬件参数，而是由 BIOS 设置、内核配置和软件读法共同决定的一个结果。

**静态预留**：开机时就固定切走一块内存交给 GPU，之后不再变动。操作系统看不到这一块，也拿不回来。BIOS 里那个选项管的就是它，常见名称是 UMA Frame Buffer Size。

**帧缓冲**（Frame Buffer）：原本指存放屏幕画面的那块显存。BIOS 里的选项沿用了这个名字，但实际预留的这块内存不只用于显示。

**动态分配**：不预先切走，GPU 需要多少，内核就临时把系统内存映射给它用，用完还回来。这台设备上负责这件事的机制叫 GTT，第 6 章展开。

**内核参数**：Linux 内核启动时接受的一串设置，写在引导程序的配置里，开机时传给内核。改它需要改配置文件并重启，改错会开不了机——[第 1 卷第 12 章](../01-开箱与安装/12-硬件问题处理.md)已经提醒过这一点。本教材要用到的参数在第 6 章说明，操作步骤在第 9 章。

**OOM**（Out Of Memory，内存不足）：进程要的内存拿不到时的报错。跑模型时最常见的形式是模型加载到一半失败，或者进程被系统杀掉。

**专用显存与共享内存**：Windows 任务管理器里的两个说法。“专用显存”对应静态预留的那一块，“共享内存”对应可以临时借用的系统内存。Linux 下没有完全对应的两个词，这是两套系统数字对不上的原因之一。

**GB 与 GiB**：两种不同的换算。1 GB = 1000³ 字节，1 GiB = 1024³ 字节，1 GiB 约等于 1.074 GB。厂商标容量用 GB，Linux 的很多工具显示的是 GiB。128 GB 的机器在 `free -h` 里显示约 125 Gi，一部分差额就来自这里。本章和第 6 章出现 GiB 的地方都是有意写的，不是笔误。

## GPU 实际能用到多少内存，由什么决定

四道门，**最小的那道决定结果**。

**第一道：BIOS 里的静态预留**

BIOS 里那个 UMA Frame Buffer Size（不同厂商也叫 Graphics Memory Allocation、GPU Memory、Variable Graphics Memory）决定开机时切走多少内存给 GPU 独占。

本教材把它设成最低档，[第 1 卷第 7 章](../01-开箱与安装/07-安装Ubuntu.md)在装系统之前就已经带你设过了：**最低可选值，常见是 512 MB；如果最低只有 2 GB，就设 2 GB。** 为什么这样设，第 6 章讲。

**第二道：内核允许 GPU 动态借用的上限**

内核里有一个上限，限制 GPU 最多能临时借用多少系统内存。AMD 官方的 ROCm 文档写明：**默认的 GTT 上限约为系统内存的 50%**（来源：AMD Strix Halo system optimization，访问日期 2026-08-13）。

也就是说，一台 128 GB 的机器，什么参数都不改的情况下，GPU 大约只能用到 60 GB 出头。要突破这个默认值，需要改一个内核参数（第 6 章讲原理，第 9 章给操作）。

**第三道：内核版本**

有些上限是内核版本本身造成的，改参数绕不过去：

- 内核 6.15 及更早版本上，ROCm 在 gfx1151 上**只看得到约 15.5 GB**，无论 BIOS 和参数怎么设。这个缺陷在内核 6.16.9 起修复（来源：ROCm issue #5444，2026-08-13 核对已关闭并标记已解决）；
- 内核 6.17 上，如果设了旧的 `amdgpu.gtt_size` 参数而 TTM 那边还是默认值，两边数值不一致，系统日志会报警告，HIP 只看到 62.2 GB（来源：ROCm issue #5595，访问日期 2026-08-13）。

所以遇到“显存上不去”，第一件要查的是内核版本，不是继续加参数。

**第四道：上层软件怎么读这两个池**

即使前三道都对了，具体某个软件也可能只读其中一部分：

- 旧版 Ollama 只读 iGPU 的专用显存、忽略动态借用的那部分，于是把 GPU 判成显存不足（来源：Ollama issue #12062，访问日期 2026-08-13）。这是历史缺陷，**已在后续版本修复**，不能用来判断当前版本的行为；
- LM Studio 按静态显存数判断能不能把模型层交给 GPU，BIOS 设成 512 MB 之后可能直接拒绝。这条记录来自项目补充材料引用的 lmstudio-ai/lms issue #589 口径，本项目**未上网核对原始页面，需要核验**。本教材主线用的是 llama.cpp、Ollama 和 vLLM，不受这个问题影响；坚持要用 LM Studio 图形界面的读者需要知道这个坑；
- `nvtop`、`btop` 这类监控工具会一直显示很小的显存数（例如 512 MB），因为它们读的是静态那一块。**这是显示问题，不是配置失败**（第 3 章、第 6 章）。

## 两条路径：静态预留和动态分配

| | BIOS 静态预留 | 内核动态分配 |
| --- | --- | --- |
| 谁决定 | BIOS 里的 UMA Frame Buffer Size | 内核参数设定的上限 |
| 什么时候生效 | 开机时切走，之后不变 | 用的时候才映射，用完还回来 |
| 空闲时这块内存归谁 | 归 GPU，系统拿不到 | 归系统，照常用作程序内存和文件缓存 |
| 上限 | BIOS 菜单里能选到的最大档，材料记录常见到 96 GB | 由内核参数决定，本教材设为 120 GiB |
| 改动方式 | 进 BIOS 改（第 7 章、第 9 章） | 改内核参数并重启（第 9 章） |
| 怎么验证 | 系统日志里的 VRAM 那一行 | 系统日志里的 GTT 那一行，以及内核参数文件 |

**这两条路径不是二选一，是相加的。** GPU 能用的总量等于静态预留那块加上动态借用的那部分。本教材的做法是把静态那块压到最低、把额度全部让给动态那条路，理由是第 6 章的内容。

**关键差别在于“拿不拿得回来”**：静态预留切走的内存，你不跑模型的时候也是空着的，系统一个字节都用不上；动态分配的额度是一个上限，不加载模型时那部分内存照常归系统用。

## 为什么 Windows 上看到的上限和 Linux 不一样

网上很多讨论会说“Max395 最多能分 96 GB 显存”。这句话有它的适用范围。

Jeff Geerling 在 2025-08-08 的实测文章里写明：**96 GB 是 BIOS 菜单和 Windows 的上限，不是 Linux 的上限**（来源见本章末尾，个人实测，单机结果，当时的固件与内核环境）。

三点区别：

1. **Windows 主要靠静态那条路。** 驱动汇报的是“专用显存”加“共享内存”两个数字，用户能调的是 BIOS 里那一档，所以菜单上限就成了实际上限；
2. **Linux 走的是动态分配那条路。** 上限由内核参数决定，能设到比 96 GB 更高。本教材设的是 120 GiB（第 6 章）；
3. **所以论坛上的“96 GB 上限”多数在讲 Windows 或者 BIOS 菜单**，不是在讲你这台 Ubuntu 机器。

**日期口径也要一起看。** 同一位作者在 2025 年 8 月的环境下实测：超过约 108 GB 加载会出现段错误。一年后社区的常态数值是 120 到 124 GiB（strixhalo.wiki 用 120 GiB 并建议留 8 GB 余量；kyuz0 的工具箱用 124 GiB）。固件和内核都在变，**同一个数字在不同日期的含义不同**。引用别人的数值时，把日期、内核版本和机型一起抄下来。

## 常见的错误认知

**一、以为 128 GB 全部可以当显存用**

不行。系统、桌面、缓存和推理进程本身都要占内存。全部划给 GPU 的结果是整机变慢甚至卡死。本教材的默认是给 GPU 120 GiB 的额度，留 8 GiB 给系统（第 6 章）。

这个说法之所以流传，一部分原因是厂商页面会写“128 GB 共享内存”，那说的是这块内存**可以被 GPU 访问**，不是“全部同时给 GPU”。

**二、以为 BIOS 里设得越大越好**

不对。静态预留切走之后系统拿不回来。BIOS 设 96 GB 的机器，系统只剩 32 GB，还要装下桌面、推理进程自身和文件缓存；而动态分配这条路空闲时那部分内存还归系统用。为什么本教材否决 BIOS 静态设大，第 6 章有完整理由。

**三、以为监控工具显示 512 MB 就是没配置成功**

不是。`nvtop`、`btop` 显示的是静态那一块，它们没有适配动态显存。判断标准是系统日志里的 GTT 那一行，以及实际加载模型时的占用曲线（第 6 章给方法，第 9 章给操作）。

**四、以为内存够大就能跑**

容量决定装不装得下，带宽决定跑多快，这是两件事（第 4 章）。128 GB 能装下 100B 级别的量化模型，速度是另一回事，要按你自己那台机器实测（第 16 章）。

**五、以为设了参数还上不去就是参数写错了**

不一定。内核版本、参数之间不一致、软件版本太旧，都会造成同样的现象。看到 15.5 GB 就查内核版本，看到 62.2 GB 或者刚好一半的数字就查参数是不是没生效、是不是和别的参数冲突（本章第 1 节的第三道门）。

## 怎么看自己那台机器现在是什么状态

下面三条都是只读命令，只看不改。**改的步骤在第 9 章。**

**看内核收到了哪些参数**

```bash
cat /proc/cmdline
```

输出的是本次开机传给内核的完整参数行。没改过的机器上看不到 `ttm.` 开头的参数，属正常。

**看内核认到的显存**

```bash
sudo dmesg | grep -i "amdgpu.*memory"
```

预期能看到两行，一行是 VRAM（对应 BIOS 里的静态预留），一行是 GTT（对应动态分配的上限）。数值随你的设置变化。这两行是判断配置有没有生效的**主要依据**，比监控工具的显示可靠。

**看动态分配的上限**

```bash
cat /sys/module/ttm/parameters/pages_limit
```

输出是一个页数，不是 GB。换算方法在第 6 章。

> 这三条命令在第 9 章还会用到，那一章是完整的设置和验证流程。现在跑一遍是为了知道你机器的起点在哪里。看到的数字先记下来，第 16 章建立设备基线时要用。

## 正常结果

读完本章，你能说清：GPU 能用多少内存由 BIOS 预留、内核上限、内核版本和软件读法四件事共同决定，取最小的那个；静态和动态两条路的差别在于空闲时那块内存归谁；96 GB 是 Windows 和 BIOS 菜单的上限，不是 Linux 的上限。

在没改过参数的机器上，你跑那三条命令看到的大致是：`/proc/cmdline` 里没有 `ttm.` 参数，日志里的 GTT 数值约为系统内存的一半。

## 看到不同结果怎么办

**`sudo dmesg | grep -i "amdgpu.*memory"` 什么都没输出**：可能是关键词不匹配（不同内核版本的日志措辞略有差异），先去掉过滤看全量输出里有没有 amdgpu 相关行；也可能是日志被后来的内容冲掉了，重启后立刻再查一次。这条命令只读日志，多跑几次没有风险。

**GTT 显示的数值大约是内存的一半**：这是**默认状态，不是故障**。AMD 官方文档写明默认上限约为系统内存的 50%。要提高见第 6 章和第 9 章。

**ROCm 只看到约 15.5 GB**：查内核版本 `uname -r`。6.15 及更早版本上这是已知缺陷，任何参数都绕不过去，唯一出路是升级内核（第 9 章会给方法）。

**日志里报 GTT 和 TTM 数值不一致**：说明同时设了两套管同一件事的参数，且数值不同。本教材只用一套写法，第 6 章有明确的“不要用的写法”清单。

**监控工具显示 512 MB**：正常，见上面第三条错误认知。

**你在 Windows 下看到的可用显存和 Linux 完全对不上**：两套系统的统计口径不同，不需要对齐。以 Linux 下日志里的数值为准。
