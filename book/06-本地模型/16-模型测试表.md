# 16　模型测试表

## 这一章的任务

把前面十五章装过的模型，一个一个在自己这台机器上量一遍，写成一份留得住的记录，并且接进[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)那份设备基线。

**这是本卷的收尾章。** 做完之后，第 1 章那两张“这台机器能跑什么”的对照表——那两张表每一行都标着“需要核验”——**就被你自己的实测替换掉了。**

- 第 8 章做完，接口通了，第 8 章那个 Python 环境还在，里面装了 `openai` 这个包；
- 第 3 章那三层判断你会用（`ollama ps`、`radeontop`、看日志）；

- [第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)那份设备基线在手上。**还没建的，先去建，这一章的结果要往里填**；
- 第 1 章那两张对照表翻出来放旁边，**测完拿实测数去对**；
- 机器上没有别的重活在跑；
- **一个模型 15 到 20 分钟。** 三四个模型测下来是半天，加上温度那一档要留一个多小时。

## 新词

**加载时间**：从发出第一个请求，到模型被读进内存、开始回答，中间这段时间。**它主要由模型文件大小和硬盘读取速度决定**，和模型聪不聪明没关系。

**首字延迟**：从发出请求到看见第一个字冒出来，花了多少秒。**这是人在界面上感受到的“卡不卡”。** 模型已经在内存里的情况下，它主要由提示词的长度决定。

**生成速度**：模型每秒吐出多少个 token。**这是人感受到的“说话快不快”。**

**实测记录**：你在自己这台机器上、在写清楚的条件下量出来的一组数。**它和别人发的数字不是同一类东西。**

> **prompt 处理和生成是两个阶段，速度不是一个数。** 这件事[第 5 卷第 19 章](../05-驱动与ROCm/19-后端选择.md)已经讲透，**本章不重讲**——本章只按上面这三项分别量，量到哪儿算哪儿。

## 为什么必须自己测

**三条理由，一条比一条实际。**

**一、别人的数字不是你的。** [第 5 卷第 17 章](../05-驱动与ROCm/17-llama.cpp-Vulkan.md)记过材料里两个流传很广的速度数字，一个是某社区指南在别的机型上的个人实测，一个是某商品页上买家评价里的一句话，**两个都没给量化档和上下文长度，也没有第三方复测**。它们说明这条路可用，不说明你能跑多快。

**二、第 1 章那两张表在等这一章。** 那两张表最后有一句话：表里的“体验”那一列是按参数量、模型结构和内存带宽做的方向性判断，**本项目没有在这台设备上逐行实测过，以第 16 章的实测记录为准**。**这一章就是那个“为准”。**

**三、交付要拿自己的数字。** [第 5 卷第 17 章](../05-驱动与ROCm/17-llama.cpp-Vulkan.md)那句话在这里落地：承诺只能拿你自己那台机器在指定版本下的实测数字，**带版本号和实测日期**。客户问“这台机器跑 30B 的模型快不快”，你手上有这张表，答得出来。

## 测哪六项

| 项目 | 怎么来的 | 说明什么 |
| --- | --- | --- |
| 加载时间 | 卸载模型之后第一次调用的耗时 | 换模型要等多久。**大模型这一项很可观** |
| 首字延迟 | 流式调用里第一个字出现的时刻 | 人在界面上感受到的卡不卡 |
| 生成速度 | 生成阶段的耗时除以生成的量 | 人感受到的说话快不快 |
| 内存占用 | `free -h` 和 `radeontop` 的 `gtt` | 第 1 章那条预算算得准不准 |
| 温度稳态 | [第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)的方法 | 这个模型能不能长时间跑 |
| 体验评价 | **你自己看它答得对不对** | 上面五项都答不了这一条 |

**最后一项没有数字，但它最重要。** 第 1 章说过：参数量和量化档能告诉你它跑不跑得动，**告诉不了你它答得对不对**。一个跑得飞快但中文别扭、经常答非所问的模型，速度数字再好看也没用。

**体验评价怎么记**：用你自己真实要干的活去问它三五句，写一句人话——“中文自然，长文有条理”“会英中混着说”“指令跟得不好，让它只输出表格它还是加解释”。**这一句在选型时比 tokens/s 有用。**

## 怎么测：先把条件钉死

**这一节比脚本本身重要。** 条件不固定，测出来的数没法互相比，也没法和以后的自己比。

**五条，每一条都要写进记录：**

1. **提示词固定。** 每个模型都用同一句。本章一律用这一句：`用三百字介绍一下你自己，不要分点。`——它够长，能看出生成速度；够短，不用等太久；**要求不分点是为了让各个模型的输出长度接近**；
2. **上下文长度固定。** Ollama 这一头用的是模型自带的默认值（`ollama show 模型名` 能看到）；走第 13 章那条路的话，`-c` 写多少要记下来；
3. **机器上别的东西停掉。** 第 4 章那个 Open WebUI 容器、别人正在用的对话，都会抢资源。**测的时候确认只有你一个人在用**；
4. **每个模型跑三次，取中间那次。** 第一次有加载和缓存的影响，单次结果波动也大；
5. **记下框架和版本。** `ollama --version` 或者 llama.cpp 那个版本号。**升级之后这份记录就该重测。**

**测加载时间之前，先把模型从内存里卸下来：**

```bash
ollama stop 模型名
```

作用：把模型从内存里放出来，文件还在盘上（第 3 章那张速查表）。**不卸的话，下面脚本量到的“加载时间”是假的**——模型早就在内存里了。

## 测试脚本

在第 8 章那个环境里新建一个文件叫 `model_bench.py`，内容照抄：

```python
import sys
import time

from openai import OpenAI

# 换成你那台 Mini PC 的地址，本机跑就用 localhost
BASE = "http://192.168.1.50:11434/v1"

# 固定的提问。每个模型都用同一句，换了就不能互相比
PROMPT = "用三百字介绍一下你自己，不要分点。"

# 模型名从命令行给
MODEL = sys.argv[1] if len(sys.argv) > 1 else "qwen3.6-35b"

client = OpenAI(base_url=BASE, api_key="ollama")


def plain_once():
    """非流式跑一次，返回（总耗时，提示词 token 数，生成 token 数）。"""
    started = time.time()
    completion = client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": PROMPT}],
    )
    spent = time.time() - started
    usage = completion.usage
    return spent, usage.prompt_tokens, usage.completion_tokens


def stream_once():
    """流式跑一次，返回（首字延迟，生成阶段耗时，收到的片段数）。"""
    started = time.time()
    first_at = None
    pieces = 0
    stream = client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": PROMPT}],
        stream=True,
    )
    for chunk in stream:
        piece = chunk.choices[0].delta.content
        if not piece:
            continue
        if first_at is None:
            first_at = time.time()
        pieces += 1
    done_at = time.time()
    if first_at is None:
        return None, None, 0
    return first_at - started, done_at - first_at, pieces


print("模型      %s" % MODEL)
print("提问      %s" % PROMPT)
print()

print("第一次调用，含加载。跑之前记得先 ollama stop 一次……")
load_started = time.time()
plain_once()
load_spent = time.time() - load_started
print("加载加一次完整回答一共 %.1f 秒。模型现在在内存里了。" % load_spent)
print()

print("量首字延迟和生成速度……")
ttft, gen_seconds, pieces = stream_once()
if ttft is None:
    print("一个字都没收到。按第 15 卷查。")
    sys.exit(1)

print("再跑一次非流式，拿准确的 token 数……")
spent, prompt_tokens, completion_tokens = plain_once()

print()
print("加载加首次回答  %.1f 秒" % load_spent)
print("首字延迟        %.2f 秒" % ttft)
print("生成阶段耗时    %.2f 秒" % gen_seconds)
print("收到的片段数    %d" % pieces)
print("片段每秒        %.1f" % (pieces / gen_seconds if gen_seconds > 0 else 0))
print("非流式那次      %.2f 秒" % spent)
print("  提示词 token  %d" % prompt_tokens)
print("  生成 token    %d" % completion_tokens)
```

跑它：

```bash
ollama stop qwen3.6-35b
~/ai-client/bin/python model_bench.py qwen3.6-35b
```

**正常输出**长这样（**数字是你自己那台机器的，这里只给形状**）：

```text
模型      qwen3.6-35b
提问      用三百字介绍一下你自己，不要分点。

第一次调用，含加载。跑之前记得先 ollama stop 一次……
加载加一次完整回答一共 xx.x 秒。模型现在在内存里了。

量首字延迟和生成速度……
再跑一次非流式，拿准确的 token 数……

加载加首次回答  xx.x 秒
首字延迟        x.xx 秒
生成阶段耗时    xx.xx 秒
收到的片段数    xxx
片段每秒        xx.x
非流式那次      xx.xx 秒
  提示词 token  xx
  生成 token    xxx
```

逐段说清楚：

- **`plain_once()`** —— 非流式跑一次。**它的用处是拿 `usage` 里那两个准确的 token 数**（第 8 章讲过这个字段）；
- **`stream_once()`** —— 流式跑一次。**流式是量首字延迟的唯一办法**——非流式那边你只能等它全说完，看不到第一个字什么时候出来（第 8 章讲过 `delta.content` 和 `message.content` 的区别）；
- **第一次调用为什么用非流式** —— 只是为了量加载。**跑之前先 `ollama stop`**，不然这个数没意义；
- **“片段每秒”不等于 tokens/s。** 流式返回的一个片段通常带一个 token，**但不保证**。要一个更严谨的数，看非流式那次的 `生成 token` 除以生成耗时，或者走第 13 章那条路看 llama.cpp 自己打印的那两行统计（[第 5 卷第 17 章](../05-驱动与ROCm/17-llama.cpp-Vulkan.md)）。**本章的表里两个数都记，别混着用。**

> **这个脚本一次只测一个模型。** 换模型就换命令行那个参数。**别写个循环一次测完**——中间要人去看 `ollama ps` 和 `radeontop`，机器也要有喘口气的时间。

## 测的时候另开两个窗口

**脚本只量时间，机器那一头要你自己看。**

**一、确认它真的在 GPU 上**

```bash
ollama ps
```

**`PROCESSOR` 那一列是 `100% GPU` 才算数**（第 3 章）。**看到混合值，这一行的速度数字就要标注“部分跑在 CPU 上”**，不能当成这台机器的正常水平。

**二、内存占到多少**

```bash
radeontop
```

**看 `gtt` 那一行的峰值**（第 3 章讲过为什么看它不看 `vram`）。**这个数要和第 1 章那条公式算出来的对一下**——对不上的话，是你的估算漏了什么，还是模型的实际占用和预期不同，值得记一句。

同时 `free -h` 看一眼 `available` 还剩多少。

**三、温度那一档单独测**

**上面那些每次只跑几十秒，测不出温度稳态。** 温度要按[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)的方法专门测——**让模型持续满载跑三十分钟以上，等读数不再明显变化。** 那一章讲了怎么制造这个负载、怎么读传感器、什么叫稳态、什么时候要重测，**本章链接过去不重抄**。

**这一档不用每个模型都测。** 挑你日常真正要用的那一个模型测一次就够，**因为温度反映的是这台机器的散热能力，不是某个模型的特性。**

## 测完怎么并进设备基线

**这张表不进基线，基线里只放一行。**

[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)那份基线是这台机器的整体记录，**它要的是一组固定条件下的对照值，不是一张选型表**。所以：

**第一步，挑一个模型当基准。** 挑你日常最常用的那个，**一般就是主线那个**。以后每次重测基线都用它，**换了模型就失去可比性**。

**第二步，把那一行抄进基线表的第八组。** [第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)那张空白基线表里，第八组叫“跑模型满载 30 分钟以上”，里面这几行由本章填：

| 基线表里那一行 | 从本章哪儿来 |
| --- | --- |
| 模型与量化档 | 测试表里基准那一行的前两格 |
| 上下文长度 | 测试表里那一格 |
| 推理框架与版本 | 测试表表头那一行 |
| tokens/s | **测试表里“生成速度”那一格，两个数一起抄，注明怎么来的** |
| radeontop 的 gtt 峰值 | 测试表里“内存占用”那一格 |
| 当时机器上还跑着什么 | 测试表表头那一行 |

**还有几行本章填不了，按[第 4 卷第 12 章](../04-Max395硬件/12-温度与频率.md)补：**

| 基线表里那一行 | 怎么来 |
| --- | --- |
| 温度稳态 | 本章“温度那一档”测出来的，抄过去 |
| 频率稳态 | 同上 |
| radeontop 的 gpu 占用 | 持续满载时看一眼，记个大概区间 |
| 风扇噪音 | 听不见 / 听得见 / 影响，三选一 |
| 整机功耗 | **要功率计。没有就写“未测”**（[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)那一节说过，别抄网上的数） |

**第三步，在基线第一组写清这次为什么记。** 第一次建就写“第一次建立”，是因为升级了 Ollama 才重测的就写清楚。**[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)说过，不写重测原因，两份基线对不上的时候你会不知道中间发生过什么。**

**第四步，这张模型测试表本身单独存一份**，和基线放在一起，**存两份**（机器上一份、机器之外一份），规矩同[第 4 卷第 16 章](../04-Max395硬件/16-设备基线.md)。

> **什么时候要重测这张表**：换了推理框架的版本、换了模型或量化档、改了上下文长度、改了 BIOS 功耗档位、换了摆放位置或者季节变了。**判断标准和基线一样——条件变了，旧记录不能直接拿来比。**

## 拿实测去对第 1 章那两张表

**最后一步，把这张表和第 1 章那两张放在一起看。**

第 1 章那两张表里的“大概什么体验”那一列，**全部标着“需要核验”，等的就是这一刻**。

对下来通常有三种结果：

- **对得上。** 那一行的判断在你这台机器上成立，可以放心引用；
- **比预期好。** 记下来。**不要因此推广到别的行**——一个模型对得上不代表整张表都对；
- **比预期差，或者根本跑不动。** 这一条最有价值。**记清楚是哪一步不对**：内存不够（对一下第 1 章的公式）、掉到 CPU 上（第 3 章）、还是上下文开太大（第 13 章）。

**从此以后，第 1 章那两张表在你这里就作废了，以你这一份为准。**
