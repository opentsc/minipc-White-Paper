# 09　变体：物流单与表格件

## 这一章的任务

一张单据出好几行数据。

**前面所有的章节，一份文件出一行。** 这一章不一样——一张送货单上有八行货，它要出八行数据。

**这是这一卷唯一一处 schema 会变形状的地方。** 前面那些 schema 都是一层的：一个字段配一个值。这一章多一层，**里面装着一串**。

**流程照旧**，第 4、5、6、7 章那套一律照用。这一章要改的还是那三样，外加台账要拆成两张。

## 开始前

- **主线第 1 章到第 7 章做完**，[第 8 章](08-变体-合同条款提取.md)那五处脚本改动做完（**这一章要用那个 `--prompt` 开关**）；
- 手上有一批物流单据，同一类的。**送货单就全是送货单，别混着快递面单**；
- 你自己数过其中三张的明细有几行。**核对的时候要用这个数**；
- 一天。

## 新词

**数组**（array）：**schema 里的一格，装的不是一个值，是一串同样形状的东西。** 写法是 `"type": "array"`，下面跟一个 `items` 说明每一样长什么样。**这一章第一次用到它。**

**表头字段**：一张单据上只出现一次的那些——单号、日期、发货方、收货方。**它们是这张单的身份。**

**明细行**：单据中间那张表里的一行——品名、规格、数量、单价、金额。**一张单有几行就是几行。**

**行内自洽**：一行数据自己对得上。数量乘单价等于金额，就是行内自洽。

**跨行自洽**：几行加起来对得上一个总数。明细金额加起来等于合计金额，就是跨行自洽。**这一章最有用的一条规则是它。**

## 这类客户的文档长什么样

四种，都是表格件，但难度差得远。

**一、送货单、出库单。** 一张纸，上半部分是表头，中间一张明细表，底下一行合计。**结构最规整，第一批就做它。**

**二、装箱单。** 和送货单像，但行数更多，一张纸上二三十行是常事。**行数一多，[第 3 章](03-定义字段.md)那条“多栏和表格串行”的毛病就出来了。**

**三、快递面单。** 热敏纸，窄长，字小，**印得淡而且会褪色**。明细少甚至没有明细，主要是单号、收寄件人、重量。**它其实不是表格件，处理起来反而简单。**

**四、报关单。** 格子最多，字最密，**还有一堆编码类字段**（商品编码、监管方式代码）。**第一批不要碰它**，等前三类跑顺了再说。

### 三个物流单特有的坑

**一、手写的收件人和签收栏基本读不出来。**

[第 3 章](03-定义字段.md)那七条毛病的第一条，在物流单上是最突出的。**签收栏就是一个人名的手写签名，模型读它是碰运气。**

**做法很直接：不要把它写进 schema。** 抽不出来的东西不要放进去，放进去只会让你每张都要复核一次。

**二、条码和二维码读不了。**

模型看到的是一堆黑条，它读不出里面的数字。**面单上条码底下通常印着同一串数字，让它读那个。**

**真要读条码，市面上有专门做这件事的工具，那是另一条路，本卷不展开。**

**三、复写纸的第二联和第三联。**

送货单一式三联，客户手上留的常常是浅蓝或者浅红的那一联。**颜色浅、字发虚，扫出来对比度低。**

`--dpi` 调到 300 有一点帮助（[第 4 章](04-单张跑通.md)那个开关），**但纸本身就淡的话，调多高都救不回来**。这一类要在报价前先看一眼样张。

## 他们的痛点

一句话：**对账的时候，一张张核。**

展开是这几种：

- **月底和承运商对账。** 对方发来一张几百行的账单，你手上是几百张送货单，**一行一行找过去**；
- **仓库收货点完数，还要把送货单上的明细录进系统。** 录入是纯体力活，**而且录错了要等到盘点才发现**；
- **客户说少发了两件。** 要翻出当时那张装箱单，看上面写的是几件；
- **月底统计某个品项这个月出了多少。** 单据都在，但没有一张能求和的表。

**这几件事的共同点：数据在纸上是一行一行的，进了系统却没有。** 这一章做的就是把那些行搬出来。

> **再标一次证据**：上面这几条痛点描述来自公开市场材料里反复出现的需求表述，**是方向判断**，不是本项目验证过的客户访谈结论。见本章最后一节。

### 这份 schema 和前面那些差在哪儿

**外面这一层还是老样子**——八格，全是字符串，`required` 全写上，`additionalProperties` 关掉。**[第 3 章](03-定义字段.md)那三条规矩一条不改。**

**新东西只有 `明细` 那一格**：

```json
"明细": {
  "type": "array",
  "items": { ... }
}
```

**`"type": "array"` 的意思是这一格装的是一串。** 一串里有几样，schema 不管，**单据上有几行就是几行**。

**`items` 说的是这一串里每一样长什么样。** 它自己又是一个完整的小 schema，**里面同样有 `properties`、`required`、`additionalProperties`**——**规矩和外面那层一模一样，只是套在里面。**

**方括号里那两坨就是明细。** 单据上有八行，这里就是八坨。

### `行号` 这一格是干什么的

**它是这份 schema 里最不起眼、也最要紧的一格。**

单据上印没印行号无所谓，**这一格的作用是给校验和复核当抓手**：

- **让模型自己数着行走。** 要求它填行号，等于要求它意识到自己在处理第几行；
- **让你知道它有没有漏行。** 行号跳了一个，或者最大的行号和总行数对不上，**一眼看得出来**；
- **让复核的人说得清位置。** “第 5 行的单价错了”，比“中间那行”准确得多。

单据上真没印行号的，**提示词里让它从 1 开始自己编**，下面那一段有这句话。

### `合计数量` 和 `合计金额` 必须是照抄的

**这一条是本章最值钱的一句设计，先说在这儿，下面提示词和校验都靠它。**

这两格要的是**单据上印着的那个合计**，不是模型把明细加一遍得出来的数。

**理由是这样的**：只有当合计来自单据、明细也来自单据，**两边加起来对不上才说明有一边读错了**。

**它要是自己算了一遍填进去，这两个数永远相等**，那条最有用的校验就废了——**它变成了在检查模型的加法能力，而不是在检查它有没有读错行。**

**没印合计的单据怎么办**：那两格留空。校验那一条自动跳过（**空的不检查**），你损失的只是这一条规则，**别用一个假的合计把它变成没用的规则。**

## 提示词要加什么

新建 `~/ai/scripts/logistics_prompt.txt`：

```text
这是一张物流单据的图片，可能是送货单、出库单、装箱单或者快递面单。
把单据上的信息读出来，严格按给定的 JSON 结构输出，不要输出 JSON 以外的任何文字。

明细表上有几行就输出几行，一行都不要漏，一行都不要合并，也不要自己补行。
行号照单据上印的抄；单据上没印行号的，从 1 开始按顺序自己编。
每一行里的品名、规格、数量、单位、单价、金额必须来自单据上的同一行，不要串行。
数量、单价、金额照单据原样抄，不要计算，不要换算单位，不要取整，不要补小数位。
合计数量和合计金额，照单据上印着的那个数抄。单据上没印合计的，这两格填空字符串。
不要自己把明细加一遍填进合计。
看不清或者单据上没有的字段，填空字符串，不要猜，也不要编。
```

一条一条说它在挡什么。

**“有几行就输出几行，不要合并，也不要补行”** —— **挡的是它自作主张。** 两行品名一样规格不同，它可能合并成一行；表格最后一行是空白格，它可能顺手填一行。**这一句是本段最基础的一条。**

**“行号没印的从 1 开始自己编”** —— 上面说过，**行号是抓手，宁可让它编也不能空着**。

**“同一行，不要串行”** —— **挡的是[第 3 章](03-定义字段.md)那条第七毛病**，把上一行的金额配到下一行的品名上。**这句话不能省**，明细行一多它就容易犯。

**“照原样抄，不要计算，不要换算单位”** —— **挡的是它顺手做算术。** 单据上写“20 包”，它可能给你换算成“10000 张”；单价写 `23.5`，它可能补成 `23.50`。**要的是票面原样**，这是[第 3 章](03-定义字段.md)那三条规矩里“全部用字符串”那一条的延续。

**“合计照抄，不要自己加一遍”** —— **这是本段最要紧的一句，理由上一节说透了。**

## 台账怎么拆成两张

**这是本章第三处改动。**

问题出在这儿：[第 5 章](05-批量处理.md)那个 `write_ledger` 是按“一份文件一行”写的，**`明细` 那一格是一串东西，塞不进一个格子里**。硬塞的话，CSV 里会出现一坨没法看的东西。

**做法是出两张表**：

```text
ledger.csv    一张单据一行。表头字段 + 明细行数 + 处理时间
lines.csv     一行明细一行。用文件名和单号串回上面那张
```

**这两张表分工很清楚**：`ledger.csv` 回答“有哪几张单、什么时候、发给谁”；`lines.csv` 回答“某个品项这个月出了多少”。**对账用的是后面那张。**

### `ocr_batch.py` 要改哪四处

**改动一，`field_names` 换成这个**，并在它上面加一行常量：

```python
LINE_FIELD = "明细"


def field_names(schema):
    """台账的列，只取不是数组的那些字段。明细单独出一张表。"""
    names = []
    for name, spec in schema.get("properties", {}).items():
        if spec.get("type") != "array":
            names.append(name)
    return names
```

**这一改是为了让台账的列自动跳过 `明细` 那一格。** 跑发票和合同的时候，schema 里一个数组都没有，**这个函数的行为和原来一模一样**。

**改动二，`write_ledger` 里改两行。** 表头那一行：

```python
    header = ["文件名"] + fields + ["明细行数", "处理时间"]
```

循环里 `rows.append(...)` 上面加一行：

```python
        record["明细行数"] = str(len(record.get(LINE_FIELD, [])))
```

**`明细行数` 这一列很有用**——扫一眼就能看出哪几张单一行都没读出来，哪几张比别的多得离谱。

**改动三，在 `note_failure` 上面插进这个新函数**：

```python
def write_lines(json_dir, lines_path):
    """明细单独出一张表：一行明细一行数据，用文件名和单号串回台账。"""
    header = ["文件名", "单号", "行号", "品名", "规格", "数量", "单位", "单价", "金额"]
    rows = []
    for path in sorted(json_dir.glob("*.json")):
        record = json.loads(path.read_text(encoding="utf-8"))
        for line in record.get(LINE_FIELD, []):
            row = [record.get("文件名", path.name), record.get("单号", "")]
            row.extend(str(line.get(name, "")) for name in header[2:])
            rows.append(row)
    with lines_path.open("w", newline="", encoding="utf-8-sig") as handle:
        writer = csv.writer(handle)
        writer.writerow(header)
        writer.writerows(rows)
    return len(rows)
```

**它和 `write_ledger` 是同一个套路**——每次从 `out/` 里重头汇一遍，不追加（[第 5 章](05-批量处理.md)那条刻意的设计）。**所以重跑几次都不会出现同一行明细记两遍。**

**改动四，`main` 最后那句 `print("台账 %d 行 ...")` 下面加三行**：

```python
    lines_path = outdir / "lines.csv"
    line_rows = write_lines(json_dir, lines_path)
    print("明细 %d 行：%s" % (line_rows, lines_path))
```

### 加三条

**第一条，明细不能一行都没有。**

```python
def check_lines(record):
    """七、明细一行都没有，多半是整张表没读出来。"""
    if not record.get(LINE_FIELD, []):
        return ["明细一行都没有"]
    return []
```

**这一条是这个变体最有用的一条。** 一张送货单读出来表头齐全、合计也有，**就是明细一行没有**——这种错在台账里完全看不出来，`ledger.csv` 那一行看着挺正常的。**明细行数那一列和这条规则，是它唯一会露馅的两个地方。**

**第二条，每一行自己要对得上。**

```python
def check_line_math(record):
    """八、每一行的数量乘单价要等于这一行的金额。"""
    problems = []
    for line in record.get(LINE_FIELD, []):
        no = text_of(line, "行号")
        count = to_number(text_of(line, "数量"))
        price = to_number(text_of(line, "单价"))
        amount = to_number(text_of(line, "金额"))
        if count is None or price is None or amount is None:
            continue
        if abs(count * price - amount) > 0.01:
            problems.append("第 %s 行：%.2f 乘 %.2f 等于 %.2f，金额写的是 %.2f"
                            % (no, count, price, count * price, amount))
    return problems
```

**这一条捞的是串行。** 上一行的单价配到了下一行的数量上，**乘出来的数和金额那一格对不上**。

**注意它连行号一起报出来了**，复核的人拿着这句话直接翻到第几行，不用整张单重看。

**第三条，明细加起来要等于合计。**

```python
def check_line_total(record):
    """九、明细加起来要等于单据上印的合计。"""
    problems = []
    lines = record.get(LINE_FIELD, [])
    if not lines:
        return problems
    for line_field, total_field in (("数量", "合计数量"), ("金额", "合计金额")):
        total = to_number(text_of(record, total_field))
        if total is None:
            continue
        added = 0.0
        for line in lines:
            value = to_number(text_of(line, line_field))
            if value is None:
                added = None
                break
            added += value
        if added is None:
            continue
        if abs(added - total) > 0.01:
            problems.append("明细%s加起来是 %.2f，%s写的是 %.2f"
                            % (line_field, added, total_field, total))
    return problems
```

**这一条是本章的“加税校验”**，[第 7 章](07-错的怎么拦.md)那条在发票上最有用的规则，在这里换了个形状。

**它专捞漏行。** 十行货读出来九行，**表头齐全、每一行自己也对得上、行号看着也连着**——只有加起来和合计对不上。

**加进 `OTHER_CHECKS` 那张表**：

```python
OTHER_CHECKS = [
    check_date,
    check_amounts,
    check_parties,
    check_lines,
    check_line_math,
    check_line_total,
]
```

### 单号重复，用一条命令查

**同一张单被扫了两遍**，在物流场景里很常见——纸质单据一式几联，不同的人各扫了一次。

这条不用写进脚本，一条命令就够：

```bash
cut -d, -f3 ~/ai/projects/logistics-ocr/ledger.csv | sort | uniq -d
```

作用：把台账第三列（单号）取出来，排序，**只打印出现了不止一次的**。什么也不打印就是没有重复。

> **第三列是单号，前提是你的 schema 字段顺序和上面那份一样**（文件名、单据类型、单号……）。**改过字段顺序的话，先打开台账数一下单号是第几列**，把 `-f3` 换掉。

### 那条边界，在这里还要多说一句

[第 7 章](07-错的怎么拦.md)那句话照样成立：**校验不过的一定有问题，校验过了的不一定没问题。**

**这一章还多一条**：

**上面那三条规则全建立在“合计是照抄的”这个前提上。** 提示词里那句“不要自己把明细加一遍填进合计”一旦失效——你改提示词的时候顺手删了它，或者换了个模型不听这句——**第三条规则就变成了永远通过。**

**它不会报错，它只是不再拦任何东西。**

**所以调完提示词之后要做一次专门的确认**：找一张你明知道明细和合计对不上的单据（票面本来就有零头调整的那种），**跑一遍，看它有没有被挑出来**。挑出来了，说明合计确实是照抄的；没挑出来，回去看提示词。

## 验收怎么定

**四件事。**

### 一、行数对数

**这一条排在最前面，因为漏行是这个变体最主要的风险。**

```text
客户点的单据张数　=　ledger.csv 行数　+　failed/ 里的份数
```

再抽几张，**数一遍纸上的行数，和 `明细行数` 那一列对**。

**先把 `明细行数` 那一列排一次序**：0 的先看，特别大的也先看。

### 二、按行抽检，不按张抽检

**这一条是这个变体和前面几章最不一样的地方。**

一张单十行，**对一张等于对了十行**。所以抽检的口径要说清楚是抽多少行，不是抽多少张。

对一行的顺序：

```text
1. 数量　　　　对账的时候这一格最要紧
2. 金额
3. 单价
4. 品名和规格　这两格错了，透视表就归错类了
5. 单位　　　　“包”和“张”差着 500 倍
```

**第五项别跳。** 单位那一格看着不起眼，**它错了，数量这一列加起来就没意义了。**

### 三、合计对数

抽出来的每一张，**把明细自己加一遍，和单据上印的合计对**。这一步是在验第三条校验规则真的在起作用（上面那一节说的那件事）。

### 四、抽多少、通过标准，客户定

**你不要单方面给一个数字**（[第 7 卷第 11 章](../07-RAG/11-变体-律所合同库.md)那条规矩）。

**准确率数字这一章一个都不给。** 要给客户一个数，按第 13 章那套办法在你自己的机器上、拿客户自己那批单据测（[第 13 卷](../13-项目交付/README.md)）。

**这个变体按张收钱还是按行收钱，是个真问题**——一张十行的装箱单和一张两行的送货单，成本差得远。**这件事第 14 章和[第 11 卷](../11-客户与报价/README.md)说，本章不下结论。**

## 这个变体的三条实话

**一、行数是这个变体的全部难点。** 内容读错一格，校验和抽检能捞回来；**漏了一行，那一行就彻底不存在了**——台账上看不见，透视表里少一笔，谁也不会去找它。**所以那三条校验规则里，第一条和第三条的分量比别的重。**

**二、手写的那部分别接。** 签收人、手写补的数量、手写改过的单价，**这几样在物流单上很常见，也基本读不出来**。谈需求的时候要把它们排除在外，**写进边界里**（[第 13 卷](../13-项目交付/README.md)）。

**三、先看样张再报价。** 复写纸第二联、热敏纸面单、褪色的旧单，**这三类的效果和干净的激光打印件不是一回事**。**要一叠真实样张，跑十张看看，再开口。**
