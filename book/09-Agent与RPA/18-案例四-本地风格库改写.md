# 18　案例四：本地风格库改写

## 这一章的任务

把一份初稿送进本地模型，按照一组本人写过的材料改写，得到三份不同改动强度的草稿，并对事实做一次检查。

这一章解决的是“写得像谁”的问题。模型速度、模型版本和本机性能的测试，仍然按[第 6 卷第 16 章](../06-本地模型/16-模型测试表.md)执行。本章不把某一次速度记录当成所有 Max395 设备的性能承诺。

做完之后手上有：

- 一个只放代表作的风格库；
- 一份风格说明；
- 一份原文；
- 轻改、标准、猛改三份草稿；
- 一份事实检查记录；
- 一份人工确认记录。

## 开始前

- [第 6 卷](../06-本地模型/README.md)已经有一个能访问的本地模型接口；
- [第 6 卷第 16 章](../06-本地模型/16-模型测试表.md)的设备基线已经建立；
- 有 3 到 5 篇自己认可的代表作。没有代表作时，不要让模型替你猜风格；
- 有一份可以公开放进测试目录的原文。实验不要使用客户隐私、密钥、内网地址和未公开材料；
- 60 到 90 分钟。第一次要花时间清理风格库，之后每篇改写的准备时间会缩短。

## 新词

**风格库**：一组用来说明写作者习惯的代表性文本，不是所有历史文章的备份。

**风格说明**：用文字写出的句长、开头、收尾、标点、常用说法和禁用说法。

**风格指纹**：模型从风格库中整理出的可检查项目。它只能作为改写参考，不能替代作者判断。

**事实保真**：改写后没有新增、删除或改变原文的事实、数字、日期、链接、人物和限定条件。

**三档改写**：轻改只调整句子和禁用词；标准改写句式和段落；猛改只保留事实骨架，重新组织表达。三档都必须通过事实检查。

## 先把风格库放对地方

在一个不放客户资料的目录里建立下面的结构：

```text
STYLE_LIBRARY_DIR/
├── 01-代表作.md
├── 02-代表作.md
├── 03-代表作.md
├── 04-代表作.md
└── 风格说明.md
```

代表作不需要多。3 到 5 篇足够。不要把不同作者、不同用途和明显不满意的文字混在一起，否则模型学到的是混合结果。

`风格说明.md` 可以先写这些内容：

```text
文章用途：例如公众号长文、产品说明、内部通知
开头习惯：先说具体问题，不使用空泛的背景句
句子习惯：长短句混用，重要事实单独成句
常用说法：填入本人确实会使用的词
不使用的说法：填入本人明确不想出现的词
标点习惯：例如少用分号，保留口语停顿
不能改变：事实、数字、日期、链接、限定条件
```

风格说明写观察到的习惯，不要写成“更高级”“更有力量”这类无法检查的要求。

## 先做风格指纹，不急着改

把风格库交给模型时，先让它只输出检查表：

```text
请只分析下面的代表作，不要改写，不要新增内容。
输出：
1. 常见开头方式；
2. 常见收尾方式；
3. 句子长度和段落长度的变化；
4. 常用词和口头表达；
5. 标点习惯；
6. 明确不应模仿的内容；
7. 仍然无法确定的地方。
每一项都引用代表作中的短例子。没有证据的地方写“未观察到”。
```

检查风格指纹。把模型臆造的“作者特点”删掉，再把确认过的结果放进改写提示词。

## 改写提示词

下面的规则是本案例的核心。原文、风格库和风格指纹都放在同一个请求里时，要把它们分开标记。

```text
你是文章风格迁移编辑，不是内容创作者。
任务：把【原文】改写成【目标风格】。

事实规则：
1. 不新增原文没有的事实、数据、案例、人物、结论或承诺；
2. 不删除关键事实、数字、时间、链接和限定条件；
3. 不确定的内容保持原样，不自行补全；
4. 保留核心立场和逻辑顺序；
5. 输出前做事实检查，列出可能被改动的事实点；
6. 如果风格要求和事实规则冲突，事实规则优先。

风格规则：
1. 只使用风格库中能观察到的习惯；
2. 不强行加入口头禅、私人细节或错误；
3. 不使用风格库没有证据支持的表达；
4. 保留原文的标题、链接和必要结构，除非本档改写另有说明。

输出：
- 先输出改写后的正文；
- 文末单独输出“## 事实检查”；
- 逐条列出事实差异；没有差异写“无”；
- 不要输出分析过程。
```

三档强度这样区分：

| 档位 | 可以改变什么 | 不能改变什么 |
| --- | --- | --- |
| 轻改 | 句长、停顿、少量词语 | 事实、段落顺序、标题和链接 |
| 标准 | 句式、段落衔接、词语和局部顺序 | 事实、立场、限定条件 |
| 猛改 | 重新组织表达和段落 | 事实骨架、数字、日期、链接和结论范围 |

## 用本地 API 跑一遍

本章不固定某台机器的地址。把自己的接口地址填进 `MODEL_ENDPOINT`，把自己测过的模型名填进 `MODEL_NAME`。

```bash
export MODEL_ENDPOINT="http://MINIPC_IP:PORT/v1"
export MODEL_NAME="MODEL_NAME"
python3 rewrite.py \
  --style-dir STYLE_LIBRARY_DIR \
  --input INPUT_FILE \
  --output-dir OUTPUT_DIR
```

实验文件在：

[level-60／05 本地风格库改写](../../labs/level-60/05-style-rewriter/README.md)

脚本会依次执行：

1. 读取风格库和原文；
2. 请求风格指纹；
3. 请求轻改、标准、猛改三份草稿；
4. 把每次请求和模型名称写入运行记录；
5. 将三份结果写入输出目录。

脚本不自动发布、不自动发送、不覆盖原文。

## 人工检查

三份草稿都要检查。至少看以下内容：

```text
□ 数字与原文一致
□ 日期与原文一致
□ 人名、机构名、型号和链接没有改变
□ 原文中的“不确定”“可能”“截至某日”等限定条件还在
□ 没有新增案例、数据、承诺或个人经历
□ 标题没有把范围写大
□ 事实检查一节和正文逐项对得上
□ 公开发布前由作者人工选择一份
```

模型生成的“事实检查：无”不能直接视为通过。要回到原文逐项对照。

## 关于 AI 检测结果

检测器的分数不是本章的验收标准，也没有稳定的“保证通过”方法。本案例验收的是：

- 事实没有被改错；
- 文风要求可以说明；
- 改动可以回看；
- 作者完成最终确认。

如果需要发布，应该加入作者自己确认过的事实和判断，并保留原文、改写稿和改动记录。不要用虚构细节来制造“像人”的效果，也不要把改写服务包装成论文代写、冒名或事实掩盖。

## 停止与恢复

- 风格库为空：停止，先放入代表作和风格说明；
- 模型接口报错：保留原文，不重试到覆盖输出；检查接口、模型名和日志；
- 三份草稿都改变事实：停止发布，缩小提示词范围，重新运行；
- 风格指纹与作者判断不一致：删除错误指纹，不能让模型继续沿用；
- 需要换模型：保留旧模型的输出和测试记录，换模型后重新做一次事实检查。

## 可以包装成什么服务

可以包装成“本地写作改稿工具”，输入是作者自己的初稿和代表作，输出是三份草稿、事实检查和改动记录。

交付前要写清：

- 支持哪些文件格式；
- 每次处理的字数和文件数量；
- 风格库由谁维护；
- 谁负责事实检查；
- 是否保存原文和输出；
- 模型升级后是否重新测试；
- 不包含公开发布、代写、事实核验和法律意见。

## 完成检查

- 风格库和历史文章备份有什么区别？
- 三档改写分别允许改变什么？
- 为什么模型说“事实检查无”还要人工对照？
- 这套流程的验收标准是什么？
- 输出文件和原文是否都可以恢复？
